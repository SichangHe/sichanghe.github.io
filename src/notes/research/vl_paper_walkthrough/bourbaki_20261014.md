# Bourbaki: Self-Generated and Goal-Conditioned MDPs for Theorem Proving
(authored by agents unless marked 🧑)
Tag: `zimmer2025bourbaki`, [paper](https://arxiv.org/abs/2507.02726)

## what is proved and measured

The paper introduces self-generated goal-conditioned Markov decision processes (sG-MDPs) for Lean theorem proving and instantiates them in Bourbaki, an ensemble of 7B language models. Its central claim is that intermediate conjectures make sparse proof rewards denser and make tree search more effective. The abstract says: “Given this more structured generation of goals, the resulting problem becomes more amenable to search.” (Abstract, p. 1.) A proof counts only when it completes the Lean goal and type-checks in the Lean REPL (Section 4, p. 6). The reported benchmark is PutnamBench's 658 Lean 4 problems; the system solves 26/658 at pass@512, compared with DeepSeek-Prover-V2's 23/658 at pass@1024 (Table 1, p. 7). These are solved-theorem counts under stated sample budgets, not a probability that an arbitrary generated proof is correct.

Section 4 states: “A proof is considered to be solved successfully if it completes the goal and type-checks in the Lean REPL.” (p. 6.) Inference: this checks the formalized goal, so the result alone does not establish that a specification captures an intended requirement or that the method transfers to Verus.

## technique: self-generated goal-conditioned MDP

what it is: augment a goal-conditioned MDP with actions that create goals. A state is a proof-token sequence `s`; an ordered stack `g` stores the current goal and generated subgoals. The predicates are `IsPrimitiveAction`, `IsGoal`, and `Solves`; `ToGoal` converts a goal action into a goal. An action that is neither a valid primitive nor a valid goal leaves both state and stack unchanged. A valid goal action pushes `ToGoal(a)` without changing the proof state. A primitive action that solves the last goal pops it; a primitive that does not solve it leaves the goal stack unchanged. The paper defines this transition explicitly: “We assume that when IsGoal is True, IsPrimitiveAction would be False.” (Section 3, p. 5.)

Inference: when to use: use it when terminal proof success is too sparse for search and the prover can state independently checkable intermediate claims. It assumes the proof assistant can validate both the conjecture and the tactic that acts on it.

steps:
1. represent the current formal proof state as `s` and initialize `g` with the theorem goal (Section 3.1, p. 5)
2. let the policy emit either a primitive tactic or a conjecture (`have` or an auxiliary definition); classify it with `IsPrimitiveAction` and `IsGoal` (Section 3.1)
3. if it is a goal, convert it with `ToGoal` and push it; if it is a primitive, execute it and pop the last goal only when `Solves` is true (transition definition, Section 3)
4. reward intermediate solved conjectures as well as the original goal; the objective uses `R(s,g0) + lambda R(s,g_t)` (Equation 1, p. 5)

Inference: a possible Verus adaptation would track candidate source and pending proof obligations in a search controller, propose intermediate lemmas, and check them with Verus. The paper supplies no Verus implementation or evidence for this adaptation.

evidence and limits: the paper's result supports the method on Lean PutnamBench only. Table 2 shows the same sample budgets improve STP from 6/644 to 7/644 at 64 and from 7/644 to 8/644 at 128; Bourbaki on DeepSeek-Prover-V2 improves 15/658 to 23/658 at 128 (Table 2, p. 8). The denominator changes because the benchmark versions differ; the paper notes earlier work used 644 problems (footnote, p. 6). The paper reports no ablation that isolates goal generation from the ensemble and reward design. Inference: generated conjectures can be malformed or easy but irrelevant; every candidate must therefore be checked and usefulness should be measured separately.

## technique: verified-reward MCTS

what it is: perform MCTS over `(s,g)` nodes, using verified outcomes rather than a learned critic. Each node stores visit count `N` and accumulated reward `W`; its empirical value is `W/N`. Selection chooses the highest UCB score to balance exploration and exploitation. The displayed score is `V̄(s,g) + C sqrt(log N(s,g)/N(s,g))`; it prints the same node count inside the logarithm and denominator (Section 3.2, p. 6). Inference: the intended parent-count convention cannot be determined from that formula alone. The paper emphasizes: “The tree search is guided by the policy π(st , ḡt ) that samples tactics and subgoals, and a value function that is computed entirely through verified outcomes – without relying on any learned critic.” (Section 3.2, p. 6.)

steps:
1. initialize a root `(s0,g0)`
2. select the highest-UCB node (Selection, Section 3.2)
3. try at most `N = 10` tactic candidates for the selected node; as soon as one is validated by PyPantograph, add one child and estimate it; if all trials fail, exclude the selected node from future selection; also exclude nodes already having `N` children (Expansion and experimental setup, p. 6)
4. initialize the new node's value with its reward; the implementation combines depth-based metrics and the number of solved conjectures, without specifying their exact combination (Estimation, p. 6; implementation details, p. 7)
5. increment `N` and add reward to `W` on the path to the root (Back-propagation, p. 6)
6. stop at `K = 512` iterations or when a complete proof is found; extract the proof tokens (p. 6)

Inference: a Verus search driver could check candidate patches, score verified intermediate lemmas, and back-propagate those scores. Verus verification of the complete target would be the success test. These are proposed implementation choices, not results from this paper.

evidence and limits: Bourbaki ensembles DeepSeek-Prover-v2-7B and Kimina-7B and uses vLLM (Section 4, p. 6), with Pantograph v0.3.2, Lean v4.20.1, and mathlib v4.20.1 (p. 7). The main 26/658 result uses this ensemble on PutnamBench. The implementation handles heuristic tactics such as `apply?` by using the plain base model to complete the rest of the proof (p. 7). The paper reports sample budgets and iteration limits but no runtime or exact reward formula. Inference: these omissions limit estimates of the cost of a Verus adaptation.

## what VL should retain

Inference: VL could evaluate a Verus adapter that proposes intermediate lemmas and measures whether they reduce verification attempts and total runtime. The Lean results support investigating this approach; they do not establish its effectiveness for Rust or the adequacy of a Verus specification.

## techniques for the catalog

- self-generated goal stack — let a prover create independently checked intermediate conjectures and solve them in last-in-first-out order
- verified-reward MCTS — use checker-validated tactics and conjectures as dense rewards while selecting nodes with UCB
- ensemble tactic synthesis — combine multiple same-scale policy models and retain candidates that the proof assistant validates
