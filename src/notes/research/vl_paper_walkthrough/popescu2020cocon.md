# CoCon: A Conference Management System with Formally Verified Document Confidentiality
(authored by agents unless marked 🧑)
Tag: `popescu2020cocon`, [paper](https://doi.org/10.1007/s10817-020-09566-9)

## system and security claim
CoCon verifies the functional kernel of a conference-management system in Isabelle/HOL, generates a Scala program from it, and wraps that program in a REST API and a web GUI. The paper’s architecture “consists of a verified kernel and some trusted components” (Sec. 1, p. 322). It proves confidentiality, safety, and traceback properties for an input/output automaton. The confidentiality properties bound what groups of users can learn about papers, reviews, discussions, and decisions (Sec. 3.4-3.5, Table 1, p. 334). The authors report that the verification took three person months, including reusable proof infrastructure and automation (Sec. 4.3, p. 345).

## technique 1: model the application as an I/O automaton
Use this when security depends on histories of requests, outputs, and secrets rather than on isolated functions. Define a state type, action type, output type, initial state, and `step : State → Act → Out × State`; a transition records source, action, output, and target. The paper’s CoCon specification is deterministic (Sec. 5.2, p. 346). Define valid traces as lists of valid transitions, each source being the target of the previous one, starting in the initial state (Sec. 3.2, p. 328). Define observation `O` (what the attacker sees), secret sequence `S`, and trigger `T` (when a release bound stops applying). The authors specify “1. what the capabilities of the attacker are; 2. which information is (potentially) confidential; 3. which flows are allowed” (Sec. 3.2, p. 328).

Inference: in Verus, model the kernel state and actions as Rust datatypes, give `spec fn step` and `spec fn valid_trace`, and state safety with `ensures` over traces. Keep the executable API separate from the ghost trace model. Verus can prove inductive state invariants, but the paper’s relational trace theorem would need explicit ghost sequences and lemmas.

## technique 2: bounded-deducibility security
Use bounded deducibility when some information may be released after a documented event, unlike absolute noninterference. Choose a relation `B` on original and alternative secret sequences. For every valid original trace in which the trigger never holds, and every alternative secret sequence related by `B`, prove there exists a valid alternative trace with the same observations and that alternative secret sequence. The paper states: “If trigger T never holds, then attacker O can learn nothing about secrets S beyond B” (Sec. 3.2, p. 329). The property is universally quantified over the original trace and the alternative secrets and existentially quantified over the alternative trace (the paper’s formula (∗), p. 329).

Step by step: (1) define `O`, `S`, `B`, and `T` (for CoCon, `O` keeps the actions and outputs of a fixed group of observer users, Sec. 3.4, p. 331); (2) state the universal/existential trace property; (3) instantiate `B` and `T` for each document and workflow phase (Table 1, p. 334); (4) prove the property using the unwinding method below; (5) separately prove safety properties (Sec. 4.3, p. 345) and traceback properties (Sec. 3.6, pp. 335-337). Inference: a Verus encoding can use `spec fn bd_secure` over finite `Seq` traces and `proof fn` lemmas; quantifier-heavy existence proofs may need carefully chosen finite trace representations and solver guidance.

## technique 3: game-like unwinding
Use unwinding to turn the trace existence proof into local transition obligations. Maintain a configuration `(σ1, sl1, σ2, sl2)` containing the current states of the original and alternative traces and the secret sequences each still has to produce. The opponent extends the original trace by one transition; if it produces a secret, that secret must be the head of `sl1` and is removed. The prover then either ignores the move (allowed only if the opponent’s transition is unobservable) or matches it with an alternative transition that is equally observable and, if observable, yields the same observation, consuming the head of `sl2` if that transition produces a secret. Alternatively, the prover takes an Independent Action: an unobservable alternative transition that produces a secret. Once the opponent has no secrets left (`sl1` empty) but `sl2` is not empty, the prover is forced to take Independent Actions, so the alternative secrets are eventually all produced. The paper explains: “The game starts with a pair of sequences of secrets, related by the bound B” and “Each time we, the Green, can choose between two options: (1) asking the opponent to move and then performing a Reaction, which can be either Ignore or Match, and (2) taking Independent Action” (Sec. 4.1, pp. 337-338). An additional exit condition lets the prover finish early when no valid trace from the opponent’s current state can ever produce the next secret in `sl1`; it is checked with a safety invariant (Prop 2, p. 341). The Unwinding Theorem (Theorem 3, p. 341) requires `Δ istate sl1 istate sl2` whenever `B sl1 sl2` and the unwinding condition; it yields BD security.

Inference: in Verus, represent the relation as a `spec fn` over states and ghost sequences; prove closure with `proof fn`s and `requires`/`ensures`. Do not write `invariant(...)` as a call or use `modifies`; loop invariants belong on the loop, and state mutation is described by Verus function contracts.

## technique 4: compositional and sequential unwinding
A monolithic relation becomes difficult as the workflow grows. Split it into a network of relations. Each component may unwind to a set of continuation relations; prove each local `unwind_to` obligation and an initialization relation. Just before Corollary 5 the paper says: “If we verify a condition as above for each component relation, we obtain an overall secure system” (Sec. 4.2, p. 342). For CoCon, the relations were chosen by milestones such as “changing a conference’s phase, registering a paper, registering a relevant agent such as a chair, a PC member or a reviewer, declaring or removing a conflict” (Sec. 4.3, p. 343). The sequential theorem (Corollary 6, p. 342) lets each `Δi` unwind to itself, to `Δi+1`, or to an exit component `Δe`; the authors call it “a sweet spot between generality and ease of instantiation” (p. 342). Steps: identify workflow milestones; define one relation per milestone, with an exit relation for situations the opponent cannot realize; prove the continuation and exit obligations; apply the sequential theorem. For Pap2 the paper uses three non-exit relations, and for Rev four (Sec. 4.3, p. 343).

Inference: Verus can encode each relation as a separate predicate and prove a chain of lemmas, allowing agent-written proofs to be checked per phase. The relation network is a proof decomposition; it does not automatically compose unverified API code.

## implementation, evidence, and limits
The verified Isabelle kernel is extracted to Scala, and wrapped by a Scalatra REST API and an AngularJS GUI (Sec. 5.1, pp. 345-346). The authors deployed CoCon to two conferences, TABLEAUX 2015 and ITP 2016, with approximately 70 and 110 users (Sec. 5.3, p. 347). The Isabelle code generator, the API layer (including identity management), and the Redis snapshot facility are trusted components; browser-level forging and lower-level attacks are out of the verification’s reach (Secs. 5.2-5.3, pp. 346-348). The paper says: “This trusted component is of course critical to the overall confidentiality guarantees, and is outside the scope of our verification” (Sec. 5.2, p. 347), referring to password hashing and the issuing and storing of salts and authentication tokens. Deployment exposed a thread-unsafe API handler whose data race could mix up the authentication tokens of two users; it took “an investigation of 3.5 days before a fix was deployed” (Sec. 5.3, p. 348).

## techniques for the catalog
- i/o automaton security model — represent state, actions, outputs, observations, secrets, and valid traces explicitly
- bounded deducibility — permit only relation-bounded secret release until a trigger event
- unwinding game — maintain paired states and remaining secret sequences with ignore, match, and independent moves
- compositional unwinding — split workflow proofs into milestone relations linked by continuation and exit obligations
