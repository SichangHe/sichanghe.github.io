# Deductive Verification of Floating-Point Java Programs in KeY

## architecture and arithmetic technique
This paper adds floating-point deductive verification to KeY. The goal is to reason about IEEE-754 rounding and special values while retaining Java heap and control-flow reasoning. Its abstract states: “Our support in the KeY verifier handles arithmetic via floating-point decision procedures inside SMT solvers and transcendental functions via axiomatization” (Abstract, p. 1). The key workflow is: write Java/JML preconditions and postconditions; let KeY symbolically execute heap and control flow; translate remaining floating-point verification conditions (VCs) to SMT-LIB; discharge them with a floating-point solver.

Technique 1 extends KeY with `float` and `double`, rounding modes, floating-point operation and comparison symbols, IEEE predicates, parser support, and JavaDL translation (Section 3.1, pp. 4–6). Use `\fp_nan`, `\fp_infinite`, and `\fp_nice` in contracts. The Rectangle example has two contracts: broad `fp_nice` preconditions and concrete input intervals. The broad contract gets a solver counterexample; the bounded contract proves that all result fields are non-NaN. The paper explains the reason for bounding: “In practice, such ranges would come from the context, e.g. from the kind of rectangles that appear in an application, or from known ranges of sensor values” (Section 3.1, p. 5).

Translate elementary arithmetic and comparisons to SMT-LIB floating-point operations. This is exact for strictfp Java because SMT-LIB follows IEEE 754; non-strictfp operations remain uninterpreted because their actual precision is unknown. Distinguish bitwise equality from IEEE equality. Use this path for absence of NaN/infinity, functional properties, roundoff bounds expressible in the supported theory, and comparison against a reference implementation.

Technique 2 handles transcendental functions with axiomatized uninterpreted symbols (Section 3.2.A, pp. 6–7). When a proof obligation contains `sin`, `cos`, `atan`, or another library function, add its uninterpreted symbol and quantified axioms to the SMT-LIB translation. A representative axiom says finite, non-NaN input to `sinDouble` yields a result between −1 and 1. These axioms capture high-level IEEE-compliant properties rather than the library implementation. The paper cautions: “Clearly, since we do not have the actual implementations of these functions, we are not able to prove arbitrary properties” (Section 3.2.A, p. 7). Use this technique when the property only needs range or special-value facts.

Technique 3 replaces quantified SMT axioms with KeY taclets (Section 3.2.B, pp. 7–8). Quantified floating-point SMT formulas can be slow or produce spurious counterexamples when not all instantiations are considered. A taclet is a KeY inference rule encoding the same logical fact; apply it only at selected terms, then send the simplified goal to the SMT solver. The authors call this a correct underapproximation for proving, but warn that incomplete instantiation can cause false positives when disproving. A heuristic triggers rules on transcendental occurrences, while experiments used manual axiom selection because eager instantiation expands goals.

## applying the method and Verus form
Start with a JML-style contract that excludes NaN/infinity or states the desired floating-point relation. Run KeY symbolic execution; close heap goals internally; export open arithmetic goals as SMT-LIB; choose direct IEEE operations for elementary arithmetic and either quantified axioms or taclets for library functions; inspect solver counterexamples before tightening legitimate input ranges. For loops, supply a loop invariant: the paper says KeY can use provided invariants but does not automatically infer floating-point invariants.

Inference: in Verus, model finite floating-point behavior with supported integer bit patterns or an abstract `spec fn` for the operation, then state `requires` ranges and `ensures` no-NaN/no-infinity predicates. Use loop `invariant` clauses for range preservation and `assert` lemmas for each operation. Inference: Verus does not directly import KeY's SMT-LIB floating-point pipeline or Java library axioms; a product must either verify a Rust IEEE implementation against a bit-level model or treat a trusted library contract as an assumption. Inference: transcendental axioms can be represented as explicit `spec fn` contracts and proof lemmas, but this proves only the stated range properties, not the implementation's numerical accuracy.

## evidence, trusted boundary, and limitations
The Java benchmark collection contains arithmetic, heap calls, loops, square root, and transcendental calls. Table 2 (p. 11) reports solver results by experiment and denominator. For valid goals with three quantified axioms, there are 80 goals: CVC4 decides 79 at 4.1 s average, Z3 25 at 18.4 s, and MathSAT is not reported; with seven quantified axioms, 80 goals give CVC4 79 at 4.0 s, Z3 52 at 35.0 s, MathSAT 80 at 8.8 s. For invalid goals with three axioms, all 9 goals remain undecided by CVC4 and Z3; with seven axioms, CVC4 decides 8/9 at 36.7 s, Z3 7/9 at 27.6 s, and MathSAT 9/9 at 3.9 s. Timeouts are excluded from averages, and each obligation has a 300-second timeout. The benchmark automode table (Table 1, p. 9) includes 20 entries; for example `Circuit.instantCurrent` closes 17 KeY goals in 14.1 s with 1,686 rules applied.

The paper's functional example exposes sensitivity: a determinant/transposed-matrix contract is rejected by CVC4 in 170.2 s and MathSAT in 16.2 s, while a reordered implementation is validated by CVC4 in 1.1 s and MathSAT in 3.9 s; Z3 times out after 30 minutes (Section 4.4, p. 12). Inference: these are per-goal measurements on the stated server, not general solver rankings. Inference: quantified axioms degrade performance; tighter input bounds can change satisfiability and runtime.

What is proved is the JML contract under the KeY semantics, solver theory, and selected axioms. Trusted elements include KeY's JavaDL translation and symbolic execution, the external SMT solver, the IEEE correspondence for strictfp translation, and all transcendental axioms. The paper does not prove actual `Math.sin` implementations or automatically discover floating-point loop invariants. Inference: threat to agent-written verified Rust is high whenever a model uses an axiom stronger than the linked library; Inference: VL should require explicit library contracts and tests that connect them to deployed code. Existing abstract interpretation and bit-precise SMT work already covers standalone floating-point snippets; the paper's distinctive contribution is combining heap/control-flow deduction with SMT floating-point and axiomatized transcendental reasoning.

## techniques for the catalog
- strict IEEE SMT translation — translate strictfp elementary operations and comparisons to SMT-LIB while preserving IEEE semantics
- special-value contracts — specify and prove absence of NaN and infinity with `fp_nan`, `fp_infinite`, and `fp_nice`
- transcendental axiomatization — model library functions as uninterpreted symbols constrained by quantified range and special-value axioms
- KeY taclet instantiation — apply selected transcendental facts as local deductive rules before final SMT solving
