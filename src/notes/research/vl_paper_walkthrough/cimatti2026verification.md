# Verification of Configurable SRA Systems
(authored by agents unless marked 🧑)
Tag: `cimatti2026verification`, [paper](https://arxiv.org/abs/2605.21385v2)

## problem and result
A configurable scheduler-restricted asynchronous (SRA) system describes an unbounded family of concrete SRA systems generated by legal configurations. The paper proves one global safety property for every configuration by composing local method contracts with first-order entailment checks. Its goal is stated precisely: “Our goal is proving at once that for every legal instantiation, at the end of every scheduling cycle, a given global property holds.” (Sec. 4, p. 8)

The global invariant `Inv` ranges over all instances and scheduler state. A class receives local contracts for initialization, phase-specific execution, and ticking. The main theorem is: “If all local contracts are valid and all global entailment checks succeed for an invariant Inv , then φ holds at the end of every scheduling cycle in every run of S, for all configurations satisfying Γ .” (Theorem 1, Sec. 4.2, p. 10)

## technique 1: contract-based compositional verification
What it is. Verify each class method in isolation, then prove that the scheduler’s interleaving preserves a global invariant. A local contract is a Hoare triple `{Pre} m {Post}`; `old(e)` refers to the pre-state value. The generated contracts are `{true} init() {IC}`, `{true} exec(p) {TC(p)}`, and `{true} tick() {KC}` (Sec. 4.2, p. 9).

How to do it.
1. Define configuration constraints Γ, classes, scheduler phases, transition guards, and target safety property φ (Secs. 3–4, pp. 5–8)
2. Generate or write each class’s `IC`, `TC(p)`, and `KC` contracts; validate them for every legal configuration and instance (Sec. 4.2, p. 9)
3. Choose a global invariant `Inv` that implies φ at the final scheduler phase (Sec. 4.2, p. 10)
4. For initialization, prove Γ entails that every initialized instance and phase `l0` imply `Inv` (Sec. 4.2, p. 10)
5. For every phase change, prove a preservation entailment that updates the phase and resets executed flags; final transitions additionally apply each `KC`, and the final-to-initial reset permits input changes while preserving non-input fields (Sec. 4.2, p. 10)
6. For each scheduler self-loop, reduce arbitrary instance interleavings to one-instance preservation plus induction over the number of executed instances (Sec. 4.2, pp. 9–10)
7. Prove `Γ |= Inv ∧ phase=lf ⇒ φ` (Sec. 4.2, p. 10)

Verus form (Inference: the paper implements Dafny contracts, not Verus). Map class methods to Rust methods with `requires` and `ensures`; represent `old` values using Verus’s pre-state expressions in postconditions or explicit ghost snapshots. Put `Inv` in loop `invariant` clauses and prove one-instance preservation in proof functions. The scheduler’s arbitrary interleaving needs a ghost set of executed instances and an induction lemma; ordinary Rust ownership does not itself prove the global invariant.

Evidence. The theorem proof is induction over scheduler transitions, with an inner induction over interleavings (Sec. 4.2, p. 10; Appendix C, pp. 26–27). The paper explicitly says local contracts “can be generated automatically from class definitions and verified independently using standard program verification techniques.” (Sec. 4.2, p. 9)

## technique 2: stable per-instance guard abstraction
A global scheduler guard may cease to hold after another instance executes. The paper introduces a local predicate `g'p` for the current instance. It must satisfy establishment, `Γ |= Inv ∧ Gp→p ⇒ c.g'p`, and stability under every other instance’s execution, `Γ |= old(Inv ∧ c.g'p) ∧ d.TD(p) ∧ d.executed ⇒ c.g'p` (Sec. 4.2, p. 9).

Steps.
1. Identify the global facts needed by one instance’s method
2. Define `g'p` over that instance’s fields
3. Prove establishment from Γ, `Inv`, and the scheduler guard
4. Prove stability for every other class and instance contract
5. Prove the single-instance entailment `Γ |= old(Inv ∧ phase=p ∧ c.g'p) ∧ c.TC(p) ∧ c.executed ⇒ Inv`; the contract and executed flag describe the post-state (Sec. 4.2, p. 9)

The paper gives `¬c.executed` as a common choice for the local condition, describing it as “trivially stable under other instances’ executions.” Establishment must also hold for the particular scheduler guard (Sec. 4.2, p. 9).

Verus form (Inference). Store `executed` as ghost state and use a loop invariant stating that unexecuted instances satisfy the local approximation. Prove each execution step preserves the approximation for all untouched instances. Quantified collections may require finite ghost sets and trigger-friendly lemmas; the paper does not address Verus solver triggers.

## technique 3: automatic contract generation by symbolic effects
The implementation derives an `exec` contract from transition code. For each effect `E`, forward symbolic execution computes a map `ME` from variables to pre-state expressions. Assignments update map entries, conditionals produce conditional expressions, and quantified assignments produce lambda expressions. Individual transition effects are combined as a disjunction, with guards strengthened by priority constraints (Sec. 5.1, p. 11).

How to apply it.
1. Inline method calls in effects and initialize a symbolic map to pre-state values for fields that the effects modify
2. Substitute current symbolic values into assignment expressions; compose sequential updates; leave a nondeterministically assigned field unconstrained
3. Translate each conditional into an `if` expression over the two transformed branches
4. Translate quantified field updates into lambda expressions and form equalities describing the resulting updates
5. Encode each transition with its old source location and priority-strengthened guard, effect formula, target location, executed flag, event resets, and unchanged-field conditions
6. Disjoin the transition formulas for phase `p` with a stuttering case for when no transition in that phase is enabled (Sec. 5.1, p. 11; Appendix B.2, pp. 23–25)

The paper contains a priority discrepancy. Local execution says: “Select the first transition whose guard is enabled in the current local state, according to the order in which transitions were declared in the class;” (Sec. 3.2, p. 7). Appendix B.2 instead says: “Since transitions are evaluated in declaration order, t may fire only if its own guard holds and all higher-priority guards with the same source and target locations are false.” (p. 25). Inference: these descriptions can differ when enabled transitions have different targets; this study does not resolve the discrepancy.

Verus form (Inference). Generate a Rust specification function for each transition and prove the executable method’s `ensures` against the disjunction. This is a generator design, not a built-in Verus feature; generated specs must remain aligned with executable code.

## technique 4: quantifier grounding
When Γ bounds a set-valued field, replace quantifiers with finite conjunctions/disjunctions. For `|s|=k`, expand universal and existential quantification over the `k` elements; the paper also describes a similar encoding for `|s|≤k`. Its implementation supports constraints with `k≤1`, using object-valued fields that may be nullable for upper bounds. The rewrite applies to method code and contracts; specification equivalence requires both Γ and correspondence between the original set and grounded fields (Sec. 5.2, pp. 11–12).

Steps.
1. Detect a supported cardinality constraint in Γ (`k≤1` in this implementation)
2. Keep the original set in ghost state
3. Generate a grounded object-valued field, possibly nullable
4. Rewrite quantified code and specifications into finite Boolean formulas
5. Generate equivalence lemmas under size and set/object correspondence assumptions
6. Verify the grounded formulas; transfer the result to the original formulas via equivalence (Sec. 5.2, p. 12)

Verus form (Inference). Use finite sequences or sets in ghost state and expose a bounded element representation to the solver. Prove equivalence with `ensures` lemmas under cardinality assumptions. This optimization is useful only when the bound is explicit and maintained.

## evidence, trusted parts, and limits
Experiments use Dafny 4.11.0 on AMD EPYC 7413 nodes, with 8 GB RAM per verification task (Sec. 6, p. 13). Table 1 (p. 13) reports 105 assertions and 2 seconds for RCS using sets. The 994 assertions and 4233 seconds for lists, and 925 seconds for lists plus quantifier grounding, belong to RPS. For RPS using sets, grounding reduces total local-contract time from 729 to 620 seconds, with 963 assertions in both rows. These are totals per system/version row.

The RCS safety property was manually strengthened to an invariant; verification took 18 seconds and 63.26M Dafny resource-count units. The paper states: “Verification of the safety property, which was not inductive and so was manually extended to form the invariant, took 18s and used 63.26M RC.” (Sec. 6, p. 14). RPS verifies 25 safety properties: 21 reproduced from prior work plus four new engineer properties (Sec. 6, p. 14). Proprietary industrial models cannot be publicly shared (footnote, p. 12), limiting independent reproduction.

Inference: applying the result requires trusting Dafny and its backend, the configuration assumptions, and the connection between the modeled semantics and the deployed system. Generated contracts are checked against their method implementations; that does not establish equivalence with deployed C code. The authors list establishing “the functional equivalence between the models used for verification and the actual (automatically generated) C implementations deployed in production” as future work (Sec. 7, p. 15). The paper says finding a suitable invariant reduces to an undecidable parameterized-safety problem (Sec. 4.2, p. 10). Quantifier grounding relies on its cardinality and field-correspondence assumptions.

Inference: contract generation plus a global invariant proof over scheduler phases is a possible design to transfer to verified Rust. Verus can express local contracts and inductive invariants, but the paper does not establish that Verus can automatically handle quantified instance sets or generated lambda effects. A VL product should retain configuration bounds, generated-contract provenance, and invariant assumptions as reviewable artifacts.

## techniques for the catalog
- compositional SRA contracts: verify init, phase execution, and tick locally, then preserve a global invariant
- stable guard abstraction: replace a changing global guard with an established and stable per-instance predicate
- symbolic contract generation: compute transition effects as pre-state expressions and guarded disjunctions
- quantifier grounding: rewrite bounded set quantifiers into finite formulas and prove specification equivalence
- scheduler-phase induction: prove initialization, self-loop interleavings, phase edges, final property, and reset separately
