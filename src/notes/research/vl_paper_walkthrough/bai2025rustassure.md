# RustAssure: Differential Symbolic Testing for LLM-Transpiled C-to-Rust Code
(authored by agents unless marked 🧑)
Tag: `bai2025rustassure`, [paper](https://arxiv.org/abs/2510.07604v1)

## scope and result

RustAssure transpiles C functions to Rust with an LLM and checks the translation by differential symbolic execution. The paper describes the check as follows: “RustAssure symbolically executes both the original C and LLM-transpiled Rust code to detect functional divergence between the original C and Rust code.” (p. 1). The tool reports a Semantic Similarity Score (S3) from graph edit distance between symbolic return values and output parameters. It is compositional: a caller can be checked while an invoked function is abstracted to return symbolic values.

The evaluation covers five codebases—libcsv (405 lines), urlparser (435), optipng (3,039), libbmp (287), and u8c (334)—and four models. Across 176 C functions, GPT-4o compiled 158, GPT-4o-mini 146, GPT-3.5-turbo 124, and Claude-3.5-Sonnet 85. The abstract's 89.8% compilability is GPT-4o's 158/176 denominator. Table I counts equivalent output values, rather than equivalent whole functions: “Eq. Output indicates return values with S3 score = 0.” The reported per-model equivalent-output percentages are 72% (GPT-4o), 74% (GPT-4o-mini), 71% (GPT-3.5-turbo), and 80% (Claude-3.5-Sonnet); Claude's high rate is paired with only 48.3% compilability. The paper reports 12 complex and 13 simple bugs, recurring across models in 20 and 17 buggy function instances, respectively (§I, p. 2): “Because these 12 and 13 bugs are present in more than one LLM model, the total number of buggy functions detected are 20 and 17, for semantic and simple bugs, respectively.”

## technique 1: context-shaped LLM transpilation

The LLM Invoker preprocesses C before prompting. First expand headers and remove unused typedefs, variable definitions, and struct definitions with Clang ASTMatchers (§V, p. 6). Then extract C struct definitions and translate them once into a Struct Transpilation Cache; supply the cached Rust definition in every function prompt so nondeterministic calls do not create inconsistent field names. Analyze uses of ambiguous fields such as `char*`: a field used as a buffer should become `Vec<u8>`, while a null-terminated string should become `String`. Include those uses in the struct prompt. For a function exceeding the model context window, split it into chunks, translate each chunk, then assemble the responses. If compilation fails, send the original C function and compiler diagnostics back to the LLM for repair. If the result contains `unsafe` or calls unsafe libc functions, request re-translation up to a configurable limit (pp. 3–4).

The motivating `u8next_` example shows why behavioral checking matters. C resets `val` to the first byte on invalid UTF-8; the generated Rust omits that assignment and returns an intermediate state (`0x02` rather than `0xC2`) for input `{0xC2, 0x41}` (pp. 2–3). Figure 5 gives the type-use rule: a reallocating `char*` buffer maps to `Vec<u8>`, while a URL string maps to `String` (p. 7).

Inference: for Verus, this stage is an untrusted synthesis front end. A Rust function that is later verified should retain a precise contract and should not inherit safety merely from a successful compile or a low `unsafe` percentage. Inference: the cached struct definition and usage analysis are useful prompts for choosing Verus data types, but they do not prove that the chosen type preserves C aliasing or ownership behavior.

## technique 2: symbolic instrumentation and compositional execution

Instrument each C and Rust function with a Symbolizer prologue and epilogue. The prologue initializes scalar, pointer, and struct arguments with symbolic values; nested pointer and struct fields are allocated and traversed to a configurable depth (10 in the evaluation). The epilogue logs explicit returns and output parameters, traversing struct fields, array elements, and pointed-to objects; for struct output parameters, it logs only modified fields. External calls are replaced by symbolic-return stubs, so each function can be analyzed independently even if another generated function does not compile or link. Compile both languages to LLVM IR, then use KLEE v3.1 to execute the IR symbolically. The paper explains, “After the Symbolizer modifies the C and Rust functions, the Symbolic Executor performs the core symbolic execution process using the KLEE [18] symbolic execution engine.” (p. 4).

KLEE emits KQuery expressions. Rust's standard library is compiled to LLVM bitcode and linked because KLEE lacks direct Rust-standard-library support. An ANTLR KQuery parser converts the returned expressions to GraphViz graphs, and networkx computes graph edit distance. A zero edit distance means the normalized symbolic graphs match; the checker treats a larger distance as divergence (pp. 4–6). For struct output parameters, the paper states, “The Symbolizer tracks which fields of struct type output parameters were modified and logs the symbolic values of only those fields.” (§III-B, p. 4).

Inference: the Verus analogue is to write a function with `requires` describing valid input ownership and `ensures` relating its returned and modified values to an abstract C behavior, then prove the relation with `assert` facts and proof functions. A Verus proof can establish the Rust contract, but it does not automatically establish equivalence to arbitrary C or to KLEE's IR model. Inference: the paper's symbolic stubs are assumptions and must be represented as trusted external contracts in a Verus threat model.

## technique 3: language-aware normalization before comparison

Raw symbolic graphs differ even when high-level behavior matches. Rust's compiler adds integer-extension and overflow-check nodes absent from C; struct layout and padding differ; nullable pointers become `Option`; C strings and arrays become Rust `String`, slices, or `Vec`. The checker removes redundant type-extension nodes (§III-C); §IV separately addresses memory layout, `Option`, strings/slices, and vectors.

For memory layout, the authors state, “RustAssure applies the #[repr(C, packed)] attribute on every Rust struct type.” (§IV-A, p. 5). They intend this to align C and Rust layouts. For `Option<T>`, the checker casts to the underlying type to access its symbolic representation (§IV-B, p. 5). For strings and slices, it accesses the data-pointer field and casts it to `char*`; the Symbolizer supplies slices with symbolic buffers and lengths of 100 (§IV-C, pp. 5–6). For `Vec`, it accesses the data buffer and compares each element with its C counterpart; when these types are wrapped in `Option`, it first extracts and casts the inner value (§IV-D, p. 6).

The Language-aware Graph Converter removes redundant type-extension nodes that the authors judge not to affect semantics. For `u8fold`, both programs add 40 to a Unicode code point, but Rust's overflow checks create extra graph nodes; normalization removes those nodes while retaining semantic operations (Figure 3, p. 5). RustAssure deliberately uses graph edit distance instead of SMT solving to simplify implementation; strict SMT equivalence is left for future work (§III-C, p. 5): “In the future, we plan to explore using SMT solvers to establish strict equivalence.”

Inference: the paper's layout explanation needs care: `repr(packed)` removes padding and can create unaligned accesses, so `#[repr(C, packed)]` does not generally reproduce the layout of an ordinary C struct. Explicit layout alone does not prove semantic equivalence. Inference: a Verus migration should specify an abstract value relation and prove it, rather than importing a graph-distance threshold as a proof. A zero S3 score is evidence from this checker, not a Verus theorem.

## technique 4: divergence diagnosis

Use the S3 graph difference to identify which return value or output parameter diverges and how. The checker found a missing pointer increment in `scan_option`: C consumes and discards `=`, while generated Rust leaves it in the option name. Symbolic minimum returns are `ptr = ptr + 3` for C and `ptr = ptr + 2` for Rust (p. 8). It also found a wrong conditional in `csv_set_blk_size`: C assigns when `p` is non-null, while Rust tests `p.blk_size != 0`; symbolic execution exposes the added constraint (Figure 7, p. 9; §VI-C, p. 8). The motivating UTF-8 bug similarly appears as a mismatch in the output parameter `ch` (pp. 2–3).

Semantic feedback is proposed, not implemented in the reported pipeline: “RustAssure can be improved with a feedback loop from the Semantic Checker that returns divergences to the LLM for targeted re-transpilation.” (§VII, p. 11). Section VI-D reports overall precision across models of 85.7% for libcsv and 88.2% for u8c, with reported recall of 100% (p. 8; Table V, p. 10). The recall assessment used 39 rewritten libcsv tests and 5 u8c tests comprising 13 inputs, manual review of the generated Rust for those two codebases, and comparison with FLUORINE. The paper states, “We also manually reviewed the generated Rust code for these two codebases and did not find any bugs missed by our system.” (§VI-D, p. 8). Inference: this supports the reported assessment on those codebases, not exhaustive correctness across all five.

Inference: a Verus repair loop could turn a counterexample or mismatching abstract value into a failing `assert`, then ask an agent to revise code or its `ensures` contract and rerun Verus. The contract must not be weakened merely to silence the mismatch. Inference: storing each mismatch as a regression lemma or test is a direct way to prevent repeated agent errors.

## evidence, assumptions, and limits

Table I gives GPT-4o compilation 158/176 = 89.8%; its S3-equivalent output percentages are denominated by each row's “Output values,” not by C functions. Across codebases, instruction coverage ranges from 79.24% to 95.04% for C and 72.21% to 95.91% for Rust (Table II). The timeout is described as follows: “We symbolized all arguments for each C and Rust function and symbolically executed them, with a timeout of 180 minutes.” (§VI-B, p. 7). Execution-time totals use eight cores; Table III reports, for example, GPT-4o totals of 5h2m (libcsv), 5h4m (urlparser), 15h5m (optipng), 6h14m (libbmp), and 11h56m (u8c). For libopenaptx, FLUORINE's artifact supplies 31 functions, all compilable, with 10 fuzzing passes and 25 passes under RustAssure's symbolic testing. RustAssure handles 42 functions, produces 38 compilable translations, and reports 33 symbolic-testing passes; those RustAssure translations were manually verified and were not fuzzed (§VI-F, p. 9; Table VII, p. 10).

Inference: interpreting these results depends on Clang/rustc lowering, KLEE, KQuery parsing, graph normalization, the abstraction of external calls, manual bug labels, and treating C behavior as the reference. The paper explicitly warns that C memory-corruption bugs absent in Rust can make functions appear nonequivalent and produce false positives (p. 4). It also reports false positives from KLEE array optimizations; alignment is described as engineering work (p. 8). Inference: RustAssure's claim that symbolic execution “can explore all paths, thus proving that all inputs produce equivalent outputs” (p. 1) is broader than its configured depth, timeout, external stubs, and language-normalization assumptions support. The measured results do not establish universal equivalence.

Inference: for a product that lets agents write verified Rust, translation and the C reference model require separate checks. Differential symbolic checking and language-aware comparison could complement Verus proofs, provided the adaptation explicitly specifies foreign calls, undefined C behavior, and the relation between C behavior and the Rust contract.

## techniques for the catalog

- context-shaped transpilation: preprocess headers, cache shared structs, analyze field uses, chunk large functions, and repair from compiler diagnostics
- compositional symbolic execution: instrument arguments and outputs, stub callees symbolically, compile both languages to LLVM IR, and run KLEE
- language-aware normalization: reconcile C/Rust layout, Option, strings, slices, vectors, and compiler-generated graph nodes before comparison
- graph-distance equivalence: parse KQuery returns as graphs and use edit distance, with zero distance as the checker’s equivalence criterion
- divergence diagnosis: report the mismatching output and symbolic expression difference so a missing operation or wrong branch is actionable
- compiler-feedback repair: send compiler diagnostics back to the LLM; semantic-divergence feedback remains a proposed enhancement
