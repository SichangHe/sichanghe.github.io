## decision

- technical value: high
  - C2VR treats executable translation, specification translation, and final
    verification as related but different migration problems
  - its best design result is asymmetric
    - code translation falls from 92 to 82 automatically verified files when
      raw ACSL is added to the LLM prompt
    - specification migration rises from 71 to 92 files when target-Rust type
      information guides the rules
  - Rust types can discharge some C memory obligations, but other source
    obligations need transformation, trusted workarounds, or an explicit
    unsupported result
- empirical strength: medium
  - the evaluation has 212 annotated single-file C programs from four sources
  - 175 remain after excluding 37 programs with non-migratable ACSL patterns
  - 92 of 175 files verify automatically and 139 verify after manual repairs
  - the authors test specification consistency on 100 selected programs
  - the study does not prove source-target equivalence, reproduce results
    independently, or migrate a production repository end to end
- actionable VL conclusion
  - create a migration-obligation ledger linking every source code construct,
    source contract, target type, target contract, trust assumption, and gate
  - translate executable code under structural constraints, then migrate
    specifications against the actual target AST and types
  - distinguish obligations discharged by Rust from obligations merely deleted,
    tested, axiomatized, delegated to FFI contracts, or left unsupported
- product threat
  - high prior-art threat to a broad claim of migrating specified C into
    verifiable Rust
  - medium capability threat because the architecture and repair taxonomy are
    concrete and the automatic result is substantial on the evaluated corpus
  - low-to-medium current substitution threat because scope, program scale,
    semantic validation, manual work, and trusted boundaries remain limited
- no product change or experiment is authorized by this note

## what C2VR does

C2VR is a four-stage, semi-automated pipeline for moving a C program and its
ACSL annotations into Rust plus Verus annotations.

- context-aware specification extraction
  - deghost ACSL ghost code into executable C where necessary
  - parse supported ACSL into contracts, loop specifications, assertions,
    logical definitions, and ghost code
  - attach each annotation to a function, loop ordinal, or assertion placeholder
  - remove annotations to produce the C input for code translation
- LLM-driven code translation
  - use three few-shot examples and constraints to generate idiomatic safe Rust
  - prohibit raw pointers and conversions back to raw pointers
  - preserve identifiers and line-level structure so specifications can be
    reattached
  - require explicit types and avoid unsupported library abstractions
  - compile with `rustc` and return diagnostics for at most three repair rounds
- type-guided specification migration
  - parse ACSL with ANTLR and apply rule-based structural transformations
  - query the translated Rust expression types and ghost-function parameter
    types for type-sensitive rewrites
  - migrate pre-state values, dereferences, memory permissions, coercions, and
    ghost-function signatures according to those target types
- embedding and verification
  - reattach contracts by function name, loop annotations by loop ordinal, and
    assertions by placeholders
  - insert ghost functions and make required lemmas visible
  - send the assembled program to Verus
  - manually diagnose and repair remaining misalignment, compilation, and proof
    failures

## specification migration rules and boundaries

- direct or type-sensitive mappings
  - `old` moves onto mutable references because ACSL and Verus represent
    pre-state differently
  - nullable pointers translated as `Option<&T>` must be unwrapped before
    dereference
  - pointer-range validity over slices becomes a length constraint
  - C implicit conversions become explicit Verus coercions
  - pointer parameters of ghost functions become slice or scalar references
    based on offset use at call sites
- properties encoded by Rust
  - immutable and mutable references express read and write permission
  - the borrow checker enforces much of the separation previously stated in
    ACSL
  - mutability limits the state a function or loop can modify, replacing many
    frame clauses
  - inference
    - an obligation should be removed only when the target type and ownership
      derivation are retained as evidence for the same property
- workarounds
  - ACSL inductive definitions become uninterpreted ghost functions whose cases
    are added as axioms
  - unsupported ACSL ghost loops are deghosted and migrated as executable code
  - boundary
    - axioms and external contracts enlarge the trusted base; verifier success
      does not validate the assumption itself
    - deghosting changes what executes and therefore needs its own equivalence
      evidence
- non-migratable patterns found in the benchmark
  - label-based state references such as `\at` and label binders
  - ACSL-specific intrinsic clauses such as `reads` and `terminates`
  - 37 of 212 programs contain at least one such pattern
  - the supported subset also excludes such real-world constructs as statement
    contracts and `\initialized`
- external calls
  - functions without Rust equivalents may retain the original C body through
    FFI
  - Verus reasons about a manually written opaque contract, not the C body
  - inference
    - this is verified reasoning across a trusted foreign boundary, not a full
      migration away from C or a proof of that foreign implementation

## evaluation

- benchmark
  - 212 annotated C programs from `tutorial_wp`, `frama-c-problems`,
    `LMS-Verify`, and `AutoSpec`
  - 439 function contracts, 246 loop specifications, 177 assertions, and 150
    logical definitions
  - average size: 50.3 lines
  - most cases are single files; two crafted programs exceed 900 and 1,300
    lines
  - programs were filtered, deduplicated, and sometimes given extra runtime-
    safety specifications by the authors
- automatic and repaired outcomes on the 175 migratable programs
  - 92 files and 212 of 415 functions verify automatically
  - manual repairs raise this to 139 files and 349 functions
  - the paper's 79.43% headline is therefore human-assisted
  - the automatic file-level rate is 52.57%
- code translation
  - Qwen3-235B-A22B produces the best reported automatic file result: 92
  - DeepSeek-R1 produces 91 files and the same 175 post-repair compilations
  - the six LLM configurations span 64 to 92 automatically verified files
  - C2Rust compiles all 175 but only 32 files verify
  - paper diagnosis
    - C2Rust emits unsupported library calls and conservatively retains mutable
      representations that add proof burden
    - LLM output is more idiomatic and verification-friendly but can rename,
      omit, or retype constructs required by the specifications
- type-guidance ablation
  - type-agnostic specification migration verifies 71 files and 159 functions
  - type-guided migration verifies 92 files and 212 functions
  - observed type-agnostic failures include incorrect `old`, reference
    mutability, nullable dereference, and ghost-call coercions
  - inference
    - specification translation should consume checked target-language types,
      not rely on a source-only textual rewrite
- specification-guidance ablation
  - adding ACSL directly to code-translation prompts verifies 82 files and 186
    functions, below the 92 and 212 without it
  - models turn proof annotations into runtime macros and infer needless
    mutability from source memory clauses
  - inference
    - preserve specification anchors and structural constraints during code
      translation, but do semantic contract migration in a separate typed stage

## what “semantics-preserving” establishes here

- authors' method
  - manually select 100 programs: 64 successful migrations and all 36 programs
    remaining unverified after manual repairs
  - derive about seven valid and two invalid inputs per function from ACSL
    precondition boundaries
  - manually build Rust harnesses
  - turn loop annotations and intermediate assertions into runtime checks
  - use arbitrary-precision integers to approximate Verus integer arithmetic
  - require correct precondition classification and all runtime checks to pass
- reported outcome
  - all 100 sampled programs are consistent on those tests
  - no tested mismatch explains the remaining compilation or proof failures
- correct boundary
  - this is useful, targeted differential evidence over generated examples
  - it is not a proof that C and Rust executions are equivalent
  - it does not show that finite tests cover the full ACSL meaning
  - it uses source preconditions as ground truth and manually authored harnesses
  - it does not independently validate axioms, foreign bodies, or every
    unsupported source behavior
  - inference
    - describe the result as “no inconsistency found in the 100-program test,”
      not unconditional semantic preservation

## specification reduction

- the authors report eliminating
  - 100 of 332 memory-permission predicates
  - 68 separation predicates
  - 409 frame conditions
- benefit
  - Rust can move recurring memory obligations from logic into checked types,
    borrowing, and mutability
- boundary
  - fewer written predicates do not imply fewer total obligations
  - the obligation has moved into source-to-target type correspondence and the
    target compiler's enforcement
  - functional contracts, slice bounds, string conventions, and properties not
    represented by Rust types still require explicit treatment

## failure and repair taxonomy

- 83 files fail the best automatic pipeline
- 15 symptoms fall into three classes
  - translation misalignment
    - missing or renamed variables and methods unavailable after type changes
  - compilation errors
    - cross-language types, unsupported Verus features, FFI variables, naming
      conflicts, and standard-library specification gaps
  - verification errors
    - trigger inference, preconditions, postconditions, loop invariants,
      arithmetic, termination, and assertions
- 10 root causes include
  - untranslatable syntax and loss of identifier or type fidelity
  - C/Rust type-system divergence and incompatible naming rules
  - incomplete verification infrastructure
  - weak nonlinear or collection reasoning and unavailable quantifier triggers
  - changed slice-bound and termination obligations
- 9 manual strategies repair 47 files
  - explicit conversions and renamed ghost functions
  - added invariants, assertions, auxiliary ghost functions, and triggers
  - propagated slice-length facts into loops
  - adjusted variants and added recursive termination/fuel annotations
- most frequent repairs
  - explicit trigger terms: 23 programs
  - added proof annotations: 18 programs
- inference
  - the taxonomy is an actionable repair backlog
  - the repaired rate is not an automatic-system result until these strategies
    are implemented and evaluated without manual diagnosis

## what was already done

- C-to-Rust migration
  - C2Rust already provides scalable conservative translation
  - Laertes, Crown, CRustS, Nopcrat, union transformation, and GenC2Rust already
    improve ownership, pointers, safety, or idiomatic target types
  - LLM systems already use segmentation, compiler repair, testing, fuzzing,
    symbolic execution, dependency graphs, callee signatures, and project-scale
    scheduling
- source and target verification
  - ACSL and Frama-C already support deductive verification over the C memory
    model
  - Verus already embeds specifications and proofs in Rust and uses ownership to
    constrain aliasing
  - prior work already demonstrates Verus on real systems
- completed VL walkthroughs
  - ranks one through six cover verified-data scaling, repository proof
    completion and retrieval, production-crate proof and internal-spec
    synthesis, verified self-training, and specification-faithfulness testing
  - rank seven isolates ordinary-Rust-to-Verus structural translation and warns
    that local verification can lose load-bearing contracts
- C2VR's defensible increment
  - migrate ACSL annotations as well as C code across the C/Rust and
    Frama-C/Verus boundary
  - use the generated target types to guide contract migration
  - quantify which C memory annotations Rust can absorb
  - report unsupported source constructs and a cross-layer repair taxonomy
- prior-art boundary
  - C2VR does not originate generic C-to-Rust translation, compiler-feedback
    repair, Rust verification, specification generation, or verifier repair
  - it is direct public prior art for an ACSL-to-Verus migration stage and a
    combined code-and-contract migration pipeline

## what VL should learn

- keep a migration-obligation ledger
  - source construct and exact source location
  - source specification and its intended property
  - target code, checked target type, and target specification
  - disposition: preserved, transformed, discharged by language, assumed,
    tested, manually repaired, or unsupported
  - evidence and trust owner for every disposition
- separate the pipeline into explicit states
  - source parsing and contextual anchoring
  - structure-preserving executable translation
  - target compilation and type extraction
  - type-guided contract migration
  - structural re-embedding
  - proof completion and repository-wide acceptance
- enforce cross-layer alignment
  - stable symbol identities instead of names alone
  - AST-based loop and assertion anchors instead of ordinals when source drift is
    possible
  - rejected deltas when code types and contract types disagree
  - no silent loss of a contract because translation removed its anchor
- represent trust explicitly
  - foreign implementation plus manually asserted contract
  - uninterpreted function or axiom introduced by a workaround
  - property discharged by borrow/type checking
  - property supported only by finite tests
  - verifier or library gap requiring a manual proof assumption
- use typed failure routing
  - translation, embedding, compilation, verification, and semantic-validation
    failures should not share one undifferentiated repair loop
  - retain the exact failed obligation, diagnostic, attempted change, source and
    target toolchain versions, and final disposition
- combine gates
  - source and target executable-behavior evidence
  - four-direction contract-faithfulness evidence from the rank-six lesson
  - absence of unauthorized assumptions and trusted shortcuts
  - target compilation and Verus proof
  - relevant repository-wide tests and verification
  - human approval for changed public requirements or trust boundaries

## recommended VL integration

- immediate design work, without changing the product
  - define the migration-obligation ledger schema
  - define typed stage transitions and failure classes
  - specify how a Rust type derivation discharges an ACSL memory predicate
  - make FFI contracts, axioms, unsupported clauses, and manual proof additions
    visible acceptance blockers or approved trust debts
  - require stable source-target anchors and a zero-unaccounted-contract check
- later evaluation proposal requiring separate authorization
  - use held-out multi-file C repositories with real ACSL and build systems
  - compare source-only, raw-spec-prompted, and typed two-stage migration under
    equal translation and repair budgets
  - report separately
    - eligible ACSL coverage
    - compilation and automatic Verus acceptance
    - source-target behavioral discrepancies
    - contract soundness and completeness counterexamples
    - assumptions, FFI, and axioms introduced
    - human repair time and repository-wide acceptance
  - require an independent source-target oracle where possible rather than
    treating target verification as equivalence

## threat assessment

- high prior-art threat
  - a published system already claims and demonstrates combined migration of C
    code and ACSL specifications into Verus
  - broad novelty claims around “C to verifiable Rust” or type-guided
    ACSL-to-Verus conversion are weak differentiation anchors
- medium capability threat
  - 92 of 175 eligible files verify without manual repair
  - target-type guidance adds 21 automatic file passes over a source-only rule
    system
  - the implementation, benchmark, repair taxonomy, and nine repair strategies
    make follow-on automation plausible
- low-to-medium current substitution threat
  - 37 of 212 programs are excluded before the headline experiment
  - 83 of 175 eligible files fail automatically and 36 still fail after manual
    repair
  - average programs are small and mostly single-file
  - consistency is tested on finite cases rather than proved across semantics
  - FFI contracts, axioms, Verus feature gaps, and manual proof work remain
  - there is no production-repository migration, maintenance result, review-cost
    study, or independent reproduction
- inference
  - VL should absorb the typed code-contract alignment architecture promptly
  - durable differentiation should rest on governed requirements, explicit trust
    accounting, repository-scale transactions, stronger equivalence evidence,
    human-review economics, and maintained proofs
