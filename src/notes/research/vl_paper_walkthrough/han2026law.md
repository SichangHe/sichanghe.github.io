# Law And Order: Tax Law Autoformalization
(authored by agents unless marked 🧑)
Tag: `han2026law`, [paper](http://arxiv.org/abs/2610.02792v1)

## system and result
LAW&ORDER translates tax forms and instructions into executable symbolic programs, verifies intermediate cell outputs on repair cases, and repeatedly repairs only functions whose outputs disagree. The abstract reports 100% cell-level and form-level accuracy on 51 held-out TaxCalcBench returns, while the strongest LLM alone reaches 66% accuracy. The paper's key design is structural correspondence (cells, schedules, dependencies align with functions) plus denotational correspondence (functions implement prescribed computations). Its stated objective is “to synthesize a symbolic program that exactly reproduces the computations specified by a tax form and its accompanying instructions.” (Section 3, p. 4.)

## technique 1: extract structure and generate a computational skeleton
The pipeline first applies a regex algorithm to tax-form PDFs, extracting computationally relevant cells and definitions. Each cell becomes a function. The authors manually audited federal and state forms and report no observed extraction errors (Section 3.1, p. 4). For every extracted cell, they generate an empty function specification: only the interface exists, and implementation logic is omitted (Section 3.2, p. 4). A cell `c_i` has a value type in integers, reals, or booleans and a function `f_i : X_i → C_i`, where `X_i` contains referenced inputs. The signatures form the tax form's computational skeleton independently of implementation language.

## technique 2: instruction-grounded synthesis
For each function signature, the LLM receives the tax form, official instruction text, and signature, then writes executable symbolic logic implementing that instruction (Section 3.3, p. 4). The authors treat instructions as the authoritative semantic source because they are operational and require less legal interpretation than statutes or regulations. The generated artifact can be Lean, C++, Python, Epilogue, or another deterministic language.

## technique 3: repair-set-assisted verification and localized correction
Repair cases contain inputs and expected outputs for every cell. The system executes the generated dependency graph, compares each cell output with its expected value, and identifies the first or affected function. That function is regenerated with its form and instruction context. Validation repeats until every cell agrees on every repair case. Algorithm 1 states the loop: execute all functions on all `(I^(k), G^(k))`; for each mismatch, set `f_j ← LLMCorrect(f_j, {x_j^(k)}, I_j)`; stop when all outputs equal gold outputs. The paper explains, “When a discrepancy is identified, the function corresponding to the affected cell is regenerated by prompting the LLM with the relevant tax form and instruction context to correct the implementation.” (Section 3.4, p. 5.)

The paper distinguishes finite behavioral agreement from universal equivalence: “Agreement on a finite benchmark establishes cell-level behavioral agreement on the repair set examples rather than universal semantic equivalence over all possible taxpayer inputs.” (Section 3.4, p. 5.)

## technique 4: separate repair and held-out evaluation
The repair set comes from OpenTaxSolver human-written returns. After synthesis and repair, the program is frozen and evaluated on independently authored TaxCalcBench returns written by CPAs and never exposed during generation or repair (Section 1, p. 2; Section 4.1, p. 5). TaxCalcBench has 51 cases. Cell accuracy is correctly computed cells divided by total evaluated cells; form-level accuracy requires every cell in a return to match (Section 4.2, p. 6).

Table 2 shows GPT-5.5 Medium LAW&ORDER at 95.0% strict return accuracy and 99.3% cell accuracy; direct translation is 17.5% and 73.3%, and self-debugging is 37.5% and 75.0%. GPT-6 LAW&ORDER reaches 100.0% for both. These percentages use the 51-return held-out set described in the setup; the paper does not provide per-model denominators beyond that shared test set.

## technique 5: semantic equivalence and counterexamples
The authors sample 50 cells and ask Claude Code to prove equivalence between Claude Opus implementations and gold implementations or find divergent inputs. Equivalence is proved for 43/50. Seven have counterexamples; six expose errors in generated code and one exposes an error in the gold implementation (Section 4.4, p. 8). The denominator is the 50 uniformly sampled cells. This check demonstrates that execution agreement does not guarantee semantic equivalence and that formal comparison can uncover specification errors.

## technique 6: coverage and dependency depth diagnostics
The benchmark contains 1,847 cells across 26 forms; 1,021 are raw inputs at depth zero, and dependency depth reaches 30 (Section 5.1, p. 8). For TY2024, repair cases with at most two inputs per form achieve 94.6% cell and 44.0% branch coverage; 51 held-out inputs achieve 98.6% cell and 73.1% branch coverage. For TY2025, repair coverage is 93.3%/44.0% and test coverage 93%/73% (Section 5.3, p. 9). The paper reports that errors concentrate in longer calculation chains and that localized repair is more stable than global self-debugging.

## what is proved, measured, and trusted
The system measures exact output agreement, repair convergence, coverage, and sampled equivalence/counterexamples. It does not prove that every generated program follows the complete tax law, and the authors note that tax forms have less legal authority than statutes or regulations (Section 1, p. 2). Human extraction audits and CPA-written cases are trusted inputs to the evaluation. The single gold implementation error found in the equivalence sample shows that expected outputs can be wrong.

## techniques for the catalog
- structural correspondence: map source cells or rules and dependency edges to executable functions
- instruction-grounded synthesis: generate each function from authoritative natural-language instructions plus its interface
- localized repair: regenerate only the function whose intermediate output or proof obligation fails
- repair/test split: tune on human-written cases and evaluate once on independent held-out cases
- equivalence checking: prove sampled implementations equivalent or produce concrete divergence inputs
- coverage/depth diagnostics: measure cell and branch coverage and prioritize long dependency chains
