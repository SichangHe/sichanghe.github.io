# Optimized Invariant Representation of Network Traffic for Detecting Unseen Malware Variants
(authored by agents unless marked 🧑)
Tag: `bartos2016optimized`, [paper](https://www.usenix.org/conference/usenixsecurity16/technical-sessions/presentation/bartos)

## scope and formal-verification relevance

The paper presents a supervised malware classifier whose input is a bag of HTTP-flow feature vectors. Its central claim is robustness to feature scaling and shifting, reordering, and changing bag size. It is a machine-learning representation paper, not a formal-verification paper: it gives no program logic, proof assistant, soundness theorem, or mechanically checked invariant. Inference: The techniques below could supply specifications for a Verus implementation; the paper does not discuss Verus.

The authors frame the problem as conditional domain shift: for each category, training and testing bag distributions may differ. They seek a transformation τ for which the transformed distributions are approximately equal. The paper states, “The representation is designed to be invariant under shifting and scaling of the feature values and under permutation and size changes of the bags.” (Section 1, p. 808.)

## technique 1: bag construction and invariant feature representation

Inference: This is useful when individual flows vary across malware versions but flows belonging to one user and hostname form a meaningful sample. The paper's procedure is:

1. Extract an n-dimensional feature vector x from every proxy-log flow (Section 3, p. 810). Examples include URL and path lengths, byte counts, query-parameter counts, character ratios, and whether parameters repeat (Table 3, p. 817).
2. Group flows into a bag X for each user and hostname/domain, with m flows and n features. Section 3 writes X as n-by-m (p. 810), while Equation 2 uses m-by-n, with flows as rows (Section 4.1, p. 811). The steps here follow Equation 2. The Sality illustration uses two bags, one per malware sample, and displays five URLs per bag (Figure 2, p. 813); it does not establish 88 flows per bag.
3. Apply local min-max scaling independently to each feature column: x̃_lk = (x_lk − min_l x_lk)/(max_l x_lk − min_l x_lk), producing values in [0,1] (Equation 3, Section 4.1, p. 811).
4. For each feature k, choose a translation-invariant distance d and compute d(x_pk,x_qk) for every pair of flows. Store these distances in the symmetric per-feature self-similarity matrix S_k, then normalize it using the local scaling from Section 4.1 (Equation 4, Section 4.2, p. 811). The paper gives the condition d(u,v)=d(u+a,v+a), but does not specify a concrete distance formula.
5. Form zX_k from column k of the scaled matrix and zS_k from the strict upper-triangular entries of the scaled S_k, excluding the diagonal. Histogram zX_k to describe feature values and zS_k to describe within-bag feature differences (Section 4.3, p. 812).
6. Concatenate all feature-value and feature-difference histograms into φ(X̃; S̃; θ), dimension 2·n·b (Equation 5, Section 4.3, p. 812). A normalized histogram bin is the fraction of components in its interval (Section 4.3, p. 812). The printed formula inconsistently labels the bin with θ_i,θ_{i+1} but tests membership in [θ_{i−1},θ_i). Inference: An implementation must choose one consistent indexing convention and specify how the maximum scaled value, 1, is included.

Inference: Reordering flows preserves the multiset of pairwise distances and hence its histogram. Histogram normalization gives a fixed-dimensional representation of bags of different sizes, but arbitrary additions or removals can change the proportions and pairwise distances; it does not prove unchanged values under every size change. The paper's Figure 1 describes the sequence as standard flow vectors, locally scaled value histograms, locally scaled self-similarity matrices, difference histograms, then concatenation (Section 4.3, p. 812). “The representation is computed for bags of samples, each of which consists of features computed from network traffic logs.” (Section 1, p. 808.)

Inference: A Verus implementation would use a struct for a bounded bag and `seq` or `Vec`-like data, with `requires` clauses for nonempty bags and `max > min` for each column before division. A `spec fn` can define min-max scaling and histogram membership; `ensures` can state that a common positive scale leaves normalized values unchanged. Pairwise-distance symmetry and histogram normalization are suitable lemma/proof-function properties. Numerical proofs would need an explicit arithmetic model, including rounding if the implementation uses floating-point or fixed-point values. The learned classifier remains outside a proof unless its weights and arithmetic are verified separately.

Evidence: In the paper's real-traffic evaluation, the proposed representation is compared with flow-based vectors, value-only histograms, difference-only histograms, and their combination (Section 8.2, p. 819). The authors report that optimized combined histograms achieved 90% precision (9 of 10 alerts malicious) and 67% recall on previously unseen malware families (Figure 11, p. 819). Table 2 gives the test positives as 2,090 bags comprising 43,380 flows (p. 815); it does not provide an exact true-positive count at that operating point.

Assumptions and failures: The authors list four limitations: static behavior, multiple behaviors within one bag, encrypted HTTPS traffic, and frequent changes in behavior (Section 7, p. 815). They state, “The representation does not model malware behaviors, where all flows associated with a malware are identical.” They report removing 10% of flows for this constraint. Most URL features are unavailable for encrypted HTTPS, reducing discrimination. It is not invariant to every transformation. The authors explicitly analyze mimicry changes and state that an attacker can alter features such as URLs, bytes, and inter-arrival times (Section 7, p. 814). Inference: a malicious actor who changes pairwise dynamics, bag membership, or feature extraction semantics can defeat the intended invariants. Inference: Empty bags or constant-valued columns make the extrema or division in Equation 3 undefined; the paper does not specify a policy. Equation 3 also cancels a common additive shift in exact arithmetic for nonconstant columns, whereas Figure 2 says the value histogram is not shift invariant (pp. 811, 813). This inconsistency needs resolution before implementing the example as a specification.

## technique 2: joint bin and classifier optimization

Inference: This is useful when manually chosen histogram edges overfit or make the classifier too complex. The paper starts with b equally spaced bins and learns weights and edges from labeled bags.

1. Represent each training bag with φ(z;θ) and a linear classifier h(z;w,w0,θ)=sign(〈φ(z;θ),w〉+w0) (Equation 6, Section 5, p. 813; its expanded sum specifies the histogram-weight product).
2. Solve the convex objective in Equation 7: hinge loss over m labeled examples plus γ times the sum of absolute differences between neighboring bin weights. The regularizer encourages adjacent weights to be equal (Section 5, p. 813).
3. Merge adjacent bins whose learned weights have the same sign, creating θ* as a subset of the original edges. Larger γ causes more merging and fewer bins (Section 5, p. 813).
4. Relearn the classifier weights with a standard SVM using θ* and a quadratic λ||w||²/2 regularizer (Equation immediately after Equation 8, Section 5, p. 813).

The authors explain the purpose directly: “The objective is a sum of two convex terms. The second term is the standard hinge-loss surrogate of the training classification error.” (Section 5, p. 813.) Their synthetic example shows that λ=0.00010 gives 2.4% training error and 14.8% test error, while λ=0.01000 gives 10.4% training error and 13.5% test error (Figure 7, p. 818); these are settings of the plotted synthetic experiment, not the malware test set. On real traffic, 256 initial bins were merged to 12.7 bins per histogram on average (Section 8.2, p. 817), and one illustrative learned histogram had 18 bins (Figure 9, p. 818).

Inference: In Verus, the optimization itself would usually be trusted as an offline artifact. A verifier can check a supplied weight vector, bin-edge ordering, and a postcondition that merged edges are a subsequence of the initial edges. For normalized counts, merging two bins preserves their weighted contribution when their weights are equal: w·p + w·q = w·(p+q). Equation 8 instead prints 2w multiplying the merged bin (p. 813), which is inconsistent with that identity. Same-sign weights need not be equal, so the actual merging rule is not an exact preservation proof; the paper retrains afterward. Proving convergence or optimality would require a separate convex-optimization development. Do not encode `proof fn` calls into runtime classification.

Evidence and limits: Figure 10 reports ROC curves for five representations, with optimized combined representation outperforming the alternatives on a test set whose positive bags come from malware categories absent from training (Section 8.2, pp. 818–819). The paper gives no confidence intervals or general proof of detection outside this dataset. The test-set denominator is available: 2,090 malicious bags and 240,549 background bags (Table 2, p. 815). Inference: the measured precision and recall establish empirical transfer for this dataset, not a universal security guarantee.

## what is proved, measured, and trusted

The paper provides mathematical definitions and informal invariance arguments, not machine-checked program proofs. Its empirical evidence includes synthetic training/test errors, ROC and precision-recall curves, and real-traffic evaluation. The abstract says the deployed system “detected 2,090 new and unseen variants of malware samples with 90% precision (9 of 10 alerts were malicious)” (p. 807). However, Table 2 lists 2,090 as the total number of malicious test bags, while Figure 11 reports 67% recall at 90% precision (pp. 815, 819). Inference: The abstract's wording should not be read as an exact true-positive count at that operating point.

Table 2 reports training positives of 132,756 flows in 5,011 bags and training negatives of 862,478 flows in 26,825 bags. Test positives contain 43,380 flows in 2,090 bags; test negatives contain 15,379,466 flows in 240,549 bags (p. 815). Thus 43,380 is a flow count, not a bag count. Table 1 lists 15,379,466 under all samples and a 1:355 ratio (p. 810), whereas Table 2 assigns that same flow count to testing negatives. Inference: These are inconsistent descriptions of the evaluation counts, not evidence of separate experiments.

The data came from 80 international companies during January–July 2015 (Section 8.1, p. 816). The paper states, “Each bag should contain at least 5 flows to be able to compute a meaningful histogram representation.” Evaluation capped bags at 100 flows (Section 8.2, p. 818). Section 8.1 reports 115 extracted features, whereas the Sality example mentions 88 (Sections 6 and 8.1, pp. 814, 816). Positive training labels came from feeds, services, and blacklists; experts manually analyzed test results. Bags not labeled malicious were treated as legitimate. The signature-based comparison device detected 2% of malicious test bags (Table 2 and Section 8.1, pp. 815–816). Inference: Feature extraction, labeling coverage, data selection, solver behavior, and parameter tuning remain trusted components of this empirical result.

Inference: For VeruLaw, the reusable lesson is to specify and verify representation-level invariants around agent-written Rust, while treating statistical efficacy as an empirical benchmark. The threat to a product of agent-written verified Rust is indirect: proofs could ensure deterministic scaling, pairwise-distance symmetry, and safe bounds, but they cannot prove that a learned detector catches unseen malware or that its training data represent production traffic.

## what VL should not redo

The paper supplies a bag/self-similarity/histogram design, a two-stage bin-learning objective, and a real-traffic comparison against standard representations. Inference: VL should reuse these ideas rather than present them as novel. Verification work could resolve the equation and example inconsistencies, specify constant columns, empty bags and numerical precision, and prove properties of a chosen implementation. Detection efficacy would still require evaluation on the product's actual traffic.

## techniques for the catalog

- invariant bag representation — group flows by user and hostname, then combine local scaling, per-feature pairwise self-similarity, and normalized value/difference histograms
- joint histogram optimization — learn classifier weights with an adjacent-weight regularizer, merge same-sign neighboring bins, then retrain an SVM on the reduced edges
- empirical unseen-family evaluation — evaluate on malware categories absent from training and report precision, recall, ROC, and dataset denominators separately
