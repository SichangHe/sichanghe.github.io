# A fully verified container library
(authored by agents unless marked 🧑)
Tag: `polikarpova2015container`, [paper](https://doi.org/10.1007/s00165-017-0435-1)

## scope and result
The paper reports full functional verification of EiffelBase2, a general-purpose container library, with AutoProof. The abstract states: “We present our experience verifying the full functional correctness of EiffelBase2: a container library offering all the features customary in modern language frameworks, such as external iterators, and hash tables with generic mutable keys and load balancing.” It reports 135 public methods and 8400 lines of code, 1.4 specification lines per code line, and 0.2 seconds per method on average (Abstract, p. 495). Sect. 4.1 (p. 509) gives 46 classes, 135 public methods, and 79 abstract and 378 concrete methods. Table 1 (p. 511) totals 8440 lines of code, of which 3489 are executable and 4951 are specification (2967 requirements, 1984 auxiliary annotations); 4951 / 3489 gives the 1.4 overhead (Sect. 4.2.1, p. 511). So the abstract's 8400 LOC counts specifications as well as executable code. The paper is not consistent on this: Sect. 1.2 (p. 496) says the library has \"over 8000 lines of Eiffel code in 46 classes\". The 531 in Table 1 is the number of methods and well-formedness conditions verified, not a line count. The paper also verified about 2700 lines of client code in Sect. 1.2 (p. 496); Sect. 4.3 reports 4021 lines in the after versions of the four client programs (Table 2, p. 513), and the text there says 4086. Inference: the paper does not discuss which components are trusted; that the Boogie encoding, Z3 and the MML axioms are in the trusted base follows from the tool architecture it describes (Sect. 3, p. 502).

## technique: model-based interface specifications
What it is. Separate a class’s abstract, observable state from its concrete heap representation. A linked list exposes a mathematical sequence model; clients prove behavior against that model and never need the node layout. The paper says, “Each EiffelBase2 class declares its abstract state as a set of model attributes” (Sect. 2.1.1, p. 499) and that, because the ghost attribute is stripped by the compiler, “any elements introduced for specification purposes bring no runtime overhead”.

When to use it. Use this for reusable libraries whose clients need stable behavioral contracts while implementations vary or use inheritance. Choose a model that is complete for the public methods: a set cannot specify an order-sensitive `first` query, whereas a sequence can.

How to do it. (1) Declare a model attribute with a mathematical model type such as sequence, set, bag, map, or relation (Sect. 2.1.1, p. 499; Sect. 3.1, p. 503, which lists sets, bags, pairs, relations, maps and sequences). (2) Specify commands by postconditions describing model updates and a frame clause restricting visible abstract state; specify queries as pure functions of the model. The paper gives `extend_back` as appending an argument and says its modify clause makes `sequence` the only observable state changed (Sect. 2.1.1, p. 499). (3) Connect model to representation with invariant clauses: `sequence_implementation` relates sequence to linked cells, while `cells_first` and `cells_linked` describe traversal from `first_cell` (Sect. 2.1.2, p. 499). (4) Check completeness and observability against the API; the paper defines these as quality criteria and says AutoProof “currently does not implement this encoding” for checking them mechanically (Sect. 3.3, p. 504). A set is not a complete model for `LINKED_LIST` because `first` cannot be defined from a set; a sequence is not an observable model of `CONTAINER` because its interface cannot distinguish element order.

Verus form. Inference: use ghost fields or `spec` state to represent the model, `requires`/`ensures` for command/query contracts, and `invariant` clauses in proof loops or datatype predicates to connect the model to Rust fields. Verus has no Eiffel `modify` keyword; frame facts must be expressed with mutable-reference borrowing and postconditions. Ghost state is erased, but the Rust implementation must update it explicitly or prove a pure relation from concrete state.

Evidence and limits. Abstract specifications let clients “reason about the effect of method calls solely in terms of the model while ignoring implementation details” (Sect. 2.1.1, p. 499). All but two classes (`RANDOM` and `DISPENSER`) have complete and observable model-based specifications (Sect. 4.1, p. 510). The completeness/observability encoding was not implemented. The MML relies on 228 Boogie axioms, most borrowed from Dafny's background theory (Sect. 3.1, p. 503).

## technique: closed/open invariants and ownership
What it is. Invariants hold only for closed objects. A mutating operation opens an object, changes state, then closes it after re-establishing the invariant. The paper states: “Programs modify objects following a protocol that requires opening an object, changing its state, and then closing it, while providing evidence that the invariant has been restored” (Sect. 2.1.3, p. 499). Ownership then makes the list the gatekeeper for its internal cells (Sect. 2.1.4, p. 500).

How to do it. (1) Put abstract-validity and representation facts in class invariants. (2) Establish ownership, for example `owns_definition` says a linked list owns exactly its cells. (3) Open the owner before modifying a cell; close it only after all invariant clauses hold. By default AutoProof implicitly opens `Current` at a public command’s start and closes it at the end, so routine bodies need no explicit calls in the common case (Sect. 2.1.3, p. 500; Sect. 3.4, p. 505). The paper says defaults work for 83% of method bodies (wrapping) and 95% of method specifications (closed pre/postconditions) (Sect. 4.2.3, p. 512). (4) Override the defaults when a method needs different behavior.

Verus form. Inference: encode ownership through Rust’s `&mut` exclusivity and ghost sets of owned nodes; use `proof fn` routines to open and re-establish predicates around mutations. Verus has no built-in `wrap`/`unwrap`, so the protocol would be represented by preconditions, postconditions, and predicate unfolding.

## technique: collaborative invariants for iterators
An iterator depends on its list but cannot own it when several iterators coexist. The paper introduces subjects and observers: an iterator registers itself with the list, and the list records active observers (Sect. 2.1.6, p. 500). The precondition of `remove_right` requires all other observers of the list to be open, while methods like `item` and `forth` do not, which allows multiple closed iterators to read the same list (Sect. 2.1.6, p. 501). The paper contrasts this with Java's version-attribute checks, which it says cannot be guaranteed, and .NET, where behavior after modification is undefined (Sect. 2.1.5, p. 500); it says safe behavior is guaranteed “without runtime overhead or functionality restrictions”. Mechanically, the implicit invariant clause `all s in subjects: Current in s.observers` forces an iterator's constructor to register with its list (Sect. 3.4.2, p. 506).

Inference: in Verus, model the subject/observer relation with ghost sets and permissions. A writer operation requires exclusive mutable access to the list and proof that iterator predicates are opened; readers retain shared borrows. Rust’s borrow checker supplies part of the exclusivity, while ghost predicates encode iterator position validity.

## technique: ghost state with implicit updates
AutoProof chooses regular ghost attributes linked to concrete fields by invariants, avoiding automatic model-variable updates that can become unsatisfiable during intermediate states. The paper says, “The downside of AutoProof’s approach is that it requires explicit updates to the ghost state inside method bodies” (Sect. 3.2, p. 503). To reduce repetition it adds an implicit assignment immediately before an object closes when an invariant clause defines a ghost attribute from an expression. This is useful for inherited “legacy” ghost fields.

Inference: Verus proofs should keep executable and ghost state separate, update ghost fields in proof code, and use `ensures` to establish the abstraction relation.

## techniques for the catalog
- model-based interfaces: expose mathematical ghost models and connect them to concrete representation invariants
- closed/open ownership: mutate owned objects only while open and re-establish invariants before closing
- collaborative iterator invariants: track subjects and observers to permit safe concurrent readers and exclusive writers
- ghost-state abstraction: maintain explicit ghost relations, with optional invariant-driven updates before closure
