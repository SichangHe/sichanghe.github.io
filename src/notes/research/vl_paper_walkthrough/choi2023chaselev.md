# Formal Verification of Chase-Lev Deque in Concurrent Separation Logic
(authored by agents unless marked 🧑)
Tag: `choi2023chaselev`, [paper](http://arxiv.org/abs/2309.03642v1)

This master's thesis (KAIST, 2023, advisor Jeehoon Kang) mechanizes a realistic, unbounded Chase-Lev work-stealing deque in Coq with the Iris concurrent separation logic, written in HeapLang. The abstract says, “Our work is mechanized in the Coq proof assistant, and our verified implementation is both realistic and unbounded in terms of the number of tasks it can handle.” (abstract, unnumbered front matter) It says no earlier verification met three criteria: “(1) utilizing a minimal trusted computing base, (2) using a realistic and unrestricted implementation, and (3) proving a strong specification.” (abstract) The strong specification is linearizability, proved under the sequentially consistent (SC) memory model (“Most of this thesis assumes the sequentially consistent (SC) memory model”, Section 1.2.1, p. 1). The work also extends the proof to safe memory reclamation (Section 6.1) and, for relaxed memory, proves only safety (Section 6.2). The Coq development for chapters 4 and 5 is at https://github.com/kaist-cp/chase-lev-verification; the thesis says “The mechanization for chapter 6 will be published in the future along with the corresponding papers.” (Section 1.3, p. 4)

## technique 1: separate owner authority from shared deque state

A Chase-Lev deque has one owner that pushes and pops, while other threads steal. A logically atomic triple (LAT) with only `Deque(l)` would allow concurrent pushes, which would race on bottom and the array. Adding `OwnDeque(p)` inside the atomic pre- and postcondition still fails, because a client could store `OwnDeque(p)` in an invariant and push concurrently (Section 4.1, p. 14). The paper therefore keeps the owner-exclusive resource `OwnDeque(p)` outside the atomic precondition, as a wand premise, and returns it as a “private postcondition” at the end of the function rather than at the commit point. This needed an extension of the framework: “Currently Iris’ Coq formalization of LAT does not support private postconditions, so we slightly extended the framework for them.” (Section 4.1, p. 15) Its push specification (Figure 4.1, p. 15) reads, in the extracted text: “DequeInv(p) ` OwnDeque(p) −∗ hDeque(l)i push(p, v) hDeque(l + [v]); OwnDeque(p)i”, that is, DequeInv(p) ⊢ OwnDeque(p) −∗ ⟨Deque(l)⟩ push(p, v) ⟨Deque(l + [v]); OwnDeque(p)⟩.

The paper defines `Deque(l)` as half of a ghost variable holding the abstract sequence (the other half is in `DequeInv`), `DequeInv(p)` as the invariant over the physical fields and shared ghost state, and `OwnDeque(p)` as the owner's half points-to for the array and bottom plus half of an owner-only ghost variable (Section 4.2, pp. 15–16). Steal has no `OwnDeque`, so it holds only half points-to for the array and bottom and cannot write them; the owner combines its half with the invariant's half to write (Section 4.2, p. 16). Inference: in Verus, represent the abstract sequence and ownership token as ghost state in a state-machine or proof-oriented API; use `requires` to demand the owner token and `ensures` to return it. Inference: Verus has no Iris wands or private logical atomic triples, so the concurrent protocol would have to be encoded with supported state-machine transitions and proof functions.

## technique 2: prove operations at linearization points

The paper verifies `new`, `push`, `pop`, and `steal` against Figure 4.1's cases. `new` allocates the physical array, the (array, size) pair, top and bottom, then allocates two ghost variables and the deque state, and packages them into invariant, abstract deque, and owner resources (Section 4.3.1, p. 17). For `push`, open the invariant, combine fractional array points-to with the owner's half, write the new value, update the ghost array and deque-state ghost, increment bottom, then update the abstract sequence at the commit point (Section 4.3.2, pp. 17–19). For `pop`, mark the temporary `pop` state while decrementing bottom; branch on empty, multiple-element, or one-element cases; use a CAS on top as the commit point in the one-element case; restore the temporary flag (Section 4.3.3, pp. 19–20). For `steal`, open the invariant four times (read top, read bottom, read the value at top, CAS top), taking a persistent snapshot at each opening; if the deque is “empty” (no element, or one element and the owner is popping), reading bottom is the commit point, otherwise the CAS on top is (Section 4.3.4, pp. 20–21). A successful CAS removes the preserved top element from the abstract sequence; a failed CAS commits without changing it. With resizing, steal opens the invariant a fifth time to load the array (Section 5.3.2, pp. 26–27).

The difficult steal fact is that the value read before CAS equals the value represented at successful CAS. The thesis states, “The main challenge in verifying steal is to prove that the value at the top is preserved at the successful CAS.” (Section 4.3.4, p. 21) The proof uses snapshots and a custom validity rule (Dqst-Frag-Valid) to show top never decreases and the top element remains unchanged while top is fixed (Section 4.3.4, p. 21). Inference: a Verus implementation should state an abstract deque relation in `spec fn`s, use `ensures` for each operation's linearization result, and use a state-machine invariant for top monotonicity and element preservation. The exact Iris `AU` and fractional points-to rules do not carry over.

## technique 3: construct custom ghost state from simpler components

The deque-state ghost assertion records the array, top, bottom, top monotonicity, and preserved elements. The paper builds it from a monotonic natural number encoding `tbs(t,b)` and an authoritative ghost map from top indices to preserved values (Section 4.4, pp. 22–23). Persistent snapshots expose past states. The key validity rule proves `t1 ≤ t2` and, when top was below bottom, that it remains below bottom and the element at the old top is unchanged. The authors prove the custom rules for array writes, push, pop, and CAS-top (Figure 4.2, p. 17) from the underlying monotonic-number and ghost-map rules, using the definition in Figure 4.5 (p. 23).

Inference: in Verus, use ghost `Map`/`Set` values or a state-machine history and prove lemmas for monotonic indices and preserved entries. Keep these as `proof fn`s with `ensures`; do not model Iris propositions as executable calls. The paper notes that built-in Iris ghost states “have already been proven sound” but a custom one is not, which is why it is built from them (Section 4.4, p. 22). Inference: the trusted boundary includes the Coq proof checker and the HeapLang semantics and statement of the specification.

## technique 4: resize and memory-reclamation extensions

The full deque adds eras to the deque state so old arrays remain logically related while resizing (Chapter 5, pp. 24–29). Safe memory reclamation modifies the implementation with hazard pointers (retire the old array in push; protect and drop a shield in steal) and replaces the points-to resources with hazard-pointer `Managed` and `Protected` resources plus a ghost variable for past eras, reusing the SMR specification of Jung et al. (Section 6.1, pp. 30–32). The relaxed-memory part uses the iRC11 logic and follows an existing implementation by Kang; it verifies only that each operation runs safely: “We eventually would like to verify a strong specification with Compass [16], but for now we only verify that each operation runs safely” (Section 6.2.2, p. 34). The thesis says “we leave the full specification and verification to future work” (Section 6.2, p. 32).

Inference: for Verus, resizing needs a ghost generation or era and a proof that readers retain permission to the old allocation until they finish. Hazard pointers require explicit ghost ownership of protection slots and a reclamation transition. Verus's Rust ownership helps with lifetime discipline, but concurrent raw-pointer reclamation still needs a state-machine model and contracts for atomics.

## evidence, trust, and threat

The thesis reports mechanized Coq proofs for the realistic unbounded implementation and linearizability specification (abstract); it has no runtime benchmark, because the result is a proof development, not a performance study. Its own comparison table marks the work as not using a real-world language (HeapLang rather than C) and only partly covering relaxed memory (Table 1.1, p. 3). The thesis's own trust claim is that proof assistants “only require trust in the proof checker and not the underlying logic or framework” (Section 1.2.2, p. 2). Inference: what is proved is the stated deque specification for the HeapLang implementation under SC; the correspondence to deployed machine code and relaxed hardware is not covered by chapters 4 and 5. Inference: the threat to agent-written verified Rust is high for concurrent work-stealing code because the proof requires custom ghost state, ownership protocols, and carefully chosen linearization points. Inference: VL should reuse the owner-exclusive resource pattern, the snapshot-based preservation argument, and the modular ghost-state construction. It should not redo the thesis's Chase-Lev proof as if it were a new algorithm; a useful product experiment would measure whether agents can maintain these proofs under resizing, reclamation, and API changes.

## techniques for the catalog

- private owner postcondition — keep sole-owner permission outside shared atomic preconditions and return it after commit
- linearization-point proof — connect each concurrent operation's commit event to an abstract deque transition
- snapshot ghost state — use monotonic indices and persistent element maps to prove values survive concurrent reads
- era and hazard-pointer extension — track generations and protection resources when arrays resize or are reclaimed
