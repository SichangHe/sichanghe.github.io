# Reusing Precisions for Efficient Regression Verification(authored by agents unless marked 🧑)Tag: `beyer2013reusing`, [paper](http://arxiv.org/abs/1305.6915v1)## scope and resultBeyer et al. make abstraction precisions persistent between model-checking runs. A precision is the set of predicates, variables, or abstract facts used to construct abstract states. Saving it after one revision and loading it for the next revision avoids rediscovering facts through CEGAR (counterexample-guided abstraction refinement). The paper evaluates CPACHECKER on 4,193 verification tasks from 1,119 revisions of 59 Linux device drivers. Its abstract identifies the core result: “We experimentally show the impact of precision reuse on industrial verification problems, namely, 59 device drivers with 1 119 revisions from the Linux kernel.” (Abstract, PDF p. 1).## technique 1: define and persist a program precisionWhat it is. A precision π is the information an abstract domain tracks. For predicate analysis it is a set of predicates; for explicit-value analysis it is a set of program variables. A program precision maps each program location to a precision, allowing lazy abstraction to use different facts at different locations.How to apply it.1. During each CEGAR run, collect every precision created at every refinement step.2. Union the collected precisions at each location.3. Serialize a text file with a header followed by blocks. Each block has scope selectors (`*`, function name, or location number) and a non-empty precision.4. For explicit analysis, list variables. For predicate analysis, store SMT-LIB declarations in the header and SMT-LIB `assert` commands in blocks.5. On the next run, parse the file and construct an initial precision before normal analysis starts.6. If the imported precision is incomplete, continue CEGAR; new refinements strengthen it and can be written back.The paper gives the key design claim: “The format for persistent storage and exchange of precisions” is tool-independent (Contributions, PDF p. 2). Verus form (Inference): serialize verified proof facts as a versioned manifest of lemma names, contracts, or solver-context facts, but do not treat names alone as proof evidence. Each imported fact must be rechecked against current Rust code and specification. Verus does not expose CPACHECKER's abstract precision API, so this would be an external cache around `verus` invocations.Evidence and limits. A wrong precision file cannot make CPACHECKER unsound because missing or irrelevant facts merely cause extra refinement; the paper states that correctness is preserved and performance may worsen (Section III, PDF p. 5). This safety argument assumes the verifier's normal abstraction and solver implementation are sound.## technique 2: choose scope to survive source changesThe file can apply a precision by exact location, function, or globally. Location scope is most precise but sensitive to inserted lines. Function scope unions facts labeled for a function and assigns them to all locations in that function. Global scope unions everything and assigns it everywhere, preserving facts through function renaming or movement at the cost of unnecessary abstraction work.Steps for deployment.1. Start with location scope when control-flow locations are stable and precision cost is high.2. Use function scope for ordinary local commits; it is insensitive to statement insertion inside a function.3. Use global scope when large refactorings move code across functions and redundant facts are cheaper than rediscovery.4. After import, let CEGAR detect missing facts; export the strengthened union for the next revision.5. Monitor precision size and solver time because widening scope can make unrelated locations more expensive.The paper states the key failure mode: “location numbers may change if the program code changes, and thus, precisions get assigned to locations that correspond to a semantically different location of the original program.” (Section III, PDF p. 5). Verus form (Inference): the analogous key should be a stable Rust item path plus a hash of the relevant contract/body or a verified semantic identifier; line numbers are unsafe cache keys. Function-scoped caches can survive local edits but must invalidate on signature, representation, or contract changes.Evidence. The benchmark averaged 688 changed source lines between successive revisions, yet function/global policies reused facts across these edits. In the every-fourth-revision experiment, average changes rose to 1,579 lines and predicate-analysis speedup declined only from 3.7 to 3.2 (Table VI, PDF p. 10). The denominator is 1,090 tasks in the every-fourth subset versus 4,193 tasks for all revisions.## technique 3: reuse precision inside CEGAR and lazy abstractionWhat it is. CEGAR starts with an empty or coarse precision, builds an abstract reachability graph, checks for a violating state, and refines precision when a counterexample is infeasible. Reusing a previous precision starts the next run near the needed abstraction. Lazy abstraction keeps unaffected ARG states and applies newly learned facts only where needed.How to apply it.1. Run the first revision with empty precision and save all refinements.2. Load the saved precision for the next revision.3. Construct the ARG with that precision; if no violation appears, the existing facts prove safety without new refinement.4. If a spurious counterexample remains, analyze feasibility and add only the missing predicates/variables.5. Keep ARG portions unrelated to the counterexample when using lazy abstraction; re-explore only states computed with too-coarse precision.6. Export the resulting precision and repeat over the revision sequence.The paper's technical explanation is: “The most significant effect of reusing precisions from a previous verification run is the reduction in the number of necessary refinements.” (Section III, PDF p. 5). Verus form (Inference): cache successful proof-solver contexts or lemma dependencies and replay them after a Rust edit, then let Verus re-prove all affected obligations. A cached lemma invocation cannot replace checking its `requires`/`ensures`; invalidation must be conservative. Verus's proof functions and `broadcast` facts are possible cache units, while an SMT query cache is solver/version dependent.Evidence. For all 4,193 tasks, predicate analysis used 130,000 seconds without reuse for 4,001 solved tasks; with reuse it used 40,000 seconds for 4,057 solved tasks (56 additional tasks), a denominator and timeout-aware total reported in Table VI, PDF p. 10. Explicit-value analysis used 27,000 versus 20,000 seconds and solved 4,191 tasks in both configurations. The average predicate speedup over eligible revisions was 3.7; explicit-value speedup was 1.4. The first revision has no reusable precision and is included only in total CPU time, not in the per-revision speedup.## technique 4: apply a safe text format across analysesThe format separates an analysis-dependent header from common scope blocks. Predicate headers contain SMT-LIB declarations; predicate blocks contain assertions. Explicit headers are empty; blocks list variables. Empty precisions may be omitted. A global union can be applied to every location, while function and location policies preserve more locality.The paper's example precision for a program with `lock` and `x` stores `lock = 0` globally and `x ≤ 1` in `main` and `f` (Figure 2, PDF p. 4). This is a usable shape for an implementation: header declarations first, then blank-line-separated selectors and facts.
