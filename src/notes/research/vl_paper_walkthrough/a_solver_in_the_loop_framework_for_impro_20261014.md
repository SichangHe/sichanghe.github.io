# A Solver-in-the-Loop Framework for Improving LLMs on Answer Set Programming for Logic Puzzle Solving
(authored by agents unless marked 🧑)
Tag: `schrader2025solver`, [paper](https://arxiv.org/abs/2512.17093)

## scope and result

The paper trains language models to emit Answer Set Programming (ASP) encodings for grid logic puzzles, using an ASP solver both to label training continuations and to rank alternatives at inference. Its task instance is (I={D,E,H,S}): natural-language description, entities and types, hints, and the unique solution. The model emits a choice-rule encoding for the entities and then one partial encoding for each hint; the solver checks whether the accumulated program still entails the ground-truth solution. The authors report two contributions: automatic solver-labeled instruction-tuning data and solver-guided best-of-N generation with regeneration and backtracking.

Inference: the transferable idea for VeruLaw is to make a verifier's counterexample or proof result a training label and a search score, rather than asking an LLM to trust its own code. The paper studies ASP, not Rust or Verus, so the transfer below is an engineering analogy.

## technique: solver-labelled trajectory data

What it is. A trajectory alternates prompts, natural-language hints, and generated ASP fragments. The authors state: “We define a trajectory T to be an alternating sequence of natural language inputs and ASP statements.” (Sampling Trajectories, p. 3.) It starts with a prompt containing general ASP instructions, (D), and (E). The reference model (M_S) emits ΓC,E, the choice rule. For each hint (h_i), it emits Γi, yielding (T={P_{D,E},Γ_{C,E},h_1,Γ_1,…,h_n,Γ_n}).

How to apply it. (1) Build a prompt with the problem description, entity declarations, and a required base choice rule (Sampling Trajectories, p. 3). (2) Append hints one at a time and sample five completions at each step; the paper used temperature 0.8 for this data collection (Classification of ASP Encodings, p. 3). (3) Concatenate the base and the first (k) fragments. (4) Run the ASP solver and compare its answer set with the ground-truth solution. (5) Label a fragment chosen when the partial program contains the ground truth; label it rejected when it gives only wrong answer sets, is unsatisfiable, or produces solver errors or warnings (Classification of ASP Encodings, p. 3). (6) Generate trajectories by depth-first search, retaining at most two chosen continuations per step; form chosen/rejected preference pairs by their Cartesian product, and retain mixed cases so the data emphasizes decisions where the solver distinguishes alternatives (Training Data Generation, p. 4). (7) Fine-tune with supervised causal language modelling; the authors say, “The chosen instances can be used to train LLMs using SFT with causal language modeling.” (Model Training, p. 4.)

Verus form. Inference: represent each generated Rust/proof fragment as a candidate continuation of a specification or proof function. Compile and run Verus on the accumulated module; classify a continuation as chosen when the verifier discharges the target postcondition and rejected when it reports an error. Keep the base Rust implementation and add one lemma, invariant, or `ensures` clause at a time. Use proof functions and `assert`/`assert forall` facts as the generated fragments; executable functions retain ordinary Rust bodies. Unlike ASP's answer-set comparison, Verus needs a complete verification obligation and may require explicit loop invariants. This mapping is an inference, not a claim made by the paper.

Evidence and limits. The data-generation setup uses LogicPuzzles' 50 training instances and samples (N=5) alternatives. Llama-3.3 70B produced 3.7 chosen and 1.3 rejected responses per input on average (standard deviation 1.82); Qwen3 32B produced 3.3 and 1.7 (standard deviation 2.04) (Training Data Statistics, p. 5). The authors retained 1,546 Llama and 1,060 Qwen training instances. They acknowledge that chosen instances may still be imperfect because solver acceptance only checks the available answer-set criterion (Discussion, p. 7). Inference: a Verus label similarly proves only the supplied specification and trusted assumptions, so specification quality and external-body contracts remain outside this feedback signal.

## technique: solver-grounded greedy best-of-N with recovery

What it is. At test time, the model proposes alternatives for the base encoding and then for each hint. A reward ranks partial programs. The paper defines (f_r(Γ,M)=1/M-1_E(Γ)-1_U(Γ)-1_{NE}(Γ)), where (M) is the number of answer sets, (1_E) flags errors or warnings, (1_U) unsatisfiability, and (1_{NE}) exceeding a configured answer-set maximum (Reward Function, p. 4). “Our test-time method is based on greedy search, i.e., it aims at maximizing the current reward and does not perform search.” (Sampling Procedure, p. 4.)

How to apply it. (1) Generate (N) alternatives for the base choice rule. (2) Score each with the solver, including the strict expected number of answer sets for the puzzle dimensions. (3) Keep the highest-scoring base. (4) For each hint in order, generate (N) alternatives appended to the selected prefix and keep the highest reward. (5) If every alternative has negative reward, regenerate (2N) alternatives. (6) If recovery still fails, backtrack to the previous hint with maximum reward that had more than one alternative, then regenerate all later hints (Sampling Procedure, p. 4). The reported inference settings use (N=5), temperature 1.0, and at most five backtracking steps for LogicPuzzles and one for GridPuzzles (Settings, p. 5).

Verus form. Inference: generate (N) candidate proof continuations, run Verus on each, and rank verified candidates above failed ones; a finer score can prefer fewer diagnostics or lower verification time. Use a state record containing the current Rust module, proof prefix, and target. Regeneration makes fresh candidates after all fail. Backtracking restores the latest prefix with multiple candidates. Verus has no paper-defined numeric reward or answer-set count, so these scoring details are an inference. A candidate must use real Verus constructs (`spec fn`, `proof fn`, `requires`, `ensures`, `invariant`, `assert`) and should never call proof code at run time.

Evidence. Table 2 reports Llama-3.3 70B on LogicPuzzles: SFT alone gives 55.4% accuracy; sequential best-of-5 gives 62.7%; adding regeneration gives 64.6%; adding backtracking gives 62.7%; both recovery mechanisms give 66.8%; and best-of-25 gives 69.2%. The denominator is the LogicPuzzles test set (74 held-out puzzles after removing 26 train/test duplicates), and the table's percentages are exact-answer accuracy (Table 2 and Evaluation Metrics, pp. 5–6). GPT-4.1-mini rises from 39.2% to 55.4% with sequential best-of-5, a +16.2 percentage-point change (Table 2, p. 6). Inference: these results support verifier-guided selection on this benchmark, but do not establish that larger N is always cost-effective; the authors report output-token cost growing linearly with N and call N=5 a trade-off for their setup.

## technique: staged prompt pipeline and solver boundary

The comparison pipeline emits six stages: structured constants, ASP formatting, predicates, the choice rule, rewriting complex logical OR constraints, and final translation of all natural-language constraints (Settings, p. 5). Only the sixth stage yields a complete encoding, so intermediate solver analysis is unavailable. Inference: a Verus agent can expose proof checkpoints after each specification or invariant addition, preserving the paper's staged decomposition while making each checkpoint verifiable. The boundary matters: the paper's solver can reject a partial encoding early, whereas a Verus obligation may remain underconstrained until a function's complete contract is present.

## what is proved, trusted, and left open

The solver proves only that a generated ASP program has the expected answer set under clingo 5.7.1 and the chosen parsing/evaluation rules. The experiments use LogicPuzzles (124 total, 50 train and 74 test, all 3x4) and GridPuzzles (3x4 through 4x6, evaluation only). Exact-match accuracy treats multiple final solutions as wrong; a Levenshtein fallback handles representation differences (Evaluation Metrics and Datasets, p. 5). The model, solver, dataset labels, prompt, and reward design remain trusted components. The authors explicitly note, “One important strength of our method is that it requires no additional human annotations as it samples ASP statements from LLMs and automatically computes a reward or categorizes them into chosen and rejected.” (Discussion, p. 7.) They also caution that automatically chosen instances may be imperfect and propose weighted rewards and reinforcement learning as future work (Discussion and Outlook, p. 7).

Inference: for agent-written verified Rust, the threat is medium. A solver loop can reduce syntactic and local proof failures, but it cannot detect a wrong functional specification, an omitted safety property, unsound assumptions about external code, or an unsafe use of `external_body`. The paper's evidence is on puzzle accuracy, not on Rust safety or Verus soundness. What VL should not redo is the basic generate–solver-label–fine-tune pattern; the paper already supplies that pattern and its recovery ablation. A useful open task is measuring whether verifier-guided proof search remains stable across dependency and specification changes.

## techniques for the catalog

- solver-labelled trajectory data: generate partial formal programs, run a solver after each step, and fine-tune on solver-chosen versus rejected continuations
- greedy best-of-N verifier search: sample alternatives, rank partial programs by verifier feedback, and recover with regeneration and backtracking
- staged formalization pipeline: decompose natural-language requirements into typed declarations, relations, choice/invariant structure, and final constraints
