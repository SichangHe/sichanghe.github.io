# Featherweight VeriFast
(authored by agents unless marked 🧑)
Tag: `vogels2015featherweightverifast`, [paper](https://doi.org/10.2168/LMCS-11%283:19%292015)

## scope and trust result
This paper formalizes a core subset of VeriFast, a separation-logic verifier for C-like programs, called Featherweight VeriFast (FVF). Its stated contribution is “a formal definition and soundness proof of a core subset of the VeriFast program verification approach” (Abstract, p. 1). The soundness proof in the article is an outline: the Introduction says “an outline for a proof of the soundness of this approach” (p. 2). The machine-checked part is a Coq development of “a slight variant of Featherweight VeriFast, called Mechanised Featherweight VeriFast” (MFVF) (Introduction, p. 2; Sect. 5, p. 42). FVF targets a toy language with routines, loops, and dynamic allocation and deallocation, and supports routine contracts, loop invariants, separation logic predicates, and symbolic execution. It leaves out function pointers and concurrency (Introduction, p. 2). The target theorem is memory safety: if verification succeeds, “no execution of the program accesses unallocated memory” (p. 2; Theorem 4.15, p. 41). Termination is not verified (Sect. 2.4.1, p. 9).

Trust boundaries, as the paper states them: soundness relies on one assumption, that the SMT solver is sound (Assumption 4.11, p. 40); completeness is not claimed (p. 40). Coq checks MFVF, not FVF, and the paper warns that errors in the stated definitions could make the theorem vacuous, which it partly addresses with a small test suite (Sect. 5, p. 42). The Coq soundness theorem uses four standard-library axioms (Sect. 5.4, p. 47). Inference: the paper does not claim that the real VeriFast tool is covered by this proof; the tool is a further trust boundary.

## technique: contract and predicate annotations
What it is. A routine contract describes resources and facts required before a call and provided after it. The paper's `swap` example uses `req cell1 ↦ ?v1 * cell2 ↦ ?v2` and `ens cell1 ↦ v2 * cell2 ↦ v1` (Example 3.1, pp. 18-19). A variable pattern `?v1` “introduces the variable x and binds it to the value found in the heap” at that position (Sect. 3.1, p. 19), so the postcondition can relate final and initial state.

How to apply it. (1) Identify each memory resource a routine needs and write it as a points-to chunk. (2) Use pattern variables to bind old values. (3) Write an `ens` clause that states which resources are present afterward and how their values relate to the old ones. (4) Join independent resources with separating conjunction `*`; it asserts both facts and that the resources are present separately in the heap, unlike ordinary logical conjunction: `a * a` generally cannot be satisfied (Sect. 3.1, p. 19). (5) For unbounded structures, define a recursive predicate such as `list(l)` (Figure 6, p. 20). Use `close` to bundle the chunks of a node and the rest of the list into one predicate chunk (Sect. 3.1, p. 20; the `range` routine closes the list before writing the result). Use `open` for the inverse, unbundling a predicate chunk into its body (Sect. 3.2, p. 21; the list reversal in Figure 14, p. 46, uses both). (6) At the end of a routine body the heap must be empty after the postcondition is consumed; a nonempty heap is a leak and fails (Sect. 3.3, p. 22).

Verus form. Inference: use `requires` and `ensures` on Rust functions, ghost variables for old values, and predicates or quantified assertions for owned resources. Rust references and Verus permissions would replace the concrete points-to chunks. A `proof fn` can establish a list-shape lemma; it must not be called as executable code. The separation split would be represented by disjoint mutable borrows or explicit ghost disjointness facts. The paper does not discuss Rust or Verus.

## technique: semiconcrete execution
The paper inserts an intermediate execution between concrete behavior and symbolic reasoning. It says “semiconcrete execution executes each routine separately, starting from an arbitrary initial state that satisfies the precondition, and checking that each final state satisfies the postcondition” (Sect. 2.8, p. 17). A routine call uses the callee's contract instead of its body, and a loop body is executed separately from an arbitrary state satisfying the invariant. The paper concludes “all executions have finite length” (p. 17), while predicates denote “data structures of potentially unbounded size” (p. 17). Semiconcrete execution still branches infinitely, which motivates the symbolic step (p. 17).

Steps, from Definitions 3.7-3.8 and Figures 8-9 (Sect. 3.8-3.9, pp. 24-27). Routine validity: (1) bind each parameter to an arbitrary value; (2) produce the precondition, meaning add its chunks to the heap and assume its facts; (3) execute the body, where each call consumes the callee's precondition and then produces its postcondition; (4) consume the postcondition; (5) check that the heap is empty (leak check). Loops: (6) consume the loop invariant on entry; (7) assign arbitrary values to the variables the body modifies; (8) then choose between two branches. In one branch, empty the heap, produce the invariant, assume the loop condition, execute the body, consume the invariant, and run the leak check. In the other, produce the invariant and assume the loop condition is false. (9) A predicate is a named, possibly recursive assertion, opened and closed around field-level operations.

The semantic guarantee is a refinement chain, quoted verbatim: “safe program(c) ⇐ sc-safe program(c) ⇐ sym-safe program(c)” (Definition 2.24, p. 18). The semiconcrete step is proved sound as Theorem 3.27 (p. 33).

Verus form. Inference: write loop `invariant` clauses that summarize the heap shape and use function contracts for modular calls. Verus does not have VeriFast's `open`/`close` commands; unfold and re-establish predicates with proof functions and `assert`/`reveal` patterns supported by Verus. Keep loop invariants strong enough to imply both safety and the next-iteration shape.

## technique: symbolic execution with path conditions
Concrete and semiconcrete execution still branch infinitely on fresh allocation addresses and nondeterministic values. Symbolic execution replaces each demonic choice with a fresh symbol and stores constraints in a path condition. The paper explains: “Infinite branching is thus replaced by picking a fresh symbol. A theorem prover is used to decide equalities between terms and other conditions involving symbols under a given path condition” (Sect. 2.8, p. 18).

Procedure (Sect. 4, pp. 34-39): (1) maintain a symbolic store, symbolic heap, and path condition (Definition 4.2, p. 35). (2) Pick a fresh symbol ς and record it by adding the formula ς = ς to the path condition; `malloc` also adds `0 < l` for the new address (Figure 10, p. 34; Definition 4.3, p. 36; Figure 11, p. 38). (3) To assert a boolean expression, translate it to a formula and ask the SMT solver whether it follows from the path condition; if not, execution fails (Sect. 4.3, pp. 35-36). (4) To consume a heap chunk, find a chunk whose arguments the solver proves equal under the path condition, not merely textually identical: with `list(l)` in the heap and `l = l'` in the path condition, consuming `list(l')` succeeds (p. 36). (5) Produce chunks by adding them to the symbolic heap (p. 36). (6) To assume a condition, block if the solver proves its negation, otherwise add it to the path condition; a conditional explores `b` and `¬b` as two branches (Sect. 4.3, p. 35; Definition 4.3, p. 36; Figure 11, p. 38). The formal definition gives `sassert(b)` as the entailment check `Φ ⊢SMT JbKŝ` and `sconsume chunks` as a search for a sub-heap whose terms the solver proves equal (Definition 4.3, p. 36).

Verus form. Inference: Verus's SMT-backed `assert`, `requires`, and `ensures` discharge path-condition obligations, while Rust control flow creates branches. Use ghost symbolic values only in specifications; do not model a runtime symbolic executor. Solver failure is a proof failure, and unsupported nonlinear or heap reasoning needs explicit lemmas.

## evidence and failure modes
The Introduction says the authors “use Featherweight VeriFast to verify the safety of both examples”: a routine pair that builds and tears down a large linked list, and the in-place reversal of a linked list (Introduction, p. 2). The paper shows the contract for `range` (Figure 6, p. 20) and symbolic traces for it (Figure 10, p. 34). Its Coq run on the in-place reversal routine returns `ok` (Figure 14, p. 46). The formal subset excludes concurrency and function pointers even though full VeriFast supports them (p. 2). Soundness of FVF is argued by an outline; the machine-checked Coq proof covers the variant MFVF (Sect. 5, p. 42). The paper lists as future work lemma functions, inductive datatypes, concurrency, fractional permissions, function pointers, predicate families and higher-order predicates (Sect. 7, p. 54).

## techniques for the catalog
- separation contracts: specify consumed and produced heap resources with preconditions, postconditions, and separating conjunction
- recursive predicates: summarize unbounded structures and open/close them around local mutations
- semiconcrete execution: use contracts and loop invariants to bound traces before symbolic reasoning
- symbolic execution: replace infinite branching with fresh symbols and SMT-checked path conditions
