# Permission-Based Separation Logic for Multithreaded Java Programs
(authored by agents unless marked 🧑)
Tag: `amighi2015permissionbased`, [paper](https://doi.org/10.2168/LMCS-11(1:2)2015)

## scope and central invariant

The paper presents a sound (but not complete) concurrent separation logic for a Java-like language with heap-allocated threads, repeated joins, reentrant monitors, and wait-notify. Its abstract states: “The program logic associates a unique static access permission with each heap location, ensuring exclusive write accesses and ruling out data races.” (Abstract, p. 1). Fractional permissions permit concurrent reads; per the abstract, permissions are transferred “upon thread starting, thread joining, initial monitor entrancies and final monitor exits” (Abstract, p. 1). The logic also uses abstract predicates for data abstraction, monitor invariants, fork preconditions, and join postconditions, plus value-parameterized types for global ownership relations (Abstract, p. 1).

## technique: permission tickets and separating conjunction

Use this when shared heap access must be checked compositionally. A points-to assertion `x.f ↦ v` both states the field value and grants an access ticket. Full permission `1` permits writing; a partial permission (less than 1) permits reading, and permissions are fractions 1/2^n in (0,1] (Sections 1.3 and 2.1, pp. 4, 7). Joining of permission tables requires the sum for each field to stay at most 1 (Section 2.3.1, p. 10), so two writers cannot own the same field; Theorem 3.1 (data race freedom, p. 27) is proved from this. The paper says, “The crucial difference to standard Hoare logic is that both these rules have a precondition of the form x.f 7→ : this formula functions as an access ticket for x.f .” (Section 1.2.1, p. 3).

Steps (a reading of the paper's rules, not a procedure the paper states): (1) give each field a permission-bearing points-to fact; (2) split a full permission into fractions for concurrent readers with the (Split/Merge) axiom (Table 1, p. 13); (3) require a points-to fact in every read/write rule: (Get) takes any permission, (Fld Set) takes full permission 1 (Figure 3, p. 15); (4) merge fractions back to 1 before a write; (5) the model treats a state whose total permission for a field exceeds one as incompatible. Separating conjunction `F * G` requires disjoint resources; the paper says “separation logic’s * implicitly excludes interfering heap accesses through aliases” (Section 1.2.1, p. 3). Inference: Verus has ownership and tracked ghost resources, but its idiomatic specifications use `requires`/`ensures`, `tracked` values, and state-machine protocols rather than the paper's points-to syntax. Inference: a Verus encoding should make a write consume exclusive authority and share read facts through a proved protocol; duplicating a tracked permission would be a proof error.

## technique: frame rule and abstract predicates

The frame rule localizes a method proof: from `{F} c {F'}`, derive `{F * G} c {F' * G}`; the formal (Frame) rule for head commands has the side condition that the free variables of `G` are not written by the command (Figure 3, p. 15). The paper states, “This rule expresses that given a command c that only accesses the part of the heap described by F , one can reason locally about command c ((Frame)’s premise) and deduce something globally, i.e., in the context of a bigger heap F * G ((Frame)’s conclusion).” (Section 1.2.2, p. 4). Abstract predicates, taken from Parkinson's thesis, “hide implementation details from clients but allow class implementers to use them” (Section 1.3, p. 5); a predicate can be opened or closed only by a receiver in the class that defines it, via the (Open/Close) axiom (Section 2.4.1, pp. 12–14).

Steps: (1) specify the exact footprint `F` a method can access; (2) prove the body from `F`; (3) carry any disjoint caller resource `G` through the call with Frame; (4) open or close an abstract predicate only in its defining class. Inference: Verus's function contracts and ownership already provide a frame-like effect for values that a function cannot access; abstract predicates map to `spec` predicates and helper lemmas that expose representation only in trusted modules. Inference: the mapping requires explicit borrow and alias arguments because Rust's references are not Java heap fields.

## technique: fork, join, and fractional postconditions

Use `Join(e, π)` to account for resources released by a terminated thread. Allocating an object of a Thread subclass issues one `Join(o,1)` ticket, via the redefined `init` predicate (Section 3.2.1, p. 23); a joining thread may pick up fraction `π` of the postcondition, and a `group` predicate provides a sound split/merge operation for multiple joiners (Sections 3.2.1–3.2.2, pp. 23–24). The class contracts tie the operations together: `fork` requires `preFork` (the same as `run`'s precondition), `run` ensures `postJoin<1>`, and `join` requires `Join(this,p)` and ensures `postJoin<p>` (Section 3.3, p. 25). With reentrant locks, `fork` and `run` additionally carry `Lockset` conditions (Figure 16, p. 43). The paper restricts `run`'s contract: subclasses cannot change it, it cannot have logical parameters, and `fork`/`join` are `final` (Sections 3.1 and 3.3, pp. 21–26).

Steps: (1) define a thread's `preFork` and `postJoin` predicates; (2) the creator receives a nonduplicable join ticket at allocation; (3) transfer the child footprint at fork; (4) let each joiner consume only its ticket fraction after termination; (5) split `postJoin` as a group when several threads join. Inference: Verus concurrency uses state-machine transition permissions and tracked tokens; model a join token as a tracked resource whose transition is enabled only after the child reaches a terminated state. Inference: ordinary Rust `JoinHandle` ownership can enforce one join, but repeated joins and fractional postconditions need an explicit ghost protocol.

## technique: monitor invariants and reentrant locks

A lock carries a resource invariant `inv`. Initial acquisition transfers the invariant's footprint to the thread; release must re-establish it. Reentrant acquisition does not transfer resources again, so the logic distinguishes initial entry from reentry using the `Lockset(π)` multiset of locks held by the current thread, with rules (Lock), (Re-Lock), (Unlock), (Re-Unlock) (Sections 4.3–4.4, pp. 37–41). A lock must first be committed (`fresh` to `initialized`), which hands `inv` to the lock (rule (Commit), p. 40). The (Lock) precondition needs `!(π contains u)`, which the paper admits requires alias reasoning: “this seems unavoidable” (Section 4.4, p. 40). In the lock-coupling example, type-based ownership (`Node<owner>` implementing `Owned<owner>`, with a `traversable` predicate) is used to establish it (Section 4.6, pp. 46–49).

Steps (a reading of the paper's rules): (1) define the lock's `inv` predicate; (2) commit the lock, giving up `inv`; (3) on initial entry, prove the lock is not in the lockset and obtain `u.inv`; (4) on reentry, extend the lockset without obtaining `inv` again; (5) before the final unlock, re-establish `u.inv`; (6) use ownership type parameters to establish the non-containment conditions needed by lock coupling. `wait`, `notify`, and `notifyAll` require the receiver to be in the lockset (Section 4.4, pp. 41–42). Inference: Verus can represent the monitor invariant as a state-machine invariant and represent lock ownership with tracked tokens; a transition for reentry should preserve the same token rather than create another. Inference: Rust's mutex APIs hide lock state, so proof-oriented wrappers or a state-machine model are needed for this reasoning.

## technique: modular examples and proof rules

The logic proves field reads with any permission, field writes with full permission, allocation with an initialization predicate, method calls by contract substitution, and unaffected state with Frame (Section 2.4.2, pp. 14–15). Soundness of logical consequence is stated as follows, with a proof “by induction on (Γ; v; F̄ ⊢ G)’s proof tree” whose pen-and-paper version is in a cited technical report: “If Fct (E) = E and (Γ; o; F̄ ⊢ G), then (Γ ⊢ E; F̄ |= G).” (Theorem 2.1, p. 14). The examples are sequential and parallel mergesort, a signal-processing pattern with multiple joins, a reentrant Set with wait-notify, and a lock-coupled sorted list (Sections 2.6, 3.5, and 4.6, pp. 18–21, 29–33, 44–49). For mergesort the paper proves memory safety and preservation of list length, not that the list is sorted (Section 2.6, p. 20); the method proofs of class List are not given; the Set methods are said to be straightforward to verify; and the lock-coupling implementation “has been verified in our system” (p. 48). The conclusion says “(simplified versions of) the examples in this paper can be verified by the tool” (Section 6, p. 52).

Inference: in Verus, the corresponding evidence is a verified function whose `ensures` contract states the abstract data-structure predicate and whose helper `proof fn`s establish field and permission lemmas. Inference: a Verus proof must retain executable Rust ownership and cannot import the paper's Java operational semantics unchanged.

## what is trusted, measured, and left open

The paper states a preservation theorem (Theorem 2.4, p. 17) and, for its model language, corollaries of null-error freeness and partial correctness (Theorems 2.6 and 2.7, pp. 17–18), data race freedom (Theorem 3.1, p. 27), and monitor-error freedom (Theorem 4.1, p. 44). The proofs given are short sketches that defer details to Hurlin's PhD thesis (“[Hur09, Chap. 6]”). The paper calls the logic sound but not complete (Section 1.3, p. 4). Semantic validity of Boolean expressions is not axiomatized: “in an implementation, we would use an external and dedicated theorem prover to decide this relation” (Section 2.4.1, p. 12), so such a prover, the logic's axioms, and the model-language semantics remain trusted components. The model language differs from real Java: it has no arrays, constructors, or casts, its programs “are not valid Java programs” (Section 5, p. 48), and joining a thread that has not been started blocks, “different from real Java programs” (Section 3.1, p. 23). The examples demonstrate expressiveness; they are not a performance benchmark.

## techniques for the catalog

- permission tickets — attach fractional access rights to heap facts, allowing reads below one and writes only at one
- separating conjunction — compose disjoint resources and obtain local reasoning through the frame rule
- abstract resource predicates — hide representation while exposing monitor, fork, and join contracts
- fractional join transfer — split terminated-thread postconditions among multiple joiners through nonduplicable tickets
- reentrant monitor invariants — transfer resources only on initial lock entry and re-establish the invariant on final exit
- ownership-parameterized types — encode static container ownership to prove lock-coupling non-aliasing
- sound Hoare proof rules — combine permission-aware field, call, allocation, frame, and consequence rules
