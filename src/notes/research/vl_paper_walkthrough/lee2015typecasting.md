# Type Casting Verification: Stopping an Emerging Attack Vector
(authored by agents unless marked 🧑)
Tag: `lee2015typecasting`, [paper](https://www.usenix.org/conference/usenixsecurity15/technical-sessions/presentation/lee)

## scope and result

CAVER is a compiler-instrumentation and runtime-verification system for C++ bad casts. A bad downcast treats an object allocated as a base or sibling as a derived object, violating the program's pointer semantics and potentially causing memory corruption. CAVER records the allocated object's type hierarchy outside the object, instruments downcasts, and checks the destination pointer against that recorded metadata at runtime. The abstract describes the core mechanism: “It performs program instrumentation at compile time and uses a new runtime type tracing mechanism—the type hierarchy table—to overcome the limitation of existing approaches and efficiently verify type casting dynamically.” (Abstract, printed p. 81).

The main application is a testing tool: “In this paper, we focus on the correctness and effectiveness of C AV ER against bad-casting bugs, and our main application scenario is as a back-end testing tool for detecting bad-casting bugs.” (Section 3, p. 84). The introduction reports, “C AV ER can protect all type castings of both polymorphic and non-polymorphic classes.” (Introduction, p. 82). Inference: this describes class coverage, not a proof that all executions are safe; verification depends on executed instrumentation and available metadata, with an explicit exception for phantom classes. The evaluation found 11 previously unknown vulnerabilities, nine in GNU libstdc++ and two in Firefox, all confirmed and fixed by vendors (Abstract, printed p. 81; Section 6.2, pp. 89–90).

## technique: Type Hierarchy Table (THTable)

What it is. For every C++ class, CAVER generates a THTable containing the possible target types of an object allocated as that class. It records serialized base-class relationships, composition relationships with offsets and sizes, the class size, name and name hash, and one-bit phantom-class information (Section 4.1, pp. 85–86). The paper calls P a phantom class of Q when Q derives directly or indirectly from P and adds neither member variables nor different virtual functions. It deliberately permits casting an object allocated as P to Q despite the language-level bad cast, because the layouts match; the authors describe such casts as harmless from a security standpoint (Section 4.1, p. 85).

The table covers both polymorphic and non-polymorphic classes because its reference is external metadata rather than a VTable or in-object RTTI. Class-name hashes avoid expensive string comparison; the authors state that all class names are available at compile time, allowing collision detection and resolution within each inheritance chain (Section 4.1, p. 85). The paper states, “Given a pointer to an object allocated as type T, the THTable contains the set of all possible types to which T can be casted.” (Section 4.1, p. 85).

How to apply it. (1) At compile time, enumerate each class's inheritance and composition graph and emit a THTable with type size, hash, base offsets, composition ranges, and phantom bits (Section 4.1, pp. 85–86). (2) Serialize bases so runtime lookup can scan them, while keeping referenced tables for nested compositions (p. 85). (3) Ensure hashes are unique for all classes that can participate in one cast chain (p. 85). (4) When the destination pointer lies within a component's offset and size range, recursively check that component's table; range membership alone does not establish a valid cast (Appendix 1, p. 96). (5) For a phantom match, require the destination pointer to equal the allocation base plus the target table's base offset, that base's hash to match the allocated type, and its phantom bit to be set (Appendix 1, p. 96).

Verus form. Inference: represent a class hierarchy as ghost maps from type identifiers to base offsets, composition ranges, and phantom flags. Define `spec fn valid_cast` over an allocation record, source/destination offsets, and a target identifier. A verified Rust cast wrapper can require an allocation record and ensure that the returned pointer corresponds to `valid_cast`; a `proof fn` recursively proves composition and base cases. Runtime hash lookup and raw-pointer arithmetic need explicit contracts and verified wrappers. Inference: Verus's type system does not recover arbitrary C++ ABI layout or dynamic class identity, so the THTable metadata and its generation remain trusted unless separately verified.

## technique: bind allocation metadata for heap, stack, and global objects

What it is. CAVER instruments heap, stack, and global allocation categories with the allocated type and base address, subject to safe-allocation pruning (Section 4.4, p. 88). Heap `new` calls invoke `trace_heap`, including an array count. Stack objects call `trace_stack_begin` on function entry and `trace_stack_end` on exit. Global objects get startup helpers registered in ELF `.ctors` (Section 4.2, pp. 86–87). The runtime stores a base-address/size range and THTable reference, then answers range queries for an arbitrary interior pointer.

How to apply it. (1) For each heap allocation, pass the allocated class table, base address, and number of array elements to `trace_heap` (Example 2, p. 86). (2) For each stack object, insert metadata at the function prologue and remove it at the epilogue; use compiler cleanup support so exceptions and stack unwinding also remove it (Section 4.2, p. 86). (3) For each global, emit an initialization helper that inserts its range before user code runs (p. 86). (4) Keep global and stack ranges in red-black trees; use a per-thread stack tree to avoid races (Section 4.2, pp. 86–87). (5) Use alignment-based direct mapping for heap metadata, giving O(1) lookup inside an allocated range; tree lookup is O(log N) for stack/global ranges (p. 87).

Verus form. Inference: use a ghost map of live allocation identifiers to base, length, and THTable, with ownership tokens for allocation and removal. A verified allocator wrapper can ensure insertion on allocation and removal on deallocation; a loop or recursive proof establishes that an interior pointer maps to exactly one live range. Thread-local and global maps require a verified synchronization abstraction. Foreign allocation, `.ctors`, exception unwinding, and raw-pointer provenance need explicit trusted specifications.

## technique: instrument and verify each downcast

What it is. Clang analyzes each `static_cast` and instruments only downcasts. It calls `verify_cast(beforeAddr, afterAddr, TargetTypeHash)` with the pre-cast pointer, post-cast pointer, and destination type hash (Section 4.3, p. 87). The runtime algorithm first locates the THTable for `beforeAddr`, returns without checking when metadata lookup reports an unknown area (Appendix 1, lines 53–56), and otherwise calls `isGoodCast` to recursively check compositions, bases, and phantom classes. If no valid target is found, `HandleBadCastingAttempt` can report, halt, or nullify the pointer according to configuration (Appendix 1, p. 96).

How to apply it. (1) Identify a downcast in the source and calculate the destination pointer that the compiler would produce (Section 4.3, p. 87). (2) Insert a call carrying the three verification values (p. 87). (3) Test storage membership in the order stack, heap, global; retrieve allocation base and THTable, or return without checking an unknown area (Section 4.3, pp. 87–88; Appendix 1, p. 96). (4) Recursively check compositions containing the destination pointer, then match ordinary bases by exact offset and target hash, then try permitted phantom bases (Appendix 1, p. 96). (5) On failure, apply the configured response: report, halt, or nullify the pointer. Reports include source/destination/allocated class and call stack (Section 3, p. 84; Appendix 1, p. 96).

Verus form. Inference: expose a verified `fn checked_cast` with `requires valid_allocation` and `ensures result.is_some() ==> valid_cast(...)`. Keep invalid casts as an explicit error result or verified panic path; do not prove safety by attaching an unverified body to the function under verification. Use `proof fn` lemmas for base offsets and recursive composition. Rust references already enforce some alias/lifetime rules, but an FFI pointer or integer-address representation still needs a ghost allocation model.

## technique: cache and statically remove checks

What it is. CAVER uses two optimizations. Safe-allocation analysis recursively applies two properties asserted by the paper: a bad cast can occur only when allocation is the source type or a child, and never when allocation is the destination type or a child. Allocation sites identified as safe are not traced (Section 4.4, p. 88). Runtime caching stores successful checks and keys a verification result by THTable reference, destination offset, and target type hash; repeated identical checks return the cached result (Section 4.4, p. 88).

How to apply it. (1) Build the allocation/cast type graph at compile time and mark allocations that can participate in an unsafe downcast (Section 4.4, p. 88). (2) Recursively propagate the two safe-allocation rules through class relationships (p. 88). (3) Instrument only remaining allocation sites. (4) On a first cast, verify it and insert the tuple `THTable || offset || TargetTypeHash` into the cache only when verification succeeds; on a repeat, accept the cached successful check (Section 4.4, p. 88).

Verus form. Inference: state the safe-allocation rules as `spec fn` predicates and prove a `proof fn` that an omitted allocation cannot produce a bad cast under the class-graph assumptions. For caching, use a ghost map from the key tuple to a result and prove that the key identifies the same type table, relative offset, and target. This is a type-based result, so reuse across allocations with the same table and offset is intended; deallocation invalidation is not part of the paper's cache scheme. The paper's static analysis is a C++ graph analysis; it does not transfer as a Verus library automatically.

## evidence and limits

CAVER built SPEC CPU 2006, Chromium, and Firefox with one, 21, and 10 build-configuration lines respectively, without program-specific code understanding (Section 6.1, p. 89). It detected all five known Chromium bad-casting cases tested, preserving relevant class hierarchies, compositions, and allocation sizes when backporting (Section 6.3, pp. 89–90; Table 2, p. 91). It also detected all eight combinations of polymorphic/non-polymorphic allocation and source/destination classes; UB SAN failed six combinations, including two crashes (Table 3, p. 91). Table 4 reports CAVER covering 241% more classes and 199% more castings than UB SAN in the evaluated applications (Section 6.4, p. 90). Inference: these percentages describe the evaluated binaries and do not establish coverage for every C++ program.

Performance depends on workload. Chromium browser benchmarks average 7.6% runtime overhead after optimization, while Firefox averages 64.6%; the two SPEC programs, xalancbmk and soplex, slow by 29.6% and 20.0%, respectively (Section 6.6, pp. 91–92). Table 7 lists Chromium's baseline/CAVER peak memory as 376/878 and average memory as 311/738; Firefox's corresponding values are 165/208 and 121/157 (p. 92; the table labels its units KB). Table 6 reports 1,077k total verified casts for Firefox and 151k for Chromium. Its caption says 1,550% more casts, while the Section 6.6 prose says 710% more. Inference: neither percentage represents the increase in those total counts, which is about 613%. The authors attribute Firefox's greater overhead mainly to its many stack allocations (Section 6.6, p. 92). The implementation is Linux x86 and uses platform-dependent `.ctors`, stack, and allocator mechanisms (Section 5, p. 88).

The tool detects a bad cast when the cast is executed and instrumented; the paper cautions, “Although C AV ER was able to correctly run all C++ benchmarks in SPEC CPU2006, only 483.xalancbmk and 450.soplex have downcast operations.” (Section 6, p. 88, footnote 5). Inference: it cannot prove that an unexecuted path is safe. It deliberately permits phantom-class casts and skips verification for unknown memory areas (Section 4.1, p. 85; Appendix 1, p. 96). Inference: VL could reuse the explicit runtime type relation and allocation records for unsafe Rust or FFI wrappers, but a static proof would additionally need to establish the correctness of metadata generation, allocation tracking, and pointer arithmetic. The paper does not evaluate Rust or Verus.

## techniques for the catalog

- type hierarchy table — store inheritance, composition, layout, and phantom-class metadata outside objects for runtime cast checks
- allocation tracing — bind heap, stack, and global allocations to their true type tables and address ranges
- instrumented downcast verification — check destination offsets and type hashes at every selected static downcast
- metadata lookup structures — use range trees for stack/global objects and direct mapping for heap objects
- safe-allocation pruning — prove allocation sites cannot participate in a bad cast and omit their tracing
- cast-result caching — reuse a verified result keyed by table, offset, and target type
