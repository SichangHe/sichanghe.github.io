# Type Casting Verification: Stopping an Emerging Attack Vector
(authored by agents unless marked 🧑)
Tag: `lee2015typecasting`, [paper](https://www.usenix.org/conference/usenixsecurity15/technical-sessions/presentation/lee)

## scope and result

CAVER is a compiler-instrumentation and runtime-verification system for C++ bad casts. A bad downcast treats an object allocated as a base or sibling as a derived object, violating the program's pointer semantics and potentially causing memory corruption. CAVER records the allocated object's type hierarchy outside the object, instruments downcasts, and checks the destination pointer against that recorded metadata at runtime. The abstract describes the core mechanism: “It performs program instrumentation at compile time and uses a new runtime type tracing mechanism—the type hierarchy table—to overcome the limitation of existing approaches and efficiently verify type casting dynamically.” (Abstract, printed p. 81).

The result is dynamic detection and mitigation, not a proof that all executions are safe. The introduction reports, “C AV ER can protect all type castings of both polymorphic and non-polymorphic classes.” (Introduction, p. 82) It depends on instrumentation observing allocation and cast sites, the runtime metadata store, compiler/ABI behavior, and the chosen handling of a bad cast. The evaluation found 11 previously unknown vulnerabilities, nine in GNU libstdc++ and two in Firefox, all confirmed and fixed by vendors (Abstract, printed p. 81; Section 6.2, pp. 89–90).

## technique: Type Hierarchy Table (THTable)

What it is. For every C++ class, CAVER generates a THTable containing the possible target types of an object allocated as that class. It records serialized base-class relationships, composition relationships with offsets and sizes, the class size and name hash, and one-bit phantom-class information (Section 4.1, pp. 85–86). A phantom class has the same data layout as a derived class and is allowed even though a strict inheritance check would reject it; this avoids false alarms for empty-inheritance patterns (Section 4.1, p. 85).

The table covers both polymorphic and non-polymorphic classes because its reference is external metadata rather than a VTable or in-object RTTI. Class-name hashes avoid expensive string comparison; all compile-time class names allow collision detection and resolution within each inheritance chain (Section 4.1, p. 85). Inference: the check can be summarized as follows: The paper states, “Given a pointer to an object allocated as type T, the THTable contains the set of all possible types to which T can be casted.” (Section 4.1, p. 85)

How to apply it. (1) At compile time, enumerate each class's inheritance and composition graph and emit a THTable with type size, hash, base offsets, composition ranges, and phantom bits (Section 4.1, pp. 85–86). (2) Serialize bases so runtime lookup can scan them, while keeping referenced tables for nested compositions (p. 85). (3) Ensure hashes are unique for all classes that can participate in one cast chain (p. 85). (4) Treat a composition as valid only when the pointer lies within the recorded offset and size range, then recurse into the component's table (p. 85). (5) Permit a phantom match only when the target table marks the corresponding base as phantom (p. 85).

Verus form. Inference: represent a class hierarchy as ghost maps from type identifiers to base offsets, composition ranges, and phantom flags. Define `spec fn valid_cast` over an allocation record, source/destination offsets, and a target identifier. A verified Rust cast wrapper can require an allocation record and ensure that the returned pointer corresponds to `valid_cast`; a `proof fn` recursively proves composition and base cases. Runtime hash lookup and raw-pointer arithmetic need explicit contracts and verified wrappers. Inference: Verus's type system does not recover arbitrary C++ ABI layout or dynamic class identity, so the THTable metadata and its generation remain trusted unless separately verified.

## technique: bind allocation metadata for heap, stack, and global objects

What it is. CAVER instruments every allocation category with the true allocated type and base address. Heap `new` calls invoke `trace_heap`, including an array count. Stack objects call `trace_stack_begin` on function entry and `trace_stack_end` on exit. Global objects get startup helpers registered in ELF `.ctors` (Section 4.2, pp. 85–87). The runtime stores a base-address/size range and THTable reference, then answers range queries for an arbitrary interior pointer.

How to apply it. (1) For each heap allocation, pass the allocated class table, base address, and number of array elements to `trace_heap` (Example 2, p. 86). (2) For each stack object, insert metadata at the function prologue and remove it at the epilogue; use compiler cleanup support so exceptions and stack unwinding also remove it (Section 4.2, p. 86). (3) For each global, emit an initialization helper that inserts its range before user code runs (p. 86). (4) Keep global and stack ranges in red-black trees; use a per-thread stack tree to avoid races (Section 4.2, pp. 86–87). (5) Use alignment-based direct mapping for heap metadata, giving O(1) lookup inside an allocated range; tree lookup is O(log N) for stack/global ranges (p. 87).

Verus form. Inference: use a ghost map of live allocation identifiers to base, length, and THTable, with ownership tokens for allocation and removal. A verified allocator wrapper can ensure insertion on allocation and removal on deallocation; a loop or recursive proof establishes that an interior pointer maps to exactly one live range. Thread-local and global maps require a verified synchronization abstraction. Foreign allocation, `.ctors`, exception unwinding, and raw-pointer provenance need explicit trusted specifications.

## technique: instrument and verify each downcast

What it is. Clang analyzes each `static_cast` and instruments only downcasts. It calls `verify_cast(beforeAddr, afterAddr, TargetTypeHash)` with the pre-cast pointer, post-cast pointer, and destination type hash (Section 4.3, p. 87). The runtime algorithm first locates the THTable for `beforeAddr`, returns without checking when metadata lookup reports an unknown area (Appendix 1, lines 53–56), and otherwise calls `isGoodCast` to recursively check compositions, bases, and phantom classes. If no valid target is found, `HandleBadCastingAttempt` can report, halt, or nullify the pointer according to configuration (Appendix 1, p. 96).

How to apply it. (1) Identify a downcast in the source and calculate the destination pointer that the compiler would produce (Section 4.3, p. 87). (2) Insert a call carrying the three verification values (p. 87). (3) Locate stack, heap, or global metadata in an order chosen by expected expense; retrieve allocation base and THTable (p. 87). (4) Check the adjusted destination against all ordinary bases, recursively all compositions, and permitted phantom bases (Section 4.3, pp. 87–88). (5) On failure, emit a detailed report with source/destination/allocated class and call stack, then apply the configured response (Section 3, p. 84; Appendix 1, p. 96).

Verus form. Inference: expose a verified `fn checked_cast` with `requires valid_allocation` and `ensures result.is_some() ==> valid_cast(...)`. Keep invalid casts as an explicit error result or verified panic path; do not prove safety by attaching an unverified body to the function under verification. Use `proof fn` lemmas for base offsets and recursive composition. Rust references already enforce some alias/lifetime rules, but an FFI pointer or integer-address representation still needs a ghost allocation model.

## technique: cache and statically remove checks

What it is. CAVER uses two optimizations. Safe-allocation analysis recursively applies two sound downcast facts: a bad cast can occur only when allocation is the source type or a child, and never when allocation is the destination type or a child. Allocations proven safe are not traced (Section 4.4, pp. 88–89). Runtime caching stores successful checks and keys a verification result by THTable reference, destination offset, and target type hash; repeated identical checks return the cached result (Section 4.4, p. 88).

How to apply it. (1) Build the allocation/cast type graph at compile time and mark allocations that can participate in an unsafe downcast (Section 4.4, p. 88). (2) Recursively propagate the two safe-allocation rules through class relationships (p. 88). (3) Instrument only remaining allocation sites. (4) On a first cast, verify it and insert the tuple `THTable || offset || TargetTypeHash` into the cache only when verification succeeds; on a repeat, accept the cached successful check (Section 4.4, p. 88).

Verus form. Inference: state the safe-allocation rules as `spec fn` predicates and prove a `proof fn` that an omitted allocation cannot produce a bad cast under the class-graph assumptions. For caching, use a ghost map from the key tuple to a result and prove that the key identifies the same type table, relative offset, and target. This is a type-based result, so reuse across allocations with the same table and offset is intended; deallocation invalidation is not part of the paper's cache scheme. The paper's static analysis is a C++ graph analysis; it does not transfer as a Verus library automatically.

## evidence and limits

CAVER built SPEC CPU 2006, Chromium, and Firefox with one, 21, and 10 build-configuration lines respectively, without program-specific code understanding (Section 6.1, p. 89). It detected all five backported Chromium bad-casting exploits (Table 2, p. 91) and all eight combinations of polymorphic/non-polymorphic allocation and source/destination classes; UB SAN failed six combinations and crashed on two non-polymorphic cases (Section 6.3, pp. 89–91; Table 3, p. 91). Table 4 reports CAVER covering 241% more classes and 199% more castings than UB SAN in the evaluated applications (Section 6.4, p. 90). These percentages compare the table counts in the evaluated binaries, not all C++ programs.

Performance depends on workload. Chromium browser benchmarks average 7.6% runtime overhead after optimization, while Firefox averages 64.6%; CAVER's measured memory is 2.3 times baseline peak/average on Chromium and 1.3 times on Firefox (Section 6.6, pp. 91–92; Table 7, p. 92). Table 6 reports 1,077k total verified casts for Firefox and 151k for Chromium. Its caption says 1,550% more casts, while the Section 6.6 prose says 710% more; neither percentage consistently describes those total counts. The authors attribute Firefox's greater overhead mainly to its many stack allocations (Section 6.6, p. 92). The implementation is Linux x86 and uses platform-dependent `.ctors`, stack, and allocator mechanisms (Section 5, p. 88).

The tool detects a bad cast when the cast is executed and instrumented; the paper cautions, “Although C AV ER was able to correctly run all C++ benchmarks in SPEC CPU2006, only 483.xalancbmk and 450.soplex have downcast operations.” (Section 6, p. 88). Inference: it cannot prove that an unexecuted path is safe. It deliberately permits phantom-class casts, and its result depends on complete allocation and deallocation tracing. Inference: for agent-written verified Rust, the product threat is lower when Rust ownership already rules out the pointer aliasing pattern, but remains substantial for raw pointers, FFI, unions, trait-object metadata, unsafe allocation, and code paths absent from tests. Inference: VL could reuse the explicit runtime type relation and allocation-lifetime invariants, while adding a static refinement proof where dynamic detection would only discover an exploit after deployment.

## techniques for the catalog

- type hierarchy table — store inheritance, composition, layout, and phantom-class metadata outside objects for runtime cast checks
- allocation tracing — bind heap, stack, and global allocations to their true type tables and address ranges
- instrumented downcast verification — check destination offsets and type hashes at every selected static downcast
- metadata lookup structures — use range trees for stack/global objects and direct mapping for heap objects
- safe-allocation pruning — prove allocation sites cannot participate in a bad cast and omit their tracing
- cast-result caching — reuse a verified result keyed by table, offset, and target type
