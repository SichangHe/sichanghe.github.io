# A Polymorphic Intermediate Verification Language: Design and Logical Encoding
(authored by agents unless marked 🧑)
Tag: `leino2010polymorphic`, [paper](https://www.semanticscholar.org/paper/7f8db62d17088defaa56f949d7ee0406d6a60715)

## purpose and architecture

The paper presents Boogie 2 as an intermediate verification language between source-language front ends and SMT solvers. Its abstract states: “Intermediate languages are a paradigm to separate concerns in software verification systems when bridging the gap between programming languages and the logics understood by theorem provers.” (Abstract, PDF p. 312) Boogie 2 adds impredicative, higher-rank polymorphism, polymorphic maps, type quantification, and a type system that rejects ill-typed intermediate programs. The paper gives two translations of typed expressions into simply typed logic suitable for SMT solvers.

Inference: the architecture is useful when several source verifiers need one common verification-condition language. The paper says: “In fact, we give two different translations into simply typed logic, and we present performance figures from substantial benchmarks that compare these.” (Section 1, p. 313) Source front ends encode heaps, procedures, and specifications in Boogie; Boogie generates verification conditions; a translator encodes types and expressions for an SMT solver. The paper's benchmarks come from Spec#, VCC, HAVOC, and Dafny (Section 1, p. 313); Section 5 (pp. 324–325) lists the Boogie and SscBoogie regression suites, Hyper-V verification conditions generated by VCC, and HAVOC benchmarks.

## technique 1: use a typed intermediate language with polymorphic maps

What it is. Boogie declares built-in `bool`, mathematical `int`, arbitrary bit-vectors, user type constructors, polymorphic functions, and first-class maps. Distinct type instantiations denote disjoint sets. A type-safe object store can be modeled as `HeapType = [α][Ref, Field α] α`, with `Heap[r,age]` an integer and `Heap[r,isMarried]` a boolean (Section 2, pp. 313–316; Figs. 1 and 2, p. 314).

How to apply it.

1. Declare uninterpreted constructors such as `Ref` and `Field α`.
2. Declare polymorphic map types for state; use map select `m[i]` and map update `m[i := x]`.
3. Declare polymorphic functions and axioms, quantifying over type variables and values. For example, `Left(Cons(a,b))=a` is quantified over arbitrary element types.
4. Require each type parameter to occur in a function or map domain/result so type inference can determine its instantiation. Add an explicit coercion `e:t` when the context is otherwise ambiguous.
5. Represent source-language modifies clauses by relating `old(Heap)` and `Heap`; polymorphic field quantification allows one clause to range over all field result types (Section 2.2, pp. 314–317).

Boogie maps are first-order individuals with select/store operations, so they can model higher-order-looking values while remaining suitable for first-order SMT theories. Extensionality is deliberately not assumed; users add extensionality axioms only when required (Section 2.2, p. 316).

Verus form. Inference: use Rust generic types and traits for executable typing, and ghost/specification maps for heap abstractions. Verus's `Map`-like specifications, `spec fn`, `requires`, `ensures`, and `old` expressions can state pre/post relations, but Verus does not provide Boogie's impredicative type quantifiers or polymorphic map encoding directly. Inference: keep type invariants in Rust's type system where possible and state cross-type logical facts as lemmas.

Evidence and boundaries. Inference: the paper's type system is a design and encoding result, not a proof that every source front end's heap model is adequate. The paper says Boogie does not promise extensionality of maps and that users supply extensionality axioms themselves where needed (Section 2.2, p. 316); such axioms and user axioms in general remain assumptions.

## technique 2: represent types as first-order terms

What it is. Encode all Boogie types as terms in a simply typed target with sorts `bool`, `int`, `U` (non-built-in individuals), and `T` (encoded types). Introduce `type: U→T` and, for each type constructor `C`, a function `C# : T^arity(C)→T`; a function `Ctor: T→int` with a unique constant per constructor expresses disjointness, and selector functions `C^-i` express injectivity (Sections 3 and 3.1, pp. 318–319).

How to apply it.

1. Normalize polymorphic map types to type constructors, selecting most-general map-type skeletons to avoid overlapping encodings.
2. Translate a source type expression to a term of sort `T`.
3. Add axioms stating constructor disjointness, injectivity, and selector/inverse behavior.
4. Encode polymorphic map select/store with separate symbols for each map skeleton and explicit type parameters.
5. In the translation of expressions, embed `int` and `bool` into `U` with cast functions `i2u`, `u2i`, `b2u`, `u2b`, plus round-trip axioms (Section 4.1, p. 322).

The paper warns that if two map types have a common instance, encoding the instance with either one's constructor is overly restrictive, and it might be encoded differently in different parts of one formula, “leading to incompleteness” (Section 3.2, pp. 319–320). Its construction defines constructors only for “most general” map types (p. 320). The target can be translated further to untyped logic by adding domain predicates and guards, which “will usually not be required” because current SMT solvers handle the four types directly (Section 3, p. 319).

Verus form. Inference: a Verus front end could encode Rust generic type identity with ghost type tags and injectivity lemmas, but ordinary Verus proofs rely on Rust's static type checker rather than reifying types as SMT terms. This encoding is therefore a backend design option for a multi-language verifier, not a direct Rust annotation.

Evidence. The paper defines the encoding and uses it in the two expression translations; it states no correctness proof for them. It says “Theoretically, further axioms are needed for a faithful model of the type system” and that, because the omitted axioms (e.g., well-foundedness) are not expected to help SMT solvers, only the axioms shown are used in the Boogie implementation (Section 3.1, p. 319). Inference: the target solver, type axioms, and front-end translation remain trusted.

## technique 3: translate expressions with type guards

What it is. The first expression encoding carries type information through logical guards. A polymorphic function becomes a `U`-typed function with a post-translation axiom stating the type of its result; quantified variables are guarded by equalities such as `type(x)= [[t]]` (Section 4.1, pp. 321–323; the function-axiom machinery is on p. 322).

How to apply it.

1. Translate source individuals to `U` and source types to `T` terms.
2. For each quantifier over values and types, add guards that each value has the translated type.
3. Add a result-type axiom for every translated polymorphic function.
4. Translate built-in `int` and `bool` operations through cast functions and corresponding type axioms.
5. Preserve user-supplied triggers: the paper says each trigger expression undergoes the encoding and that the encoding must not interfere with user-defined or inferred triggers (Section 2.4, p. 318).

The paper's `Mojo` example adds the function axiom `type(Mojo#(x)) = int#`, then separate guarded axioms for integer and `GuitarPlayer` arguments (Section 4.1, p. 321). The paper calls this translation “rather naive” with the disadvantage of “complicating the propositional structure of formulae”, and attributes the slowdown on VCC to the large number of Boogie functions, which “leads to a large number of additional axioms” (Sections 4.1 and 5, pp. 321 and 325).

Verus form. Inference: this resembles adding explicit ghost predicates that guard a polymorphic lemma with the relevant Rust type or trait invariant. Verus's type checker already rejects ill-typed terms, so duplicating all type guards in specifications is usually unnecessary unless a dynamic type/tag model is being verified.

## technique 4: translate with explicit type arguments

What it is. The second encoding passes each type parameter as an ordinary extra function argument. A polymorphic function `f<α>(x)` becomes `f#(type-argument,x)`; triggers then match on terms carrying the required type information, avoiding most type guards (Section 4.2, pp. 323–324; the type-argument translation of expressions is on p. 324).

How to apply it.

1. Reify each inferred type parameter as a term of sort `T`.
2. Add those terms as leading arguments to translated functions and map operations.
3. Translate quantifiers so type variables are ordinary `T` variables.
4. Ensure triggers mention the explicit type arguments, making e-matching type-specific.
5. Use this encoding when the solver uses e-matching: the paper says it “crucially depends on the usage of an SMT solver with e-matching” and “trades generality for performance”, being not applicable with most first-order theorem provers (e.g., superposition provers) (Section 4.2, p. 323). In the Z3 2.0 rows of Fig. 5 it has lower average time than type guards in all three categories.

Verus form. Inference: model a generic lemma with an explicit ghost type parameter or trait witness when SMT triggers need help. Verus does not expose SMT trigger control in the same way, so the correspondence is conceptual. Inference: avoid inventing runtime type arguments solely for proof; keep them in proof-only state.

## technique 5: preserve triggers and evaluate translations

What it is. Triggers guide SMT e-matching for quantified formulas. The paper says the logical encoding must not interfere with triggers, since that might lead to “poor performance (too many instantiations) or incompleteness (too few instantiations)” (Section 2.4, p. 318). The paper evaluates type guards, type arguments, and an intentionally unsound “No Types” translation that erases type information (Sections 1 and 5, pp. 313 and 324–325).

How to measure it. Boogie 2 generates the verification conditions with each translation and writes them to separate files; Z3 2.0 then runs on “altogether more than 10,000 verification conditions”, with a 120s timeout (1800s for the Boogie tests), averaging time over three runs, on an Intel Core 2 Duo, 3.16GHz, with 4GB (Section 5, p. 325). In Fig. 5 (p. 324, Z3 2.0, average time over valid and invalid outcomes), VCC (7840 conditions) takes 3.447s with type guards, 2.181s with type arguments, and 2.196s with no types. The paper says the type-argument encoding is close to “No Types” and “even faster in two categories”, and that type guards are “on average about 55% slower on the VCC examples, and perform similarly on the HAVOC examples” (p. 325). In Fig. 5's Z3 1.3 row for the Boogie tests, type arguments (1.212s) are slower than type guards (1.107s). In the related-work comparison with Couchot and Lescuyer, the paper says “we measure a slowdown of at most 95% with the type guards encoding and at most 45% with the type arguments encoding” (Section 5, p. 325); the text does not name the baseline. Inference: the Fig. 5 HAVOC averages relative to no types (0.709s/0.367s and 0.524s/0.367s) are consistent with those two figures, so the baseline is probably the no-types translation.

Verus form. Inference: treat quantifier triggers and solver context as part of proof performance, while checking semantics independently. A Verus benchmark should record solver version, timeout, successful obligations, and whether quantifier facts are exposed. Inference: a trigger-preserving translation is relevant to VL only if VL introduces a polymorphic intermediate representation; ordinary Rust type checking may make the typed encoding unnecessary.

## what is proved, trusted, and still missing

The paper gives a formal type system, two logical encodings, and performance evidence that advanced types are feasible. Its conclusion says: “Our experimental data support the idea that including such advanced features in an intermediate verification language is both desirable for verifier front ends and feasible for performance.” (Section 6, p. 326) Inference: it does not provide a machine-checked proof of the full Boogie implementation, Z3, the source-language front ends, or the adequacy of user axioms; the paper makes no such claim. The unsound “No Types” baseline is explicitly a comparison point, not a usable correctness translation.

Inference: VL should preserve a typed intermediate layer if it combines multiple front ends or models polymorphic libraries. It should retain explicit type information in generated SMT formulas and maintain user triggers through translation. Reimplementing Boogie's complete polymorphic map encoding is unnecessary for a Rust-only verifier unless a concrete generic-heap benchmark requires it.

Inference: for agent-written verified Rust, the direct threat is medium at the infrastructure boundary and low at ordinary function proofs. Agents can generate specifications whose generic types or map axioms are inconsistent, or trigger solver blowups by exposing too many quantified facts. Verus's static typing blocks many malformed terms, but it does not validate the semantic adequacy of ghost type models or external-library contracts. The paper does not study agent-written Rust, so this threat estimate is an inference.

## techniques for the catalog

- typed intermediate verification language — use a shared polymorphic, map-aware IR to separate source front ends from solver logic
- first-order type-term encoding — represent type constructors, maps, and built-in casts as simply typed terms with axioms
- type-guard translation — preserve typing by adding result-type axioms and guards to quantified formulas
- explicit type-argument translation — pass type terms as function arguments so SMT triggers remain type-specific
- trigger-preserving evaluation — compare typed translations and an unsound type-erasing baseline with fixed solver, timeout, and hardware
