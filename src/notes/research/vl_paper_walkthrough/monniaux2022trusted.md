# The Trusted Computing Base of the CompCert Verified Compiler(authored by agents unless marked 🧑)Tag: `monniaux2022trusted`, [paper](https://doi.org/10.1007/978-3-030-99336-8_8)## result and methodMonniaux and Boulmé audit the trusted computing base (TCB) around CompCert and two forks. CompCert proves that, for a defined-behavior C source, generated assembly has the same observable behavior, but the audit asks which unverified models, extractors, interfaces, printers, runtimes, and platform assumptions can still invalidate that chain. The paper’s abstract says, "We comprehensively analyze aspects of CompCert where errors could lead to incorrect code being generated" (abstract, p. 204).## technique 1: decompose and audit the TCB by semantic boundarywhat it is and when to use itThe paper partitions CompCert’s TCB into Coq checking and extraction, links from user C text to the formal AST, assembly back-end printing and pseudo-instruction expansion, ABI/value models, runtime libraries, and assembling/linking. This decomposition finds bugs that a theorem-prover-only view misses. The authors conclude, "By construction, the bugs of CompCert are located in a limited subpart of the software, called its TCB, which may however not be as small as we may naively expect" (section 7, p. 228).how to apply it1. list every formal theorem and its exact preconditions2. draw each boundary from user artifact to modeled artifact and from modeled output to executed artifact (sections 4–6, pp. 217–227)3. mark code that is trusted because it is unverified, extracted, generated, linked, or supplied by hardware/runtime4. search commits, bug reports, fuzzing results, and tests for failures at each boundary (sections 4.1, 5.1, 5.2, pp. 217–223)5. state which failures can produce wrong code, merely reject compilation, or affect performance (section 5.3, p. 224)Verus form
