## system and verification idea
Julien de Castelnau's master's thesis, dated March 20, 2026, presents OptiGPU, an extension of OptiTrust for deriving GPU programs from verified C-like CPU programs. The user supplies an initial proof and an OCaml optimization script. The thesis states, “Rather than requiring the user to verify an already-optimized GPU kernel, OptiGPU lets the user write and verify a simple CPU program, and then apply correctness-preserving transformations to produce an optimized GPU kernel.” (Chapter 1, p. 4.) Figure 1.1 (p. 5) depicts host code, a GPU kernel, and a proof certificate as outputs.

Verification operates on Opti𝜆, OptiTrust's imperative intermediate language, using separation-logic resources, contracts, and ghost proof steps (Sections 2.1–2.2). GPU operations are largely admitted functions: “Recall that an admitted function is one where the typechecker does not verify the body satisfies the contract.” (Chapter 4, p. 32.) The thesis claims functional correctness, data race freedom, and deadlock freedom, but states, “Finally, we have axiomatized the reasoning rules of OptiGPU; we leave it to future work to present a formal semantics and a soundness proof.” (Chapter 1, p. 7.) Inference: these are guarantees within the implemented axiomatic model, rather than an established end-to-end soundness theorem for generated CUDA.

## technique 1: proof-preserving source transformation
Begin with a pure specification and an imperative implementation; supply contracts, permissions, loop invariants, and ghost proof steps. Apply an OCaml script that composes transformations such as tiling, reordering, fission, and array hoisting. Transformations update loop contracts and resources along with executable code. Section 2.2.2 illustrates fission by deriving the new loop contracts from the resources available between the two original statements. It also illustrates updating a permission when a variable is inlined. The thesis explains the intended trust boundary: “The burden of maintaining proofs within transformations means that OptiTrust’s trusted codebase is confined to its typechecker, as opposed to relying on a set of trusted transformations that perform some validation.” (p. 19.)

GPU conversion requires an exception to checking every individual rewrite. First optimize the serial program, then introduce a kernel launch, describe the thread hierarchy, and select GPU memories and instructions. Chapter 5 states, “Within a phase, the transformations do not guarantee correctness, and typechecking should be temporarily suspended.” It continues, “However, the end of each phase represents a clear step in the GPU conversion process, which we will be able to typecheck and provide feedback to the user on, even if the program is not syntactically valid according to the CUDA code generator.” (p. 48.) Inference: a similar workflow for Verus would require a separate source transformation tool and verification at explicit phase boundaries; this thesis does not implement such a Verus tool.

## technique 2: model GPU execution with transition contracts and thread-for
Represent host/device transitions with `kernel_launch`, `kernel_setup_end`, `kernel_teardown_begin`, and `kernel_kill`. Their contracts exchange execution-context permissions: `HostCtx`, `KernelSetupCtx`, `ThreadsCtx`, and `KernelTeardownCtx`. They also track launch parameters and the shared-memory allocation allowance. Figure 4.2 and Section 4.1 (pp. 33–35) require the complete grid's `ThreadsCtx` at teardown and recover `HostCtx` at kernel termination. The thesis explains, “ThreadsCtx is the central execution resource that allows OptiGPU to verify that instructions are executed at the expected levels, such as a barrier being executed by a block, or memory operations being executed by a single thread.” (p. 34.)

A `thread for` divides the surrounding thread interval into equal chunks and associates resources with iterations using `DesyncGroup`. Unlike ordinary fork/join loops, completing a thread loop does not automatically allow resources to move between threads. The thesis states, “By both consuming and producing a DesyncGroup, thread for ensures that once some threads are given a resource, other threads cannot own that resource without using a barrier to communicate.” (Section 4.2, p. 37.) `blocksync` requires a block-sized thread context and converts desynchronized global/shared-memory resources into ordinary groups; it cannot synchronize thread registers (Section 4.4, pp. 44–45).

The conversion procedure first uses intermediate `magic thread for` loops, without the `ThreadsCtx` requirement, and inserts `magic_barrier` after each converted loop. It processes tail loop nests from the inside out, using loop fission and barrier hoisting to move synchronization outward. The user chooses which enclosing loops become thread loops, converts the intermediate loops to real `thread for` loops, and later selects realizable barriers. This placement strategy is a heuristic. The user retains control: “As we have mentioned, the user can always manually insert their own proofs and transformations to optimize barrier placement if necessary.” (Section 5.2, pp. 50–53.) Inference: explicit resource ownership and synchronization obligations are relevant to a future Verus GPU backend, but importing this pattern alone would not prove that backend sound.

## technique 3: refine memory and generate CUDA
Start with generic `Any` memory operations. Conversion transformations target a declaration, change its memory operations, and update corresponding permissions. Global memory allocation/copies require the host context; global/shared loads and stores require a single-thread context. Shared memory is allocated during setup and freed during teardown, with a byte allowance tracking the launch's requested allocation. Shared-memory and thread-register resources include distributed dimensions for blocks or threads; `DMINDEX` distinguishes these coordinates for reasoning (Sections 4.3 and 5.3, pp. 38–43, 53). Thread-register memory exists in the language, but the thesis explicitly limits transformation support: “We note that while thread registers are supported in the language, we have not yet implemented the conversion transformations for them.” (Section 5.3, p. 53, footnote 4.)

CUDA generation extracts kernels, replaces thread loops with their bodies and computed CUDA indices, lowers memory operations, and replaces `DMINDEX` with zero. Tagged sequences of barriers collapse into one CUDA barrier. Current shared-memory generation uses static declarations; dynamic shared-memory generation is future work (Chapter 6, pp. 55–58). The code-generation pass is itself a transformation, but “it is not verified, as OptiGPU cannot typecheck CUDA itself.” (p. 55.) Inference: checking the intermediate program leaves CUDA lowering and printing as a trust assumption.

## evidence and limits
The evaluation uses two case studies, matrix transpose and parallel reduction, with reference kernels from Nvidia's `cuda-samples`, commit `4f73561`. Section 7.1 (pp. 59–60) reports an RTX 5060, CUDA 13.0, nvcc 13.0.88, and compilation with `-O3`. Performance is effective bandwidth, `(input bytes + output bytes) / kernel runtime`: “We averaged out the runtimes of kernels over 1000 runs.” The measurement excludes host allocation and copies: “Although OptiGPU generates host and device code, the host-side CUDA operations like cudaMalloc and cudaMemcpy would dominate the runtime and create too much noise, so we only use the runtime of the device portion.” (p. 60.) The transpose input is 4096×4096; reduction uses a 16M-element array and 256 threads per block.

Table 7.4 (p. 60) reports transpose bandwidth of 297.7 GB/s for OptiGPU versus 340.6 GB/s for the reference. Reduction reaches 297.9 GB/s versus 349.4 GB/s for the targeted `reduce3` reference and 376.8 GB/s for `reduce6`, the best-performing reference on that system. The caption defines the last comparison: ““Optimal” in the case of reduction represents the best performing kernel from cuda-samples (reduce6), while “Reference” is the kernel we tried to recreate in OptiGPU (reduce3).” The author attributes the transpose gap to unoptimized indexing, based on manual edits. For reduction, the script sums adjacent elements instead of the reference's grid-stride pair, and lacks an explicit register accumulator; manual edits identify the accumulator as the cause of the approximately 50 GB/s reference gap (Section 7.2, pp. 60–61).

Table 7.5 (p. 62) counts lines excluding whitespace and comments. Transpose inputs contain 9 C-code lines, 9 annotation lines, and 57 script lines; its transformed intermediate output has 89 C-code and 359 annotation lines, and generated CUDA has 37 lines, including 26 kernel lines. Reduction inputs contain 8+24 C-code and 14+71 annotation lines, plus 143 script lines; its intermediate output has 93 C-code and 180 annotation lines, and CUDA has 54 lines, including 37 kernel lines. The two reduction input counts distinguish the initial program from a separately verified tree-reduction routine that is inserted and inlined. The comparison is internal: “Our primary reference point for this goal is Kuiper [15], but as both Kuiper and OptiGPU are work-in-progress prototypes, we do not attempt to directly compare the proof burden required in each tool.” (Section 7.3, p. 62.) Inference: these line counts suggest automation potential, but two examples and output annotation counts do not establish general reductions in human proof effort.

The thesis limits its feature coverage: “It supports the most essential features of CUDA, but we have not yet added support for atomics, tensor cores, asynchronous instructions, or other modern CUDA features.” (Chapter 1, p. 6.) Its case studies cover array/tensor-like programs; graph algorithms, formal GPU semantics, a soundness proof, dynamic shared-memory generation, and thread-register conversion remain outside the demonstrated implementation. Inference: the relevant idea for VeruLaw is preserving proofs while refining a simple program; application to verified CUDA additionally requires justified GPU axioms and code generation.

## techniques for the catalog
- proof-preserving rewriting — update a verified AST together with its contracts and resources, checking completed GPU conversion phases
- GPU transition contracts — track launch, setup, teardown, thread execution, and shared-memory allowances as explicit resources
- thread-for conversion — use desynchronized resource groups and collective barriers to control resource reassignment between threads
- memory refinement — convert generic memory operations and permissions to GPU memories; thread-register conversion is not yet implemented
- CUDA lowering — generate host/device code from the checked intermediate program through an unverified code-generation pass
