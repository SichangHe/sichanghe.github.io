# Bootstrapping LCF Declarative Proofs
(authored by agents unless marked 🧑)
Tag: `scott2017bootstrapping`, [paper](http://arxiv.org/abs/1703.05351v1)

## scope
The paper is a short (14 pages including references) account of building declarative proof automation in ProofPeer from an LCF kernel. ProofScript conversions turn a user's conjecture into CNF, a built-in `callmetis` sends the problem to the METIS resolution prover, and the returned certificate is translated back into the kernel's terms. The abstract frames the premise: “Suppose we have been sold on the idea that formalised proofs in an LCF system should resemble their written counterparts, and so consist of formulas that only provide signposts for a fully verified proof.” (Abstract, p. 1). The paper describes the CNF side in detail (Sec. 4) but only the data representation of the certificate side (Sec. 5); it does not give the per-node replay code.

## technique: external prover behind a small kernel
LCF systems are “based on small kernels of inference/typing rules”, and all theorems are ultimately proven by applying them (Introduction, p. 1). ProofPeer adds a built-in `callmetis` that exchanges ProofScript data with a wrapper around METIS. METIS is a generic resolution prover for first-order logic with equality, based on a small LCF-style kernel with full proof recording; ProofPeer ports it to Scala so it can run on the JVM and JavaScript (Sec. 3, p. 2). The authors caution that functions that get data from third parties may break ProofScript's functional purity, and say that their METIS port is deterministic and `callmetis` returns the same output for the same input (Sec. 3, pp. 2–3).

Inference: the architecture below is my summary of the paper's design, not a procedure the paper states: (1) keep the trusted kernel small; (2) expose a declarative script language for assumptions and intermediate formulas; (3) send a normalized problem plus selected lemmas (the `by metis [...]` list) to an external prover; (4) receive a proof certificate; (5) translate every certificate node into kernel inference steps; (6) accept only a theorem the kernel produced. Inference: this is relevant to VL's use of an external synthesis model: generated Rust/proof candidates must be checked by Verus, while the generator is not trusted.

## technique: conversions and conversionals
The paper says: “Conversions are operated upon using higher-order functions called conversionals, which allow us to build conversion strategies out of existing conversions, targeting individual parts of a term and responding to failure by trying alternative strategies.” (Sec. 4.2, p. 4). Historically a conversion takes a term `t` and produces an equational theorem `t = t'` or throws an exception; ProofScript has no exceptions, so conversions signal failure through return values (`nil`). `orElseConv` tries a second conversion if the first fails; `thenConv` sequences conversions via a derived rule for transitivity of equality; `combConv` uses the kernel destructor `destcomb` and the rule `combine`; `absConv` descends under an abstraction using the kernel `destabs` and `abstract` rules (Secs. 4.2.1–4.2.2, pp. 4–5). The paper reports: “Most of the 1500 lines of ProofScript library code which integrates ProofScript with METIS does so by way of conversions. We define about 50 conversions and conversionals which are used around 500 times.” (Sec. 4.2, p. 4).

`rewrConv1` takes a quantified equational theorem, strips the quantifiers with `destabs` into a context with fresh constants, runs a matching algorithm primed with those constants to get an association list `[(x1,t1),...,(xn,tn)]`, specializes the original theorem's quantifiers with the `ti`, and applies the equational form of Modus Ponens; if no substitution is found it returns `nil` (Sec. 4.2.3, pp. 5–6). The paper calls the matching algorithm “quite rudimentary, but sufficient for our purposes” (footnote 1, p. 5). `convRule` applies a conversion to a theorem's term and uses equational Modus Ponens to prove the converted theorem; a conversion from `φ` to `⊤` proves `⊢ φ` (Sec. 4.2.4, p. 6).

Verus form. Inference: conversions would correspond to proof lemmas that rewrite a `spec fn` expression and return an `ensures` equality; conversional traversal would be ordinary ghost recursion over syntax. Verus likely lacks ProofScript's higher-order conversional combinators, so a Rust implementation would probably need explicit enums, recursive `proof fn`s, and `assert`/`assert_by` checks.

## technique: verified CNF pipeline
The authors conclude: “With conversions, the ProofScript code which performs the CNF conversion is structurally very similar to the pseudocode algorithms which do the same, but with the benefit that any result is formally verified for correctness.” (Sec. 4.5, p. 9). The paper's full CNF conversion has five passes (Sec. 4.3, pp. 6–7): convert to first-order (eliminate set builder notation; lift abstractions into arguments of β redexes; lift terms of type P used as first-order function or predicate arguments); negation normal form (eliminate connectives other than ∧, ∨, ¬; push negations to the leaves and remove double negations); prenex form (pull quantifiers to the front); CNF of the propositional matrix; and elimination of quantifiers by skolemisation. The paper says the user's conjecture and the CNF refutation problem are shown logically equivalent “by successive term rewriting” (Sec. 4, p. 3) with conversions.

Skolemisation repeatedly rewrites with the theorem `⊢ ∀p. (∀x. ∃y. p x y) = (∃f. ∀x. p x (f x))` (Sec. 4.5, p. 8). Because ProofScript's metalogic is monomorphic, “an arbitrary number of variants of (1) may be needed” (p. 8), so the authors define a parameterized `skolemThm[a,b]` and use the `table` keyword to memoise calls and avoid reproving identical instances (Sec. 4.5, p. 9). The tautology checker (Sec. 4.4, p. 7) is truth-table evaluation: it collects rewrite theorems for connectives on `⊤` and `⊥`, case-splits each variable with `⊢ p = ⊤ ∨ p = ⊥`, and uses a derived conversional `upConv` to descend to the leaves and work upward, hoping to reach `⊤`. It is used for propositional theorems of a few variables (“at most three at a time suits our purposes”) and is integrated into declarative proofs with the keyword `by`, as in `theorem andDeMorgan : ∀p q. (¬(p ∧ q)) = (¬p ∨ ¬q) by taut`. The case split requires that the law of excluded middle has first been proven, which the paper does with Diaconescu's proof modified for Hilbert's indefinite description operator (p. 7).

Verus form. Inference: represent formulas as a ghost algebraic datatype and prove each normalization pass with recursive lemmas preserving semantic equivalence. Skolem functions become ghost witnesses with explicit `requires` existence facts. Memoisation would be an optimization for proof generation, not a trust boundary; Verus would still check each instantiated lemma.

## technique: certificate reconstruction and variable maps
METIS certificates are returned to ProofScript as a tree rooted at the empty clause, with nodes labelled by the clause derived and the rule used: Axiom, Assume, Refl, Equality (leaves); RemoveSym, Irreflexive, Subst, Resolve (Sec. 5.1, pp. 9–10). METIS treats clauses as sets of literals; ProofPeer keeps clauses normalised with respect to associativity and idempotency of disjunction, so they are lists of literals with unique elements. Duplicate-removal passes are needed only to implement Subst and Resolve and are done by the conversion `nubClauseConv` (Sec. 5.1, p. 10). Certificates are nested lists with literals in an S-expression-like encoding (p. 10).

METIS variables are identified across clauses even as they are substituted independently; ProofScript identifies bound variables only up to α-equivalence, and the authors cannot reliably control the naming of fresh ones (Sec. 5.1.1, pp. 10–11). Direct use of de Bruijn indices would be “disastrous” given hundreds of fresh variables, so each clause is a pair: a list of METIS variables (plain integers) and a quantified ProofScript theorem, `([v1,...,vn], ⊢ ∀x1...xn. φ1 ∨ ... ∨ φm)`, where the i-th bound variable corresponds to `vi` (p. 11). The METIS clause `{p(3, 8), ¬q(2, 5)}` can be represented by several such pairs, for example `([3, 2, 8, 5], ⊢ ∀x y z w. p x z ∨ ¬q y w)`. For a substitution the authors must work out how many bound variables are needed afterward, generate fresh constants, and recreate the index-to-variable mapping; after resolution a METIS variable that has disappeared is deleted from the mapping (p. 11). The paper calls this “a lot of delicate work” not expected of the average user (p. 12). User-facing examples invoke `by metis [empty, oneDef, power, subset, ext]` to prove set-theoretic theorems (p. 12).

Verus form. Inference: a certificate tree could be an enum consumed by a recursive `proof fn`; each node's theorem would have an `ensures` equal to the clause derived from its children. Variable maps would be ghost vectors with uniqueness invariants. Inference: the external METIS implementation would only need to be trusted for availability; logical soundness would rest on the reconstructed Verus proofs.

## evidence, limits, and threat
Evidence is a working ProofPeer integration and a few illustrative theorems (`one`, `two`, `oneNotZero`, p. 12); the paper reports no benchmark, runtime table, or success rate. The paper's stated reliance is on the kernel's rules, with `callmetis` required to be deterministic (Sec. 3, pp. 2–3). Inference: the certificate-translation code and the CNF conversions sit between the kernel and the user, but any error in them can only make a proof fail, not be accepted wrongly, because the kernel produces the final theorem. Inference: threat to agent-written verified Rust is low to medium if VL follows this kernel-replay architecture, because an untrusted generator can suggest proof scripts while Verus checks the final obligations. Limitations stated or evident in the paper: only first-order METIS is used; ProofScript's monomorphic metalogic forces type-specific Skolem-theorem instances (Sec. 4.5); the variable-map bridge is delicate (Sec. 5.1.1); the conclusion says future work will add more ATPs to advise METIS (Sec. 6, p. 13).

## techniques for the catalog
- LCF kernel replay — keep a small trusted inference kernel and reconstruct all automation results inside it
- conversional rewriting — compose higher-order term conversions with sequencing, fallback, subterm, and abstraction traversal
- verified CNF normalization — prove first-order, NNF, prenex, CNF, and Skolem transformations by equational conversions
- truth-table tautology checking — split Boolean variables and rewrite valuations upward to prove small propositional lemmas
- certificate reconstruction — translate METIS resolution trees while maintaining explicit maps from bound to free variables
