# Gillian: Compositional Symbolic Execution for All
(authored by agents unless marked 🧑)
Tag: `santos2020gillian`, [paper](http://arxiv.org/abs/2001.05059v1)

## scope and trust boundary

Gillian is a language-independent framework whose reusable unit is a compiler from a source language to GIL plus a memory model. The paper states: “We present Gillian, a language-independent framework for the development of compositional symbolic analysis tools.” (abstract, p. 1). It supports whole-program symbolic testing, full verification, and bi-abduction (abstract, p. 1). The meta-theory is proved once for an abstract state model; each language instantiation must prove memory-specific lemmas. “Hence, the soundness theorems of whole-program symbolic execution, veriﬁcation, and bi-abduction are proven in general once and for all, and can be instantiated to each target language provided that the user proves the necessary memory-speciﬁc lemmas.” (Introduction, p. 2)

Inference: In Verus, the analogous trust boundary is a verified Rust program plus a Verus specification and solver. A reusable state-model library could carry generic lemmas, but each Rust heap representation and unsafe boundary still needs its own proof obligations. Gillian's compiler and memory model are trusted as implemented unless separately certified.

## technique 1: parameterize symbolic execution by actions

what it is and when to use it. GIL is a small goto IR whose commands are parameterized by actions supplied by a memory model. The paper's motivation is that users supply a compiler to GIL and a memory model with actions, instead of writing each analysis from scratch (Introduction, p. 1-2). Inference: use this when several source languages have different heaps, pointers, objects, or allocation rules but should share one symbolic interpreter and soundness proof.

how to apply it (paper method). First define a state model as states, values, and actions. The paper's definition is: “A state model S ∈ S is a triple h|S |, V , Ai, consisting of: (1) a set of states on which GIL programs operate, |S | ∋ S, (2) a set of values stored in those states, V ∋ v, and (3) a set of actions that can be performed on those states, A ∋ α.” (Definition 2.1, p. 3). Next provide `setVar`, `setStore`, `getStore`, expression evaluation, and nondeterministic action execution. Compile each source command to GIL assignments, branches, calls, and action commands. A "proper" state model also defines `assume`, `symb`, and `fresh` actions (p. 3); Gillian's built-in allocators generate fresh symbols (Section 2.1.1) and its lifting adds these three actions to a user memory (Definitions 2.5 and 2.6, p. 7), so the user supplies only the memory actions. Instantiate a concrete memory model and a symbolic memory model (Definitions 2.3 and 2.4, p. 6; the While example is in Section 2.4). Then define an interpretation function from symbolic memories to concrete memories (Definition 3.4, p. 12) and prove that it preserves the memory actions (Equation 1, p. 12; Lemma 3.7 for While, p. 14). Theorem 3.6 then makes the lifted relation a soundness relation for the states, and Theorem 3.2 gives soundness of the GIL semantics.

Verus form. Inference: represent the concrete heap abstraction as a Rust datatype with `spec fn` observers and executable transition functions; represent symbolic state as a ghost datatype. Use `requires`/`ensures` on transition functions and `proof fn` lemmas for the interpretation relation. GIL's nondeterministic action relation has no direct executable Verus equivalent; model it as a ghost relation or a set of possible post-states. Rust ownership changes the representation of heap resources, while the action interface and interpretation proof pattern carry over.

what evidence shows it works. The authors instantiate Gillian to JavaScript and C data-structure libraries. Table 1 reports whole-program symbolic testing times for six structures in each language: JavaScript tests use 3–6 tests and 28,389–137,379 GIL commands, taking 0.21–1.36 s; C uses 1–5 tests and 1,008–15,256 commands, taking 0.11–0.33 s (Table 1, p. 23). The tests were written "with the goal of achieving full line coverage for each of the data structures" (Section 6.3, p. 23). These are per-library measurements, not success percentages.

limits and assumptions. Soundness depends on the user proving the memory-specific lemmas (Introduction, p. 2). The paper gives no meta-theoretical guarantees for GIL programs that use the external procedure call (Section 2.1, p. 4). Gillian-C assumes that the size of dynamically allocated memory is known (Section 6.2, p. 23). Trust in Gillian-JS rests on the JS-2-JSIL compiler and the JSIL-to-GIL compiler, the latter checked by replaying 8797 Test262 concrete tests (Section 6.1, p. 22); for Gillian-C, C-to-C#m is verified in Coq as part of CompCert, while the C#m-to-GIL compiler is the authors' own (Section 6.2, p. 23). Solver cost dominates some cases: “the core of the obtained time does not lie with the number of executed commands, but rather with the time spent in the ﬁrst-order solver” (Section 6.3, p. 23). Inference: a Verus port inherits SMT sensitivity and must state what unsafe code, compiler, and solver are trusted.

## technique 2: separation-logic predicates to merge paths and verify procedures

what it is and when to use it. The guarantee of naive symbolic execution covers only concrete executions that follow the same path as the given symbolic execution (Section 4.1, p. 14). Gillian adds core predicates, user predicates, separating conjunction, fold/unfold, and specification calls; since logical commands provide a way to merge symbolic traces, Theorem 4.6 "is applicable to programs which branch and loop" (Section 4.3, p. 18). The paper explains: “To account for branching, we need a mechanism for merging symbolic execution traces.” (Section 4.1, p. 15).

steps. Define core predicates with getter and setter actions that are inverses. The required law is printed as “This well-formedness constraint captures the intuition behind getters and setters and states that they have to be, essentially, each other’s inverses.” (Equation 2 discussion, p. 16). Define user predicates `pred pn(x) :− P0 ; ... ; Pn` whose alternatives are assertions built from `emp`, boolean expressions, core predicates, other predicates, and separating conjunction (Section 4.2, p. 15). For JavaScript the authors write the predicates by hand; for C they generate recursive predicates from type information and extend them with information about the values (Section 6.3, p. 23). Annotate each function with `{P} f(x) {Q,e}` (Section 4.3, p. 18). During verification, a `fold` command removes the footprint of one predicate definition with its getter and adds the folded predicate with `setP`; a spec call uses the getter of the precondition to remove its footprint and the setter of the postcondition to produce its footprint, without executing the body (Section 4.3, p. 18). The paper's operational rule says: “The rule folds the predicate denoted by pn(e). First, it obtains the j-th deﬁnition of the predicate to be folded, P j , and uses its getter, getP j , to remove the corresponding footprint from the current state; then, it uses the action setP to extend the current state with the folded predicate.” (Section 4.3, p. 18). The user proves that the core getter/setter interpretation is well formed (Lemma 4.7 does this for While, p. 19), and the generic verification theorem (Theorem 4.6, p. 18) then applies. The bindings of logical variables in `fold` and spec calls are found by a search algorithm in the implementation, which the paper does not describe (p. 18).

Verus form. Inference: encode ownership predicates as ghost `struct` facts or `spec fn` predicates over a model heap; use `proof fn` lemmas to split and recombine resources. Verus has no separation-logic `fold` command, so folding is expressed by strengthening or weakening ghost facts and calling lemmas. Function contracts use `requires` and `ensures`; a specification call corresponds to proving the callee contract and letting Verus avoid body expansion. Rust borrow checking supplies additional alias guarantees; predicate facts still describe recursive shape and values.

Evidence and limits. Table 2 verifies 2–6 functions per library with 2–9 specifications, taking 0.17–5.57 s per library; Gillian-C's binary-search tree is the slowest at 5.57 s because of complex Z3 entailments (Table 2, p. 24). The paper's verification theorem requires a well-formed core predicate interpretation (Section 4.2, p. 16). The paper also notes that, compared to whole-program symbolic testing, the number of executed commands is "dramatically lower" but the times are longer; the authors attribute this to whole-program symbolic testing not using procedure summaries during execution and to verification involving considerable predicate manipulation (Section 6.3, p. 24). Inference: predicates can encode a wrong ownership abstraction unless their getter/setter laws are proved against the actual Rust representation.

## technique 3: bi-abduction for missing resources

what it is and when to use it. Bi-abduction infers missing heap resources when no specifications or (unit) tests are given (Section 5, p. 19). The paper changes the signature of action execution so that an action whose resource is missing returns a fix assertion; the instrumented state applies the fix and continues, while recording all fixes so that specifications can be generated up to a bound (Sections 5 and 5.1, pp. 19-20).

steps. Change the action result type to either success or a set of assertion fixes. Require every fix to satisfy the paper's soundness condition: “if we extend the original state with the generated ﬁx, it must be possible to execute the action successfully.” (Section 5.1, p. 19). The paper leaves proving this to the user (footnote 6, p. 19), and only fixes that mention logical variables already in the initial state are admissible (p. 20). Couple the state with an accumulated assertion `P` (Definition 5.1, p. 20). When an action fails with a fix `Q`, extend the state with the footprint of `Q`, execute the action, and keep `P * Q` (Definition 5.1). Theorem 5.2 relates a successful bi-abductive execution to a normal execution from the initial state extended with the accumulated `P`. The paper says that the fixes are used to generate procedure specifications and bug traces, but this paper's body does not detail that generation step. For While, `lookup` and `getCell` can fail and be fixed (the fix adds the missing cell with a fresh logical variable); `mutate` always succeeds; `setCell` and `dispose` may fail but this cannot be corrected (Section 5.2, p. 20-21).

Verus form. Inference: use a ghost precondition synthesizer that proposes missing ownership facts, then prove the final Rust contract from those facts. Verus cannot execute a failed proof action and mutate a runtime state; this is a meta-level inference pass generating `requires` clauses. The resulting contract is checked by ordinary Verus proofs. Fixes that mention fresh logical variables need explicit ghost identities and framing lemmas.

Evidence and limits. Table 3 reports inferred success/bug (and JavaScript error) specifications and times. For Gillian-JS, BST yields 26/0/5 specs in 3.98 s; for Gillian-C, BST yields 37/8 in 0.37 s (S/E/B for JS, S/B for C; Table 3, p. 24). The specifications describe behaviour "up to a given bound" (Section 6.3, p. 24), so the counts are not exhaustive correctness. For C, bug specs were obtained by introducing errors into the code; for JavaScript, a bug spec means a native error such as a TypeError (Section 6.3, p. 24). The authors say that Gillian-JS bi-abduction times "are still quite long" because they have not solved the bi-abduction issues of JaVerT 2.0 related to the internal branching of the JavaScript semantics (Section 6.3, p. 24). The authors warn that inferred specifications “could contain false positive bug reports that need to be treated afterwards either automatically or by the developer.” (Section 6.3, p. 24). Inference: agent-written verified Rust should treat inferred contracts as candidates requiring human review, especially around unsafe pointers.

## techniques for the catalog

- action-parameterized symbolic execution — compile languages to GIL and instantiate a state/memory action model, reusing generic soundness proofs
- predicate-based path merging — use getter/setter core predicates, separating conjunction, fold/unfold, and contracts to merge branches and verify recursively
- bi-abductive resource inference — turn failed actions into assertion fixes (proved correct by the user), continue execution, and generate procedure specifications up to a bound
