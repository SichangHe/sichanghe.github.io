# Lancet: A Formalization Framework for Crash and Exploit Pathology
(authored by agents unless marked 🧑)
Tag: `dai2025lancet`, [paper](https://www.usenix.org/conference/usenixsecurity25/presentation/dai)

## framework and semantics
Lancet formalizes memory-corruption causes and exploit primitives with three ownership relations: cell owner and value owner (per memory cell) and pointee owner (per register or memory cell, naming the subject a pointer was created to point to). The introduction states the purpose: “To bridge this gap, we propose a formalization framework, Lancet, to formally define common memory corruption vulnerabilities, which account for over 70% of vulnerability fixes [38].” (§1, p. 375). Its machine, LancetISA, is a deliberately minimal register-register instruction set (§3.2, p. 378); a program is an instruction sequence over registers, memory, a heap-size map, a stack-subject map, and the three ownership maps. “Operational semantics of a language specify unambiguously how to execute a program written in that language.” (§3.3, p. 378). The paper gives a big-step semantics over a concrete state, and updates ownership on allocation, deallocation, loads, stores, pointer copies, and arithmetic. Register, memory, heap-object and stack-object tracking is precise; ownership tracking (cell, value, pointee owners) is “over-approximate with respect to ownership information” (§3.3, p. 380).

Use this technique when a crash or exploit must be explained at the level of the exact memory cell and pointer relation. Steps (§3.3–3.4, pp. 378–382; §5, p. 383): (1) transpile x86 instructions to LancetISA; mov, string and SIMD moves map to mov, store and load, bitwise and arithmetic instructions map directly, and LEA becomes a combination of bin and mov; (2) initialize ownership of globals, GOT and PLT from symbol tables, segment information and the proc file, and of stack frames by tracing stack-adjustment instructions such as sub rsp, 18h; heap ownership is created by the malloc rule; (3) execute each instruction of a concrete instruction trace with the big-step rules; (4) apply the vulnerability predicates (the function Vulns) to the state around each instruction; (5) report the instruction at which a predicate holds, with the subject identifiers involved. The paper's implementation summarizes memcpy and memmove effects and bypasses their internal instructions to enhance performance (§5, p. 383).

The key formalization insight is that violations are predicates over the semantic state. For example, CROSS_BOUNDARY fires on a binary (arithmetic) instruction when the destination register's pointee owner equals the cell owner of the original address but differs from the cell owner of the arithmetic result, so the violation is reported before the out-of-bound access itself (OOBW, on store); EXPIRED_WRITE fires on a store when the pointee owner of the base register differs from the cell owner of the written cell; stack-after-scope and dangling-pointer rules use the same ownership maps (§3.4, pp. 381–382). The paper states the guarantee direction explicitly: “The vulnerability detection rules rely on the over-approximate ownership information, meaning false-positives detections may occur. They are also non-exhaustive, meaning absence of detected vulnerabilities does not imply total memory safety.” (§3.4, p. 382). It adds that, for covered vulnerability types in a sequential execution, a vulnerability that occurs will be reported (no false negatives for those rules).

Inference: Verus can encode a compact executable state (`Seq`/maps for registers, cells, and owners), pure specification functions for each instruction transition, and proof lemmas that an interpreter preserves map well-formedness. `requires` establishes initialized ownership; `ensures` states that a reported CROSS_BOUNDARY witness satisfies the predicate over the ownership maps; because the paper's rules are over-approximate, a proof that the witness is a true out-of-allocation access would need a stronger, separate model of allocations. A `while` loop invariant can preserve “at most one cell owner and one value owner” for non-overlap executions. This is an inference because the paper uses its own operational semantics, not Verus. Verus proofs would still trust the x86-to-Lancet transpiler, symbol extraction, and any summarized library handler unless those are modeled and verified.

## downstream technique: fast crash triaging (FCS)
FCS consumes a dynamic instruction trace, runs Lancet semantics, and returns the violated rule plus annotated context for an LLM patching agent (§4.1, p. 382; §5, p. 383). The paper states, “FCS, which triages crashes to deduplicate reported errors and extract essential crashing context that can be embedded into LLM prompts” (§4.1, p. 382). It identifies the key variables behind a satisfied rule, retrieves their cell, value and pointee owners, annotates the relevant instructions and maps them to source statements, with the focus depending on error type (§4.1, p. 382). The paper does not describe the deduplication algorithm. It also says: “FCS is not designed as a sophisticated root cause diagnosis tool, but rather as an improvement over sanitizers.” (§4.1, p. 382). In the AIxCC deployment, Pin collected instruction traces because Intel PT was unavailable, instrumenting up to 100,000 instructions before the corruption site (§5, p. 383). The patching agent used GPT 4.0 in an interaction mode with “security expert”, “user” and “tool” roles, and the FCS report is embedded in the “user” prompt (§5, p. 383).

Inference: a verified Rust FCS would prove deterministic trace replay, deduplication-key stability, and that every emitted diagnosis corresponds to a violated predicate. It cannot prove that a finite trace contains the true root cause, that Pin records all relevant instructions, or that an LLM-generated patch is correct without a separate patch specification.

## downstream technique: exploit primitive fingerprinting (EPF)
EPF extends the same semantics with predicates for primitive transitions, such as invalid free, dangling-pointer use, and ownership overlap. Analysts feed an exploit trace and read the ordered transitions rather than only the initial crash. For House of Spirit, the paper says: “This technique can be identified by checking whether the domain of the free argument is stack or not.” (§4.2, p. 382). Primitive definitions are in Figures 5 and 10 (InvalidFree: H undefined or more than one cell owner; MemOverlap: a malloc'd cell whose cell owner is not only the allocator). The paper demonstrates, in §6.2, p. 386 (Figure 7), an off-by-one NULL overflow transitioning to overlap, invalid free and use-after-free in House of Einherjar, by tracking cell-owner sets. Inference: the method is to execute the trace, record each newly satisfied primitive predicate, and report the sequence; the paper shows this through case studies rather than stating it as an algorithm.

Inference: in Verus, define a ghost sequence of primitive labels and prove each append corresponds to a semantic rule becoming true. The allocator is a major assumption: the paper notes, “Note that, the current EPF treats the allocator as a black box.” (§6.2, p. 386; also §7, p. 388), so allocator-dependent exploit steps are outside the proof boundary.

## evidence, trust, and limits
The evaluation has 116 test cases (§1, p. 375). Table 1 lists 18 crash rows and Table 2 lists six exploits; the paper also uses 67 Juliet memory-corruption tests and 25 non-memory-corruption tests (§6.2, p. 384), and 18 + 6 + 67 + 25 = 116 (Inference: this arithmetic is mine). The text of §6.2 says “all 14 crashes listed in Table 1”, which does not match the 18 rows in Table 1, so the 14-crash figures below carry that unresolved discrepancy. FCS and EPF together completed 20 cases within 25 seconds; the longest was 201 seconds for 195 million instructions (§6.1, p. 383). On the 14 crashes, ASan missed one and gave incorrect vulnerability types for four, while FCS identified all and, in the paper's words, reported “between 7 and 441, 687 instructions ahead of ASan in 9 cases” (§6.2, p. 384). The largest advance, 441,687 instructions, is Table 1's Vim CVE-2024-43374 row (printed “∆441, 687”; the text extraction splits the thousands separator). On 67 Juliet memory-corruption cases, ASan produced 50 correct, 11 inaccurate, and six missed; FCS produced 65 correct, one inaccurate, and one missed (§6.2, p. 384). On the 25 non-memory-corruption Juliet cases, ASan produced 12 correct, 1 inaccurate and 12 missed, while FCS produced 3 correct, 1 inaccurate and 21 missed (§6.2, p. 384): FCS is weaker there. EPF succeeded on all six exploit cases; ASan (tuned to continue after errors) missed one and only reported the initial corruption in the other five (§6.2, p. 385). For LLM patching, only two cases (CVE-2024-41965, Nginx CPV15) were studied in depth, and the paper cautions: “we cannot conclude that this advantage will directly translate into FCS outperforming ASan in facilitating vulnerability patching, though our observations over a limited dataset suggest this.” (§6.3, p. 386). On CPV15 the FCS-guided GPT 4.0 patch failed to compile because it used a fabricated macro, MAX_BASE64_INPUT (§6.3, p. 387). These denominators and settings are the paper's stated test sets, not universal rates.

## techniques for the catalog
- ownership operational semantics: model cells, values, and pointees and update ownership through a small instruction machine
- vulnerability predicates: define CROSS_BOUNDARY, EXPIRED_WRITE, and related rules as state predicates with witnesses
- FCS crash triage: replay bounded traces, deduplicate crashes, and emit semantic root-cause context
- EPF primitive fingerprinting: record the ordered ownership violations that form an exploit's primitive transition
