# Cooperative Verification via Collective Invariant Generation
(authored by agents unless marked 🧑)
Tag: `haltermann2020cooperative`, [paper](http://arxiv.org/abs/2008.04551v1)

## purpose

CoVerCIG lets a master verifier outsource loop-invariant generation to independent helper tools and inject the results back into the master's analysis. The abstract states: “Our framework named CoVerCIG allows a master verification tool to delegate the task of invariant generation to one or several specialized helper invariant generators.” (Abstract, PDF p. 1.) The goal is black-box reuse: helpers run unchanged, while mappers and adapters translate tasks and results.

The paper works with GNU C control-flow automata (CFAs), integer states, and safety properties encoded as an error label. A correctness witness is the exchange format. A helper such as SeaHorn that returns only a Boolean answer needs an adapter that turns its LLVM-level invariants into a witness; UltimateAutomizer already produces witnesses, but the authors still added an adapter "due to currently existing technical incompatibilities" (Section 4.2, PDF p. 7). VeriAbs needs neither mapper nor adapter. In the evaluation no helper needed a mapper (Table 2, PDF p. 6). The master runs alone first, requests help after a configurable timer, and either restarts or continues after invariants are injected.

## technique 1: master-helper architecture and witness injection

when to use it

Use this when a verifier is incomplete on loops but specialized invariant generators can analyze the same program. The paper's helpers help only on tasks whose safety property holds: invariants can help prove a property but cannot refute one (Section 5.3, PDF p. 8).

steps

1. Choose a master analysis, such as k-induction or predicate abstraction, and extend it with an internal function `injectWitness` that loads a witness, extracts its invariants and injects them into the analysis (Section 3.1, PDF p. 4; Section 4.1, PDF p. 5).
2. For helpers that need a different property encoding (for example `assert(n==y)` instead of an error label), implement a mapper doing simple syntactic replacement (Section 3.1, PDF p. 4).
3. Run the master alone for a configurable `timerM`; when it sets `requestsForHelp` (or solves the task, in which case its answer is returned), start all helpers in parallel, each with timeout `timeoutH` (Algorithm 1, PDF p. 5). The default experiment uses 50 seconds for the master and a 300-second helper timeout (Section 5.2, PDF p. 7).
4. Convert helper invariants to standardized correctness witnesses. If a helper emits LLVM-level invariants, translate IR variables to C variables, map basic blocks back to C locations, and build a witness from the CFA (Figure 4, PDF p. 4; Example 4.1, PDF p. 6).
5. Discard trivial invariants (Algorithm 1, line 8). Inject the remaining witnesses into the master, restarting it first if `restartMaster` is set. For k-induction, the paper describes proving a witness correct before adding its invariants to the maintained set; for predicate abstraction, it describes extracting predicates from the invariants, splitting conjunctions into individual clauses, and inserting them into the available predicates (Section 4.1, PDF p. 5).
6. With `termAfterFirstInv` set, stop the other helpers as soon as one returns a non-trivial witness; otherwise wait until every helper has finished or timed out (Section 3.2, PDF p. 4-5). The defaults in the evaluation set both `termAfterFirstInv` and `restartMaster` to true (Section 5.2, PDF p. 7).

The framework is explicitly decoupled: “The helpers run in parallel as black boxes without cooperation.” (Section 1, PDF p. 1.) Inference: a Verus service could treat independent lemma generators as helpers, serialize candidate `invariant` clauses, and have Verus validate them before adding them to a proof. Verus's verifier is the master; the paper's C witness format and adapters do not carry over directly.

## technique 2: translating helper invariants

SeaHorn illustrates the hard case. It solves constrained Horn clauses over LLVM IR with the solver Spacer and returns only a Boolean answer, not a witness (Section 4.2, PDF p. 6). The authors obtain its invariants and basic blocks with the launch parameter `--show-invars` and use LLVM-IR with debug information (`-g`). In Example 4.1 (PDF p. 6) the debug comments give the IR-to-C variable mapping; the authors note that “a more sophisticated procedure is needed since LLVM-IR uses a three address code” in general, where intermediate variables must be resolved to C expressions. The adapter analyzes the IR program structure (using basic functions from PHASAR) to identify the loop block, maps the invariant to the loop head, builds the CFA of the C program, stores the invariant at its node and converts that to a witness. The example invariant is `v1 − v4 − v3 = 0`, corresponding to `n − x − y = 0`.

The paper's validity argument is brief: it says the implementation relies on the correctness of masters, helpers and adapters, and that an incorrectly translated invariant “may however influence the performance only negatively” (Section 5.4, PDF p. 10). The paper does not state why; Inference: the reason is that the master checks witnesses before use (the paper describes this for k-induction), so VL should retain generated Verus lemmas as untrusted suggestions until the compiler checks them; a translation bug must be unable to bypass Verus's proof obligations. A Rust mapping would preserve source spans or stable symbolic names rather than rely on LLVM debug metadata.

## technique 3: combining complementary generators

The helpers use different algorithms: SeaHorn uses constrained Horn clauses and Spacer; UltimateAutomizer uses predicate abstraction, automata, and path-based refinement; VeriAbs is a portfolio of four verification techniques, each made of sequentially composed components, selected by analyzing the loop structure and variable intervals. The four are random fuzz testing, array abstraction followed by BMC, explicit-state model checking followed by standalone invariant generation, and a fixed sequence of different verification approaches (Section 4.2, PDF pp. 6-7). Run helpers in parallel when their strengths cover different loops, but account for shared CPU and timeout costs.

The study evaluates 342 SV-COMP 2020 tasks: all ReachSafety-Loops tasks plus 55 randomly selected tasks from ProductLines, Recursive, Sequentialized, ECA, Floats, and Heap (Section 5.2, PDF p. 7). Runs use three virtual machines, each with an eight-core Intel Xeon E5-2695 v4 and 16 GB memory, and give each task 15 minutes CPU time on eight cores and 15 GB memory (same section). With k-induction as master, standalone solves 146 tasks correctly; with one helper the totals are 148 (SeaHorn), 158 (UltimateAutomizer), and 163 (VeriAbs). Predicate abstraction rises from 116 to 122, 132, and 125 respectively (Table 3, PDF p. 8). All additional solved tasks were true results; there were no additional false results, and one (SH, UA) or two (VA) tasks were no longer solved correctly because of CPU sharing (Section 5.3, PDF p. 8). The authors state “the total number of correctly solved tasks increases using CoVerCIG by 12% for k-induction and 14% for predicate abstraction used as master” (Section 5.3, PDF p. 8). Inference: these match the best single helper, with denominators 146 and 116 (163/146 and 132/116).

Two helpers can help predicate abstraction: UltimateAutomizer plus VeriAbs reaches 136 tasks, which the paper reports as a 17% increase (Table 6, PDF p. 10; Section 5.3, PDF p. 9); 136/116 gives the same figure. For k-induction no pair beat VeriAbs alone (163). All three helpers together solve only 154 k-induction tasks and 129 predicate-abstraction tasks, which the paper attributes to sharing the CPU time (Section 5.3, PDF pp. 9-10). Waiting for all helpers (wait-100, wait-200) generally does not pay off (Table 6, PDF p. 10). For `timerM`, both masters do best at 50 seconds; predicate abstraction is unaffected by 50, 100 and 200 seconds, while k-induction with VeriAbs falls from 163 to 161 to 156 (Table 5, PDF p. 9). The paper reports that CPU time is not significantly higher in most cases; averaged over all tasks CPU time even decreases, while the average over correctly solved tasks increases (Table 4, Section 5.3, PDF p. 8-9).

## Verus application and limits

Inference: implement a coordinator that asks multiple agents for loop invariants, stores each proposal as a proof item, invokes Verus validation, and injects only validated facts into the next proof attempt. Use `invariant` clauses and `assert`/lemma proof functions in the Verus form documented by the project. The paper describes witness validation only for its k-induction master and says nothing that guarantees the property or a C-to-Rust translation is correct. Verus's solver context, ownership model, and source-level contracts differ from CFA witnesses; adapters must preserve semantics, not merely syntax.

## what is proved, trusted, and missing

The evidence is empirical, not a theorem about all programs. It establishes that this implementation improved solved-task counts on the specified 342-task sample under the stated machines and limits. The paper states that the implementation "relies on the correctness of the used master verifiers and helpers (which are given) as well as on the adapters (which we build)" (Section 5.4, PDF p. 10); the benchmark labels and the solver (MathSAT5) are trusted too (Inference). The paper notes that SeaHorn runs in a docker container whose CPU usage Benchexec cannot measure, so it was measured externally and rounded up, "obtaining a lower bound for the correctly solved tasks" (Section 5.4, PDF p. 10). It also notes that tasks were a random sample plus loop benchmarks, so results “may not completely carry over to arbitrary real-world programs.” (Section 5.4, PDF p. 10.) Both masters and two helpers participate in SV-COMP and might be tuned to these tasks; the authors argue this does not affect validity because they measure additionally solved tasks.

Inference: for VL, the product threat is moderate but concrete: agents may produce mutually inconsistent invariants, and an orchestration layer may waste resources or inject a malformed lemma. CoVerCIG already demonstrates black-box collective invariant generation; VL should not redo that architecture as a novelty. A useful adaptation is measuring whether independent LLM proposals improve Verus proof completion, proof time, and repair rate on Rust upgrades, with validated proposals and explicit denominators.

## techniques for the catalog

- master-helper invariant delegation — let a master verifier request loop invariants from unchanged specialized tools
- correctness-witness exchange — serialize, validate, and inject helper invariants through a standard witness format
- source-aware invariant adaptation — map IR variables and blocks back to source locations before witness construction
- parallel complementary portfolios — combine generators with different algorithms while measuring CPU sharing and timeout effects
- timed restart and injection — choose when to request help and whether to restart or augment a running analysis
