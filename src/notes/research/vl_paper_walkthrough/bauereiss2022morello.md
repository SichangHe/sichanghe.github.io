# Verified Security for the Morello Capability-enhanced Prototype Arm Architecture
(authored by agents unless marked 🧑)
Tag: `bauereiss2022morello`, [paper](https://doi.org/10.1007/978-3-030-99336-8_7)

## verified architecture pipeline
The paper mechanizes a security theorem for the full sequential Morello ISA. The source is Arm’s executable ASL specification, translated to Sail and then to Isabelle/HOL; Isla generates tests, and a C emulator and Arm ACK tests provide validation. The authors describe “a mechanised proof of capability monotonicity for the full sequential Morello ISA specification (including all instructions, system registers, capability compression, etc.), with large parts of the proof automatically generated” (Sec. 1, contributions list, p. 178). The abstract states “62,000 lines of specification, translated to 210,000 lines of Isabelle” (p. 174); the proof is factored through “a narrow abstraction” of four properties of CHERI instruction execution, expressed over a monadic intra-instruction semantics (Sec. 1, p. 177).

Inference: the same architecture applies to verified Rust systems: define an executable reference semantics, translate or re-express it in Verus-friendly datatypes, and prove a small abstraction theorem that every concrete instruction preserves the abstract security relation. Translation correctness is a separate trusted or verified boundary; it does not follow from the downstream proof.

## technique 1: abstract capability monotonicity
Use this when a machine or kernel must guarantee that execution cannot create authority. Define capability reachability, capability invariants, instruction-fetch and instruction-execute traces, and a transition between states. The paper’s abstraction is the conjunction of four instruction-local properties (Sec. 4.4, pp. 186–189): capability register writes, capability stores, privileged-register access, and memory accesses. Property 1 says a tagged capability written to a register is derivable from the capabilities available to the instruction, except for sealed-capability invocation writes to PCC or IDC and the load of an exception-handler capability into PCC when an exception is raised. Then lift the local property to arbitrary alternating fetch/decode/execute traces. The theorem’s assumptions are exact: “1. all traces tfi and te i satisfy the architecture-specific assumptions, 2. the capabilities in s satisfy the architecture-specific capability invariants, 3. none of the fetch and execute traces tfi and te i raise an ISA exception, 4. the address translation mapping stays invariant along t, and 5. unsealed versions of the invoked sealed capabilities in t are reachable in s” (Sec. 4.5, p. 190). The conclusion is that “the set of capabilities reachable in s0 is a subset of the capabilities reachable in s” (p. 190). The paper’s proof of the theorem is an induction on the number of instructions in the trace (Sec. 4.5, p. 191).

Inference: in Verus, define a ghost `Set<Capability>` or finite sequence of reachable capabilities, a `spec fn` for derivation, and per-instruction `ensures` stating subset preservation. A loop over instructions carries the subset relation as an `invariant`. Exceptions and domain transitions need explicit branches that weaken or reset the invariant. Verus cannot assume capability non-forgeability unless the representation and constructors enforce it; unsafe raw pointers or `external_body` would defeat the guarantee.

## technique 2: abstraction factoring for scale
The full ISA is too large for a direct monolithic proof. Define generic CHERI predicates for capability tags, sealing, bounds, permissions, and derivation. Prove reusable lemmas over the abstract instruction semantics, then instantiate each Morello instruction and system-register operation. The paper combines custom Isabelle proof tactics with “an external tool that automatically generates lemmas about the functions and instructions in the architecture” (Sec. 5.3, p. 193). About 100 ASL functions and instructions needed manual overrides of the generated lemmas, and the capability-encoding functions (notably CapSetBounds) were proved manually, with one lemma discharged by the CVC4 SMT solver used as an oracle (Secs. 5.2–5.3, pp. 192–193). The generated lemmas are checked by Isabelle, so the tool need not be trusted. The authors say this approach let them keep up with weekly snapshots of the ASL specification (Sec. 5.3, p. 193).

Evidence is concrete: “The proof consists of around 37 000 generated lines, 8 600 manually written lines, as well as 8 900 lines for the abstract model, monotonicity proof, and proof tools.” It executed in 7 hours 20 minutes CPU time, 3 hours 23 minutes elapsed with parallelism, and 18 GB peak memory (Sec. 5.3, p. 193). Inference: for VL, generated proof obligations should be paired with a small manually reviewed abstraction layer; generated Rust or proof text alone is not a security argument.

## technique 3: model-based ISA test generation and cross-model validation
Use model-based testing to find specification and implementation mismatches. The paper’s test generator uses the Isla symbolic execution tool on the Sail model: it runs the reset function, makes the harness-controllable state symbolic, symbolically executes each instruction of a random instruction sequence, passes the path conditions to Z3 for concrete initial and final states, and builds a test with a hand-written harness (Sec. 7, pp. 195–196). Separately, the Sail-generated C emulator was run on Arm’s ACK tests and compared with a Morello Arm Fast Model baseline, giving a 98.1% pass rate compared with the baseline (Sec. 6, pp. 194–195). The generated tests were used for early testing of the Morello implementation, as the basis for developing a Morello version of QEMU, and found further ASL bugs (Sec. 7, pp. 196–197). The paper states that its generator “generates instruction-sequence tests that give good specification coverage, used in early testing of the Morello implementation and in Morello QEMU development, and we use Arm’s internal test suite to validate our model” (Abstract, p. 174).

Inference: a Verus project can generate bounded traces from the verified specification and differential-test the executable Rust implementation. Tests do not prove all traces. The paper states a coverage goal, not a percentage: “all of the specification code for manipulating capabilities and for instructions that were added or modified for Morello would be executed in some test” (Sec. 7, p. 196); do not report it as exhaustive.

## bugs, trust, and product threat
The workflow found specification defects, including a top-byte normalization bug in `CapSetBounds`, a missing unsealed check in `BranchToCapability`, and missing capability checks in `DC ZVA` (Sec. 5.4, p. 194). The CapSetBounds bug was found by the initial SMT checking, the BranchToCapability bug by the Isabelle proof; the paper reports all findings were reported to Arm and fixed. These are evidence that formalization and proof can expose design bugs before deployment. The paper’s stated non-goals and limitations (Sec. 1, p. 179) include: the hardware implementation is not verified and components outside the ISA such as the GIC are not covered; only the sequential architecture is considered; an arbitrary but fixed address translation mapping is assumed; privileged capability creation instructions and external debuggers are assumed disabled; the proof depends on an SMT solver as an oracle for one lemma; and the ASL-to-Sail-to-Isabelle conversion is not verified, with possible mismatches against the Sail-generated C emulator used for validation.

Inference: the trusted base also includes the Isabelle kernel. This is a high threat area for agent-written verified Rust when unsafe interfaces, authority-bearing handles, or translation layers sit outside the proof. VL should borrow the narrow-abstraction pattern, explicit assumption list, and differential test generation. It should not claim end-to-end capability security from a local subset theorem.

## techniques for the catalog
- capability monotonicity — prove every instruction preserves subset reachability of capabilities under explicit trace and invariant assumptions
- abstraction factoring — isolate generic CHERI properties and instantiate them across a generated full-ISA model
- model-based ISA testing — generate instruction-sequence tests from the formal model by symbolic execution, and use them to test implementations and emulators
