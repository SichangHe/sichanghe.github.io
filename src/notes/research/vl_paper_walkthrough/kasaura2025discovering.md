# Discovering New Theorems via LLMs with In-Context Proof Learning in Lean
(authored by agents unless marked 🧑)
Tag: `kasaura2025discovering`, [paper](http://arxiv.org/abs/2509.14274v4)

## scope and contribution

The paper presents a Conjecturing-Proving Loop (CPL) that alternates an LLM conjecturer, an LLM prover, Lean Server, and a growing Lean library. Its central design separates statement generation from proof generation, then feeds verified statement-proof pairs back as context. The authors state: “We propose the Conjecturing-Proving Loop, a pipeline for automatically generating mathematical conjectures and proving them in Lean 4 format.” (section 1, PDF p. 2). The goal is discovery of new, meaningful theorems, rather than only solving a supplied benchmark theorem.

## technique: separate conjecture generation from proof search

Use this when jointly sampling a statement and proof mostly returns easy statements whose proofs happen to be easy. The paper's pipeline is explicit (section 3.1, PDF p. 3):

1. initialize a Lean library (user input and previously verified declarations)
2. ask the conjecturer LLM for novel Lean 4 statements using that library as context
3. have Lean Server reject syntactically invalid or non-novel statements; novelty is checked with Lean's `exact?` in a context importing Mathlib4, the generated library, and verified conjectures (section 3.2, PDF p. 3)
4. send each surviving statement to the prover LLM, which may use the same context as lemmas
5. exit this proof loop as failure if the prover judges the conjecture unprovable; otherwise have Lean Server check its proof, accept success, or return errors and retry until the 16-trial limit (section 3.3, PDF p. 4)
6. append only verified statement-proof pairs to the library and repeat from step 2

The conjecturer prompt asks for `theorem ... := sorry` statements without proofs, while the prover prompt must produce code after `:=`, forbids `sorry`, and may return an empty string if it judges a theorem unprovable (sections 3.2–3.3, PDF pp. 3–4). The separation is intended to avoid duplicate statements and allocate multiple proof attempts to a fixed statement. The authors summarize the design: “By separating the conjecturing and proving phases, we avoid the generation of identical theorems and encourage proving more difficult theorems.” (section 3.1, PDF p. 3).

Inference: a Verus implementation would represent conjectures as candidate `spec fn` properties or `ensures` contracts and send each candidate to Verus, retaining only candidates whose proof functions verify. A Rust orchestration process can keep the candidate library and invoke Verus repeatedly; it must not put `sorry`-like axioms into the accepted library. Verus's executable function, `requires`/`ensures` contracts, loop invariants, and `proof fn` lemmas are the relevant constructs. Adapting Lean's `exact?` novelty check to Verus would require a separate design for identifying redundant candidate properties.

Evidence: the authors report: “In CPL, 106 theorems were generated on average, and the target theorem was discovered 5 times out of 20. In SL, 328 theorems were generated on average, but the target theorem was never generated in any of the 20 runs.” Fisher's exact test gave p = 0.024 (section 5.2, PDF p. 6). The target was the intersection theorem for alpha-open sets, anonymized as P2. The authors describe it as “the most difficult part of the proof that α-open sets form another topology”. They used GPT-o3 and generated 20 libraries per framework, each until API usage reached 14,000,000 tokens (section 5.1, PDF p. 6). Figure 2 reports proof lengths in Lean-code characters; the paper cautions that difficulty and length in Lean “are not necessarily the same as the difficulty or length in natural language” (section 5.2, PDF pp. 6–7, footnote 5). Inference: these results support better discovery of this target, not a general increase in theorem count or mathematical difficulty.

## technique: retain verified proofs as in-context strategy examples

Use this when a prover can produce valid code for some statements but fails on a harder statement. CPL includes the entire previously generated library in the prover context (section 3.1, PDF p. 3). The prover therefore sees theorem statements and their checked proof terms before the target statement. The paper describes the intended effect as: “the proving ability of LLMs can be improved by in-context learning, when the verified proofs generated by LLMs themselves before the statement of a target theorem is provided are given as context.” (section 1, PDF p. 2).

To apply it, preserve each verified pair, format it as ordinary Lean declarations, place those declarations before the target, and return Lean's error message after every failed attempt. Do not treat an LLM assertion as evidence; Lean acceptance is the filter. In a targeted re-proof experiment, the authors replayed every CPL theorem with either its prior generated library or only the seed definitions. The authors report: “in the setting with contexts, 99% of the theorems (2106/2123 theorems) were proved, while in the setting without contexts, only 91% of the theorems (1935/2123 theorems) were proved.” The unit counted here is a theorem, whereas the discovery experiment counts libraries. McNemar's test reported p = 4 × 10^-35 (section 5.3.2, PDF p. 7).

For the target theorem, five generated contexts were each tested 16 times, and the authors made 80 attempts without a generated library. They report: “in the setup that included the generated library as context, the re-proof succeeded 7 times, whereas, in the setup without the library, it failed in all 80 attempts.” The average library length before discovery was 49 theorems. This experiment changed the prover's instruction for returning an empty string from “not provable” to “false” (section 5.3.3, PDF p. 8). The authors state: “The generated proof of this theorem, shown in Appendix A, does not use other generated theorems as lemmas.” Inference: this example supports learning proof strategies from context beyond using generated lemmas directly; it does not establish that every generated target proof avoided those lemmas.

Inference: in Verus, retain verified `proof fn` lemmas and their contracts as prompt examples, then ask a model to write a new `proof fn` or strengthen a function's `ensures`. Re-run Verus after every attempt and feed diagnostics back. Keep only verified examples in the prompt corpus; verification still depends on the supplied specification.

## technique: stratified search for hard statements

The paper models SL's accepted-theorem probability as proportional to `s(T) r(T)`, where `s(T)` is statement-generation probability and `r(T)` is proof success probability. CPL's probability is proportional to `s(T)(1-(1-r(T))^N)` for N proof attempts (section 4, PDF p. 5). Increasing N shifts the accepted distribution toward statements with nonzero proof success probability, including those with low success probability. The authors derive expected proof-trial costs and show `E_SL <= E_CPL`, explaining why CPL yields fewer total theorems while shifting its accepted distribution toward low-r statements. This is a sampling argument under a simplified model that ignores context effects; it is not a measured universal law.

Inference: a Verus search controller can assign a fixed retry budget per candidate contract and keep candidates after failed proofs, instead of sampling a fresh contract-proof pair each time. Retry budgets should be observable because larger N increases verification cost. The controller can rank candidates by semantic novelty and proof difficulty, but difficulty estimates beyond Verus diagnostics are an engineering extension (inference).

## what is proved, measured, and trusted

Inference: Lean kernel checking proves the accepted Lean declarations under Mathlib and the supplied definitions. The experiments measure discovery counts, re-proof rates, proof lengths, and statistical tests; they do not prove that an LLM's conjecture is mathematically useful beyond Lean's formal statement. Its correctness depends on Lean, the imported declarations, the seed definitions, and whether the formalization captures the intended topology fact.

The natural-language control gave each model 16 trials with the definitions as context. The authors report: “GPT-4o incorrectly stated that the proposition is false 10 times and generated incorrect proofs 6 times. GPT-o3 never generated an incorrect proof, but it always judged incorrectly that the theorem is false.” Responses were checked by hand (section 5.3.3, PDF p. 8). Inference: these counts demonstrate failures on this target under these prompts, without establishing whether the theorem occurred in model training data.

Inference: the narrow domain of three topology notions, GPT-o3 main comparison, 16-attempt limit, and token budgets constrain generalization. The authors state: “The propositions highlighted in this study were relatively natural to conjecture.” Their proposed next step is to “produce deeper and more insightful mathematical statements” (section 6, PDF p. 8). Inference: the threat to VeruLaw is moderate for proof-search orchestration: CPL supplies a concrete pattern for harvesting verified lemmas and retrying contracts, but it does not solve Rust translation, specification adequacy, unsafe APIs, or dependency trust. Reusing the architecture without Verus-specific novelty and contract checks would therefore leave major product risks unchanged (inference).

## techniques for the catalog

- conjecture-proving separation — generate Lean statements first, then spend a bounded proof budget on each surviving statement
- verified-proof context — feed only kernel-checked prior statements and proofs to the next prover prompt
- Lean novelty filtering — use `exact?` against Mathlib and the generated library before proof search
- verifier-feedback retries — return Lean diagnostics to the prover for up to a fixed attempt limit
- stratified hard-theorem sampling — use multiple proof attempts so acceptance is less biased toward statements with easy proofs
