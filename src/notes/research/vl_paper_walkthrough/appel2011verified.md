# Verified Software Toolchain (Invited Talk)(authored by agents unless marked 🧑)Tag: `appel2011verified`, [paper](https://www.semanticscholar.org/paper/9cdd6da72a90e4fd786012b33f85efc16cdac0d3)## central result and scopeAppel describes the Verified Software Toolchain (VST), a Coq-verified composition of a static analyzer, compiler, runtime or operating-system context, and machine-language semantics. Its end theorem connects source-level claims to machine-level observations. The abstract says: “Our verification approach is modular, in that proofs about operating systems or concurrency libraries are oblivious of the programming language or machine language, proofs about compilers are oblivious of the program logic used to verify static analyzers, and so on.” (abstract, p. 1)The paper is an invited technical overview, not a new benchmark report. Its evidence is the semantic construction, the listed proof obligations, and the Foundational Proof-Carrying Code comparison. It does not give an aggregate count of VST-verified applications or a runtime denominator. The abstract also states the foundational boundary: “the trusted base for proofs of observable properties of the machine-language program includes only the operational semantics of the machine language, not the source language, the compiler, the program logic, or any other part of the toolchain.” (abstract, p. 1)## technique: observable, extensional specificationswhat it is and when to use itSpecify behavior as input-output observations shared by source and target languages. The specification ignores internal loads, stores, and execution time, allowing compiler optimizations while retaining externally visible system calls, lock operations, and shared-memory transfers. This is appropriate when compiler correctness should preserve externally visible behavior rather than a particular instruction sequence. The paper states: “Specifications of program behavior must be robust with respect to translation from source language to machine language.” (Section 1, p. 3)how to do it1. Define a common observation language for source and machine programs (Section 1, p. 3).2. Treat system calls and lock acquire/release as observable events that expose controlled memory portions (Section 1, pp. 3–4).3. Restrict the concurrency model to well-synchronized programs, where accesses occur under exclusive or shared permissions (Section 1, p. 4).4. State extensional properties over observations; do not promise execution time or other intensional behavior (Section 1, p. 4).Verus form
