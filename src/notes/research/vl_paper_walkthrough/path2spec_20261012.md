# Path2Spec: Path-Aware Specification Generation via Large Language Models
(authored by agents unless marked 🧑)
Tag: `huang2026path2spec`, [paper](https://arxiv.org/abs/2609.33438v1)

idea: use execution paths as the intermediate representation for java/jml spec generation
- per path, llm gives symbolic pre and output expression, then path-specific jml
- verify with OpenJML/CVC4, repair with verifier errors (limit e.g. 5), merge verified cases
- single-prompt whole-program methods give overly general contracts
- results on 385 programs (120 SG-Bench, 265 SV-COMP), gpt-5
  - 325/385 = 84.4% verified vs SpecGen 197/385 = 51.2%
  - "verified" = OpenJML exit 0, not spec completeness
pipeline steps
- symbolic path extraction
  - prompt schema `Path [N]: Input: [condition] Output: [expression]`
  - 267 gold paths: gpt-5 91.0% correct, 0.4% missed, 3.4% wrong postcondition
  - jpf misses 13.5% of paths, but is sound
- per-path generation and repair
  - path input to `requires`, output to `ensures`
  - failure stays attached to its path
  - gpt-5 2 compile errors, 8 timeouts vs SpecGen 73, 95
  - but exposes more counterexample failures (50 vs 20) once malformed output is fixed
- first-branch recursive decomposition when repair fails
  - split at first `if`/`switch`/loop, retry subprograms
  - partial result returned if a subprogram stays irreducible
  - ablation gpt-5: path-only 81.6%, decomposition-only 66.0%, full 84.4%
- incremental bottom-up merge
  - merge one path, reverify, concatenate with `also`, dedupe loop clauses
  - no ablation supports the merge design
  - single-shot without repair already 66.2%, so structure gives most of the gain
- logical-strength evaluation
  - z3 compares pre domain and post range against ground truth: complete / incomplete / undecidable
  - 173 pairs, gpt-5 complete 65.9% vs SpecGen 78/173 (45.1%)
  - human ranking 3.4/4 vs 2.4/4, kappa 0.86 (SV-COMP), 0.46 (SG-Bench)
verus takeaways (inference)
- path cases to `requires`/`ensures` or case lemmas, loops get separate invariants
- reject repairs that drop a path case or weaken its output relation
- ownership and mutable borrows have no jml analogue
- "verified" does not mean complete, check strength separately
