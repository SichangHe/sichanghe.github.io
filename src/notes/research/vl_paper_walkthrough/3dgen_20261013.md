# 3DGen: AI-Assisted Generation of Provably Correct Binary Format Parsers
(authored by agents unless marked 🧑)
Tag: `fakhoury20243dgen`, [paper](https://arxiv.org/abs/2404.10362)

agent writes a small checkable DSL, never the final code
- 3D DSL: typedefs, structs, casetypes, value constraints
- EverParse (verified) compiles it to C
  - proof is reused, not new: parse (serialize s) == Some s and serialize v == b
  - trusted: F⋆, Karamel, Z3, C compiler, new SMT encoding (no agreement proof)
- generated 3D is short: mean 26 lines (6 to 99) vs 158 to 1208 lines of C
  - 20 protocols, GPT-4-32k, temperature 1.0
- model errs on DSL syntax: bitfields, int primitives, reserved words
- inference, Verus: agent writes only a spec fn or a verified-combinator-library format (e.g. Vest), not proof fn
candidate-set refinement loop (Algorithm 1)
- keep all type-checking candidate specs
- grow labeled positive/negative packet set
- drop any candidate that misclassifies a packet, feed failing pair back
- result: survivors are consistent with tests, nothing more
  - more refinement rounds do not reliably help
  - setup: 5 candidates, at most 15 refinements, tests built once (200)
three agents split by visibility
- planner runs checker and executor
- developer holds DSL manual
- domain expert holds RFC
- reason: 32k context, shield agents from unrelated steps
- no single-agent baseline, so benefit is unmeasured
- failure: RFC prose ambiguity (VXLAN flag order only in the ASCII diagram)
z3 test generation from the spec itself
- inline parser combinators into one first-order state-to-state SMT function per format
- sat on succeed or fail yields positive or negative packet
  - cost: under 3 person-weeks, about 2000 lines
- branch-trace uninterpreted function forces one input per path
  - depth-first over traces, 200 tests, at most 100 branch points
- tests cover only the candidate's own branches, so a missing constraint is never violated
- Verus carry-over is weak: Verus returns no models
  - unsat half works: proof fn showing a spec accepts nothing
differential query between two specs
- unsat both ways = equivalence proof; sat = distinguishing packet
- Verus form carries over directly: proof fn ensures accepts_a(s) == accepts_b(s)
  - failure may be an incomplete proof, not a real difference
- pairs of passing candidates: 7 of 8 protocols had distinct candidates
- vs handwritten specs: 2/7 equivalent, 3/7 handwritten wrong, 2/7 generated under-constrained (TCP, IPv4)
  - handwritten bugs fixed in EverParse: UDP length constraint, ICMP 32 bytes read as 32 bits, VXLAN id 2 bytes short
- heuristic: prefer the stricter candidate (only 2 supporting cases)
- tool compares, a human reading the RFC decides which side is right
legacy tool as labeler, audited
- Wireshark labels packets
- pass: 9/20 protocols (23/100 attempts) on Wireshark labels
- all 11 failures were Wireshark not enforcing RFC constraints (20 constraints)
- 20/20 only after two authors corrected labels, so not independent
- warning: do not blindly match a legacy tool
tests from a reference spec
- generate tests from the trusted spec, so every constraint gets a negative test
- IPv4: 2 passing specs, both proved equivalent to handwritten
- presupposes the answer, useless for new formats
paper inconsistencies
- "pass@5" means count of 23/100 in definition, 45% (9/20) in results
- averages of refinements are not multiples of 1/5, denominators not given
- refinement cap 15 vs Ethernet 16 and OSPFv3 15.6
- `first > 42` described as `first < 42` twice
