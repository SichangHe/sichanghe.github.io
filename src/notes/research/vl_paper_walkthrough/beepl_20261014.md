# BeePL: Correct-by-compilation kernel extensions
(authored by agents unless marked 🧑)
Tag: `priya2025beepl`, [paper](https://arxiv.org/abs/2507.09883v1)

## what BeePL guarantees and what remains trusted

BeePL is a language and verified compiler for eBPF kernel extensions. Its type system checks types, termination, effects, helper signatures, section attributes, and nullable pointers. Compiler transformations guard undefined operations and structured byte accesses. BeePL source is translated to C, then to BPF bytecode through an eBPF backend added to CompCert. The BeePL-to-C compiler is implemented in Rocq with paper-based correctness proofs; the CompCert eBPF backend has mechanized proofs in Rocq; the parser, lexer, and pretty-printer remain in the trusted computing base. The paper states: “While the core compiler is verified (BeePL using paper-based formal proofs and CompCert (with extension of eBPF backend) in Rocq), the parser, lexer, and pretty-printer remain part of the trusted computing base.” (section 2, PDF p. 6)

The authors give pencil-and-paper proofs of type soundness, preservation, progress, termination, absence of undefined behavior, no uninitialized memory access, no null dereference, and bounded byte-pattern access for their formal language model. These are guarantees for the stated BeePL semantics and properties. Inference: these proofs do not establish kernel behavior, helper implementation correctness, external-call termination, or parser correctness. Section 2 reports: “Our development contributes 33,635 lines of Rocq code as a CompCert extension.” (PDF p. 6) Table 2 lists ten CVE identifiers in six rows and marks them as prevented by BeePL features. Inference: this is a design analysis; the paper does not report reproducing the exploits.

## technique 1: specify source-level safety properties

Inference: what it is and when to use it: define one high-level judgment that connects a well-typed program and well-formed initial state to a finite execution with a final state and value. Use it before designing a type system or compiler so each enforcement mechanism has a stated target.

How to do it (paper, §2.1): quantify over program P, states s and s′, result v, and step count n. Require `P` to be well typed and s well formed. State separate properties: every dereference targets initialized memory; every dereference is non-null; structured access has offset plus size within the allocation; helper calls match signatures and sections; execution terminates; and evaluation never returns `undef`. Assign each property to a language feature, type rule, runtime check, or compiler transformation. The paper says: “The formal specification provides a high-level judgment involving a program 𝑃, an initial state 𝑠, a final state 𝑠 ′, a result value 𝑣, and a step count 𝑛.” (section 2.1, PDF p. 7)

Inference: Verus form: encode state, memory, and execution as ghost/spec data and define `spec fn` predicates for well-formedness and safety. Give executable functions `requires` and `ensures` contracts for each property. Prove termination with a decreases clause where the loop structure supports it. This proves the chosen model, not the Linux kernel’s actual memory or helper semantics.

Evidence and limit: the formal proofs are pencil-and-paper for BeePL, including BeePL-to-C correctness, and mechanized in Rocq for the CompCert eBPF backend. The termination proof states: “For external function calls, we assume they terminate and do not prove this within BeePL’s semantics.” (section 4.2, PDF p. 20)

## technique 2: make nullable pointers explicit with option types

Inference: what it is and when to use it: distinguish definitely valid references from references returned by external helpers that may be null. Use it whenever a map lookup or kernel helper can fail.

How to do it (paper, §1.3 and §3): represent internal allocations with non-null `τ★`; represent external nullable references as `option(τ∗)`. Forbid direct dereference of an option. Require `match` with `Pnone` and `Psome`; dereference only in the Psome branch. The compiler lowers the match to an explicit C null check. In the CVE-2022-23222 example, `bpf_map_lookup_elem` returns `option(long★)`, Pnone returns −1, and Psome safely dereferences. The paper says: “Unlike traditional C-style programming where null checks such as if (p != NULL) are manually inserted and easy to forget, BeePL uses option(𝜏∗) to enforce nullability at the type level.” (section 3, PDF p. 9)

Inference: Verus form: use an enum-like Rust value such as `Option<&T>` or an abstract option pointer, pattern-match it, and put dereference permissions only in the Some branch. A Verus proof can establish that a dereference requires a non-null pointer and valid permission. Raw pointers and foreign helpers need explicit external contracts; do not mark the function being verified as `external_body` to evade the obligation.

Evidence: the BeePL type checker rejects `!p` when p has option type; the generated C inserts a null test. Table 2 associates this mechanism with CVE-2022-3606, CVE-2022-0433, CVE-2022-23222, CVE-2025-21852, and CVE-2024-38566. Inference: the CVE mapping depends on accurately modeling the vulnerability causes.

## technique 3: transform partial arithmetic into total safe operations

Inference: what it is and when to use it: rewrite division, modulo, shifts, and the overflow cases described for those operations so generated code has defined behavior even when source operands are unsafe.

How to do it (paper, §1.3, §2.1): type-check operand types and guard operations using their actual operands, including values after truncation. Before code generation, rewrite a potentially unsafe operation to a conditional. For CVE-2021-3600, a 64-bit nonzero r0 is truncated to 32-bit w0=0; the unsafe `w1 % w0` becomes `if w0 == 0 then 0 else w1 % w0`. For CVE-2020-8835, insert an explicit upper-bound check on a shift amount. The formal semantics define the guarded result and prove it is never `undef`. The paper states: “This transformation ensures that unsafe modulo or division operations on zero are never emitted, effectively eliminating this entire class of verifier-bypass vulnerabilities.” (section 1.3, PDF p. 4)

Inference: Verus form: define a total spec function for each operation, with a branch returning a policy-defined fallback on a zero divisor or oversized shift. Prove the executable wrapper equals that function and specify whether fallback zero is acceptable to the product. Verus integer semantics and target machine arithmetic must be modeled explicitly; a proof over mathematical integers does not by itself prove BPF ALU behavior.

Evidence and limit: BeePL’s Lemma 5 proves operator evaluation returns a value different from `undef`; the proof relies on the compiler transformation and Lemmas 9–10. Inference: zero is the defined BeePL result for these unsafe arithmetic cases; preservation concerns BeePL semantics, rather than arbitrary C behavior on the same inputs.

## technique 4: use bytes pattern matching for bounds-safe parsing

Inference: what it is and when to use it: parse packed kernel data as byte sequences with typed patterns instead of raw pointer arithmetic. Use it for network headers and variable-length external buffers.

How to do it (paper, §3 and Lemma 8): represent input as `bytes`; select a target type and bind its extracted fields. The match semantics check `length(bytes) ≥ sizeof(type)` before extraction. On failure, select the fallback branch without extracting data from the insufficient buffer. Prove that successful extraction is within bounds. The paper says: “Hence, no rule in the semantics permits extraction from out-of-bounds memory, and all memory accesses during match evaluation on byte values are within valid bounds.” (Lemma 8, PDF p. 22)

Inference: Verus form: model a byte slice with a length invariant, write a spec extraction function requiring `offset + sizeof(T) ≤ slice.len()`, and prove the Rust parser checks that condition before indexing. Use slice permissions and integer bounds; do not rely on an unproved C cast.

Evidence: Lemma 8 proves the bound for BeePL’s MBYTES rule and fallback MBYTESF. The result covers the language’s structured patterns. Appendix §7.2 limits the described struct deserialization to non-pointer fields: “At this moment, we focus only on structs whose fields are of non-pointer types.” (PDF p. 43)

## technique 5: compile through a verified semantic-preserving pipeline

Inference: what it is and when to use it: prove that each compiler pass preserves the source semantics and safety invariants, then compose the passes to a target backend.

How to do it (paper, §4.3 and Appendix 7): parse BeePL into an AST, type-check, translate expressions to CompCert Csyntax, and invoke CompCert’s verified compilation pipeline. Extend CompCert with an eBPF backend. For loops, evaluate bounds once, store them in fresh variables, initialize a fresh index, update it by one in the chosen direction, and check whether the range is empty before entering the loop. The generated C loop also tests its index against the stored bound each iteration. The authors give a paper proof of BeePL-to-C correctness in Lemma 23. For the CompCert backend, model eBPF’s R10 stack convention using a non-architectural base register BP. Reserve the caller stack pointer and return address at the top of the modeled frame, above R10, and translate Mach accesses using the invariant `R10 = BP + δ`. These saved values are unavailable to the eBPF callee. The paper says: “This end-to-end path—from BeePL to BPF via C—enables the generation of safe and semantically sound BPF bytecode, suitable for secure deployment in the kernel.” (section 4.3, PDF p. 23)

Evidence and trusted boundary: the backend is proved in Rocq and CompCert supplies verified passes, but parser/lexer/pretty-printer are trusted. The backend does not support Mach tail calls or fetching parameters from the caller’s stack; floating-point programs are rejected at assembly generation. LLVM’s existing eBPF assembler produces the ELF file from the assembly. Section 6 states: “Our framework does not currently analyze stack usage or enforce stack frame size limits, nor does it perform detailed scope or liveness analysis.” (PDF p. 26) Helpers are assumed correct and remain trusted.

## techniques for the catalog

- source safety specification — state one formal judgment for well-typed programs and each required eBPF property
- option-based null safety — encode nullable helper results and require pattern matching before dereference
- totalizing compiler transformations — guard division, modulo, and shifts, including their described overflow cases, before target code generation
- bounds-safe byte patterns — check typed extraction sizes before parsing packed data
- verified compilation pipeline — prove semantic preservation from typed source through C and BPF backend
