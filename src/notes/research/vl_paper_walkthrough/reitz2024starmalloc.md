# StarMalloc: A Formally Verified, Concurrent, Performant, and Security-Oriented Memory Allocator
(authored by agents unless marked 🧑)
Tag: `reitz2024starmalloc`, [paper](https://arxiv.org/abs/2403.09435v1)

## scope and result

StarMalloc is a concurrent C memory allocator designed from hardened_malloc and verified in F★/Steel concurrent separation logic, then extracted to C. The paper combines a layered heap model, generic reusable data-structure predicates, ownership-transfer contracts, security postconditions, and specification-guided implementation. It also reports performance, security tests, Firefox integration, and proof effort.

The paper claims: “In this work, we present StarMalloc, a verified, security-oriented, concurrent memory allocator that can be used as a drop-in replacement in real-world projects.” (Abstract, PDF p. 1). Section 5 states “26,000 lines of F★ code, extracting to about 4,300 lines of executable C code” (PDF p. 15). Table 2 reports a total of 26,102 lines excluding whitespace and comments, including a row labeled “C glue” with 303 lines (Section 6.4, PDF p. 20). The paper does not explain how these counts reconcile. The allocator has 27 size classes for 16-byte multiples through a 4-kilobyte page, four arenas in the evaluation configuration, and per-size-class locks (Sections 3.1 and 6.1, PDF pp. 6 and 18).

## technique 1: layered separation-logic specifications

What it is. Steel contracts combine separation-logic ownership with dependent types and ordinary `requires`/`ensures` clauses. A predicate describes which memory a component owns; separating conjunction means disjoint ownership. The frame rule lets a local proof preserve unrelated memory. Concurrent separation logic extends this to thread safety. The paper’s allocator contract is `malloc : Steel ... emp ... null_or_slarray`, with a postcondition that a non-null result has length at least the requested size (Section 4.1, PDF pp. 8–9).

How to apply it. Inference: reconstruct the paper’s method as follows. (1) Define an abstract ownership predicate for each resource, such as an allocated array or a lock-protected size class. (2) State a function’s precondition as the ownership it consumes and its postcondition as ownership it returns. (3) Add dependent value properties with `requires` and `ensures`, such as returned length or alignment. (4) Prove local operations under the frame rule, carrying unrelated resources unchanged. (5) Compose layers only through interfaces, keeping representation details abstract.

Verus form. Inference: use Rust data types and `spec fn` predicates for abstract ownership and value relations, `requires`/`ensures` on functions, and proof lemmas for frame-like preservation. Verus does not use Steel’s `slprop` effect indices; ownership must be represented with Verus ghost state and supported proof-oriented APIs. Inference: a lock contract can expose a ghost state predicate and transfer it across acquire/release transitions.

Evidence and limits. The paper states that the Steel signature guarantees “memory safety, functional correctness, and thread-safety” (Section 4.1, PDF p. 9). It limits the security proof: “Our chief result is that the allocator remains correct and memory-safe in the presence of all these security mechanisms; proving that the implementation of these mechanisms effectively defend against attacks would require an attacker model that is, to the best of our knowledge, beyond what current state-of-the-art in program verification can do.” (Section 4.3, PDF p. 14). Section 5 lists “axiomatization of memory-related syscalls, e.g., mmap” (PDF p. 17). Inference: the real OS behavior must satisfy those axioms.

## technique 2: generic combinators for reusable heap proofs

What it is. The authors avoid repeating proofs by defining generic predicates and lemmas once, then instantiating them. `starseq` folds a sequence into a separating conjunction indexed by position. `sldep` ties ownership of a mutable metadata object to a predicate that depends on its current mathematical contents. `slrefine` combines ownership with a pure well-formedness property. These abstractions connect bitmaps, slots, slabs, linked lists, and size classes without exposing representation at every layer.

How to apply it. Inference: reconstruct the paper’s method as follows. (1) Choose a mathematical sequence for fixed-size metadata. (2) Define a generic fold predicate `starseq p s` that owns each element through predicate `p`. (3) Prove generic lemmas to extract one index and update one element. (4) Tie concrete metadata to its abstract sequence with a dependent predicate (`sldep`). (5) Define well-formedness separately with a pure predicate (`is_list`, bounds, acyclicity, partition). (6) Refine ownership with that property (`slrefine`). (7) Instantiate the generic predicates for each allocator layer; reuse the lemmas without reproving them.

The paper says: “This reduces both code duplication and the proof effort; we only need to perform proofs on the generic version, instantiations come at no extra cost.” (Section 4.2, PDF p. 10). The method supports representation replacement: linked lists were replaced by doubly-linked lists by changing `arraylist_sl` and operations with the same interface, while code and proofs operating on the list contents remained unchanged (Section 4.2, PDF p. 12).

Verus form. Inference: encode generic folds as recursive `spec fn`s over `Seq` or bounded arrays, and prove reusable lemmas for indexing and updates. Use abstract predicates in module contracts, keeping concrete arrays behind `pub` interfaces. Verus’s executable Rust and specification sequences differ from F★’s `slprop`; the transfer is a design pattern, not a direct translation.

Evidence and limits. Section 5 lists “statically allocated doubly linked lists, efficient bitmaps, AVL trees, frozen arrays, FIFO queues” among the generic libraries (PDF p. 17). Table 2 reports 1,520 bitmap, 2,754 list, 494 queue, 4,283 AVL, and 3,692 miscellaneous lines (Section 6.4, PDF p. 20). Inference: these rows sum to 12,743 lines. With the 12,972 StarMalloc and 303 C glue lines, the rows sum to 26,018, whereas the printed total is 26,102. The paper does not explain the discrepancy; these are line counts, not proof-success percentages.

## technique 3: model allocator architecture in ownership layers

What it is. StarMalloc models regular allocations as arenas, size classes, page-sized slabs, and fixed-size slots. Slot metadata is a bitmap; metadata lives in a separate mapped region. A slab predicate ties bitmap bits to ownership of slot slices. Slabs are partitioned into empty, partial, and full lists; an AVL tree records large allocations above 4 kilobytes. Each size class has a lock protecting its metadata; a frozen array permits concurrent read-only access to initialized size-class descriptors.

How to apply it. Inference: reconstruct the paper’s method as follows. (1) Separate large and regular allocations by page-size threshold. (2) For regular allocations, map a fixed virtual region and divide it into compile-time arenas. (3) Round requests to one of 27 size classes (or a generic configured list). (4) Represent each slab as a page and each slot as a fixed slice; update the bitmap under the size-class lock. (5) Maintain disjoint metadata lists and prove that they partition all slabs. (6) For free, validate region membership, derive arena/size-class/slot by pointer arithmetic, update metadata, and quarantine an empty slab. (7) For large allocations, track the mapped pointer and length in the AVL map, protected by a separate lock; look up the pointer and length before calling `munmap` on free (Sections 3.1 and 4.2, PDF pp. 5–7 and 14).

Verus form. Inference: use bounded arrays and index/range lemmas for slots and slabs, ghost maps for large-allocation extents, and a state-machine or lock API for per-size-class ownership. Pointer arithmetic and OS calls need explicit external specifications; a Verus proof cannot assume C `mmap` behavior without a contract.

Evidence and limits. The frozen-array interface supports concurrent reads: “we instead implement a novel model of frozen arrays in Steel, that can be safely accessed concurrently by any thread once initialized, but do not provide any update facility.” (Section 4.2, PDF p. 13). The lock model has an explicit limit: “this model does not allow to formally prove the absence of deadlocks.” (Section 4.2, PDF p. 13). The authors use the scoped `with_lock` combinator to alleviate this issue. For alignment, the paper states “our assumption that calls to mmap always return page-aligned memory” (Section 4.2, PDF p. 13). Inference: the allocator proof depends on its external specifications; it does not establish OS correctness or correctness of arbitrary clients.

## technique 4: security mechanisms as localized specification extensions

What it is. Section 4.3 specifies zeroing, quarantine, and guard pages through extra predicates and postconditions with localized changes. Section 3.2 also describes segregated metadata and canaries informally. Segregated metadata limits overwrite damage. Free zeroes memory; allocation checks that the memory remains zero and returns `NULL` if corrupted. Empty slabs enter a FIFO quarantine; Section 3.2 describes `madvise(DONT_NEED)` to return their pages to the OS. Guard pages use `PROT_NONE`. The canary description says: “We check the integrity of a canary when freeing a slot, which can detect overflows a posteriori (but often too late to entirely prevent attacks).” (Section 3.2, PDF p. 8).

How to apply it. Inference: reconstruct the paper’s method as follows. (1) Add a zero-content conjunct to `malloc`’s postcondition: every returned byte below the requested size equals zero. (2) Add a `Quarantine` status and fourth list to slab metadata; move empty slabs there and reclaim them FIFO after a configured delay. (3) Add a `Guard` status and fifth list; prove the required guard-page pattern and expose only an abstract guard predicate. (4) For quarantine, modify `sc_data` and `slabs_sl`; keep layers above `sc_malloc` and below `slab_sl` unchanged (Section 4.3, PDF pp. 14–15). The exploit tests are separate empirical evidence, described in Section 6.2.

The zeroing contract is explicit: the postcondition includes `∀ (i:nat{i < size}). get (h1.[r]) i == 0` conditional on a non-null result (Section 4.3, PDF p. 14). The guard predicate is monotone: once a slab is marked guard, the proof does not recover ordinary ownership (Section 4.3, PDF p. 15).

Verus form. Inference: state zeroedness and quarantine status in ghost predicates and `ensures`; model a guard page as an abstract resource whose only allowed transition is introduction. External `mmap`, `madvise`, and signal behavior need `external_body`-style trusted contracts only at the boundary, never on the function being verified. Inference: a Verus canary proof would need an explicit corruption model and detection contract; this paper does not present such a proof.

## technique 5: specification-guided implementation and verified specialization

What it is. The implementation follows the specification’s abstraction boundaries. Complex bitmap or list code is hidden behind interfaces, simplifying verification conditions and permitting independent module builds. F★ normalization specializes generic code at compile time from a client-provided size-class list, replacing error-prone C macros while leaving proofs unchanged.

How to apply it. Inference: reconstruct the paper’s method as follows. (1) Write the abstract contract and predicates first. (2) Implement each layer against that interface. (3) Keep optimization changes inside a module whose interface remains unchanged. (4) Parameterize static configuration (size classes, arenas) as pure values. (5) Use `norm` to reduce configuration-dependent lists and pattern matches before extraction, leaving executable calls in the supported C subset. Section 5 explains: “After normalization, all occurrences of lists disappeared, which enables KaRaMeL to extract to the idiomatic C init shown below.” (PDF p. 16).

The paper reports: “the entire verification of StarMalloc only requires 30-40 minutes on a modern laptop” (Section 5, PDF p. 16), while implementation effort was two person-years (Section 6.4, PDF p. 20). The authors explain: “F★’s normalizer is a key component of its typechecker, and hence already part of the TCB.” (Section 5, PDF p. 17). Inference: this reuse of the normalizer does not establish correctness of the subsequent C extraction or compilation.

Verus form. Inference: use generic Rust functions over const parameters or type parameters, prove them once, and instantiate configurations with compile-time constants. Keep implementation details private behind contracts; use `spec fn` models for configuration. Verus proof reuse depends on stable contracts, while F★ normalization and KaRaMeL extraction have different trust and compilation semantics.

## evidence and measured behavior

The performance setup was a 4-core/8-thread Intel Xeon E5-1620 at 3.60 GHz, 12 GB RAM, Linux 6.1, glibc 2.38, performance governor, and `vm.max_map_count` raised to 1,048,576 (Section 6.1, PDF p. 18). Table 1 normalizes execution time and RSS to hardened_malloc = 1.0 across 30 listed benchmarks; StarMalloc is within 0.84×–1.38× of hardened_malloc on most real-world applications, with redis at 16.379× and rptestN at 19.537× (Table 1, PDF p. 19). The authors attribute these outliers to allocations above StarMalloc’s page-size slab limit: “differences in redis seem to be due to a large number of allocations of size slightly exceeding the page size.” (Section 6.1, PDF p. 18). The stated range covers most applications; the table also has espresso at 2.284× and lua at 1.554×. Firefox 118.0.2 ran the complete JetStream2 suite. The authors report “a performance overhead of 5.1% and 12.1% compared to a version compiled with hardened_malloc and glibc respectively” (Section 6.3, PDF p. 20). Inference: each percentage uses the corresponding Firefox build as its baseline, rather than averaging Table 1 rows.

Section 6.2 reports caught use-after-free cases from Yagemann et al. and the bzip2 CVE-2016-3189, and states: “We prevent the “fastbin_reverse_into_cache”, “fastbin_dup” and “tcache poisoning” exploits, all of which are successful with the most recent version of glibc (2.38).” (PDF p. 20). Inference: no detection percentage follows because the paper gives no total count of attempted exploits. The effort estimate is explicit: “We estimate that our implementation effort for StarMalloc took two person-years.” (Section 6.4, PDF p. 20).

## proof boundary and VL risk

The formal claims cover modeled memory safety, functional allocator behavior, thread safety, zeroing postconditions, and layered data-structure invariants (Sections 4–5). Inference: the end-to-end guarantee also depends on F★/Steel and the proof toolchain, extraction and compilation, OS and pthread behavior matching their models, and the ABI wrappers. The paper explicitly assumes page alignment and axiomatizes memory-related syscalls. It supplies no formal attacker model and does not formally prove absence of deadlocks or effectiveness against attacks (Sections 4.2–4.3). Canary behavior is described in Section 3.2, without a canary-specific formalization in Section 4.3.

Inference: a passing allocator proof can mislead users if it relies on incorrect foreign-function or hardware contracts, stale configuration assumptions, or an incomplete attacker model. The strongest reusable lesson is the architecture: specify ownership and functional behavior in layers, isolate mutable representations behind interfaces, and make security mechanisms contract extensions. VL should not redo generic bitmap/list/AVL proof libraries or the specification-guided modularity idea. Inference: a Verus study could add evidence for a verified Rust implementation, explicit accounting of trusted assumptions, and measured proof maintenance under configuration and dependency changes.

## techniques for the catalog

- layered separation logic — specify ownership, values, and thread safety with compositional predicates and contracts
- generic heap combinators — define reusable sequence, dependent-ownership, and refinement predicates, then instantiate them across data structures
- allocator invariant layers — tie slots, bitmaps, slabs, lists, size classes, arenas, and large-allocation maps into modular ownership contracts
- localized hardening proofs — extend specifications for zeroing, quarantine, and guard pages while limiting changes to affected layers
- specification-guided extraction — implement to contracts, specialize static parameters by verified normalization, and extract to C behind explicit trust boundaries
