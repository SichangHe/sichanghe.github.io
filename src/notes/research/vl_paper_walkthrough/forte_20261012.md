# Forte: sensitivity proofs for imperative Rust
(authored by agents unless marked 🧑)

forte checks how much outputs change when private inputs change, for a restricted imperative rust fragment
- combines rust exclusive borrows, flux refinement types, verus proofs of the accounting rules
- not an agent, and not repository-scale verified rust generation
- headline limit: proved math contracts of primitives are linked to rust primitive bodies by inspection
  - quote: "We trust the Rust body of each trusted primitive to implement the function the corresponding theorem describes, by inspection" (§5, p.14)
  - 313 non-comment library lines outside kernels
λ-forte calculus (§3–4)
- each sensitive value carries one coefficient per declared source
  - addition adds coefficients, scaling scales them
- mutable calls strongly update the borrowed location, frame rules preserve the rest
- branches and loops use public control flow, loops infer growth from counters
- metric preservation: two runs stay within derived bounds
  - exclusivity supplies the distinct-location condition and nothing else
  - refutation: aliasing both `&mut` params of "add one into the other" gives stale sensitivity 1 after doubling, rust rejects the call
  - takeaway: framing needs disjoint write capabilities, not just the addition formula
verus mechanizes only the scalar fragment, 46 verified items
- covers strong updates, public branches/loops, source reads, procedures with exclusive-borrow params
- paper proofs additionally cover env-polymorphic schemes, by-value params, fresh locals
- vector primitive obligations proved separately
- keep this split in any assurance claim
library engineering (§5)
- no compiler fork, no new checker
- opaque structs hide payloads and carry a fixed tuple of 3 sensitivity coefficients
  - changing width means regenerating types
  - tuples keep arithmetic solver-friendly, avoiding quantified array/map reasoning
- flux soundness is unary (one run), sensitivity is relational
- budget token: non-Copy moves block reuse of one token
  - but "nothing prevents a program from minting a second token" (§5, p.14), so one budget per run is a protocol
trusted base and out of scope
- trusted: verus, flux, rustc, fixpoint, smt, source declarations, metrics, raw-data injection
- sampler: "we still trust that the sampler draws from that density and that exp is monotone" (p.22)
  - §8 proposes SampCert (lean, verified samplers) as a replacement, not done
- idealized arithmetic: overflow and float rounding outside the guarantee
  - the checked-sum example proves overflow avoidance separately
- stored refs, long-lived borrows, sensitive closures, polars transformations outside core scope
- secret-index histogram writes sit in trusted leaves
evaluation (author-reported, not autonomous generation)
- reimplements kernels from 5 opendp transformation families
  - crate: 64 functions check in 0.41 s
  - 43 leaf items 0.68 s, 46 calculus items 1.31 s, apple m4
  - table 4: 131 lines, 23 signature lines, 2 extra hints
- 14 verus items prove privacy-loss arithmetic, independent-release composition, pointwise-to-set-sum weights
- 10 negative controls reject tightened claims (clamped sum, loop bound, noise scale, split budget, ...)
  - 2 more fail before refinement checking: aliased borrows, unclamped sum
  - constructed tests, not newly found bugs
- opendp survey at 4198f76: 68 trusted stability closures
  - 14 with linked proof docs, 54 without, 31 are polars
  - counts documentation linkage, not proof validity
  - saving claimed only for the stability-map half
engineering lessons (proposed, not evaluated)
- map each trusted signature to a named theorem
- keep metric and unit conversions explicit
- use ownership for framing
- add negative controls for weakened bounds, aliasing, budget misuse
