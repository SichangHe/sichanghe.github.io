# Flux: Liquid Types for Rust

source: Lehmann, Geller, Vazou, Jhala, “Flux: Liquid Types for Rust” (OOPSLA 2022), full text in the batch PDF/TXT

## what is proved and trusted
Flux extends Rust types with logical indices, existential refinements, ownership-aware locations, and strong references. Its formal theorem is type soundness under a Stacked Borrows dynamic borrow checker: “well-borrowed evaluations of well-typed programs do not get stuck” (section 3, theorem 3.1). Rust’s borrow guarantees and the dynamic borrow checker are assumptions; Flux does not re-prove Rust’s compiler or unsafe code. The evaluation is an empirical comparison with Prusti, not a proof that Flux handles all functional correctness.

## technique 1: index values and APIs with refinements
What it is: attach logical indices to base types (`i32[n]`, `RVec<T>[n]`) and use existential predicates for sets such as positive integers. Refinement parameters are ghost variables instantiated from call arguments.

When to use it: use indices for exact values or structural measures (especially lengths), and existential predicates for inequalities/ranges. This makes safety preconditions ordinary types.

How: define constructors and operations with indexed signatures. The paper’s RVec API has `new -> RVec<T>[0]`, `len(&RVec<T>[@n]) -> usize[n]`, `get(..., idx: usize{v:v<n})`, and `push(&strg RVec<T>[@n], value:T) ensures *self:RVec<T>[n+1]` (section 2.3, figure 3). A caller can therefore obtain a vector-length index and must prove an index is below it before access.

Evidence: the authors verify vector bounds in seven algorithm benchmarks and Wave sandbox modules. Flux uses 145 specification lines for 944 Rust LOC, versus Prusti’s 315 for 921 LOC (table 1).

Limits: Flux targets lightweight properties; the paper explicitly says Prusti can verify deep functional correctness such as sortedness that Flux cannot (section 5). The introductory `abs` example overflows at `i32::MIN`; the paper says Flux can verify the absence of overflows statically but, to keep examples short, assumes overflows are checked at run-time (footnote 2, section 2.1).

Quote: “Reﬁnement types allow expressions in some underlying, typically decidable, logic to be used to constrain the set of values inhabited by a type” (section 2.1).

## technique 2: ownership-indexed mutation and strong references
What it is: combine Rust ownership with location indices so mutation updates a location’s type without aliasing unsoundness. `&mut` preserves an index; `&strg` (strong reference) records a strong update that changes the indexed type.

When to use it: use ordinary mutable references when an operation preserves an invariant (for example vector length), and strong references when mutation changes a measure (for example `push` increments length).

How: declare a strong-reference precondition and postcondition, as in `incr`, whose Flux signature takes `x: &strg i32[@n]` with `ensures *x:i32[n+1]` (figure 2), or `push`’s `RVec<T>[n]` to `RVec<T>[n+1]`. Flux’s spatial phase infers identifier-to-location mappings and where refinements are assumed/asserted; checking generates Horn constraints; liquid inference solves them (section 1, contribution 2; section 4).

Evidence: the formal soundness proof models the aliasing dependency using Stacked Borrows, and table 1 shows the resulting APIs verify without user loop annotations.

Limits: the soundness argument depends on Rust’s aliasing guarantees and well-borrowed executions. Flux restricts the positions where a refinement parameter can be declared in a function signature (section 4.1).

Quote: “Flux extends and reﬁnes Rust’s mutable references with a notion of strong references that precisely track strong updates that alter the type of the mutated object” (section 1).

## technique 3: polymorphic liquid inference for quantified invariants
What it is: encode a universal property over container elements in a polymorphic refined element type, then infer quantifier-free predicates with Horn clauses. This replaces explicit quantified loop assertions.

When to use it: use it when every element of a collection satisfies the same predicate, such as all KMP table entries being below the current index or all sandbox addresses staying in a region.

How: parameterize `RVec<T>` by a refined `T`; carry that type through `get_mut`, `push`, and loops. Flux’s fixpoint solver infers unknown refinements from quantifier-free templates. In the KMP example, Prusti needs `forall x: usize, x<t.len() ==> t.lookup(x)<i`; Flux represents the element type polymorphically and infers the equivalent constraint (section 5.4).

Evidence: `kmeans` and `kmp` were chosen to highlight quantified invariants via polymorphism; the Wave modules ported were those with non-trivial Prusti specifications (loop invariants or quantified pre/postconditions). On all eight benchmarks, Flux used zero loop-annotation lines; Prusti used 88 lines, 9% of 921 LOC overall, with a maximum of 24% for heapsort (table 1).

Limits: the authors note Flux cannot express deep specifications such as sorted-ness that Prusti can (section 5). Inference, not stated by the paper: richer relations between elements may not fit quantifier-free templates and may require redesigning an API.

Quote: “by using polymorphism to quantify over the elements of t, Flux can reduce the inference of this invariant to the inference of a quantifier free formula” (section 5.4).

## measured comparison
Setup: Fedora 36, 32 GB RAM, 12th-gen Intel i7-1280P; Prusti commit 673a095d, Z3 4.8.6, OpenJDK 17.0.4.1 (section 5.1). Flux total verification time was 7.13 seconds versus Prusti 246.65 seconds (table 1), including FFT 0.70 s versus 166.76 s and Wave 4.50 s versus 28.74 s. The authors speculate the gap is due to quantified loop invariants in the SMT solver and say further Prusti experimentation may bring the times closer (section 5.2). These are reported benchmark measurements, not a general speed theorem.

## implications for VL (inference)
Flux suggests a VL verifier can reduce proof burden by exposing length/value indices and ownership-preserving APIs, while making collection-wide invariants element-type properties. It is a complementary design point to Verus’s richer program logic. Product risk remains for properties outside quantifier-free liquid templates, unsafe code, and Rust compiler/borrow-checker trust; VL should not redo Flux’s basic indexed-vector and inferred-loop-invariant ideas without a concrete integration gap.

## techniques for the catalog
- indexed refinement APIs — index values and collection measures in types so safety preconditions become ordinary typed calls
- ownership-aware strong updates — use Rust ownership and strong references to track mutation that changes a refinement index
- polymorphic quantified invariants — encode universal container properties in refined element types and infer them with quantifier-free Horn constraints
- liquid loop inference — spatial mapping, Horn generation, and fixpoint solving synthesize loop invariants without user annotations
