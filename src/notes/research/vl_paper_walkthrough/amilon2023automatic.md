# Automatic Program Instrumentation for Automatic Verification (Extended Technical Report)
(authored by agents unless marked 🧑)
Tag: `amilon2023automatic`, [paper](http://arxiv.org/abs/2306.00004v1)

## What the paper proves

The paper introduces a framework that rewrites rich specifications into simpler assertions and ghost state before automatic verification. Its central claim is soundness plus weak completeness (Theorem 1, section 2.3, p. 9): a bad source program cannot become apparently correct merely because instrumentation was added, and a failing original assertion in the instrumented program also fails in the original. The framework has three parts: ghost-variable declarations and initial values, schematic rewrite rules for assignments, and an instrumentation invariant over the ghost variables. A separate search chooses which matching statements to rewrite. The authors instantiate the framework for square tracking, universal array quantification, maximum, and sum.

The motivating example is triangular numbers. The source computes `s` by a loop and then sets `NN = N*N`; nonlinear arithmetic makes automatic invariant inference difficult. The square operator tracks `i*i` in `x_sq` and the current `i` in shadow variable `x_shad`. The paper states: "The insight needed to elegantly verify the program is that the value i*i can be tracked during the program execution using a ghost variable x_sq." (section 1, p. 3). In the instrumented loop, a rewrite of `i=i+1` asserts that `i==x_shad`, updates `x_sq = x_sq + 2*i + 1`, increments `i`, and sets `x_shad=i`; a rewrite of `NN=N*N` replaces the multiplication with `NN=x_sq`. The invariant is `x_sq = x_shad²` (Figure 2, p. 4; Figure 1, p. 3). This is a reusable ghost-shadow pattern: every relevant assignment must either update the tracked expression or fail an assertion that exposes a missed update.

## technique 1: define a sound instrumentation operator

What it is. An operator is a tuple `(G,R,I)`: fresh ghost variables with initial values, schematic rewrite rules, and an invariant. A rule matches an assignment `r=t` and replaces it with code that may assign only to `r` and the ghosts. Definition 1 (section 2.2, p. 7) requires the invariant to hold in the initial ghost state, and for each rule: the replacement terminates for pre-states satisfying the invariant; it assigns only to `r` and the ghosts; it preserves the invariant when its assertions are treated as assumptions; and it preserves the original assignment's semantics. The paper summarizes the purpose in the introduction: "Instrumentation operators are designed to be sound, which means that rewriting a wrong selection of program statements might lead to an instrumented program that cannot be verified, i.e., in which assertions might fail, but instrumentation can never turn an incorrect source program into a correct instrumented program." (section 1, p. 4).

How to apply it. (1) Identify a difficult expression or specification construct. (2) Choose ghosts that represent its value and, where needed, a shadow copy of source variables. (3) Write rewrite rules for every statement form that can change the represented value; add guard assertions before using a shadow. (4) State an invariant only over the ghosts. (5) Prove that the invariant holds initially and that every rule meets the four per-rule conditions 2(a)–(d) of Definition 1. (6) Apply selected rules to a source program and retain the original assertions. The paper's square rules R1–R4 show the shape: initialization `x=α` sets `x_sq=α²` and `x_shad=x`; increment updates by `2α*x+α²`; scaling multiplies the square; and `y=x*x` reads `x_sq` after asserting the shadow agrees (Figure 2, p. 4).

Verus form (inference). A Rust implementation would keep tracking fields or ghost variables in a verified wrapper, use `requires`/`ensures` on proof helpers, and maintain the relation with `assert` and `invariant` loop annotations. Verus has no direct schematic rewrite operator, so source rewriting or a macro would generate the ghost updates; the invariant proof remains in Verus. The shadow check is an executable assertion or a proof assertion depending on whether the shadow is ghost-only. This is an inference because the paper's language is a core imperative language and CHCs, not Verus.

Evidence and limits. The paper states that "The operators described in this paper, i.e. square, universal quantification, maximum, and sum, have been verified in the verification tool Frama-C [14]." and that the verified versions "are adaptations for the C language semantics and execution model", assuming C native arrays rather than functional ones (end of section 4.2, p. 17). The contribution list claims "machine-checked proofs of the correctness of the instrumentation operators for quantifiers ∀ and the extended quantifier \max" (section 1, p. 5), a narrower claim than the p. 17 sentence; the paper does not reconcile the two. Paper-and-pencil proofs are given in Appendices D–F (Lemmas 2–4). Soundness does not make every instrumentation verifiable: a wrong selection of statements may yield an instrumented program that cannot be verified (section 1, p. 4). Inference: a missed write is exposed by a guard only when the tracked shadow or interval is subsequently used (for example the `assert(x == x_shad)` in R2–R4, or `assert(qu_ar == a)` in Figure 4).

## technique 2: counterexample-guided instrumentation search

What it is. Because an operator leaves statement choices nondeterministic, the paper searches the finite space of candidate rewritings. Algorithm 1 starts with a candidate instrumentation, asks a verifier whether the instrumented program is correct, and refines the candidate set using counterexamples. For each failing candidate, it removes candidates that make the same rewrite decisions on the statements occurring in the counterexample, then tries another candidate. A successful candidate proves the original program by operator soundness. The paper says: "We propose a counterexample-guided algorithm for this purpose, which starts from some arbitrarily chosen instrumentation, checks whether the instrumented program can be verified, and otherwise attempts to fix the instrumentation using a refinement loop." (section 1, p. 4).

Steps. (1) Take the set `Cand` of all candidate rewrite choices, one per control point `p` from its applicable rules plus "not modified" (⊥); the paper says this set can be exponentially big and "should be represented symbolically (using BDDs, or using an SMT solver managing the set of blocking constraints from line 13)" (section 3, p. 11). (2) Pick a candidate and instrument the program with it. (3) Ask the oracle `IsCorrect`, which "could be approximated, for instance, using a software model checker" and may ignore the complex functions being eliminated (section 3, p. 10). (4) If it proves the instrumented program correct, return that candidate. (5) If the counterexample ends in a failing assertion that also exists in the original program, return `Incorrect`. (6) Otherwise the instrumentation may have been wrong: remove from `Cand` every candidate that agrees with the picked one on the instrumentation of the statements occurring in the counterexample (line 13). (7) Repeat until one of those returns, or `Cand` is empty and the algorithm returns `Inconclusive`. The paper notes that the loop terminates because the space is finite and each iteration eliminates at least one candidate (section 3, p. 11). In the implementation the check in line 5 can time out and be attempted again later, so the number of steps can exceed the size of the search space (section 5.2, p. 19).

Verus form (inference). The verifier call can be a Verus compilation/proof run over generated Rust variants. A generator can toggle ghost updates at candidate program points; failed proof traces or diagnostics provide refinement clues, although Verus does not expose the paper's CHC counterexample format directly. `assert` statements corresponding to original postconditions must be distinguished from instrumentation guards before classifying a counterexample.

Evidence. Lemma 1 (section 3, p. 11; proof in Appendix B) states: if Algorithm 1 returns an instrumentation `r`, then `P_r` and `P` are correct; if it returns `Incorrect`, then `P` is incorrect; and if some `r` makes `P_r` correct, the algorithm returns some `r'` with `P_r'` correct. MonoCera implements the strategy over constrained Horn clauses, by adding the rewrite rules to Eldarica and extending TriCera, "largely following Algorithm 1 but with a few minor changes due to the CHC setting"; the paper says the CHC setting makes the implementation "available to various CHC-based verification tools, for instance JayHorn (Java) [31], Korn (C) [18], RustHorn (Rust) [35], SeaHorn (C/LLVM) [25] and TriCera (C) [19]" (section 5.1, p. 17). To handle complicated access patterns the implementation applies several operators at once and increments their number when Algorithm 1 returns `Inconclusive` (section 5.1, p. 17). Inference: these results assume the oracle answers; with backend timeouts the practical outcome can be no verdict.

## technique 3: interval tracking for universal array quantification

What it is. Operator `Ω∀,P` tracks a contiguous interval of an array on which predicate `P` holds universally. Ghosts `qu_lo`, `qu_hi`, `qu_ar`, and Boolean `qu_P` represent the interval, array snapshot, and truth value. On a store, the operator resets tracking to the one-element interval `[i, i+1)` when the tracked interval is empty, when the write is far outside it (not adjacent), or when the write may overwrite the sole false element; otherwise it conjoins the new predicate value and extends the interval if the write is adjacent. A quantified expression checks that its range lies inside the tracked interval when `qu_P` is true, or contains the tracked interval when `qu_P` is false, then returns `qu_P` (Figure 4, p. 13). The invariant is `qu_lo = qu_hi ∨ (qu_lo < qu_hi ∧ qu_P = forall(qu_ar, qu_lo, qu_hi, λ(x,i).P))`.

Steps. (1) Initialize an empty interval and `qu_P=true`. (2) Rewrite each `store(a,i,x)`; if the interval is empty, the write is far outside it (not adjacent), or the write may overwrite the only false point, reset to `[i,i+1)` with value `P(x,i)`. (3) Otherwise assert the ghost snapshot equals the old array, update `qu_P` with `P(x,i)`, and extend the interval for an adjacent write. (4) Rewrite `select` similarly, without resetting for reads inside the interval. (5) Rewrite `b=forall(a,l,u,P)`; return true for an empty range, else assert the range relation and assign `b=qu_P`. (6) Prove invariant preservation for each rule. The paper explains: "If qu_P is true, then it is sufficient that quantification occurs over a sub-interval of the tracked interval, and vice versa if qu_P is false." (section 4.1, p. 14).

Verus form (inference). Represent the interval bounds and snapshot as ghost state, use a sequence or map model of the array, and prove a quantified predicate over the interval with `forall` specifications. A loop `invariant` can maintain the interval relation; stores need lemmas for snapshot equality and range extension. Verus's specification quantifiers differ from the paper's `forall` expression, so the generated ghost proof is an adaptation.

Evidence and limits. The authors prove `Ω∀,P` is an instrumentation operator (Lemma 2, section 4.1). It tracks one contiguous range; the paper notes that one could instead track several ranges (section 4.1, p. 14), and the implementation can apply several operators at once (section 5.1, p. 17). It assumes programs in a normal form where `store`, `select` and `forall` occur only in simple assignments (section 4.1, p. 12), and its assertions fail when the tracked array differs from the one accessed.

## technique 4: cancellative aggregation tracking

The aggregation framework models a finite array slice with a monoid homomorphism. Maximum uses the monoid over extended integers with `max`; sum uses `(Z,+,0)`. For `Ωsum`, ghosts `ag_lo`, `ag_hi`, `ag_sum`, and `ag_ar` track a slice and its sum. A store into an empty tracked interval or far outside it (neither inside nor adjacent) resets tracking to the single stored element. A store inside subtracts the old value from `ag_sum` before adding the new value; adjacent stores extend bounds. A sum expression asserts exact array and bound equality, then returns `ag_sum` (Figure 5, p. 16). The paper states: "Since \sum is cancellative, when storing inside of the tracked interval, the previous value at the index being written to is first subtracted from the sum, before adding the new value, ensuring that the correct aggregate value is computed." (section 4.2, p. 16).

Steps. (1) Choose a monoid and homomorphism for the aggregation. (2) Initialize an empty interval. (3) Rewrite stores with reset, subtract-old/add-new, or adjacent-extension branches. (4) Update the array snapshot. (5) Rewrite aggregate reads with exact range and snapshot assertions. (6) Prove `ag_lo=ag_hi` or `ag_sum=sum(ag_ar,ag_lo,ag_hi)`. Maximum additionally tracks an index `ag_max_idx` where the maximum is stored, "in order to not have to reset tracking on every store inside of the tracked interval" (section 4.2, p. 15; full definition in Appendix E, Figure 7). Unlike sum, a store that overwrites the previous maximum with a smaller value resets tracking (Figure 7).

Verus form (inference). A `Seq<int>` ghost model and a `spec fn` sum can express the homomorphism; proof lemmas establish replacement as `old_sum - old_value + new_value`. Loop invariants maintain bounds and snapshot equality. Maximum needs a ghost index and a lemma connecting it to the slice maximum. These are inferred mappings; the paper verifies C/CHC operators, not Rust.

Evidence and limits. The paper's test suite has 117 programs from the SV-COMP repository plus 26 crafted by the authors (min: 6, max: 8, sum: 9, forall: 3); tests were run on a Linux machine with an AMD Opteron 2220 SE at 2.8 GHz and 6 GB RAM with a timeout of 300 seconds, against CPAchecker 2.1.1 (k-induction), SeaHorn 10.0.0 (default settings) and TriCera 0.2 (section 5.2, p. 18). For each SV-COMP program the authors created one benchmark per possible rewriting using a quantifier or aggregation, and for other tools they used the original loop versions. Table 3 reports 96 `forall` tests, of which MonoCera verified 30; it verified 16/26 `sum`, 8/12 `max`, and 9/17 `min` tests. For the SV-COMP subset, MonoCera verified 42 programs, while CPAchecker verified 1 and SeaHorn and TriCera 0; on crafted arrays of size 100 or unbounded, only MonoCera succeeded (section 5.2, p. 18). The denominator is the number of tests in each operator row; the rows sum to 151 tests (17+12+26+96), not 143, because one program can yield several rewritings. Table 3 also gives MonoCera's average verification time per row (33 s to 91 s). The table's "Inst. space" is the number of instrumentations producible and "Inst. steps" the number of iterations of the Algorithm 1 loop; retries after timeouts can make steps exceed space (section 5.2, pp. 18–19).

## trust, reuse, and product implications

The proved object is the instrumentation operator's conditions (Definition 1) and, from them, soundness and weak completeness (Theorem 1), plus backend verification of each instrumented program. Inference: trusted components therefore include the verifier, the CHC translation, the Frama-C adaptation used for operator proofs, and the correctness of the rewrite implementation; the paper does not state this list. The paper does not mention Verus, and its only Rust connection is that CHC-based tools such as RustHorn could use the implementation (section 5.1, p. 17); it does not prove anything about a Rust or Verus translation. The paper implements and evaluates only the quantifier and aggregation operators (section 5.1, p. 17); square tracking for non-linear arithmetic is a worked example, and "non-linear arithmetic" appears among planned future operators (section 7, p. 20). Inference: VL should check whether Verus's sequence, map, and quantifier support can host such invariants before reimplementing these ideas. Inference: for agent-written verified Rust, interval and sum instrumentation could reduce proof burden, but generated rewrites introduce a serious threat if a missed mutation is not guarded or if the source-to-ghost transformation is trusted outside Verus. The operator invariant and original-assertion distinction are therefore the key safety boundary.

## techniques for the catalog

- sound instrumentation operators: rewrite difficult expressions with ghost state, guards, and a proved invariant
- counterexample-guided instrumentation search: refine candidate rewrite choices using verifier counterexamples
- universal interval tracking: maintain a contiguous array range and answer forall queries with range assertions
- cancellative aggregation tracking: update sums by subtracting replaced values and adding new values
