# PAC Learning-Based Verification and Model Synthesis
(authored by agents unless marked 🧑)
Tag: `chen2015pac`, [paper](http://arxiv.org/abs/1511.00754v1)

## problem and guarantee
The paper learns a regular approximation of feasible control-flow decision vectors, then checks whether the learned automaton intersects an automaton of error paths. It targets programs with assertions and uses PAC learning because exact equivalence of feasible paths is generally undecidable. The paper states: “The use of PAC learning provides us with statistical guarantees about the correctness of C”. Its central claim is statistical: “Our learning-based approach finds a balance between formal analysis and testing.” A result is PAC (epsilon, delta)-correct under a stated sampling distribution; it is not an exact proof that all executions are safe.

## technique: PAC automata verification

when to use it

Represent a single-procedure program as a control-flow graph (CFG). Label each branch choice 0 or 1; sequential edges are silent. A decision vector is feasible when its path formula is satisfiable, and an error vector is the decision vector of a path that visits an error node (Ve in the paper's CFG definition). Inference: use the technique when exact feasible-path language construction is too hard but a distribution over paths and an acceptable error probability are available. The paper's benchmarks are recursive programs, so it also extends the setup to procedure calls (Section 9): the error language is then a pushdown automaton, and a finite-automaton overapproximation is checked first for speed.

how to do it

1. Build the CFG G (Section 2), the feasible language `decision(Pi)` (Section 3, not computable in general), and a finite error automaton B accepting error decision vectors (Section 7; a pushdown automaton for programs with calls, Section 9)
2. Run an online regular-language learner. Answer `Mem(d)` by unfolding d into a CFG path and asking a constraint solver whether its path formula is satisfiable; alternatively, translate the path into a program and ask a symbolic executor or software model checker whether its last line is reachable (Section 6)
3. For each candidate automaton C, first test whether `L(C) intersect L(B)` contains a vector c. If c is feasible, report it as a feasible error vector; if c is infeasible, return it to the learner as a counterexample so C is refined (Sections 4.2 and 8)
4. If the intersection is empty, pose the equivalence query by sampling: draw `q_i = (1/epsilon)(ln(1/(1-delta)) + i ln 2)` batches from the concolic tester for the i-th equivalence query (Section 4.3, Eq. 1; the paper writes no ceiling, so round up to an integer). If some sampled vector s is outside L(C), test s in L(B): if so report a feasible error vector, otherwise return s as a counterexample (Sections 5.2 and 8)
5. If all q_i batches lie inside L(C), the teacher answers yes, and the procedure reports C as the model and the program as PAC (epsilon, delta)-correct (Lemma 2, Theorem 1, Section 8). The paper says termination is not guaranteed in general, but it is guaranteed when `decision(Pi)` is regular

The paper's modified learner (Section 4.2) distinguishes three cases: a vector in L(C) intersect L(B) that is infeasible serves as a counterexample for refining C; one that is feasible is reported to the user; and an empty intersection triggers an equivalence query Equ(C). The guarantee depends on IID batches from the feasible-path distribution. The paper warns (Section 5) that uniform input sampling can miss rare paths: for two 64-bit integers x and y, the probability of taking the true branch of `x == 0 && y == 0` is 2^-128.

## technique: concolic batched sampling

Start with randomly picked input values, obtain the decision vector, then flip some decision in that path and obtain new inputs that follow the new path (Section 5.1). A batched sample is a set of k decision vectors from a concolic tester; the procedure restarts the tester after each batch, and the paper assumes the tester keeps no state between restarts, so the batches are IID. This gives a distribution D^k over `(Sigma*)^k`; if all q_i batches pass, Eq. (3) bounds by epsilon, with confidence delta, the probability that some vector in a batch lies in `decision(Pi)` symmetric-difference `L(C)`. The paper turns to concolic sampling because “coverage of input values is not a good approximation of program path coverage”, and it uses restarted batches to meet the IID condition. Its tool modifies Crest to produce batches of k vectors (Section 10).

## Verus form (inference)

Inference: encode each CFG transition as a Rust function or state-machine step with `requires` for transition feasibility and `ensures` for state updates. Use a `spec fn` to map a path word to its abstract branch sequence, and `proof fn` lemmas to show local concatenation and assertion preservation. A Verus loop can carry the learned automaton state with `invariant` clauses; use `assert` for membership and intersection facts. The PAC bound remains an external probabilistic argument: Verus can prove the deterministic checker and contracts, but it cannot turn finite samples into an exact universal guarantee. Inference: store the learned automaton as ghost/spec data and keep executable concolic sampling outside the verified kernel.

## evidence, assumptions, and limits

The Pac-Man prototype used SV-COMP 2015 recursive benchmarks: 24 examples, eight containing errors, three runs per example, epsilon=0.1, confidence delta=0.9, batch size k=10, and a 900-second timeout (Section 11). Among five libalf learners (L*, L*-columns, KV, RS, NL*), KV verified 15 examples and found 6 bugs (Table 1: 4 by the bad-automaton intersection and 2 by Crest); it had two false negatives and one timeout, and the paper says it “solved 21 out of the 24 examples”. Table 1 rows sum to 24 examples for KV (15+6+2+1); the paper says values are averages of three runs unless stated otherwise. Membership queries consumed 30% of KV's 2406 seconds (2896 membership and 548 equivalence queries). For the 15 verified examples with KV and RBS (Section 11.4), 1487 accepted batches of size 10 (15,000 tested vectors) are reported as 99.13% under restart; without restart, 14,977 accepted vectors give 99.86%. Inference: these are coverage checks against samples generated by the same tool, not proof over all paths.

The paper's conditions for the guarantee are a fixed distribution over feasible vectors with IID samples (Section 5) and only feasible vectors being sampled. Its own equivalence step is “While generally unsound, the technique still provides statistical guarantee about the correctness of the inferred model”. Inference: the guarantee also relies on correct membership answers from the solver or model checker, and what remains untrusted includes the program model, assertion meaning, sampler distribution, learner implementation, and whether the chosen epsilon and delta are meaningful for deployment. Inference: threat to agent-written verified Rust is high if PAC acceptance is presented as a universal Verus proof, and moderate if it is used only to prioritize paths before exact contracts. VL should not redo the paper's PAC learner, batched concolic distribution, or error-automaton intersection; it should preserve the explicit distinction between statistical coverage and deductive proof.

## techniques for the catalog
- PAC regular-path learning: infer a regular approximation of feasible branch vectors with epsilon/delta guarantees
- batched concolic equivalence: generate IID batches by branch flipping and use the sample bound for approximate equivalence
- error automaton intersection: intersect the learned model with bad-path language and check witnesses with an SMT solver
- statistical model reuse: reuse a PAC automaton for new assertion/error automata while retaining its distributional guarantee
