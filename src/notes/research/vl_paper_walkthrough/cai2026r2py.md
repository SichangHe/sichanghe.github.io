# r2py: AI-Assisted Conversion of R Statistical Packages to Python
(authored by agents unless marked 🧑)
Tag: `cai2026r2py`, [paper](https://arxiv.org/abs/2608.16911)

## scope and result
The paper presents r2py, an orchestrated process for translating an R package into a native Python package while preserving numerical behavior. Its target is a port whose functions, arguments, returned structures, and numerical results match R at declared tolerances. The authors apply it to KernSmooth and rpart. The abstract states: “Translation fails silently where the languages diverge, as in transform normalization, integer width, and argument evaluation.” (Abstract, p. 1.) The two conversions reproduce R across 518 and 846 tests (Abstract, p. 1; Table 1, p. 17). Inference: this is a translation-validation pattern for a Verus port: retain a trusted reference implementation, generate the target, and compare observable behavior, while adding proof obligations for properties that tests cannot cover.

## technique 1: dependency-first decomposition
Inference: Use this when a package has many source files and calls across files. In Methods, one sub-agent processes each R source file, enumerates function definitions (including nested closures), and classifies calls as language, internal, or external compiled-code dependencies. Internal dependencies become a directed acyclic graph; each function receives a level from the longest path from a root, and conversion proceeds deepest level first. The paper reports three levels for KernSmooth and six for rpart; hand checking corrected three rpart call sites before conversion (Methods, “Structural analysis and conversion ordering,” pp. 10–11). The purpose is to make every callee’s signature available before translating callers.

Inference: in Verus, make each Rust module or function’s dependency order explicit, then verify callees before callers. Use `spec fn` for mathematical summaries, `requires` and `ensures` for pre/postconditions, and `proof fn` lemmas to establish the summaries used by callers. Rust ownership and concrete control flow remain; R’s dynamic dispatch and 1-based indexing require an explicit representation and proof of index conversion.

Evidence: the paper says, “Structural analysis must come first, because the dependency graph it recovers (Fig. 2) determines the order in which functions can be translated at all.” (Section 2.1, p. 3.) The audit is human-reviewed, so the graph is not trusted merely because a model emitted it. Assumption: dependencies are sufficiently static to form a DAG; the paper does not describe recursive R definitions.

## technique 2: a complete construct catalog and authoritative guides
Inference: Use this when independent model invocations might make inconsistent language-semantic choices. A second per-file pass records every call site, enclosing function, line number, and complete call expression. CSVs are merged by construct. One agent per unique construct reads source context and documentation and writes a guide containing hazards, all usage patterns, a general strategy, and paired R/Python examples. The catalogs contain 46 constructs at 509 sites for KernSmooth and 172 constructs at 1,298 sites for rpart; 34 constructs overlap (Methods, pp. 11–12).

The paper gives the reason: “Because each agent runs as an independent, stochastic invocation with no memory of decisions taken elsewhere, resolving such questions case by case offers no way of detecting inconsistency short of exhaustive pairwise comparison.” (Section 2.2, p. 4.) Inference: a Verus project should maintain a reviewed mapping for recurring source idioms (for example, R missing values, matrix layout, and error paths) before code generation. Each guide can state the corresponding Verus invariant and the conditions under which it applies. A guide is evidence about intended semantics, not a proof; each translated function still needs executable tests and Verus verification.

## technique 3: structured function artifacts and assembly
Conversion runs one function per invocation in topological order. Each invocation receives the R function, structural JSON, guides, and dependency table, and emits JSON containing imports, a typed Python signature, and body lines. The representation lets a caller read already-converted callee signatures mechanically. The assembly pass fixes relative imports, duplicate imports, and filenames that cannot be Python module names, then parses every assembled module (Methods, pp. 12–13).

The paper records explicit translations: named lists become dictionaries, `missing()` becomes a sentinel tested by identity, S3 class assignment becomes a reserved dictionary key, environments become dictionaries, indices are converted at crossings, and matrices passed to compiled code use column-major order (Methods, p. 12). Inference: in Verus, preserve these boundary conversions as named wrapper functions and prove their shape/index properties. Use `seq`/`Vec` lengths and `requires` bounds, and encode class tags as enums or discriminated structures rather than unproved dynamic dictionaries. The JSON intermediate form is useful for review but is not itself trusted evidence.

## technique 4: layered equivalence verification
The authors apply four checks in sequence: static source comparison, realistic workflow execution, translation of the package’s historical regression tests, and a generated test suite. Static agents compare control flow, errors, and returned structures without executing code. Workflow execution exposes runtime semantic errors. Historical tests are translated and run against captured R references. Generated tests cover positive, negative, and boundary inputs. The paper reports that static audit found defects in every subsystem; realistic workflows exposed roughly 16 further issues; historical tests found defects in six of 14 rpart scripts; generated tests found additional defects (Section 2.3, p. 5).

Inference: this is directly reusable for Verus ports. Differential tests can validate Rust against the original implementation; Verus proofs should establish local safety and functional contracts; historical regression suites should remain mandatory because generated tests may miss deep states. A Verus form is a postcondition such as `ensures result == reference_spec(input)` where the reference is a mathematical specification, not a runtime call to an unverified function. The paper’s guarantee is bounded: “The layered sequence provides not a guarantee but a succession of independent opportunities for a defect to be caught.” (Section 2.3, p. 5.)

The tests use declared tolerances. KernSmooth assertions range from 10^-10 to 10^-3 and have median 10^-6; rpart ranges from 10^-12 to 10^-4 and has median 10^-7 (Methods, “Test generation and reference comparison,” p. 14; Table 1, p. 17). Two of 846 rpart tests differ because Python cannot reproduce R’s unevaluated call echo; 94 cases reject the same input with different error descriptions (Section 2.3, p. 6). These denominators and settings matter: passing 518 or 846 tests does not prove all inputs or exact error text.

## technique 5: reconstruct only the compiled API boundary
Inference: Use this when compiled code depends on a runtime that the target language does not provide. KernSmooth reaches Fortran through `.Fortran()` and can call retained code with NumPy buffers. rpart reaches C through `.Call()` and expects R `SEXP` objects. The authors statically inventory 235 rpart reference sites over 51 API identifiers, write sequential blueprints, generate one C++ header per item, and assemble a master include. A thread-local arena frees transient objects at wrapper exit; persistent objects are heap allocated and explicitly released. Five C-linkage wrappers translate between `SEXP` internals and plain arrays, catch exceptions, and expose opaque handles for environments and expressions (Methods, pp. 12–13).

The evidence is concrete: 30 of 35 C files needed no modification and five only changed include directives; seven generated-header defects were found. The hardest defect was a namespace-static callback pointer duplicated across translation units and discovered only when a custom split callback ran (Section 2.4, p. 7). Inference: a Verus port should isolate any foreign runtime behind an `external_body` boundary only when that boundary is deliberately trusted and separately tested; verified Rust code should not mark the function under verification as external. Model the boundary’s memory and callback ownership with explicit structs and `requires`/`ensures`, and prove Rust-side marshaling; the foreign runtime remains trusted.

## technique 6: FFI numerical semantics and root-cause instrumentation
For Fortran wrappers, the paper checks that f2py mutates preallocated output arrays, declares scalar outputs with explicit output intent, removes dimension arguments absorbed from array shapes, and allocates two-dimensional arrays in Fortran order. For rpart, cffi ABI mode keeps buffers and views alive for each call (Methods, pp. 13–14). Inference: equivalent Rust FFI requires slice-length and layout preconditions and a proof that no view outlives its owner; Verus can verify the Rust marshaling layer, while native Fortran/C behavior remains an assumption.

When cross-validation differed, the authors compared fixtures byte-for-byte, C sources directly, compiler flags, disassembly, and instrumented per-fold errors, split values, and stopping decisions. Only the minimum-split threshold differed (20 in R, 21 in the port); capturing whether an argument was originally absent fixed it. They also found a real out-of-bounds write in the original C source and deliberately preserved it because a faithful port must reproduce the source (Methods, pp. 15–16). Inference: root-cause instrumentation should precede changing verified Rust; a proof can expose an unsafe source defect, but product policy must decide whether compatibility or repair is intended.

## what is proved, measured, and trusted
Measured evidence is numerical differential agreement under the stated test sets and tolerances, plus build and workflow checks. The retained compiled source is byte-identical, so the authors attribute divergences to the translated layer. Human review of structural graphs, guides, and repairs is trusted. R, Python, compilers, f2py/cffi, captured reference values, and unexercised paths remain trusted assumptions. The paper explicitly says it is not turnkey and studied only two packages without contributed dependencies (Discussion, pp. 7–9). Inference: threat to agent-written verified Rust is high at semantic boundaries (indexing, defaults, layout, callbacks) and lower for locally proved pure functions; differential tests reduce but do not eliminate the threat. VL should reuse the staged artifacts and boundary inventory rather than redo this decomposition, but must add Verus proofs for contracts that the paper tests numerically.

## techniques for the catalog
- dependency graph conversion order: classify calls and translate callees before callers
- construct catalog guides: settle every recurring source construct in a reviewed artifact
- layered differential verification: combine static audit, workflows, historical tests, and generated boundary tests
- foreign-runtime reconstruction: implement only the API symbols actually referenced at the compiled boundary
- FFI root-cause instrumentation: log intermediate values to localize semantic divergence before changing code
