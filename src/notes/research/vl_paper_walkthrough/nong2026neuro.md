# Neuro-Symbolic Proof-of-Vulnerability Generation with Open-Weight Models
(authored by agents unless marked 🧑)
Tag: `nong2026neuro`, [paper](https://doi.org/10.48550/arxiv.2608.04217)

## scope and result
POVGEN generates concrete proof-of-vulnerability inputs for disclosed CVEs when no public trigger exists. It combines vulnerability localization, path-sensitive exploration, fine-tuned open-weight models, and SMT solving. The pipeline has a patch-guided mode and a patch-free mode. The abstract reports 78.98% valid PoVs on 490 ARVO cases, compared with 50.20% for the best fuzzing baseline and 2.45% for KLEE; on 250 real-world CVEs without public PoVs it reports 74.80% valid PoVs and 65.1% in patch-free mode. The paper states: “POVGEN first localizes vulnerability-relevant regions (utilizing patch information if available), then performs path-sensitive reachability analysis, and finally generates PoVs by extracting and solving constraints with LLM-guided reasoning backed by an SMT solver.” (Abstract, p. 1)

## technique 1: on-demand interprocedural slicing and manifestation localization
Use this when a whole-program search is too large and the patch line is only an indirect clue. Build a system-dependence graph from per-function dependence graphs plus interprocedural control/data edges. Start from the patching function when a patch exists, otherwise from program entries. Apply forward and backward slicing, then iteratively ask an open-weight model which context functions are semantically needed and expand the slice. The training algorithm performs `ConstructSDG`, `GetPatchLocation`, `InitialSlice`, repeated `QueryLLMForContext`/`ExpandSlice`, and fine-tuning on slices, patches, and manifestation points. The expansion threshold is three rounds based on InterPVD and ARVO statistics. During generation, run the same slicing and feed each slice to the Manifestation Localization Model (MLM), which outputs a vulnerable statement or `None` for irrelevant slices.

The paper states: “The goal of slicing here is to construct a compact yet semantically sufficient context for manifestation localization.” (Sect. III-B1, p. 4) Negative slices train the MLM to reject contexts without a manifestation point; if no slice contains it, a patch-to-manifestation slice is added. The patch-guided path target is Entry → Patch → Manifestation; patch-free mode targets Entry → Manifestation.

Inference: In Verus, the slice itself can be an audited input to a proof task, but LLM-selected context must be checked against a source-level dependency graph. A `spec fn` can define node reachability and a proof function can establish that every retained path is a real call/return path; model localization remains heuristic evidence.

## technique 2: generate structured constraint-training data
Use this when general LLMs hallucinate formulas or malformed inputs. For each training program, mark input variables symbolic, run traditional symbolic execution, optimize raw constraints, and solve them with an SMT solver. Fine-tune a Constraints Extraction Model (CEM) on `(path, optimized constraints)` and a Constraints Solving Model (CSM) on `(constraints, PoV)` pairs. Augment benchmark data with templates for symbolic loop bounds, pointer dereference, nested loops/arrays, and pointer arithmetic with symbolic offsets. Optimize constraints by constant folding, algebraic simplification, logical simplification, and canonical reordering. The paper states: “The CEM learns to derive SMT constraints from given paths, mapping program semantics to logical formulas.” (Sect. III-B2, p. 5)

Inference: For Verus, generated constraints should become explicit preconditions and postconditions checked by the verifier; an SMT-produced input should be replayed through the verified Rust implementation. CEM output is a proposal until parsed and proved equivalent to path predicates.

## technique 3: anchored random-walk path exploration
Use this when enumerating all interprocedural paths causes path explosion. Construct an interprocedural control-flow graph (ICFG), including function CFGs, resolved call edges, and matching return edges. Run backward BFS from the manifestation point and, in patch-guided mode, the patch location to compute shortest distances. Starting at the program entry, perform repeated forward random walks. At each branch choose a successor with weight `1/(d+1)`, where `d` is its distance to the current anchor; switch the anchor from patch to manifestation after reaching the patch. Maintain a call stack so a return edge is legal only when its identifier matches the top frame. Stop at the target, a step/restart limit, or no valid successor. Repeat with different seeds and retain up to 200 candidate paths in parallel. The paper states: “This keeps the walk biased toward the anchor while retaining diversity.” (Sect. III-D2, p. 6)

Inference: In Verus, candidate paths can be represented as ghost traces with a proof that each edge is valid and calls/returns are stack-consistent. Randomness and distance weighting are outside the proof; verify the selected trace before using it for a contract.

## technique 4: neuro-symbolic PoV generation with solver fallback
For each candidate path, prompt CEM with the path, vulnerability description, and optional patch to extract constraints. Prompt CSM with the same context and constraints to generate a Python script that constructs the PoV. Validate the script/output; when CSM fails, pass the constraints to an SMT solver and use its satisfying assignment. Generating a script avoids ambiguity in raw bytes, escape sequences, and binary fields. The paper states: “To improve robustness, POVGEN incorporates an SMT solver as a fallback.” (Sect. III-D3, p. 6)

The resulting artifact is executed against the vulnerable program and checked for the expected sanitizer or failure condition. Patch validation compares the generated PoV on vulnerable and patched versions. The authors report six flawed patches in disclosed CVEs, all later fixed, and five previously unreported vulnerabilities, four confirmed and fixed by maintainers.

## evidence, ablations, and limits
Table I’s denominator is 490 ARVO vulnerabilities: POVGEN succeeds on 78.98% with patches and 65.10% without; LibFuzzer reaches 50.20%, AFL++ 40.61%, AFLGo 44.49%, and KLEE 2.45%. Table VII’s denominator is 250 real-world CVEs lacking public PoVs: 74.80% valid PoVs overall. Removing SMT lowers ARVO success from 78.98% to 76.53%; removing simplification lowers it to 74.29%; removing both simplification and augmentation gives 72.45%; removing manifestation localization gives 64.29%. The fine-tuned CEM obtains 89.63% semantic recall versus 57.04% for its base Llama model and 86.14% for Claude-Sonnet-4 on the reported 52-sample comparison. The paper states: “POVGEN requires an average of 98.21 minutes to reproduce a vulnerability, most of it in Step 2 (Path-Sensitive Reachability Exploration, 75.71 min) and Step 3 (Neuro-Symbolic PoV Generation, 21.89 min).” (Sect. V-E, p. 9)

Only Step 1 incurs API cost, averaging $0.04 per sample for GLM-5.2; local CEM/CSM inference has no per-sample API charge. The PJSIP motivating example analyzes 106.8k source lines and averages 4.57M tokens across explored paths. Limitations include dependence on source/build tooling, imperfect static ICFGs, localization errors, and SMT models that omit libraries or environment behavior. KLEE’s low rate reflects whole-program path explosion, while the paper’s model outputs are not proofs of semantic equivalence.

Proved or mechanically checked: the study’s SMT satisfiability checks, path execution artifacts, and source-tree validation of model-selected context. Trusted: Joern/SySeVR slicing, SVF ICFG construction, KLEE/Z3, model behavior, generated scripts, sanitizer observations, and benchmark labels. Inference: The threat to agent-written verified Rust is substantial when an LLM-generated constraint or input is accepted without replay in the verified implementation; POVGEN’s staged narrowing and solver fallback are useful as a test-generation front end, not as a substitute for Verus proofs. VL should reuse the decomposition into localization, valid path traces, and contract-checked input synthesis.

## techniques for the catalog
- manifestation slicing: iteratively expand dependency slices from patches or entries and localize the vulnerable statement
- constraint-data specialization: generate optimized symbolic constraints and solver inputs to fine-tune extraction and solving models
- anchored random walks: bias ICFG exploration by backward-BFS distances while preserving path diversity and call-stack validity
- solver-backed PoV synthesis: use CEM/CSM to produce an executable input generator and SMT as a validated fallback
- patch differential validation: execute a generated PoV on vulnerable and patched revisions to expose incomplete fixes
