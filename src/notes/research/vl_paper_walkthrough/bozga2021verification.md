# Verification of Component-based Systems with Recursive Architectures
(authored by agents unless marked 🧑)
Tag: `bozga2021verification`, [paper](http://arxiv.org/abs/2112.08292v1)

## problem and model

Bozga, Iosif, and Sifakis define Configuration Logic (CL) for distributed systems with finitely many component types but an unbounded number of instances and recursive architectures. A configuration contains component local states and interactions; finite-state component machines provide behavior. The running token-ring rules define a chain recursively, then close its ends with a transfer connector. “We study a sound verification method for parametric component-based systems.” (abstract, p. 1). The method targets universal safety questions such as deadlock freedom and critical-section exclusion across every architecture size generated by the CL definitions.

Inference: this is a useful abstraction for VL when Rust components are replicated or recursively composed. It verifies a family through an invariant schema instead of checking one concrete deployment, but it does not produce executable Rust or prove implementation-level memory behavior.

## technique: Configuration Logic and recursive architecture definitions

What it is. CL uses predicate symbols and inductive rewriting rules. A rule composes disjoint resources with the commutative connective `*`; existential variables connect ports and component instances. The token-ring example has `Ring()`, `Chain(x1,x2)`, and `Comp(x)` rules. Base and inductive chain rules represent every finite chain of length at least two.

When to use it. Use CL when architecture size is unknown and the topology follows recursive patterns such as chains, rings, trees, or nested components.

How to do it.
1. Declare each component type and finite-state local states (section 1.1, pp. 2–3).
2. Define a base architecture rule and an inductive rule that adds one component and connector to a smaller predicate instance.
3. Compose the recursive predicate with additional connectors to close the architecture (the `Ring` rule).
4. Supply a behavior map assigning each component type to a finite-state machine and a CL sentence for initial configurations.
5. Keep `*` operands disjoint; the paper explains that this prevents two component declarations from denoting the same instance (p. 3).

Verus form. Inference: represent a component instance as a Rust struct and recursive architecture as an inductive ghost predicate over an owned tree or sequence of indices. Use `spec fn` predicates for topology and local-state ownership, and `requires`/`ensures` on transitions. A Verus proof can show disjoint ownership and local invariants for one encoded family, but CL's unbounded recursive interpretation and automatic rewriting-tree generation would need an external model or manually supplied induction lemmas.

Evidence and limits. The paper's formal semantics and examples establish the encoding; there is no product-scale benchmark in this article. The later undecidability theorem means no complete decision procedure exists for the target class.

## technique: rewriting trees and canonical models

What it is. Expanding each predicate atom by one rule yields a finite rewriting tree. The tree records architecture shape up to permutations of component indices. A canonical model maps each tree node to a concrete component/interaction and initial local state.

How to do it.
1. Start at the CL sentence's root predicate.
2. Repeatedly replace predicate atoms with one of their defining rules until only component and interaction atoms remain (section 5, pp. 17–21).
3. Record variable substitutions introduced by existential binders along each tree path.
4. Construct the canonical model from the fully expanded tree and mark initial states according to the rule labels.
5. Use the tree as the finite index structure for subsequent automata and MSO formulas.

The paper says, “These rewriting trees describe architectures, up to a permutation of the indices of components of each type.” (section 1.2, p. 5).

Verus form. Inference: use a ghost tree datatype and prove by structural induction that each node's component index is unique and every connector endpoint is present. Verus has no built-in rewriting-tree or canonical-model engine; these artifacts must be represented and proved in Rust ghost code or generated externally.

Evidence and limits. Canonicalization supports soundness modulo index permutation, but the paper's decision procedures remain semi-algorithms because the architecture family can be undecidable.

## technique: path automata and flow formulas

What it is. A path automaton traverses a rewriting tree while tracking where an existential variable is introduced and where it is instantiated in a component atom. From the automaton and interaction profiles, the method synthesizes an MSO flow formula `Φ(Y,Z,R)` describing one operational transition's pre-set and post-set.

How to do it.
1. Build the rewriting tree and label each node with its rule.
2. For each variable, track binder introduction and subsequent substitutions down the tree using a path automaton (section 1.2, p. 5; section 6.2–6.3, pp. 31–35).
3. Encode component-state sets as second-order variables and interactions as relations.
4. Generate a flow formula relating pre-state tuple `Y` and post-state tuple `Z` for every enabled interaction.
5. Use the formula as the transition relation in all later invariant and error queries.

Verus form. Inference: define a ghost transition relation over sets or maps of component states and prove that each executable Rust step implies `Φ`. Quantifier-heavy MSO automation is outside ordinary Verus usage; export the relation to an external solver and import only checked lemmas or finite certificates.

Evidence and limits. Lemma 10 and the surrounding construction establish correspondence between `Φ` and Petri-net transitions (section 6.4, pp. 36–37). The approach assumes the component behavior is a finite-state map and the architecture's interaction profile is faithfully encoded.

## technique: structural trap and mutex invariants

What it is. Each unfolding induces a marked Petri net. Instead of iterating abstract interpretation to a fixpoint, the paper synthesizes structural invariants directly: a trap set must remain marked, and a mutex set must remain marked exactly once. Their intersections over-approximate all reachable markings.

How to do it.
1. Derive the initial marking `Init(Y,R)` from the tree's component-state labels (figure 10, p. 40).
2. Define `θ(X,R)` to express that `X` is a trap: every flow transition entering from `X` also leaves into `X`.
3. Define `Θ(X,Y,R)` as the conjunction of the initial marking and all trap constraints reachable from initial trap seed `Y`.
4. Define `ω(X,R)` analogously for mutexes, preserving both emptiness and singleton cardinality.
5. Define `Ω(X,Y,R)` and use `Θ ∧ Ω` as the inductive over-approximation (section 6.5, pp. 38–41).

The paper defines a trap as a set whose initial intersection is nonempty and whose marked input to every transition implies a marked output; a mutex starts with exactly one mark and preserves at most one (definition 11, p. 39). “By substituting the reachable set with the intersection of the trap and mutex invariant, we obtain the following sufficient queries” (section 6.5, p. 39).

Verus form. Inference: encode a trap as a ghost predicate over a `Map<ComponentId,State>` and prove preservation for every Rust transition; encode a mutex as a uniqueness lemma. Use `invariant` clauses in loops or transition proofs, and `ensures` on executable transition functions. The paper's universal quantification over all generated trees still requires an induction principle or external certificate.

Evidence and limits. Lemma 11 proves `Reach ⊆ Θ ∩ Ω`; this is an over-approximation, so it can contain spurious errors. The paper explicitly notes that a satisfiable verification condition “might indicate the presence of a spurious error caused by the over-approximation introduced by the invariant synthesis” (section 1.2, p. 5).

## technique: WSκS verification conditions for deadlock and reachability

What it is. Error sets are encoded in WSκS, a decidable monadic second-order theory over trees. `DeadLock(X,R)` says no transition pre-set is included in marking `X`; `ErrSet` requires enough distinct places for a target tuple of local states. The final query conjoins the error formula, `Θ`, `Ω`, `Init`, and `RewrTree`.

How to do it.
1. Build `RewrTree_Δ(R)` to constrain `R` to a legal rewriting tree.
2. Add `Init(Y,R)`, `Θ(X,Y,R)`, and `Ω(X,Y,R)`.
3. Add `DeadLock(X,R)` for deadlock freedom or `ErrSet⟨q1,…,qn⟩(X)` for forbidden reachability (figure 11, p. 42).
4. Ask a WSκS satisfiability solver for the conjunction.
5. If the conjunction is unsatisfiable, theorem 3 gives a sound negative answer: no deadlock or no target reachability in any generated instance.

Verus form. Inference: prove the same implication with a Rust ghost state machine and an inductive invariant; encode `DeadLock` as a lemma that every non-error marking has an enabled transition. Verus does not decide WSκS or quantify over arbitrary recursive trees, so use external WSκS as a certificate-producing front end and independently verify finite proof obligations where possible.

Evidence and limits. Theorem 3 establishes soundness of unsatisfiability implications (section 6.6, pp. 42–43). WSκS is decidable but non-elementary in general; the paper bounds these formulas by 4EXPTIME by quantifier alternation depth and reports that similar encodings were fast in preliminary experiments, without denominators or timings (p. 43). Satisfiability is not a proof of a real bug because invariants over-approximate reachability.

## what is proved, trusted, and risky for VL

The formal results prove undecidability for general parametric deadlock and critical-section questions, soundness of rewriting-tree semantics, inductiveness of trap/mutex invariants, and soundness of unsatisfiable WSκS verification conditions. Trusted components include the CL-to-tree translation, path automaton, WSκS solver, finite-state behavior abstraction, and the correspondence between Rust code and the abstract component model. Inference: agent-written verified Rust is threatened by abstraction mismatch—Verus may prove a component contract while the recursive deployment topology, connector ownership, or environment assumptions differ. VL should borrow the paper's explicit architecture model, generated transition relation, and over-approximation warning. It should not redo generic structural-invariant synthesis or WSκS encoding without first checking existing Petri-net and parameterized-verification tools.

- recursive configuration logic — define unbounded component architectures with inductive resource rules and disjoint composition
- rewriting trees and canonical models — expand rules into finite architecture trees and canonical indexed configurations
