# Parsel: Algorithmic Reasoning with Language Models by Composing Decompositions
(authored by agents unless marked 🧑)
Tag: `zelikman2022parsel`, [paper](https://arxiv.org/abs/2212.10561)

## scope and result

Zelikman et al. introduce Parsel, an intermediate language and synthesizer for hierarchical program generation. A language model first decomposes a task into natural-language function descriptions; a language model samples implementations of each function; a synthesizer composes candidates and tests combinations against constraints. The paper's core observation is that modular functions let a search reuse implementations instead of regenerating complete programs. “With Parsel, we automatically decompose algorithmic tasks into hierarchical natural language function descriptions and then search over combinations of possible function implementations using tests.” (Abstract, PDF p.1)

Parsel's evaluated validation evidence is executable tests, generated tests, CodeT scores, and benchmark pass rates; the paper's experiments do not run a formal verifier. The paper does sketch a verifier use: Appendix D shows Parsel-to-Lean (Figure A.10), where “the ability to run Lean on proof with no errors/warnings indicates the proof is correct (but is not a guarantee that the proof statement matches our claim in language)”, so each Lean function has an “implicit constraint”. Section 4 adds that Jiang et al.'s sketch-then-prove approach “could be expressed in Parsel by generating each sketch step as a function and using formal verification for each lemma as the Parsel validation step.” (Section 4, PDF p.8; Appendix D, PDF p.17.) Inference: the relevance to verified Rust is that its decomposition and candidate-search structure could organize specification, proof-lemma, and implementation generation, but passing tests do not prove a contract.

## technique 1: the Parsel intermediate language

A Parsel program has lines that are function descriptions, references, or constraints. Descriptions say what a function does in natural language and can include a name and arguments. References tell a model that one function should call another description. Constraints are executable checks; if absent, the framework may generate them. The paper states: “In Parsel, each line contains a function description, a constraint, or a reference to a description.” (Section 2.1, PDF p.2)

Apply it as follows. (1) Write a high-level algorithm sketch. (2) Split it into named functions with signatures and concise behavior descriptions. (3) Add references from parents to children. (4) Add input-output assertions or unit tests for functions whose behavior can be checked locally. (5) Keep descriptions modular so a child implementation can be replaced without editing its parent. In the paper's knapsack example, parsing, per-size dynamic programming, and output formatting are separate functions, and the root composes them.

Inference: in VL, each description could state a Rust function's mathematical postcondition, each constraint could be a Verus `ensures` obligation or proof lemma, and references could become calls between verified modules. The Rust/Verus mapping is not in the paper; the paper's only verifier example is Lean (Appendix D, Appendix Q.1), and it has no ownership model or Rust/Verus semantics.

## technique 2: SCC factoring and sequential synthesis

The dependency graph is split into strongly connected components (SCCs). When there is no recursion, every function is its own SCC and can be implemented in topological post-order. For each function, the synthesizer prompts a code LLM with its description, signature, and child descriptions, samples candidate implementations, and selects one satisfying that function's constraints. The paper says: “By factoring the dependency graph into strongly-connected components (SCCs), we ensure the complexity grows exponentially only with the size of the largest strongly-connected component but not the total number of functions.” (Section 2, PDF p.2)

Steps (Sections 2.3.1–2.3.2, PDF pp.3–4). (1) Build the call graph. (2) Compute SCCs. (3) Process acyclic components from leaves toward the root. (4) For a function, aggregate child signatures and descriptions into the model prompt. (5) Generate several implementations. (6) Run that function's constraints and retain passing candidates. (7) Make parent prompts refer to the selected child interface, not its source details. (8) Continue until the root is implemented.

Recursive SCCs require joint implementation because each function can call another in the same component. The paper searches combinations of candidate implementations for the SCC and tests the resulting group. Inference: a Verus-oriented generator could make an SCC contain mutually recursive proof functions and implementations, then require all `requires`/`ensures` and termination obligations to pass together. Verus's actual termination and recursive-proof syntax must be supplied separately; Parsel does not specify it.

## technique 3: combinatorial mix-and-match search

For each function, generate a set of candidates once, then search minimal combinations instead of sampling complete programs. If function i has candidate set I(fi), the composed space is the Cartesian product; generation cost is roughly linear in candidates while the number of complete programs can grow exponentially. Constraints prune combinations. When all functions have tests and the graph is acyclic, post-order local selection is enough. When only the root has tests, the synthesizer tests complete combinations. For test-less inner functions, the paper adds dependency edges from the test-less child to its parent, so a parent's constraint evaluates the child indirectly.

The paper reports: “Since Parsel will ‘mix-and-match’ function implementations, the number of distinct candidate programs available to test grows exponentially with k, while the generation cost for the components is linear.” (Section 3.1, PDF p.5). Use this when candidate generation is expensive and execution tests are cheap. The paper states the limit: “when few functions have constraints (as in this evaluation) or there are complex recursive dependencies, it could become expensive to exhaustively evaluate all possible programs” (Section 3.1, PDF p.5). Without SCC factoring, the number of implementation sets is O(n^k) for k functions with n implementations each (Section 2.3.2, PDF p.4). Appendix F's solver evaluates a shuffled list of the direct product of implementations until one passes all constraints; Appendix M reports a 0.04 second timeout per solution and at most 100,000 implementations evaluated per generated Parsel program.

Inference: VL could mix implementation candidates with proof candidates, retaining only combinations whose Verus verification succeeds. A proof obligation should be a hard constraint, while tests can be a cheap pre-filter. This is a proposed adaptation, not a Parsel result, and it must preserve soundness by never treating a passing test as a proof.

## technique 4: automatic test generation and constraint propagation

If a top-level function has no tests, Parsel asks a language model to generate tests and selects the implementation with the highest CodeT score. For inner functions, the dependency approach lets parent constraints validate them indirectly. Generated tests are treated as potentially incorrect: the paper says, “For generated tests, we select the best implementation based on CodeT score [11], as some generated tests could be incorrect.” (Section 2.3.2, PDF p.4)

Steps. (1) Detect missing constraints. (2) For an inner function, add a dependency edge to a constrained parent. (3) For an unconstrained root, prompt for tests. (4) Run all candidate implementations on the tests. (5) Rank candidates by CodeT score. (6) Retain the best candidate and continue composition. Inference: this improves search but leaves underspecification and incorrect generated tests as failure modes. In the HumanEval runs the tests came from prompting GPT-4 for assert-based tests and set-aggregating 100 completions (Appendix S.1, PDF p.55).

Inference: use this in VL only as a triage stage before Verus; generated examples can suggest lemmas or counterexamples but cannot discharge `ensures`. A robust system would ask Verus to prove each generated property and record the property as trusted only after proof checking.

## technique 5: evidence from benchmark evaluation

On APPS competition problems, the authors translate generated high-level plans into Parsel, sample n Parsel programs and k implementations per function, and report pass@n×k against direct Codex and AlphaCode generation. The paper reports an increase from 14.5% to 25.5% in its stated comparison (Section 3.1, PDF p.5). On HumanEval, GPT-4 plus Parsel reaches 85.1% pass@1 with generated tests; the procedure sampled until three Parsel programs had an implementation pass one generated test, then selected the candidate passing the most tests. It averaged 3.5 Parsel programs per problem with eight implementations each, fewer than 32 complete implementations on average. Without filtering, up to eight Parsel programs achieved 91.5% pass@any, while 64 direct programs achieved 82.3%; with 128 direct programs versus 16×8 Parsel, rates were 84.1% and 93.9% respectively (Figure 5, PDF p.6).

The ablation tests whether the plan alone explains the gain: translating the same plans directly to Python dropped pass@8×16 from 25.5% to 6% on 100 randomly sampled APPS problems, and the problems it solved were a strict subset of those Parsel solved. The paper concludes “the step-by-step decomposition provided by the high-level plan is not by itself responsible for the observed improvements by Parsel” (Section 3.1, PDF p.5); the 25.5% comes from the full pipeline and the 6% from a 100-problem subset, so the two numbers are not on identical problem sets. The human-expert study solved 5/10 problems in six hours; GPT-3-generated Parsel solved 2/10 with eight attempts per problem. The authors identify decomposition generation as the bottleneck. These are benchmark results with denominators and sampling budgets; they do not measure proof success, specification accuracy, or Rust safety.

## what is proved, measured, and trusted

Measured: executable benchmark pass rates, sampled candidates, evaluation counts, and a robotic-plan human comparison (two Prolific surveys, 20 participants each ranking five questions, 100 rankings per survey; Parsel plans were judged more accurate than the baseline in 69% of comparisons; Section 3.2, PDF p.7-8). The robotic executability check is itself a Parsel constraint, which the paper notes explains the higher executability (Appendix O.2). Trusted (Inference): model-generated decompositions, function descriptions, candidate code, generated tests, test harnesses, and the benchmark's oracle. The paper includes a 21-function Lisp interpreter as a larger synthesis example (Section 5, Appendix H) with test constraints and no formal semantic proof. Its reported failure cases: for decimal_to_binary, generated Parsel often relied on statefulness (an integer cannot be mutated); for decode_cyclic, GPT-4 alone solved it but its solutions match Chen et al.'s Figure 2 (not the dataset's canonical solution) with minor comment differences, which the authors say indicates possible contamination (Section 3.1, PDF p.6). A 2.7B CodeGen model solved no problems (Section 5).

Inference: for agent-written verified Rust, Parsel mainly affects productivity rather than proof soundness directly. It may increase the number of candidate implementations and expose compositional proof opportunities, but it can also produce plausible code that passes weak tests while violating ownership, termination, or security contracts. VL probably should not redo generic LLM decomposition and test-search benchmarks, since the paper's APPS and HumanEval results already show benefit on Python tasks (not verified Rust). A focused experiment would compare Parsel-style decomposition plus Verus checking against direct verified-code generation, counting proved contracts, failed obligations, repair time, and specification errors.

## techniques for the catalog

- hierarchical function decomposition — express an algorithm as named descriptions, references, and local constraints
- SCC-aware synthesis — process acyclic functions in post-order and jointly search recursive components
- combinatorial implementation search — mix candidate implementations across functions and test minimal combinations
- dependency-based constraint propagation — validate unconstrained children through constrained parents
- generated-test ranking — use model-generated tests and CodeT scores to choose candidates when specifications are absent
