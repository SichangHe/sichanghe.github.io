## purpose and result
SLEAN is a deterministic, file-driven workflow that sends the same debugging inputs to multiple LLM providers, cross-critiques their outputs, and asks an arbitrator to produce a final fix list. The paper's abstract says: “The three-phase protocol formed by independent analysis, cross-critique, and arbitration, filters harmful AI-generated code suggestions before production deployment.” (Abstract, p. 1). It is an orchestration and auditability technique, not a formal verifier. The case study uses 15 deliberately buggy, autogenerated software codebases and 69 proposed fixes; 22 were accepted (31.9%, 95% CI 20.9–42.9%) and 47 rejected (Abstract, p. 1; Case Study Methods, p. 6). The paper has no single-model baseline, so it does not show that the three-phase workflow beats one model alone (Inference).

## technique 1: deterministic three-phase ensemble
Inference: Use this when several models should inspect the same evidence while preserving independent reasoning and a complete audit trail. The paper's phases are:

1. Phase 1 sends the same task description and corpus to each provider, with no provider seeing a peer's output; each audit is saved verbatim (Background, pp. 1–2; Methodology and System Design, p. 5).
2. Phase 2 gives each provider the original inputs, its own Phase 1 audit, and the peer audit; each writes a consolidated assessment listing agreement, disagreement, and proposed changes (Background, p. 2; Methodology and System Design, p. 5).
3. Phase 3 gives an arbitrating provider the original inputs, both audits, and both consolidations; it emits the definitive synthesis with accepted and rejected fixes, reasons, and attribution (Background, p. 2; Methodology and System Design, p. 5). The Methodology section adds that attribution and confidence “follow the prompt template and are not enforced by program logic” (p. 5).
4. Preserve all five outputs in a versioned results directory: two audits, two consolidations, and definitive fixes (Methodology and System Design, p. 5).

The paper states: “Providers never communicate directly; all interaction flows through the orchestrator with fixed prompts, which prevents early convergence and captures the provenance of every claim.” (Background, p. 2). Inference: a Verus implementation can prove workflow-state transitions with an enum and `requires`/`ensures`, such as requiring Phase 2 only after both Phase 1 artifacts exist and Phase 3 only after all four prior artifacts exist. Verus can check hashes, file indices, and nonempty artifact invariants; it cannot prove an LLM's semantic analysis.

## technique 2: bounded corpus ingestion and provider abstraction
Inference: Use this when source code and logs must be distributed reproducibly across providers with different context limits. The implementation scans supported extensions recursively, sorts files stably, decodes UTF-8 with a recovery path, and joins files with filename delimiters (Methodology and System Design, p. 5). Prompt management checks that the prompt directory exists and that referenced templates are nonempty (p. 5).

The token manager estimates tokens from character counts, applies provider-specific limits with a 75% safety margin, segments at file boundaries, and truncates one oversized file at line boundaries with explicit elision markers (p. 5). The abstract provider class requires explicit `temperature` and `max_tokens`, while a common request wrapper performs exponential backoff and bounded retries; provider clients normalize endpoint/authentication differences (p. 5).

In the experiment, OpenAI gpt-3.5-turbo and Anthropic claude-sonnet-4-20250514 used temperature 0.1; max tokens were 3,000 and 4,000, respectively. OpenAI's context limit was 16,000 tokens and Anthropic's 200,000; the 75% margins preceded automatic chunking, which was applied only in Phase 1 (Case Study Methods, p. 6). The final arbitrator was configured as OpenAI with the same settings as the first provider (p. 6), although the analysis section also calls the arbitrator “also AI B” (p. 7); the paper does not reconcile the two statements. Inference: represent the corpus manifest, chunk boundaries, retry count, and configuration as Rust structs and prove bounds and stable ordering in Verus. Network calls, model behavior, and tokenization remain trusted external effects; do not mark a provider call `external_body` when the function itself is the subject of verification.

## technique 3: prompt contracts and rejection quality criteria
Inference: Use this when arbitration should reject plausible but harmful patches. Phase 1's template requires an executive summary, root cause, prioritized fixes with exact snippets, implementation strategy, and testing recommendations. Phase 2 asks for technical accuracy, investigation depth, fix quality, and evidence-strength checks. Phase 3 performs contradiction detection and peer validation using five quality criteria for accepting a fix: technically sound, peer validated, non-conflicting, minimal impact, and evidence-backed, with explicit rejection criteria (Case Study Methods, pp. 6–7).

The arbitrator classifies every proposition as accepted or rejected. Acceptance is computed as `(accepted fixes / total propositions) × 100`, rounded to one decimal place; accepted fixes are enumerated from “DEFINITIVE FIX LIST” and rejected fixes from “REJECTED FIXES” (Case Study Methods, p. 7). The paper reports: “All fixes were independently validated by applying each fix to the buggy codebase, executing the program with test inputs, and verifying resolution of the reported behavior.” (Case Study Methods, p. 7). Inference: a Verus-backed repair pipeline can turn each quality criterion into a required Boolean field and require a proof or test artifact before accepting a patch; Verus can prove that a patch preserves specified invariants, but the LLM's root-cause claim and test adequacy need independent evidence.

## techniques for the catalog
- isolated three-phase ensemble: run independent audits, peer cross-critiques, and one attributed arbitration while persisting every artifact
- bounded corpus orchestration: stable-scan source files, chunk under provider-specific limits with safety margins, and use a common client interface with retries
- criteria-checked repair selection: require technical soundness, peer validation, non-conflict, minimal impact, and evidence before accepting a proposed fix
- auditable fix metrics: enumerate accepted and rejected propositions and compute acceptance and contribution statistics from explicit source headers
