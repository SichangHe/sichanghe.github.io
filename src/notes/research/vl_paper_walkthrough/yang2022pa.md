# PA-Boot: A Formally Verified Authentication Protocol for Multiprocessor Secure Boot
(authored by agents unless marked 🧑)
Tag: `zhang2022pa`, [paper](https://arxiv.org/abs/2209.07936)

## protocol and threat model

PA-Boot authenticates application processors (APs) before a bootstrap processor (BSP) allows secure boot to continue. It targets two supply-chain attacks: a replaced AP and a man-in-the-middle interposer on inter-processor communication. The paper’s abstract states: “The fine-grained formalization of PA-Boot and its fully mechanized security proofs are carried out in the Isabelle/HOL theorem prover with 306 lemmas/theorems and ∼7,100 LoC.” (abstract, page 1). The two attacks are (a) AP replacement and (b) an extra interposer chip on the inter-processor-interrupt (IPI) channel between BSP and AP (section III-A, page 3). The threat model trusts the CPU-chip manufacturer, board manufacturer, OEM, the BSP (its authenticity is ensured by the onboard baseboard management controller before the protocol runs), cryptographic accelerators, and the immutable bootROM; it allows a compromised AP, modified NVM certificates, and a Dolev–Yao attacker with full control of the BSP–AP channel who cannot break the cryptography (the black-box cryptography assumption; section V, page 6). Cold-boot attacks, snooping on the shared memory bus, and side-channel attacks are out of scope (section III-A, page 4).

## technique 1: two-phase certificate and challenge-response protocol

Use an initiation phase to validate the root and processor certificates. Each processor reads `RootCertHash` from bootROM and `(Certroot, CertBSP, CertAP)` from NVM, checks `RootCertHash = Hash(Certroot)`, and validates the other processor’s certificate with `validCert`. Use a challenge-response phase to authenticate the AP and establish a session key (section IV-B, page 5). The AP sends a challenge packet: a nonce `N_AP` encrypted with `PubK_BSP`. The BSP decrypts it, generates a nonce `N_BSP` and an ephemeral key pair, and sends a challenge-response packet `(N_AP, N_BSP, Hash(EPubK_BSP))` encrypted with `PubK_AP`, plus `EPubK_BSP` in the clear. The AP checks that `N_AP` matches and that the hash matches the received `EPubK_BSP`, generates its own ephemeral key pair, and replies with a response packet `(N_BSP, Hash(EPubK_AP))` encrypted with `PubK_BSP`, plus `EPubK_AP`. The BSP checks it the same way. Both sides then compute `Ks` from their own ephemeral private key and the other side’s ephemeral public key with Diffie–Hellman. The checks are on nonces and hashes of ephemeral keys; signatures are used for certificate validation. A mismatch enters an error-specific state and eventually `ABORT`; a clean run reaches `END`. The protocol also extends to several APs authenticated in sequence (remark, page 5). The paper summarizes the design: “PA-Boot steers the secure boot process in a certificate-based, two-phase manner: The processor certificates are validated in the initiation phase and thereafter, in the challenge-response phase, the AP identity is authenticated and the inter-processor communication channel is encrypted.” (section IV, page 4).

Verus form (Inference): model certificates, nonces, protocol states, and packet transitions as Rust structs/enums. Give certificate validation and packet parsing contracts with `requires` for key relationships and `ensures` for validity or an error state. Represent `Ks` derivation with a cryptographic specification and keep the concrete crypto library behind a narrow external contract unless it is itself verified. Maintain a loop `invariant` that a successful state has authenticated certificates and that any error state cannot advance to `END`. This is a Verus encoding inferred from the Isabelle model, not a technique implemented in the paper.

## technique 2: abstraction refinement from Sh to Sl

Define a high-level labelled transition system `Sh = ⟨S,s0,s̄,Λ,∆⟩` (section V-A, page 6): a finite-state acyclic system with a finite state set `S`, initial state `s0`, an ideal state `s̄` marking attack-free authentication, finite event labels `Λ`, and deterministic labelled transitions `∆`. `Sh` captures the simplest protocol behavior and carries a security context with two indicator functions: benignity `B` (the AP and the NVM certificates are genuine) and free-of-attack `M` (no man-in-the-middle attack along a run). Refine it into `Sl`, whose state is a record with fields `bsp`, `ap`, `env`, and `status` (`INIT`, `OK`, `ERR`, `ATTK`, `END`, `ABORT`), and whose transitions come from 11 events: 10 processor events (read ROM, read NVM, verify root-certificate hash, verify certificate, generate nonce, send packet, receive packet, parse packet, generate ephemeral key, generate session key) and one attacker event (man-in-the-middle attack) (Table II, page 6). The paper proves `Sh ⊑ Sl` in Isabelle/HOL by interpreting locales as parametric theory modules (section V-B, page 6); it verifies the properties on `Sl`, and uses `Sh` to gain confidence in the specification. The authors explain, “The high-level specification Sh provides a simple system behavior description, while the low-level specification Sl, closer to implementation, details all possible protocol executions and attacker interactions.” (section III-B, page 4).

The paper says the refinement proof between `Sl` and `Sh` extends confidence in `Sh` to `Sl` (section III-B, page 4). Properties are stated first on `Sh`, then refined to `Sl` as Isabelle lemmas (section VI, page 7). Functional correctness (Property 1, Lemma 1) says benignity of the security context is invariant along every run; on `Sl` this means the NVM contents, both private keys, and both `RootCertHash` values never change. Security (Property 2) says a run of `Sh` ends in `s̄` if and only if the initial context is benign and the run is free of man-in-the-middle attacks. On `Sl`, three lemmas cover three scenarios (section VI-B, pages 7–8): Lemma 2.1, a benign and attack-free run ends in `END`; Lemma 2.2, if the AP or NVM certificates are tampered with, the run visits an `ERR` state (certificate validation of the AP or BSP, or response) and ends in `ABORT`; Lemma 2.3, if a challenge, challenge-response, or response packet is modified, the run visits `ATTK` and then `ERR`, and ends in `ABORT`. The low-level properties are trace properties proved by induction on traces of `Sl`; Lemmas 2.2 and 2.3 are decomposed into auxiliary lemmas per trace and chained together (page 8). The paper names three goals: authenticity of the AP, integrity of packets and NVM certificates, and confidentiality of `Ks`.

Verus form (Inference): define an abstract `spec fn` transition relation and a concrete executable transition function. Prove a refinement simulation lemma for every concrete step, using `requires`/`ensures`; maintain a state-machine `invariant` linking concrete fields to the abstract state. Prove trace properties by induction over a ghost vector of events. Verus has no Isabelle locale interpretation, so module-level assumptions must be represented by explicit predicates and lemmas.

## technique 3: extracted-model validation of C

Implement CPA-Boot in about 1,400 lines of C for the ARM64 bare-metal environment (section VII-A, page 8), embedded in the ARMv8 bootwrapper and using wolfSSL for ECC-based cryptography. Perform a code-to-spec review establishing near one-to-one correspondence between Isabelle events and C functions. Extract executable code from `Sl` in OCaml with Isabelle/HOL’s built-in extraction. Give the extracted OCaml function an abstract test input, instantiate the same input as a concrete one for CPA-Boot, run both, and compare the outputs: the OCaml side reports whether the protocol ends in `END` or `ABORT`, and the C side reports whether it proceeds to the next boot stage or aborts (section VII-B, page 9). Example from the paper: the OCaml model represents a tampered AP with an abstract private-key value `BAD_PRIVK`, while the C side links a modified private-key file of CPU1. The paper says, “To build confidence in the consistency of the formal model and the implementation, we develop a test framework that extracts executable code from our Isabelle model Sl and validate it against CPA-Boot.” (section VII, page 8).

Verus form (Inference): use a reference Rust model and implementation with a relation `impl_state_matches_spec`; run differential tests over generated traces, but treat testing as evidence of correspondence rather than a proof. For proof, connect each implementation transition to the abstract transition with a verified lemma. Keep C/FFI and cryptographic libraries in explicit trusted boundaries.

## evidence and limits

The Isabelle development contains 91 locale/definitions (`Sh` 1, `Sl` 90) and 306 properties/lemmas (`Sh` 2, `Sl` 304). Table III gives about 50 + 850 lines of specification and about 50 + 6,150 lines of proof, about 7,100 lines in total, and the text says the proof effort amounts roughly to 8 person-months (Table III and text, page 8). CPA-Boot is evaluated on ARM Fixed Virtual Platforms (FVP) with Cortex-A72 CPUs, CPU0 as BSP and CPU1 as AP; an extra CPU2 mimics the interposer chip (section VII-C, page 9). Table IV (page 10) lists six attack instances (AP replacement, root-certificate tampering, AP-certificate tampering, challenge-packet, challenge-response, and response-packet manipulation) and marks all six as detected. Table V (page 10) counts executed instructions, averaged over three boot trials of Gentoo Linux (kernel 5.16.0), with overhead defined as CPA-Boot instructions divided by bootwrapper plus kernel instructions: 4.98% for the dual-processor run (`87,570,653` CPA-Boot instructions), 3.09% for CPU0, and 2.97% for CPU1. The paper counts instructions, not cycles, because FVP is not cycle-accurate. The paper says, “The results demonstrate the consistency of the outputs for matching inputs across various scenarios particularly those covered in Table IV, thereby increasing confidence in the accuracy of our C implementation.” (section VII-B, page 9).

What is proved is the Isabelle model’s functional and security properties under its threat assumptions (including trusted BSP, immutable bootROM, trusted crypto accelerators, and black-box cryptography), plus refinement between the two specification levels. The paper does not verify the C code: it relies on a code-to-spec review plus the OCaml-versus-C test comparison, and lists deriving verified C code as future work (section VIII, page 11). Deployment on real hardware is only discussed: it needs the protocol code and root-certificate hash in the CPU’s bootROM (section VIII, page 11); the evaluation is on FVP only. Inference: the trusted base of the whole system also includes the code-to-spec review, the code extraction, the C toolchain and wolfSSL, and the FVP model; the paper does not list these as such. Inference: an agent-written verified Rust boot component for VL would still need a concrete refinement and foreign-function-interface story. Inference: PA-Boot already covers generic certificate and challenge-response verification and model-to-C validation, so VL should reuse the layered-proof pattern rather than claim those mechanisms as new.

## techniques for the catalog

- two-phase processor authentication: validate certificate chains, then authenticate AP identity and derive an encrypted session key
- abstraction refinement: prove concrete low-level traces refine a small high-level transition system before proving security properties
- trace-property induction: decompose normal, tampered, and man-in-the-middle guarantees into lemmas over all concrete runs
- model-to-code validation: extract executable model code and compare it with a reviewed implementation on matching attack scenarios
