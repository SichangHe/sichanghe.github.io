## direct answer

- what KVerus does
  - takes an unverified Verus function whose specification already exists
  - builds a typed repository metadata graph
    - nodes include functions, specifications, lemmas, structures, enums, traits, and type aliases
    - edges include type, containment, trait, alias, call, and specification dependencies
  - retrieves dependent code up to a fixed graph depth of three
  - builds semantic lemma knowledge
    - keeps existing comments
    - asks an LLM to summarize undocumented lemma signatures and contracts
    - embeds those descriptions for requirement-driven retrieval
  - builds version-aligned Verus knowledge
    - parses official documentation and examples
    - temporarily registers relevant Verus pull requests when documentation lags
  - generates a proof, runs Verus, classifies errors, retrieves targeted guidance, and refines for at most ten queries
  - stops automation at verifier-passing code
    - a human still decides specification correctness, maintainability, style, and upstream acceptance
- central idea
  - repository proof completion is primarily a context-selection and knowledge-reuse problem
  - a model's semantic pattern matching must be connected to structural facts the verifier enforces
    - exact dependency paths
    - available lemma contracts
    - current Verus syntax and solver behavior
- what it does not do
  - it does not determine whether the specification expresses human intent
  - it does not autonomously repair an incorrect specification
  - it does not remove the need for expert review or proof cleanup
  - the ASE paper workflow starts from existing unverified Verus, not arbitrary ordinary Rust
    - the repository's later `main` branch now advertises broader migration, specification, audit, and cleanup skills
    - those later product claims are not evidence for the evaluated ASE method

## full-paper results

- repository-level proof completion
  - 183 of 359 tasks, 51.0 percent
  - multi-round prompting baseline: 16 of 359, 4.5 percent
  - MathSpec-Bench: 81 of 104 versus 10
  - Memory Allocator: 50 of 89 versus 1
  - CortenMM: 52 of 166 versus 5
- single-file proof completion
  - KVerus: 251 of 313, 80.2 percent
  - AutoVerus: 178 of 313, 56.9 percent
  - AlphaVerus: 78 of 313, 24.9 percent
  - multi-round prompting: 139 of 313, 44.4 percent
  - KVerus used 5.70 million tokens and 1,912 queries
  - AutoVerus used 13.50 million tokens and 3,922 queries
- knowledge ablation
  - repository tasks depend strongly on structural code and lemma knowledge
    - MathSpec-Bench falls from 81 solved to 42 without code metadata and 63 without lemma knowledge
    - CortenMM falls from 52 to 10 without code metadata and 7 without lemma knowledge
  - single-file tasks depend strongly on current Verus knowledge
    - Human-Eval falls from 54 solved to 4 without it
  - inference
    - VL should route different failure classes to different knowledge stores instead of using one undifferentiated prompt
- toolchain evolution
  - on Verus `20250328`, KVerus solves 254 tasks and AutoVerus 234
  - on Verus `20250813`, KVerus solves 251 and AutoVerus 178
  - the paper attributes the divergence to version-aligned guidance after an explicit `decreases` requirement changed
  - the paper's CortenMM history reports eight Verus synchronizations in six months
- real repository integration
  - 23 previously unverified CortenMM functions
  - 1,387 generated proof lines, including six new lemmas
  - 21.0 percent of the module's proof code
  - 9 targets concern tree-model mathematics
  - 12 concern state-machine invariants and refinement
  - 2 concern executable functional correctness
  - the paper reports that all patches passed Verus and were accepted upstream
- important negative evidence
  - KVerus repeatedly failed on an RCU transition whose specification omitted two soundness conditions
    - a human repaired the specification
    - failure was useful evidence, not proof that the model could infer the correct contract
  - one generated proof exceeded 100 lines while a human proof used 34
    - verifier validity did not imply maintainability

## what was already done

- AutoVerus
  - generated proof annotations for small Verus functions with fixed specifications
  - used expert prompts and verifier-error refinement
  - did not solve repository dependency or evolving-toolchain context
- SAFE
  - created synthetic verified data and fine-tuned a model
  - improved proof generation but did not supply KVerus's repository knowledge layer
- AlphaVerus
  - used verifier-guided tree search and self-improving translation
  - remained oriented toward constrained tasks
- RAG-Verus / repository-level program verification
  - already established retrieval for cross-file Verus proof completion with given contracts
  - KVerus's incremental boundary is typed dependency context, semantic project-lemma reuse, versioned Verus knowledge, error-targeted refinement, and CortenMM integration
- VeruSAGE
  - already tested proof agents on systems-derived Verus tasks with complete specifications
  - it is stronger evidence about agent behavior and failure analysis, not specification formation
- StarVerus
  - already moved upstream to specification plus proof generation using caller and callee context
  - this prevents VL from claiming novelty for generic repository-scale contract-and-proof generation
- Formal Disco
  - already showed scalable generation and diversity-aware selection of verifier-accepted training traces
  - KVerus addresses operational repository knowledge and maintenance instead of data generation
- KVerus's defensible increment
  - a concrete, open, repository-aware proof-maintenance workflow for existing Verus code
  - explicit separation between machine proof validity and human integration judgment
  - accepted proof patches in a real verified systems project

## what VL should learn

- make repository knowledge a maintained product object
  - stable fully qualified identities for code and proof objects
  - typed dependency edges with provenance
  - lemma contracts, comments, synthesized descriptions, and embeddings
  - toolchain-versioned documentation, diagnostics, and successful repairs
- separate knowledge acquisition from proof search
  - deterministic indexing owns symbols and dependency closure
  - the model identifies proof requirements and selects semantic lemmas
  - the verifier owns proof validity
  - a human or explicit semantic gate owns specification intent and maintainability
- route failures by cause
  - missing dependency
  - missing or inappropriate lemma
  - stale Verus knowledge
  - proof construction error
  - likely specification defect
  - integration or style failure
- treat proof generation as maintenance
  - pin the toolchain for every run
  - retain verifier diagnostics, retrieved context, chosen lemmas, and patch lineage
  - re-run repository proof CI after code, library, solver, or Verus changes
  - measure repair success over chronological changes, not only stripped static benchmarks
- preserve failure as evidence
  - repeated failure after adequate retrieval should trigger specification review
  - the agent must not weaken or invent assumptions merely to obtain green output
- optimize accepted proofs after correctness
  - remove redundant assertions under repeated verification
  - keep proof minimization separate from generation
  - include reviewability and project style in the acceptance record

## recommended VL integration

- immediate design changes
  - add a versioned repository knowledge layer to the existing CLI
    - symbol graph
    - specification references
    - lemma catalog
    - toolchain knowledge
  - retrieve a bounded dependency slice for each target
    - use graph depth as a starting heuristic, not a correctness boundary
    - log omissions discovered during refinement
  - add a requirement-analysis stage before proof generation
    - list the facts and lemma shapes the proof needs
    - resolve each item to a source or mark it missing
  - use typed failure routing
    - only proof failures enter proof repair
    - suspected contract failures stop for semantic review
  - add proof-minimization after verifier success
    - delete one candidate assertion or helper at a time
    - retain a deletion only after exact repository verification
  - keep immutable receipts
    - executable-code boundary
    - specification identity and provenance
    - dependency and lemma retrieval set
    - model and toolchain identity
    - verifier output and whole-project result
- strengthen beyond KVerus
  - fail closed on specification uncertainty
  - compare contracts with requirements, tests, callers, comments, and named mutants
  - include callers as well as outgoing dependencies
  - evaluate retrieval recall and harmful-context rate
  - report per-run success rather than only the union across runs
  - use held-out repositories and chronological maintenance tasks
- separate authorization required
  - implementation in VL repositories
  - reproduction of the KVerus benchmark numbers
  - comparison of depth-three traversal with adaptive retrieval

## product threat

- overall: high strategic threat and medium-high current substitution threat
- high capability overlap
  - KVerus directly solves proof completion with cross-file Verus context
  - it combines dependency retrieval, lemma reuse, verifier feedback, and toolchain adaptation
  - this is closer to VL's operational core than rank-one Formal Disco
- high prior-art threat
  - generic claims around repository-aware Verus proof agents, semantic lemma retrieval, or verifier-driven maintenance are no longer credible novelty anchors
  - accepted CortenMM patches make the work harder to dismiss as benchmark-only
- medium-high implementation threat
  - the paper method, fixed paper branch, Zenodo archive, scripts, prompts, and benchmark-fetching instructions are public
  - a competitor can reproduce or extend the pipeline without reconstructing it solely from prose
- medium current substitution boundary
  - only 51.0 percent of repository tasks are solved under the paper's union-of-three-runs metric
  - the method assumes existing Verus specifications and shared lemmas
  - specification correctness and proof maintainability remain human responsibilities
  - evidence centers on Verus and one real repository
- inference
  - KVerus compresses VL's differentiation toward specification governance, adaptive bidirectional repository reasoning, trustworthy change control, whole-project evidence, and longitudinal maintenance quality
  - proof completion alone is insufficient product differentiation

## limitations and cautions

- the paper reports the union of three runs rather than mean success, variance, or confidence intervals
- the repository baseline is prompt-only
  - it isolates the benefit of the complete knowledge stack
  - it does not isolate whether a simpler graph retriever could capture most gains
- dependency traversal stops at depth three
  - the paper says this covers most target chains
  - no retrieval-recall or missed-dependency distribution is reported
- semantic lemma summaries are model-generated
  - Verus checks any final lemma use
  - misleading summaries can still waste search or omit the right lemma
- specifications and shared lemmas are retained in benchmark tasks
  - results measure proof completion, not end-to-end intent discovery
- frontier-model dependence limits reproducibility and cost portability
- upstream acceptance is strong practical evidence
  - the paper does not report review effort, rejected patches, time-to-merge, or maintenance after later changes
- v2's public artifact improves inspectability
  - this walkthrough authenticated availability but did not execute it
