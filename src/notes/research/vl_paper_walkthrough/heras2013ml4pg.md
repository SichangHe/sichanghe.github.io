# ML4PG in Computer Algebra verification
(authored by agents unless marked 🧑)
Tag: `heras2013ml4pg`, [paper](http://arxiv.org/abs/1302.6421v3)

## scope and trust boundary

Heras and Komendantskaya use ML4PG, a machine-learning extension to Proof General, to suggest proof patterns during Coq/SSReflect development. The abstract says it “provides statistical proof hints during the process of Coq/SSReflect proof development.” (Abstract, p. 1). They apply it to CoqEAL, a refinement library for verified computer-algebra algorithms, and use the suggestions to formalize an efficient triangular-matrix inverse.

ML4PG is a proof-development assistant, not a proof checker. It extracts low-level features from existing proof scripts, clusters lemmas, and presents likely analogues for a stuck goal. The developer still inspects the suggested proofs and formulates a strategy. The paper states: “the user is left with the task of finding a proof strategy from the suggestions provided by ML4PG.” (Section 2, p. 3). Inference: a Verus analogue may prioritize candidate lemmas or proof traces, but only Verus checking establishes correctness; statistical similarity is evidence for search, not a trusted fact.

## technique 1: separate efficient algorithm correctness into refinement stages

what it is and when to use it. Define a rich, easily specified algorithm, prove its correctness, then refine it through progressively executable representations. Use this when a fast representation is difficult to reason about directly.

steps from the paper. CoqEAL splits formalization into three steps: “S1. define the algorithm relying on rich dependent types, as this will make the proof of its correctness easier;”; “S2. refine this definition to an efficient algorithm described on high-level data structures”; and “S3. implement it on data structures which are closer to machine representations.” (Section 2, p. 2). For triangular matrices, use SSReflect's abstract `invmx`, define recursive `fast_invmx` on a high-level matrix decomposition, prove equivalence between `invmx` and `fast_invmx`, then define list-of-lists `cfast_invmx` and prove `seqmx_of_mx (fast_invmx M) = cfast_invmx (seqmx_of_mx M)` (Lemma 1, p. 3). Per Proof Strategy 1 (p. 3), a morphism lemma changes the representation, and translation lemmas state the equivalence between executable and abstract counterparts of matrix operations.

Verus form. Inference: define a mathematical Rust/Verus spec over sequences or maps, prove the algorithmic implementation correct against it, then refine to an executable vector or slice representation. Use `spec fn` for abstract operations, `ensures` for refinement equivalence, and `proof fn` lemmas for representation morphisms. Keep the executable data structure and its invariants explicit; unlike Coq's locked matrices, Rust code executes directly, so refinement must also preserve ownership and bounds.

evidence and limits. The paper's CoqEAL library contains approximately 400 definitions and 700 lemmas (Section 2, p. 2), making manual strategy search difficult. The triangular inverse example demonstrates a method for one algorithm; it does not report a percentage of all CoqEAL developments successfully refined. Inference: staged refinement can reduce proof complexity, but each abstraction boundary adds a theorem and a potential mismatch.

## technique 2: retrieve proof patterns by feature extraction and clustering

what it is and when to use it. Represent proof scripts by simple structural features, cluster similar lemmas, and show clusters containing a stuck goal. Use this when a library has many related lemmas but its methodology is hard for a new user to discover.

steps from the paper. During Proof General interaction, extract low-level features from Coq/SSReflect proofs; extend Coq's compilation procedure to extract lemma-features from already-developed libraries (Section 3, Step 1, p. 4). In the example, features were extracted from 18 CoqEAL files involving 720 lemmas. Send the statistics to a selected unsupervised clustering implementation (Step 2). ML4PG is integrated with MATLAB K-means and Gaussian and Weka K-means, FarthestFirst and Expectation Maximisation; the CoqEAL example uses MATLAB K-means, the default (Step 2, p. 4). Choose a granularity from 1 to 5; ML4PG computes the number of clusters from library size (Step 3, p. 4); the default granularity is 3. Run clustering 200 times, then use cluster proximity and frequency as thresholds to choose the single "most reliable" cluster to display (Step 4, pp. 4-5).

Verus form. Inference: extract features from Verus proof functions, lemma calls, invariant shapes, quantified triggers, and contract structure. Cluster successful proof traces and use the nearest cluster to suggest lemma names or a sequence of calls. The features should identify the target obligation and relevant type/trait parameters; otherwise similarity can be syntactic noise. Feed every suggestion back through Verus, and store only accepted traces as training evidence.

evidence and limits. Table 1 runs five clustering algorithms at five granularities (with n = 72, 80, 90, 102, 120 for g = 1 to 5). Its caption says the table shows "the sized of clusters" containing the four target lemmas (`cfast_invmxP`, rank, fast multiplication, determinant). The reported sizes are, for Gaussian, 24, 12, 10, 10, 10 for granularities 1–5; MATLAB K-means gives 20, 14, 4, 0, 0; Weka K-means 16, 11, 4, 0, 0; Expectation Maximisation 52, 45, 43, 39, 14; FarthestFirst 30, 27, 27, 26, 20 (Table 1, p. 5). Each entry is the size of the cluster containing the four target lemmas for that algorithm and granularity; the paper does not explain the entries 0. The authors write that "the clusters obtained by almost all variations of the learning algorithms and parameters include the lemmas which led us to formulate Proof Strategy 1", and that Expectation Maximisation and FarthestFirst results "include several additional lemmas that make difficult the discovery of a common pattern" (Section 3, p. 5). Inference: the 0 entries mean no cluster with all four lemmas at that setting, and cluster size is a retrieval tradeoff, not a proof-success rate. The paper does not give a success rate.

## technique 3: inspect retrieved analogues to synthesize a reusable strategy

what it is and when to use it. Treat cluster members as worked examples, compare their proof scripts, and abstract the common sequence into a strategy. Use this when the machine learner can find similar lemmas but cannot safely invent the proof itself.

steps from the paper. Invoke ML4PG while stuck on the inductive case of `cfast_invmxP`. Inspect the three suggested lemmas, the counterparts of Lemma 1 for rank, determinant and fast matrix multiplication (Figure 1, Section 2, p. 3). Compare their scripts and extract the shared strategy: apply the morphism lemma to change from abstract to executable matrices, then apply translation lemmas for each matrix operation. Apply this strategy to the target lemma. The paper calls it “Proof Strategy 1 Apply the morphism lemma to change the representation from abstract matrices to executable ones. Subsequently, apply the translation lemmas of the operations involved in the algorithm” (the sentence continues with a definition of translation lemmas; Section 2, p. 3).

Verus form. Inference: when a Verus goal about a concrete vector implementation resembles prior verified algorithms, retrieve complete proof functions and identify shared representation lemmas. Apply a `proof fn` that first establishes the abstraction relation, then calls operation-preservation lemmas. Use `assert`/`calc` to bridge equalities and `ensures` to expose the final relation. Keep strategy extraction as an offline or interactive tool; do not generate executable proof calls without Verus checking.

evidence and limits. The strategy was found by the user inspecting the three suggested lemmas, which follow it and to which Lemma 1 can be fitted; it was not mechanically generated. The authors identify future work: “we could apply symbolic machine-learning techniques such as Rippling [1] and Theory Exploration [3] to automatically conceptualise the proof strategies from the suggestions provided by ML4PG” (Section 2, pp. 3-4). Thus the demonstrated workflow still depends on expert inspection. Inference: agent-written Rust benefits from retrieval, but an agent can copy a superficially similar invariant and prove the wrong property if contracts are weak.

## technique 4: tune granularity and repetition to balance precision and recall

what it is and when to use it. Vary clustering granularity and repeat randomized clustering, then select results with high within-cluster proximity and frequency. Use this when one clustering run or one cluster size gives either too many unrelated suggestions or misses relevant analogues.

steps from the paper. Let granularity 1 produce few large clusters with low correlation and granularity 5 produce many small clusters with high correlation (Section 3, Step 3, p. 4). The paper says that "results of one run of a clustering algorithm may differ from another; then ML4PG runs the clustering algorithm 200 times, obtaining the frequency of each cluster as a result" (Step 4, pp. 4-5). The clustering output also gives a proximity measure; the two measures "are used as thresholds to decide on the single 'most reliable' cluster to be shown to the user" (p. 5). Inspect the resulting cluster rather than accepting its membership as a proof.

Verus form. Inference: expose a retrieval parameter controlling cluster size and rerun randomized embedding/clustering, but report run count, corpus size, feature schema, and solver-verified suggestion count. Use high granularity for a narrow invariant pattern and lower granularity for discovering broader library analogies. The only accepted outcome is a Verus proof that compiles under the recorded configuration.

evidence and limits. Inference: the 200-run repetition is a stability heuristic; the paper reports it as a procedure and gives no confidence interval. Expectation Maximisation and FarthestFirst retained more lemmas at low granularities, which the authors say made common-pattern discovery difficult; for the other algorithms at granularities 1 and 2, "the clusters can be refined when increasing the granularity value" (Section 3, p. 5). Inference: a product should show several candidate clusters and their stability rather than hide the parameter choice.

## proved, measured, trusted, and product threat

The paper demonstrates ML4PG-assisted discovery of a CoqEAL proof strategy and reports, in Table 1, the size of the cluster containing the four target lemmas for five algorithms and five granularities, over the 720 lemmas extracted; ML4PG runs the clustering 200 times (Section 3, Step 4). It does not prove that clustering is semantically sound, nor does it report an end-to-end percentage of lemmas solved by ML4PG. Inference: the trusted components are Coq/SSReflect's kernel, feature extraction, the clustering implementation, and human interpretation of suggestions; the paper does not list them. Inference: existing work provides library-scale proof-pattern retrieval and a refinement methodology, and VL should reuse these ideas rather than build a generic language model that guesses lemma names without corpus evidence. Inference: the threat to agent-written verified Rust is search bias and specification drift, not unsoundness when Verus checks every result. The larger threat is accepting a retrieved pattern before checking that its abstraction relation and postcondition match the product code.

## techniques for the catalog

- staged refinement for efficient verification — prove an abstract algorithm, refine to high-level structures, then prove correspondence to machine representations
- proof-feature clustering — extract proof-script features and cluster library lemmas to retrieve likely analogues
- human-guided strategy synthesis — inspect analogous proofs and abstract their common lemma sequence into a reusable strategy
- stability and granularity tuning — vary cluster granularity and repeat randomized runs, using proximity and frequency to select suggestions
