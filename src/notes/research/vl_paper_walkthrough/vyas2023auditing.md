# Auditing Framework APIs via Inferred App-side Security Specifications
(authored by agents unless marked 🧑)
Tag: `vyas2023auditing`, [paper](https://www.usenix.org/conference/usenixsecurity23/presentation/vyas)

Bluebird audits Android framework APIs by inferring security specifications from preloaded apps and comparing them with framework-side access control. It combines static analysis, UI and NLP evidence, contribution and context clues, and probabilistic inference. A low framework prior that becomes a high posterior indicates an access-control gap requiring investigation; it does not identify the exact missing check.

## technique: framework priors and app-entry recovery

Inference: use this when framework APIs lack written specifications but callers reveal how sensitive operations are expected to be. The paper states: “Bluebird pairs human-like understanding of app-side logic (e.g., using NLP techniques) with statically-derived app-side program semantics to infer the likely sensitivity level of an API, solely from the perspective of the apps calling it.” (section 1, PDF p. 6062)

Steps: (1) build an interprocedural control-flow graph for each framework API; (2) traverse it depth first, extract permission, user-ID, and process-ID checks, resolve conditions and arguments, and normalize them using AceDroid; (3) assign a prior probability to API sensitivity, with weak/no framework access control receiving low prior; (4) identify direct app entries through reachability analysis, using EdgeMiner to connect implicit control flows; (5) resolve explicitly constructed local intents by tracking target arguments through def-use chains, build a component call graph, and add indirect app entries. Intent resolution is limited to explicit constructions (section 4.2, PDF pp. 6066–6067). The implementation uses WALA for bytecode analysis and produces priors and probabilistic constraints. The paper states: “Bluebird starts by extracting framework-side security checks to estimate priors (i.e., initial sensitivity of APIs).” (section 4.1, PDF p. 6066)

Inference: in Verus, model the normalized access-control policy as a specification and prove that each Rust entry point satisfies it. Verus cannot infer undocumented policy from arbitrary UI text; a separate static-analysis and NLP pipeline would supply candidate specifications, which must be treated as assumptions until reviewed.

## technique: evidence extraction from traditional checks and UI

What it is and when to use it. Infer entry sensitivity from explicit permissions and from UI indicators such as password fields, dialogs, non-disposable controls, and multiple confirmations. This addresses app protections that are not represented as framework checks.

Steps: (1) inspect component declarations for permissions and exported flags; (2) inspect lifecycle code for programmatic permission, UID, and user checks; (3) inspect XML and dynamically constructed UI for type, identifiers, hints, and labels; (4) assign low or high sensitivity from traditional checks using Rules 2–3; associate sensitive UI types, non-disposable dialogs, and multiple confirmations with high sensitivity at medium confidence using Rules 4–6, and textual evidence using Rule 7; (5) feed each predicate into the joint probabilistic model. For textual UI evidence, label extracted UI text using invoked AOSP APIs’ access control and fine-tune a pretrained BERT Cased model. The paper reports 4,516 labeled texts from 698 preloaded apps and F1 0.969: “The final model had an F1-score of 0.969.” Its sample counts are internally inconsistent: it lists 4,208 sensitive and 309 non-sensitive samples, whose sum is 4,517, and describes downsampling the sensitive class by two to 2,258, although half of 4,208 is 2,104 (section 4.2, PDF p. 6068).

Inference: a Verus proof can consume a reviewed `spec fn sensitive_entry(...) -> bool` and prove downstream authorization obligations. The neural classifier, training data, and decompilation correctness are outside Verus and should be recorded as evidence, not proofs.

## technique: contribution and context clues

What it is and when to use it. Propagate sensitivity only when an invoked API plausibly contributes to an entry’s sensitive behavior and when invocation context supports that propagation. This reduces false alarms from auxiliary methods and path-sensitive APIs.

Steps: (1) collect names, permissions, UI text, classes, method names, and argument types; (2) embed caller and callee descriptors with a transformer encoder; (3) compute cosine similarity and recursively combine it along the call chain using `Contribution(ep, api) = Max(Sim(ep, api), Contribution(ep, c(api)) * Sim(c(api), api))`; (4) construct Rule 8 probabilistic constraints with implication probability equal to the contribution score times ph = 0.9; (5) perform backward interprocedural data-flow analysis from each API to classify arguments as modifiable, non-modifiable, or user-modifiable; (6) detect special inputs often used in path-sensitive access control, such as user or app IDs, without assuming that the API actually checks them; (7) propagate low or high confidence according to Rules 9–12. The paper’s example explains that passing `Process.myUid()` as an argument can implement an implicit app-side security specification. Rule 12 propagates low entry sensitivity with low confidence and high entry sensitivity with high confidence (section 4.4, PDF pp. 6068–6069).

Inference: for Rust, encode path-sensitive preconditions directly in `requires`; prove that caller arguments satisfy the same branch condition as the callee. Verus can verify the implication once supplied, but cannot establish that a learned naming similarity reflects semantic contribution.

## technique: probabilistic fusion and gap classification

What it is and when to use it. Encode priors and uncertain clues as probabilistic rules, solve a factor graph, and compare posterior with prior. Bluebird uses ProbLog. Section 3 describes a gap as a posterior above the prior; section 4.6 makes classification explicit: compare the posterior against an empirically determined preset threshold, then report LOW-to-HIGH cases. The paper states: “The auditing procedure classifies the posterior probability as either LOW or HIGH by comparing it against a preset threshold (empirically determined).” (section 4.6, PDF p. 6069) The paper reports a motivating example where the posterior reaches 0.94 (section 3, PDF p. 6066). It also states: “Finally, Bluebird detects APIs with access control gaps if the posterior probabilities are more than the priors.” (section 3, PDF p. 6066)

Steps: (1) create random variables for each API and app entry; (2) assign prior probabilities from framework and app access-control evidence; (3) add conditional rules for UI, NLP, contribution, data flow, and context; (4) solve posterior marginals with a factor-graph engine; (5) classify LOW→HIGH as an access-control gap, LOW→LOW as compliance, and HIGH as do-not-audit; (6) manually investigate and build proof-of-concept exploits.

Evidence. Bluebird evaluated seven AOSP and seven custom ROMs spanning Android 8.1, 9, 10, 11, 12, and 13; the custom ROMs came from six vendors. It reported 391 private APIs with likely gaps (section 1, PDF p. 6062; Table 3, PDF p. 6071). Section 5.4 reports gaps ranging from 15% to 44%. Inference: Table 3 supports these rounded percentages when the denominator is private APIs with app invocations, not all private APIs. Two authors manually investigated 10% of custom-ROM gaps; a false positive required both authors to agree (sections 5.4–5.5, PDF pp. 6070–6071). For AOSP, the authors assumed security rather than verified it: “We did not attempt to verify whether they are indeed FPs since we consider AOSP as ground truth.” They estimated an average 17% false-negative rate on synthetic cases created by changing strongly protected AOSP APIs’ priors from HIGH to LOW (section 5.3, PDF p. 6070). Table 5 lists 11 vulnerabilities, with six bounty awards; section 6 says all reports were acknowledged and nine fixed, while Table 5 marks the two clipboard DoS cases “Won’t Fix” (PDF pp. 6072–6073). The paper reports: “We found that about 18% of framework files and 22% preloaded apps could not be properly decompiled by existing preprocessing tools or analyzed by WALA.” (section 5.1, PDF p. 6070)

## techniques for the catalog

- framework-prior extraction — recover normalized access checks from API control-flow graphs and assign sensitivity priors
- UI and NLP evidence — infer app-entry sensitivity from permissions, UI structure, text, and a domain-trained classifier
- contribution/context propagation — use call-chain similarity and argument data flow to condition sensitivity transfer
- probabilistic gap inference — solve priors and uncertain clues with a factor graph and flag LOW-to-HIGH APIs
