# RLSF: Fine-tuning LLMs via Symbolic Feedback
(authored by agents unless marked 🧑)
Tag: `jha2024rlsf`, [paper](http://arxiv.org/abs/2405.16661v3)

## core method

RLSF places a symbolic reasoner in the reinforcement-learning environment. The model emits a formal-language object; a compiler, solver, prover, algebra system, or domain checker returns a certificate identifying errors; a reward function converts that certificate into a vector aligned with response tokens; PPO updates the model. The paper's abstract defines the distinction: “RLSF uses poly-sized certificates (e.g., proofs) generated by symbolic tools to identify and correct errors in model outputs, offering token-level guidance without requiring differentiable reasoning systems.” (Abstract, p. 1).

Algorithm 1 is the reusable procedure:

1. for each epoch and prompt batch, sample a response from the current model
2. call `SymbolicReasoner(batch, response)` to produce a certificate
3. call `RewardFunc(certificate)` to produce a vector with the same shape as response tokens
4. run PPO with the prompt, response, and vector reward
5. replace the current model and continue (Algorithm 1, p. 3)

The framework applies when outputs are in a formal language and a reasoner can verify segments using a chosen delimiter; segments can be lines, words, characters, or parser tokens (Section 3, p. 3). Inference: for Verus Rust, segment generated code by lines or tokens, run Verus/compiler diagnostics, map failed obligations to the responsible spans, and reward verified spans. This adaptation would need its own implementation and evaluation with Verus.

The paper contrasts dense symbolic feedback with RLHF's scalar reward. It describes using certificates to “provide a feedback signal to the RL agent” (Section 2, p. 2) and says RLSF “does not require the reasoning systems to be differentiable” (Section 1, p. 2). The authors qualify the certificate-size claim: “It is possible that the problem addressed by these symbolic tools is NP-hard, and therefore, in general, we cannot always expect certificates that are polynomial in the input size.” They add that compilers, computer algebra systems, and solvers work well in practice (footnote 2, p. 2). Inference: Verus diagnostics are suitable feedback even when a complete proof object is too large, but a product must distinguish a diagnostic from a sound proof certificate.

## certificate construction for code

For natural-language pseudocode to C++, the symbolic reasoner runs `g++` and a test suite. It returns erroneous line set `E` and test pass rate `r`. Tokens in compiler-flagged lines receive reward 0; tokens in unflagged lines of non-compiling code receive `1`; tokens in compiling code receive `1+r`, where `r` is the fraction of tests passed. BOS/EOS receive `1+r` when the complete code compiles and 0 otherwise. The paper states: “Our token-level feedback assigns a high reward p = 1 + r to tokens in syntactically correct lines (positive case) and a low reward n = 0 to tokens in erroneous lines (negative case).” Before compilation, a fixed set of 21 preprocessor directives and a `using namespace std;` line is prepended to generated code because SPoC omits them (Section 4.1, p. 4). Inference: this suggests the following application recipe:

1. define the formal output grammar and segment boundaries
2. compile or verify the generated object
3. identify failed segments and a graded global score
4. assign the vector reward to the corresponding tokens
5. train with PPO and evaluate compilation and test results

Inference: a Verus version should map each syntax, type, or proof failure to the smallest code span available, set zero reward for spans that cause failed verification, and give positive reward to verified spans. A passing compile is weaker than a passing Verus proof; the latter should be the acceptance signal for verified Rust.

The SPoC evaluation uses 16,326 accepted solutions from 677 problems, with 158 test problems and 1,778 test pairs; 14,548 pairs from 519 problems are training data (Section 4.1, pp. 3–4). The paper uses passing every test as a weaker substitute for general functional equivalence, which is undecidable (footnote 3, p. 3). Its metrics differ: CompAcc is the percentage of generated programs that compile; FCorrAcc is the percentage of test cases passed per generated program, averaged across programs, with non-compiling programs scored zero; Pass@1 is the percentage of first-attempt programs that compile and pass all tests (Section 4.2, p. 4). For code-gemma-2b, RLSF reaches 63.95% CompAcc, 41.30% FCorrAcc, and 28.80% Pass@1, versus SFT's 11.31%, 9.87%, and 9.00% (Table 1, p. 5). Inference: these test-based metrics do not establish formal proof success.

## chemistry and algebra feedback

For molecule generation, forward synthesis, and retrosynthesis, RDKit checks SMILES syntax and domain rules. Token-level feedback marks invalid syntax; semantic checks penalize missing functional groups or introducing atoms absent from reactants. The paper reports a representative rule: in forward synthesis, an output that introduces nitrogen when reactants contain only hydrogen and carbon is penalized (Section 5.1, p. 5). For molecule generation, the caption specifies that a missing required functional group penalizes the entire generated molecule; syntax errors receive token-level penalties, and EOS receives 1 only if the entire response is correct (Figure 3, p. 6). Metrics are exact match, Morgan-fingerprint Tanimoto similarity, and validity (Section 5.2, pp. 5–6).

On Galactica-1.3b, RLSF gives molecule-generation EM 8.5%, FTS 38.2%, validity 81.4%; forward-synthesis EM 19.8%, FTS 60.3%, validity 99.8%; retrosynthesis EM 34.5%, FTS 64.4%, validity 99.5% (Table 2, p. 6). The comparison is against GPT-4 zero-shot and SFT/RL baselines on the same task tables; exact match and validity measure different properties of the predictions. Inference: for Verus, domain checks such as ownership, bounds, or API protocol predicates can similarly produce local rewards, but passing a domain heuristic is not a proof of Rust safety.

For Game of 24, the model proposes intermediate equations in a breadth-first Tree-of-Thoughts search. SymPy checks syntax and arithmetic, regex checks that each input number is used exactly once and catches missing or extra numbers, and the feedback vector penalizes erroneous tokens. The illustration assigns erroneous tokens 0 and correct tokens 1, with EOS assigned 1 only when the entire response is correct (Figure 4 and Appendix C, p. 10). The search retains the top five candidates at each step (Appendix C.1, p. 10). Training uses games indexed 800–900, and testing uses games 901–1,000 (Section 6.1, p. 7). On the held-out games, RLSF reaches 17% for gemma-2b-it and 26% for llama2-7b-chat, compared with 2% and 1% for ToT prompting and 1% for Boolean RL (Table 3, p. 7). Inference: this is a search-and-training result, not evidence that symbolic feedback improves arbitrary theorem proving.

## costs and implementation limits

The authors modified the TRL library to accept dense rewards and used PPO with LoRA on all linear attention and FFN layers (`lora_r = 16`, `lora_alpha = 16`) (Appendix D, pp. 10–11). Symbolic checks are fast for RDKit retrosynthesis (0.003 s per generation) and SymPy arithmetic (0.002 s), but g++ takes about 0.5 s per generation; asynchronous `Popen` keeps code-synthesis overhead near one hour per 24-hour iteration (Section 3, p. 3). Inference: Verus proof checking may be slower and should be batched or cached; the reward pipeline must record tool versions and diagnostics to make training reproducible.

The paper reports gains on five domain-specific tasks but explicitly limits its claim: “While we do not claim to improve general reasoning capabilities, RLSF leverages symbolic reasoning tools to improve downstream domain-specific tasks where syntax and semantics play a critical role.” (Section 7, p. 7). It identifies slow or resource-intensive symbolic tools as a limitation and suggests precomputed rewards or DPO-style alternatives (Section 7, p. 7). Inference: the environment, reasoner, certificate parser, reward mapping, and PPO implementation require validation; the reported experiments do not establish a formal guarantee of improvement after training.

## techniques for the catalog

The first five entries summarize Sections 3–6 and Appendix A; the last combines reported parallelization with the future-work proposal in Section 7. Verus adaptations above are inferences.

- certificate-driven PPO — run a symbolic checker on each response and convert its certificate into a token-aligned vector reward
- compiler and test localization — assign 0 to tokens in compiler-flagged lines and `1+r` to tokens in unflagged lines, using global test pass rate `r` (0 when compilation fails)
- domain-rule token feedback — use SymPy and RDKit checks to penalize erroneous tokens where possible; penalize the entire molecule when required functional groups are missing
- formal-language segmentation — choose line, word, character, or parser-token boundaries for segment-wise feedback
- non-differentiable verifier training — keep the symbolic tool external to gradients while using its sound diagnostics for RL
- reward-cost engineering — parallelize symbolic queries with `Popen`; consider DPO-style training with precomputed symbolic rewards for slow tools (Section 3, p. 3; Section 7, p. 7)
