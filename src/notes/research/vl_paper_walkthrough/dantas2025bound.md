# The 4/δ Bound: Designing Predictable LLM-Verifier Systems for Formal Method Guarantee
(authored by agents unless marked 🧑)
Tag: `dantas2025bound`, [paper](https://www.semanticscholar.org/paper/e56ec1f3374f283d9485928b389b248f6a589e23)

## scope and claimed result
The paper models an LLM plus verifier as a five-state absorbing Markov chain: CodeGen, Compilation, InvariantSynth, SMTSolving, and Verified. Its abstract states: “We prove that for any non-zero stage success probability (δ > 0), the system reaches the Verified state almost surely.” It derives “a precise latency bound of E[n] ≤ 4/δ” (Abstract, p. 1). The model requires each stage to advance with independent per-attempt probability δ; failure retries the same stage. The paper's claim is mathematical for this model, not an evaluation of an actual LLM API.

## technique 1: sequential absorbing-chain model
Use this when a verification workflow has mandatory stages and retries. Section 3.1 defines four transient states `(s1,s2,s3,s4)` and absorbing `s5=Verified`. For each stage j, residence time Mj is geometric: “The number of iterations required to exit state j, denoted Mj, is modeled by a Geometric random variable” (Sec. 3.1.1, p. 6). The paper defines success as leaving the current state with probability δ and gives `P(Mj=k)=(1−δ)^(k−1)δ` and `E[Mj]=1/δ` (Sec. 3.1.1, p. 6). Apply it by (1) enumerating mandatory milestones, (2) assigning a measured or assumed δ to each, (3) retrying the current milestone after failure, and (4) summing residence times. “The total time to reach the absorbing state, T, is the sum of the independent residence times spent in the four transient states” (Sec. 3.1.2, p. 6). Inference: a Verus orchestration can represent each milestone as a Rust enum and prove a decreasing retry budget or eventual progress only for a finite bound; Verus cannot prove probabilistic almost-sure termination without a probabilistic model outside ordinary `requires`/`ensures` proofs. The paper's theorem assumes δ>0, independent trials, fixed stage ordering, and eventual termination of each generated program (Sec. 4.2; Sec. 6.2.1, pp. 9, 25).

## technique 2: bounded model checking and k-induction pipeline
Use BMC to find finite-depth violations, then k-induction to extend the argument. The paper's method is explicit: “For BMC, loops are unrolled to depth k and the program is converted to SSA form, assigning unique versions to variables to simplify state representation for logical encoding” (Sec. 3.2.3, p. 9). It then says: “BMC verifies properties within finite bounds, generating verification conditions solved via SMT solvers” (Sec. 3.2.3, p. 9). Encode the SSA model and property φ into a verification condition; “An unsatisfiable result indicates correctness within the bound” (Sec. 3.2.3, p. 9). Finally check the k-induction base case (all paths up to k) and inductive step (if the property holds for k consecutive states, it holds for the next) (Sec. 3.2.3, p. 9). Inference: the closest Verus form is a Rust function with `requires` and `ensures`, loop `invariant` clauses, and a `decreases` measure; SSA conversion, SMT solving, and counterexample traces remain verifier internals rather than Verus source constructs. The paper warns that state-space explosion motivates symbolic model checking and BMC (Sec. 3.2.3, p. 9).

## technique 3: SMT verification conditions and counterexamples
Use SMT after translating program paths and specifications into logic. The paper explains that SMT combines Boolean satisfiability with decision procedures for “bit-vector theory for fixed-width integers and bit-level operations, array theory for memory operations and data structures, linear arithmetic for integer and real constraints, and uninterpreted functions” (Sec. 3.2.4, pp. 10–11). The SAT core proposes assignments, theory solvers check consistency, and conflicts refine the search. A satisfiable verification condition produces “a concrete counterexample – an execution trace showing the sequence of states leading to the property violation” (Sec. 3.2.4, p. 11). Inference: in Verus, write the semantic contract and let the verifier's SMT backend discharge arithmetic and sequence facts; expose counterexamples through failed verification diagnostics rather than runtime proof calls. The trusted result is the solver/verifier implementation and its axioms; generated LLM text is only a candidate until checked.

## technique 4: vectorized Monte Carlo validation and calibration
The experiment tests the chain rather than real LLM calls. For each δ in `{0.1,0.2,…,0.9}`, it samples a 10,000×4 matrix with `Mi,j ~ Geom(δ)` and computes each trial by row sum (Sec. 5.2.2, p. 19). The protocol states: “For each δ value in {0.1, 0.2, . . . , 0.9}, execute 10,000 independent trials” (Sec. 5.2, p. 18), with seeded random generation and logging. A trial is success when it takes at most 1,000 iterations (Sec. 5.2.3, p. 20). Table 8 reports 10,000 trials per δ, 100.00% success for every δ, means 39.876 at δ=.1 through 4.443 at δ=.9, and conservative factors 0.9942–1.0043 (Sec. 6.1.1, p. 21). These denominators are per-δ trial counts; the paper's “over 90,000” total is nine settings × 10,000. It also reports P99 latency 97 at δ=.1 and 7 at δ=.9 (same table). Inference: VL could estimate δ separately for code generation, compilation, proof synthesis, and solving, then budget retries using the weakest stage; this is a planning heuristic, not a Verus proof.

## evidence, trust, limits, and product threat
The paper measures synthetic geometric draws, iteration count, confidence intervals, variance, tail latency, runtime, and memory. It does not prove that a deployed LLM has stationary independent δ. Its own validity section states: “Experiments use modeled behavior (sum of independent Geometric distributions); validation with real LLM and application programming interface (API) is future work” (Sec. 6.2.2, p. 25). It also assumes constant δ, only five states, and a 1,000-iteration cutoff (Sec. 6.2.1). The reported 100% rates therefore have denominator 10,000 synthetic trials per setting, not production attempts. Inference: the framework is useful for retry-budget instrumentation but is weak evidence for the safety of agent-written verified Rust; a wrong contract can be proved consistently, and the theorem says nothing about specification correctness. Existing BMC, k-induction, SMT, and LLM invariant-generation techniques are already described here; VL should reuse their roles rather than claim them as new.

## techniques for the catalog
- absorbing-chain retry model — represent mandatory verification stages as transient states with geometric residence times and an absorbing Verified state
- BMC plus k-induction — unroll loops, encode bounded VCs, then prove base and inductive cases
- SMT VC solving — combine SAT with theories and inspect concrete counterexample traces
- vectorized convergence calibration — sample independent geometric stage times, aggregate rows, and compare empirical means and tails with `4/δ`
