# CBMC: The C Bounded Model Checker
(authored by agents unless marked 🧑)
Tag: `kroening2023cbmc`, [paper](https://arxiv.org/abs/2302.02384) (link from the paper text: arXiv:2302.02384v1)

## bounded model checking method

CBMC translates C programs, assertions, and bounded loop executions into a bit-precise formula, solved by a SAT or SMT back end. “If the formula is satisfiable, then an execution leading to a violated assertion exists.” (Section 1, p. 1) Conversely, “if the formula is unsatisfiable, no assertion can be violated with the given unwinding bounds” (Section 5.4, p. 26). Section 1 (p. 1) names these uses: bug finding, property checking, test input generation, detection of security vulnerabilities, equivalence checking and program synthesis. It lists CBMC’s advantages as “its precision, robustness and simplicity” (p. 1).

The complete pipeline (Figure 2, Section 5, pp. 19–26): parse and type-check source; convert it to GOTO programs; analyse and transform; instrument properties; symbolically execute and unwind loops into static single assignment (SSA) form; encode the equation as CNF or SMT; call a solver; decode a satisfying model as a counterexample.

Inference: use it when a Rust or C property can be checked over a finite execution bound.

## technique: assertions and built-in property checks

Put `assert` or `__CPROVER_assert(condition, "description")` at the property boundary (Section 3.3, p. 12). CBMC can also generate checks for signed overflow, division by zero, pointer and array bounds, memory leaks, and related properties (Table 1, p. 2; Section 3, p. 6; option list in Section 5.2, p. 23). The paper’s absolute-value example initially reports “VERIFICATION SUCCESSFUL” with zero verification conditions; the paper calls this “vacuous” because the source contains no assertion (Listing 2 and discussion, pp. 3–4). Running `cbmc --function abs --signed-overflow-check abs.c` generates one VCC; SAT finds a model and reports “arithmetic overflow on signed unary minus in -x” (Listing 3, p. 4). Adding `--trace` shows the triggering input x = −2147483648 (Listing 4, p. 5).

Steps the paper shows on `login.c` (Section 3.2, pp. 9–11): run with `--unwind 20 --bounds-check` (C5); list the generated properties with `--show-properties` (C6); optionally print the verification conditions with `--show-vcc` (C7); run the decision procedure (C8); add `--trace` for the counterexample (C9). The generated properties “need not necessarily correspond to bugs” because the preliminary static analysis can be imprecise; the solver decides which hold (Section 3.2, p. 11; Section 3, p. 6). A satisfiable result for a property gives a concrete counterexample trace, not just an abstract warning (Section 3.2, p. 11).

Inference: in Verus, express the same obligation as `requires`/`ensures` and use executable test harnesses for counterexamples. Verus’s contracts are not CBMC assertions: a Rust contract is proved for all executions accepted by the verifier, while CBMC’s bounded SAT result is finite unless loop completeness is separately established.

## technique: loop unwinding with soundness controls

CBMC replaces a loop by nested conditional copies of its body. For five iterations, the first copy is guarded by `cond`, the next copy sits inside it under another `cond`, and so on; this is trace-equivalent to the original for traces with up to five iterations (Section 5.3, p. 25). “In many cases, CBMC is able to determine automatically an upper bound on the number of loop iterations” (p. 25), but this “may fail if the number of loop iterations is highly data-dependent” (p. 26); then the user gives `--unwind B` (global) or `--unwindset L:k,...` (per loop; ids from `--show-loop-ids`) (Section 5.3, pp. 24, 26).

Workflow assembled from the options in Section 5.3 (p. 24); the paper does not present it as one procedure:

1. inspect loop identifiers with `--show-loop-ids`;
2. choose a global `--unwind B` or per-loop `--unwindset` bound;
3. add `--unwinding-assertions` so CBMC inserts assertions, not assumptions, that the loop exit condition holds at the bound (the bound was sufficient);
4. the paper says successful verification with `--unwind` or `--unwindset` “is unsound, unless the specified bounds amount to complete loop unwinding”; treat a run without unwinding assertions as bug hunting only (Section 5.3, p. 24; Section 3.1, p. 8).

The paper warns that `--partial-loops` changes the program: “neither assumptions nor assertions are generated during loop unwinding”, which “may result in traces that cannot occur in the original program” (Section 5.3, p. 24). It also notes that unwinding counts backjumps, so a loop testing `i<100` needs a limit of 101, not 100 (Section 5.3, p. 26). The paper states that CBMC “currently does not increase the maximum length of paths as bounded model checking proceeds, and is thus not complete” (Section 5.3, p. 24).

Inference: Verus’s loop invariants are the unbounded analogue. A Verus proof should state and prove an invariant rather than silently selecting an execution bound; bounded harnesses can still use CBMC-style finite exploration to find bugs before invariant proof.

## technique: nondeterministic inputs and assumptions

Use nondeterministic functions to model arbitrary inputs, then constrain them with `__CPROVER_assume`. The paper’s `one_to_hundred` example calls `nondet_uint`, assumes `result>=1 && result<=100`, and returns the result (Section 3.3, p. 12). The user must ensure the assumption is satisfiable, “otherwise the model checking step will pass vacuously” (p. 12). Assumptions are not retroactive: they only affect assertions that follow them in program order, so an assertion placed before the assumption fails (p. 12). Nondeterminism also does not implement universal quantification; assuming `a[x]>=0` for one nondeterministic `x` does not establish `a[y]>=0` for another (Section 3.3, p. 13).

Inference: Verus uses universally quantified specifications and explicit `requires` predicates, so an assumption should become a precondition only when it describes the actual caller contract. A ghost nondeterministic input can model an arbitrary value, but adding a satisfiability check or concrete harness is necessary to avoid vacuous proofs.

## technique: counterexample-guided debugging

When SAT finds a model, CBMC consults the equation of guarded statements: “each statement with a guard evaluating to true under the computed model constitutes an assignment occurring in the counterexample” (Section 5.4, p. 26). For `login.c`, `--bounds-check --pointer-check --trace` reports the out-of-bounds write at `buffer[index]` with index 16 and the `getchar` input values that trigger it (Section 3.2, pp. 10–11, Listing 9). The paper says that adding a branch limiting the input to 15 characters fixes the bug, after which CBMC reports all properties proved (p. 11): reproduce the path, add a guard or fix the code, then rerun.

Inference: VL can use counterexample traces as a repair input for agent-written Rust, but must distinguish a bounded witness from a proof failure. The trace should be stored with property name, source location, model, architecture, and unwind bound.

## architecture and evidence

The intermediate GOTO language keeps “assignments, gotos, function calls, declarations, assertions, and assumptions” (Section 5.2, p. 21). SSA conversion yields “a mathematical equation over renamed program variables in guarded statements”; the guards determine whether an assignment is made in a concrete execution (Section 5.3, p. 24). CNF encoding is bit-precise; SMT back ends include Z3 and CVC4 and are selected with `--smt2`, `--z3`, or `--cvc4` (Section 5.4, p. 26). “The CNF formula, which can be printed using --dimacs, is passed to the SAT solver, which tries to find a satisfying assignment.” (Section 5.4, p. 26) The paper lists “limited support for unbounded verification” as a weakness (Table 1, p. 2).

Inference: the trusted components include the C semantics and front end, the encoding, the selected solver, and CBMC’s trace decoder; the paper does not enumerate a trusted base.

The paper’s tutorial numbers are single runs: the overflow run reports 221 variables, 203 clauses, and 0.00414769 s (Listing 3, p. 4), and the version banner reads CBMC 5.12 on 64-bit x86_64 macOS (Listing 2, p. 3). Section 6 (pp. 27–30) is a performance history: 22 CBMC versions from 4.0 (June 2011) to 5.20 (December 2020), 9 SV-COMP categories, run with BenchExec on Ubuntu 16.04 and an Intel Xeon Platinum 8175M at 2.50GHz with limits of 15 GB and 900 s (p. 27). The paper says these scores “cannot be compared with the official SV-COMP results” (p. 27), and concludes that performance improved through “a steady stream of incremental enhancements and bug fixes” (p. 30). On MemSafety-Heap, incorrect results fell “from a sixth incorrect results in CBMC 4.6 down to a single incorrect result since CBMC 5.9” (Section 6, p. 30).

Inference: a bounded result is sound only when unwinding assertions pass or loops are fully unwound; completeness depends on bounds or additional reasoning.

Inference: Kani’s CBMC backend makes these controls directly relevant to VL. Agent-written verified Rust should record architecture, integer widths, loop bounds, assumptions, and solver mode; otherwise a green bounded result is difficult to interpret or reproduce.

## what VL should reuse and what it should not redo

Inference: reuse CBMC’s explicit property instrumentation, SSA-style trace decoding, assumption-vacuity warnings, loop-bound assertions, and machine-readable output options (`--json-ui`/`--xml-ui`, Section 5.1, p. 20). Do not redo a bounded checker without preserving the distinction between a finite safety result and an unbounded proof; the paper notes that for unbounded loops “CBMC is used for bug hunting only” (Section 3.1, p. 8).

## techniques for the catalog

- bit-precise bounded model checking: unroll finite executions and solve assertion violations as SAT/SMT constraints
- property instrumentation: combine user assertions with generated overflow, memory, and bounds checks
- loop unwinding assertions: detect insufficient bounds instead of silently assuming loop exit
- nondeterministic assumptions: model arbitrary inputs while guarding against vacuous constraints
- SSA counterexample traces: decode solver models into source-level failing executions
