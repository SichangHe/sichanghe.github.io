# PrefixGuard: Online Failure Warning and Trace-Grounded Diagnosis for LLM Agents
(authored by agents unless marked 🧑)
Tag: `huang2026prefixguard`, [paper](https://arxiv.org/abs/2605.06455)

## purpose and result
PrefixGuard links early failure prediction with an inspectable symbolic execution model. The abstract states, “We introduce PrefixGuard, a neuro-symbolic method that uses learned events to connect online failure warning with finite-state execution diagnosis.” (abstract, p. 1) A GRU predicts risk from prefixes; a deterministic finite automaton (DFA) replays the same learned events; composing the DFA with rule monitors supports model checking. Scope: four agent benchmarks (WebArena, τ2-Bench, SkillsBench, TerminalBench), trained and tested on a trajectory split in which every held-out task also occurs in training; the conclusion says "Performance on unseen tasks and agents remains unmeasured." (Section 6, p. 10)

## technique: structured trace and risk-aligned event learning
What it is: turn each agent step into a fixed StepView record, map records to a small event alphabet, and train a recurrent risk monitor from terminal outcomes. “For each execution step, we extract metadata, observation, action, tool, arguments, result, and status into a StepView record.” (Section 2.2, p. 3)
How to do it: have an LLM propose a field parser from training trajectories, freeze the parser, fit TF-IDF on training data, and represent each record as a vector. The parser is proposed once, offline, by an LLM (gpt-5.4-nano in Appendix A.2), so no LLM is called at scoring time. A projection produces K event logits (K = 16, or 32 on TerminalBench; Table 4); use softmax probabilities for the GRU and the highest-probability event for DFA replay. During training use Gumbel-softmax samples, derive horizon-specific prefix targets from terminal labels (a prefix is positive if the run fails and at most H steps remain; Appendix B.3), minimize binary cross-entropy plus the balance loss, select a checkpoint by validation AUPRC, and freeze it before calibration and DFA induction (Section 2.2, pp. 3–4). The alert threshold is set by split-conformal calibration on successful calibration runs at a nominal 10% false-alarm (FAR) budget (Section 3.1, p. 6).
Verus form: Inference: record source edits, `cargo verus` invocations, solver diagnostics, and proof failures as structured events. A warning model can prioritize review, but it cannot replace a Verus proof. The actual property remains a Rust contract such as `fn f(x: int) requires x >= 0 ensures result >= 0 { ... }`, with loop `invariant` or `proof fn` support where needed.
Evidence: across 24 benchmark–horizon settings, PrefixGuard exceeded the strongest baseline in mean test AUPRC; average gains were 12.0–21.9 percentage points. At a nominal 10% false-alarm rate, test recall ranged 56.1%–93.0% across benchmarks (abstract, p. 1). The strongest baseline was PPM-LSTM in every benchmark (Section 3.2, p. 6). Inference: these are predictive-monitor metrics, not proof correctness.
Limits: the event symbols are learned and have no predefined tool meaning; interpretability depends on aligning them back to recorded steps. A GRU fed the same TF-IDF features without the event projection scored 0.4–2.4 points higher in AUPRC (Section 3.2, p. 7), so the discrete events cost a little accuracy. The 10% budget is nominal: realized test FAR exceeded 0.10 for some seeds, for example for all three seeds at every τ2-Bench horizon (Tables 10–11, Appendix C.1, p. 19).

## technique: risk-compatible DFA induction and replay
What it is: induce a compact, risk-labeled DFA from frozen hard events and prefix labels. The DFA has states, event transitions, a start state, and horizon-specific state risk; replay maps each execution to a state path. The paper says, “The DFA replays an execution as a state path and can be combined with rule monitors to check task requirements.” (Section 1, p. 2)
How to do it: organize hard event sequences into a prefix tree; merge states only when empirical risk and recursively corresponding next-event risks are compatible under a Hoeffding-style test (merge tolerance η = 0.05); fold into the compatible state with closest risk (ties broken by support, then node index); compact reachable states; add an absorbing sink for missing transitions. State risks are estimated separately on calibration prefixes with smoothing; the training-prefix risks guide merging only. Replay the event sequence, then align each state with the original action and feedback to locate divergence (Sections 2.3 and 3.3, pp. 4–5 and 7–8; Appendix A.4).
Verus form: Inference: the DFA is an external trace abstraction. A Verus implementation can expose a state-machine model with a state variable and transition proof, but the event replay itself does not prove the Rust implementation. Use `requires` and `ensures` for each transition and `invariant` for repeated execution; keep the DFA as diagnostic evidence.
Evidence: DFAs averaged 5.0–32.3 states and retained 90.9% of paired GRU test AUPRC on average (Section 3.3, pp. 7–8). In the τ2-Bench example (H=3, seed 13) the failed run reaches alert state s6 at t=13 with risk .965 and returns to it at t=19, while the successful run stays in low-risk s8 (Figure 5 and Section 3.3, p. 8).
Limits: coarse states can group prefixes with different risks. With GRU alerts as reference, DFA alert recall was 71–98%; DFA precision was 64–88% on τ2-Bench, SkillsBench and TerminalBench but 37–76% on WebArena, which the paper attributes to few test prefixes leaving each state too coarse (Section 3.3, p. 8). Separately, the DFA's own risk threshold at the 10% FAR budget raised no alert at all on WebArena and on SkillsBench for H ≥ 24 (Appendix E.2, Table 24, pp. 29–30), because the highest-risk state was reached by too many successful calibration runs; the alert-state set matched to GRU alerts avoids this.

## technique: product composition with task-grounded safety monitors
What it is: refine learned DFA states by composing them with a monitor for an explicit safety specification. The paper writes, “The specification requires a read-class event between every two write-class events.” (Section 4, p. 8)
How to do it: define abstract event classes or concrete tool-call facts; write each requirement as an LTLf safety property and compile it into a monitor automaton; annotate DFA edges with tool-call facts; form product states `(s,u)` where `s` is the learned risk state and `u` tracks specification status; search for violating product states; because the DFA can recombine edges into paths not observed in training, verify every flagged violation against the original trajectory before counting it (Section 4, pp. 8–9; Appendix F.2).
Verus form: Inference: this corresponds to a Verus transition-system proof in which a ghost state records whether a required read occurred before the next write. State transitions carry `requires` and `ensures`; a loop `invariant` states that no forbidden write sequence has occurred. Unlike the paper's LTLf monitor, the Verus proof checks the executable Rust transition relation, while the product monitor checks paths of the learned DFA, which are then validated against recorded traces.
Evidence: on one τ2-Bench DFA, the read-between-writes specification raised AUPRC from .457 to .510 (Section 4, p. 9; nonterminal test prefixes, H=3, seed 13, Appendix F.1, p. 34); it separated three prefixes in the same DFA state s9 into ready, awaiting a read and violated, with calibration risks of 0.098, 0.158 and 0.308 (Table 2, p. 8). The full audit covered 359 retail executions: 265 successes and 94 failures across 114 tasks and four agents. After verification, five specifications flagged violations in 21 of 265 successes (7.92%) and 19 of 94 failures; "Five flagged successes were never rejected by the runtime yet violate a specification" (Section 4 and Table 3, p. 9). In the task-27 case both the failed and the successful run violate φ1, so a flagged violation alone does not separate failure from success (Section 4, pp. 9–10).
Limits and assumptions: the five requirement families were derived by inspecting the failures and fixed before whole-population counting, and the audit is "a retrospective audit of the same executions used for requirement discovery" (Appendix F.2, p. 35); runs that never trigger a property satisfy it vacuously (Section 4, p. 9); Table 3 also reports unknown verdicts, 8 successful runs under φ4. Inference: results depend on accurate edge annotations and trace validation, and a false or incomplete task specification produces a formally checked but irrelevant result.

## techniques for the catalog
- risk-aligned event monitor — encode trace steps, train a recurrent prefix-risk predictor, and freeze its event mapping
- compact DFA replay — merge compatible event histories into risk-labeled states and align replay paths with concrete actions
- product model checking — compose DFA transitions with explicit safety monitors and validate every violation against the original trace
