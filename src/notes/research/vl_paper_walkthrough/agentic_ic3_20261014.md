# Agentic-IC3: Enabling Semantic Proof Search in IC3 Model Checking
(authored by agents unless marked 🧑)
Tag: `fan2026agenticic3`, [paper](http://arxiv.org/abs/2609.27162v1)

## problem and result
The paper integrates a language-model agent with a persistent, word-level IC3 model checker. The checker retains soundness: it validates each proposed proof update with SAT/SMT checks, while the agent supplies semantic proof-search guidance from RTL, the property, frame lemmas, proof obligations, and solver feedback. The abstract says, “The backend checks proposals before updating the proof state, preserving soundness and providing feedback for further reasoning.” (Abstract, PDF p. 1.) The system adds three actions: Propose lemmas, Observe derived expressions, and Backtrack to revise a prior proposal (§4, PDF pp. 6–11).

Evaluation used 14 hardware benchmarks, one CPU core, 16 GiB, and a 3,600-second timeout per run (§5, PDF p. 12). Agentic-IC3 solved 10/14; rIC3 and A-IC3 solved 5/14 each and Pono-IC3Bits 0/14 (Table 2, PDF p. 13). Four cases were solved by Agentic-IC3 and by none of the three baselines. Inference: These results support this configuration on the selected suite, without establishing general performance. The paper reports, “Across the ten completed runs, time spent awaiting agent responses accounts for 87% of the aggregate runtime.” (§5.1, PDF p. 12.)

## technique 1: word-level semantic lemma proposals

what it is and when to use it

IC3 proves a safety property by building an inductive invariant from frame lemmas. In word-level mode, a lemma can express a multi-bit relation such as register equality or an arithmetic bound. Inference: Use semantic proposals when bit-level literal removal misses a relationship present in RTL. The motivating two-copy controller example has a local lemma excluding `DONE` at frame 1, but the agent proposes the cross-copy relation `s1 = s2`, which captures synchronization across phases (§3, PDF pp. 5–6). The paper states, “Useful generalizations depend on the design behavior and the property being checked.” (§1, PDF p. 2)

how to do it

1. Encode RTL to a word-level transition system; expose RTL signal names, widths, assumptions, property, current proof obligation, active frame lemmas, and solver feedback. The paper states, “The agent proposes lemmas using a subset of Verilog expressions, including arithmetic, comparisons, bitwise operations, and concatenation.” (§4.1, PDF p. 7)
2. At a SAT generalization request, collect predecessor states and conventional generalized regions; at an UNSAT request, collect checked blocking lemmas. The agent examines the batch and proposes one or more expressions.
3. Parse and type-check each expression and compile it to quantifier-free bit-vector SMT. Validate a lemma before admitting it to frames.
4. For SAT proposals for obligation `(q, i)`, test the conjunction against the predecessor query. If it excludes no predecessor, request revision. In proposal order, use bounded model checking to find a reachable violation within `i − 1` transitions; return a violation for revision, otherwise recursively block `(¬ℓ, i − 1)`. Repeat the predecessor query after each refinement; once it is UNSAT, proceed to UNSAT generalization. For UNSAT proposals, check initiation `Init ⇒ ℓ` and relative inductiveness `Fi−1 ∧ ℓ ∧ T ⇒ ℓ′`; add a passing lemma to frames F1…Fi and remove batch lemmas it implies.
5. Keep each admitted lemma even if a later proposal is abandoned; it has passed its own checks.

The paper’s concrete fp-adder revision illustrates the method. An early equality requirement was too strong because one operand had not yet been updated. Recursive feedback exposed a transition from state 0 to state 1 with unequal old operands; the agent backtracked and replaced it with `b1 = b2` only when `s1 ≥ 2` and `a1 ≠ 0`, and decoded-field equality only for `3 ≤ s1 ≤ 10` and `a1 ≠ 0` (§5.3, PDF pp. 15–16).

Verus form

Inference: A possible Verus adaptation would model the Rust state, transition relation, and safety predicate, then check candidate equality or arithmetic lemmas against that model. An IC3-style implementation would also need frame bookkeeping. This is a proposed adaptation, not an implementation or result evaluated in the paper.

evidence, assumptions, failure

Agentic-IC3 solved 10/14 in the full comparison; its remaining four cases timed out (Table 2, PDF p. 13). The current language cannot conveniently express quantified indexed relations: the FIFO trajectory needed sixteen disjuncts for address offsets (§5.3, PDF p. 16). The system also lacks stateful observations for values across execution stages, a limitation implicated in the timed-out `picorv32_insn_sub` run (§5.3, PDF pp. 16–17). The paper states, “Some useful proof relationships connect values from different execution stages, while the current observation mechanism only defines expressions over the existing state.” (§5.3, PDF p. 16.) Inference: Trusted components include Pono, Yosys, Bitwuzla, the Verilog-expression parser and compiler, and the hardware model; checking proposed formulas does not validate those components.

## technique 2: batch generalization

what it is and when to use it

Batching gives the agent multiple predecessor regions or blocking lemmas at once, making relationships across examples visible. Inference: Use it when single-state generalization overfits concrete register values. The paper states, “SAT batches contain predecessor states and their generalized regions, while UNSAT batches contain blocking lemmas obtained during IC3 search.” (§4.2, PDF p. 8.) The SAT algorithm collects up to `b` predecessors, generalizes each, and excludes each covered region before collecting the next (Algorithm 1, PDF pp. 8–9). The UNSAT algorithm collects checked blocking lemmas, then lets a validated proposal replace every batch lemma it implies (Algorithm 2, PDF pp. 9–10).

how to do it

1. Set a maximum batch size `b` and proposal limit `mmax`; the evaluation used `b = 5`, `mmax = 5` (§5, PDF p. 12).
2. For SAT, enumerate predecessors satisfying `Fi−1 ∧ T ∧ q′`; conventional-generalize each state to G; add `¬G` to the enumeration query; stop at `b` or UNSAT.
3. Ask for candidate lemmas with conjunction `L`. If `Fi−1 ∧ T ∧ q′ ∧ ¬L` is UNSAT, no predecessor is excluded: request revision. Otherwise, process candidates in order with BMC to depth `i − 1` and recursive blocking as above.
4. For UNSAT, collect checked lemmas before adding them to frames. Request generalization when the batch reaches `b`, or earlier when search needs the lemmas. For each candidate ℓ, identify batch members with `ℓ ⇒ B`, check initiation and relative inductiveness, add a passing ℓ to F1…Fi, and remove covered members. Return a failed check's counterexample for revision; continue until every batch member is covered.

Verus form

Inference: An external proof-search tool could batch state samples or obligations, propose Verus lemmas, and ask Verus to check each candidate. The paper does not implement or evaluate this adaptation.

Evidence and limits

The paper reports, “The total decreases from 515 to 137, a reduction of 73%, with the largest reductions on fifo_vis (173 to 7) and cache (22 to 2).” (§5.2, PDF p. 13.) Both configurations solved 10/10; batching reduced runtime on nine of ten, including 3.3× on `fp_divider` and 2.6× on `fp_adder` (Table 3, PDF p. 14; discussion, p. 13). These denominators are the ten benchmarks solved by the full system, not all 14.

## technique 3: derived observations and controlled backtracking

what it is and when to use it

An observation is a named, type-checked expression whose value is added to future requests. It exposes a relation hidden by raw registers (§4.3, PDF pp. 10–11). In the FIFO example, the four-bit `obs.occupancy = rb.head − rb.tail` makes ring-buffer occupancy comparable with shift-register length; arithmetic is modulo 16 and empty flags distinguish empty from full (§5.3, PDF p. 15). The agent may repeatedly Observe before proposing a lemma; observations persist across the session.

Backtracking cancels a recursive SAT attempt and revisits the parent obligation with retained admitted lemmas. The paper states, “Admitted lemmas remain in their validated frames and can prune subsequent search, since each has passed its own proof checks independently of the abandoned proposal.” (§4.4, PDF p. 11.) Inference: Use it when deeper feedback reveals an unproductive proof direction, including an equality required before the relevant update. The fp-adder example restricts equalities to control states after the corresponding register updates (§5.3, PDF pp. 15–16).

how to do it

1. Return `Observe(e)`; parse, type-check, register name, definition, and width.
2. Reissue the request with observation values evaluated on states and counterexamples; then propose a lemma using the observation.
3. At a SAT generalization request for `(¬ℓ, i − 1)` created by a parent proposal, `Backtrack` ends the recursive attempt and skips remaining lemmas from that proposal response. Re-run the parent's predecessor query with retained validated frame lemmas; if predecessors remain, collect a new batch and request guidance.

Verus form

Inference: Define observations as pure `spec fn`s over the ghost/model state, and use them in `assert` or lemma proofs. A history observation requires explicit ghost state and initialization/update invariants; it must not alter executable behavior unless that state is deliberately part of the verified model.

Evidence and limits

Without observations, the ablation solved 9/10; the full system solved 10/10. On `gulwani_fig1a_2_ebmc`, observations yielded 175.73 seconds and 7 generalizations, while no-observation timed out after 41 generalizations (Table 3, PDF p. 14). With backtracking enabled, generalizations decreased from 67 to 23 on `fp_adder` and 43 to 11 on `nerv_causal`; both configurations solved all ten. Inference: These selected runs do not establish a general runtime benefit. The paper warns that observation definitions currently describe only existing state, and quantified or temporal relationships require backend extensions (§5.3, PDF pp. 16–17).

## what is proved, what remains trusted, and product threat

The backend checks initiation and relative inductiveness before admitting lemmas. For SAT proposals it first checks that at least one predecessor violates the proposed conjunction, then checks bounded reachability and recursively attempts to block the negated lemmas (§4.2, PDF pp. 8–10). The benchmark measures solved cases, runtimes, agent wait time, generalization counts, observations, and backtracks (Tables 2–3, PDF pp. 13–14). Inference: These checks do not establish that an LLM explanation is correct, that the RTL model matches deployed hardware, or that the property captures the product requirement. For VeruLaw, the useful pattern is to check agent proposals independently. Latency is an observed cost; weak specifications, model/implementation mismatch, and missing temporal state remain concerns when adapting the method. A product could log candidates, checker results, counterexamples, and retained lemmas, and make trusted assumptions explicit. Reusing these proof-search patterns does not establish novelty for VL.

## techniques for the catalog

- word-level semantic lemma proposals — expose RTL-level equalities and arithmetic relations, then admit only solver-checked initiation, inductiveness, BMC, and recursive-blocking results
- batch generalization — collect multiple SAT predecessor regions or UNSAT blocking lemmas so proposals capture cross-state relationships
- persistent derived observations — register typed expressions whose values enrich later proof requests and make hidden relations explicit
- proof revision by backtracking — abandon a recursive proposal after counterexample feedback while retaining independently validated lemmas
