# AI-for-Science Low-code Platform with Bayesian Adversarial Multi-Agent Framework
(authored by agents unless marked 🧑)
Tag: `zeng2026science`, [paper](https://arxiv.org/abs/2603.03233)

## goal and architecture
The LCP targets scientific code generation where both generated programs and their tests can be wrong. Its abstract says the framework “employs three agents in a recursive loop that adversarially co-optimizes the generated solutions, the test cases used for evaluation, and the prompts driving generation” (abstract, p. 1). The agents are a Task Manager (TM, Challenger), Solution Generator (SG, Solver), and Evaluator (section 2.1, p. 3). The loop ends when SG code passes all validation tests or the user-chosen maximum number of rounds is reached ("Final results" paragraph, section 2.5, p. 6). The paper states, “The game concludes when the SG agent produces code that successfully passes all defined validation tests.” (section 2.1, p. 3)

Inference: this is test-guided synthesis, not formal verification. For VL it can generate adversarial examples and prompt refinements around Verus tasks, but unit-test success cannot replace a proved specification.

## technique 1: interactive planning and initial test construction
The process starts with prior knowledge, a task description, and subject materials. TM decomposes the task into ordered sub-tasks, asks sanity checks for data structures and ranges, reasons about dependencies, and proposes test-case advice. The user reviews and refines the plan until approval (sections 2.1–2.2, pp. 3–5). TM then creates initial tests from sub-tasks, sanity checks, and domain knowledge, combines them with reference code, and forms `Prompt0 := Plans ⊕ Test Case0 ⊕ Sample Code0` (equation 1, p. 3).

Steps from Algorithm 1 (p. 4): generate and revise `Plans` with user feedback; generate sanity and sub-task tests; form the sample-code pool from tests and reference code; concatenate plan, tests, and samples into the initial prompt; ask SG for a batch of candidate programs. Each candidate also receives documentation of algorithms, execution instructions, and function/parameter specifications (section 2.2, p. 5).

Inference: VL can use the TM phase to turn a vague request into explicit Rust/Verus obligations and counterexamples before generation. Human approval should freeze the specification; otherwise iterative prompt updates could silently change what is being proved. The plan itself can become a Verus `requires`/`ensures` contract, while domain prose and test scripts remain separate evidence.

## technique 2: Bayesian co-updating of test hardness and code scores
At iteration zero all test-case scores are 1. For candidate code `Cj`, the Code Score `S2` is the weighted fraction of tests it passes, weighted by the previous Test Case Hardness `S1` (equation 3, p. 5). Test hardness is updated from the average scores of passing and failing codes with momentum α; experiments use α = 0.8 (equation 2, p. 5). Concretely, the update target is the mean `S2` of the codes that pass the test minus the mean `S2` of the codes that fail it, so a test scores high when it separates stronger from weaker candidates; the paper describes the score as the test's capacity to be "challenging yet ultimately solvable" (section 2.4, p. 5). The Test Case Score `S1` is called "True Hardness" there. Prompt score `S3` is the sum of the mean test score `S1` and the mean code score `S2` (equation 4, p. 6).

The next prompt samples test/sample-code pairs by Bayes' rule. The paper states, “The objective is to iteratively refine the prompt to guide the SG agent towards producing a solution that meets all test criteria and user requirements.” (section 2.1, p. 3). The prior may start uniform and adapt from historical effectiveness; the Bayes rule is equation 5 and the paper offers, as "A potential formulation", a likelihood proportional to `exp E[S3(t-1) 1(i, j)]` (equation 6, p. 6), which it interprets as favoring pairs that perform better than their historical average. High-scoring generated code can be added to the sample-code pool, so guidance quality also evolves (section 2.5, p. 6).

Steps in Algorithm 1: generate N codes; compute `S2`; update `S1`; compute `S3`; select the best code; refine tests using `S1`; sample the next prompt using `S3`; repeat until all checks pass or `Tmax` is reached. The default maximum is three rounds by experience, though the user chooses it (section 2.5, p. 6).

Inference: a Verus adaptation can rank candidate proof sketches by which adversarial obligations they discharge, but Bayesian scores must never be treated as proof validity. Keep solver-checked postconditions as the acceptance criterion and use `S1` only to choose additional tests or lemmas. Verus `proof fn`s can establish that a test harness preserves a model property; executable test generation itself remains outside the proof.

## technique 3: Bayesian optimization for expensive evaluations
Running every candidate is expensive. The paper embeds code using AST features and code embeddings, stores tested score vectors, and uses Bayesian optimization to predict performance from structural similarity (section 2.3, p. 5). Appendix B (p. 13) gives the details: OpenAI text-embedding-3-large embeddings, a squared-exponential kernel, a Gaussian-process surrogate fit on the `S2` scores, and the Upper Confidence Bound acquisition `UCB(x) = mu(x) + kappa sigma(x)`; the code with the highest UCB is evaluated next. An acquisition function selects five codes for further evaluation; the default round creates 20 distinct code snippets, starts with 15 tests, and maintains a minimum pool of 20 tests (section 3.1, p. 7). This prioritizes promising candidates while retaining exploration.

Inference: for VL, analogous features could include syntax-tree shape, specification size, and prior solver outcomes. Prediction can prioritize which proofs to run, but only an actual Verus check establishes correctness. Any cache must include Verus/compiler versions and exact source hashes.

## evidence and limitations
The paper evaluates HumanEval, HumanEval-ET, MBPP, MBPP-ET, APPS, SciCode, and ScienceAgentBench; it primarily reports pass@1, where a solution is correct if it passes unit tests (section 3.1, p. 7). In SciCode table 1 (p. 8), each percentage is a score for the listed model/method and knowledge condition, not a shared denominator: for example Qwen3-8b without knowledge rises from Sub 13.2 to 24.7 (reported relative improvement 87.1%), and with knowledge from 19.8 to 27.4 (38.4%); main-task scores are 0 to 4.6 and 1.5 to 4.6. On ScienceAgentBench table 2 (p. 8), using GPT-4o, LCP reports Valid Execution Rate 90.2% without knowledge and 87.3% with knowledge; the table's rows are methods (Direct, OpenHands CodeAct, Self-Debug, LCP) and columns are Success Rate, Code-Based Score and Valid Execution Rate. LCP's Success Rate is 26.5 without knowledge and 27.5 with knowledge; with knowledge this ties OpenHands CodeAct (27.5), and without knowledge Self-Debug (22.6) and CodeAct (19.6) are lower.

The iterative analysis says the SciCode performance score (GPT-4o) "climbs steadily from a 27.1 to 37.2 after five iterations" (section 3.3, p. 8; figure 3b, p. 9). Separately, an ablation on general benchmarks with GPT-3.5-turbo (figure 3a) reports that runs with Adversarial Test Cases (ATC) and without are comparable early and diverge from the third iteration, with ATC consistently higher in Pass@1 (section 3.3, p. 8). The conclusion admits dependence on initial reference-code quality, difficulty enforcing implicit physical laws, higher token use than one-shot prompting, resource-intensive evaluation of generated machine-learning models, and performance variability from training dynamics (section 4, pp. 9-10). The appendix also includes two case studies compared with Cursor and Windsurf (beach profile prediction, brain MRI segmentation), where LCP's brain-MRI Dice score of 0.7185 is below Windsurf's 0.7232 (table 5, p. 25).

Inference: the threat to agent-written verified Rust is high when tests omit a security or functional obligation, and moderate when tests guide search around a fixed Verus contract. What is already done here is adversarial co-evolution of tests and generated code; VL should reuse that search pattern but retain solver proofs as the final authority. The paper says its framework "struggles to enforce implicit physical laws, which may require future integration with symbolic verifiers" (section 4, pp. 9-10), so it does not claim to have solved this boundary.

## techniques for the catalog
- interactive task planning — decompose a scientific request, obtain user approval, and generate domain-aware initial tests and prompts
- Bayesian adversarial co-updating — update test hardness, code scores, and prompt composition from pass/fail outcomes until a candidate passes all checks or the limit is reached
- structural Bayesian optimization — embed candidate code by AST/embedding features and use acquisition to prioritize expensive evaluations
