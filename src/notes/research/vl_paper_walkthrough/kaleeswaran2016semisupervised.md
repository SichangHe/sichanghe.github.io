# Semi-Supervised Verified Feedback Generation
(authored by agents unless marked 🧑)
Tag: `kaleeswaran2016semisupervised`, [paper](https://arxiv.org/abs/1603.04584v1)

## method and use case
The paper addresses large sets of student programs where manual feedback does not scale. Its method combines unsupervised clustering with formal equivalence checking. The abstract states: “We cluster submissions by solution strategy and ask the instructor to identify or add a correct submission in each cluster.” It then says: “We then verify every submission in a cluster against the instructor-validated submission in the same cluster.” (Abstract, p. 1.) Inference: use this when submissions share an algorithmic strategy but differ in syntax and may contain distinct faults.

The workflow is: collect unlabeled submissions; extract strategy features; cluster by equal feature vectors; ask the instructor to validate one correct submission per cluster or add one; compare each candidate with that reference; return verified corrections after establishing equivalence of the corrected fragments; leave cases the tool cannot handle for manual evaluation. If a cluster has no correct example, add one and recluster. Inference: VL could use this as a triage layer for generated Rust proofs, grouping similar proof obligations before expensive verification, but clustering is not evidence of correctness.

## technique: strategy-feature clustering
For iterative dynamic-programming submissions, the paper extracts the DP-array type and dimensions, whether input is reused as the DP array, the number of top-level loops containing updates, loop nesting depth, loop-index directions, and the updated DP element (Section 2.1, p. 3). It uses static analysis, pattern matching, and inter-procedural dependence tracking to identify arrays whose values depend on themselves. The paper says: “All our features are discrete valued. Therefore, our clustering algorithm is very simple and works directly by checking equality of feature values.” (Section 3.1.3, p. 5.) Page references here count PDF pages in the unnumbered arXiv manuscript.

Apply it by labeling input, initialization, update, and output statements; identifying top-level loops; computing the discrete feature tuple; and grouping submissions with equal tuples. The method intentionally does not encode exact initialization or update expressions, leaving correctness to verification (Section 2.1). Inference: in Verus, analogous features could include function shape, loop structure, and invariant vocabulary, but Rust’s types and proof blocks require a new extractor. Inference: equality of these features alone need not establish that two programs implement the same strategy. The authors report that their manual evaluation found the same strategy within each observed cluster (Section 5.1, p. 8).

## technique: counter-example guided equivalence and feedback
The reference and candidate are aligned by labeled matching fragments. First compare iteration spaces, including guards, and suggest corrections if they differ. Then check a loop-body query `ψ = pre ∧ ϕ1 ∧ ϕ2 ⇒ post`, where `pre` states equality of arrays, indices, and inputs at iteration start, `ϕ1` and `ϕ2` encode the reference and candidate bodies, and `post` states equality of DP arrays at iteration end; unchanged input variables are checked syntactically (Sections 2.2 and 3.2.2, pp. 4, 6).

When SMT finds a counterexample, select the reference and candidate guarded statements it satisfies. If their guards are equivalent under the precondition, replace the candidate assignment with the reference assignment renamed into candidate variables. Otherwise, split the candidate guard by the renamed reference guard: use the reference assignment on the overlap and retain the candidate assignment elsewhere. Refine the candidate formula and repeat (Section 3.2.3, pp. 6–7). The paper reports: “If an equivalence check fails, our algorithm uses the counter-example generated by the SMT solver to refine the equivalence query.” (Introduction, p. 2). In the matrix-path example, counterexample `j=0` produces the correction `D[i][j] = D[i-1][j] + A[i][j]`; a second counterexample for `j=i ∧ j≠0` produces the diagonal case; a final valid query establishes the fixes (Figure 5, p. 4). Algorithm 1 bounds refinements by δ (10 in the experiments) and suggests replacing the candidate body by the renamed reference body when the bound is reached (Section 3.2.3, p. 7).

Inference: a possible Verus adaptation is a proof lemma with `requires` describing equal initial states and `ensures` describing equal final DP arrays. Its counterexamples could guide candidate code corrections; the paper does not propose invariant synthesis. Inference: feedback generation would be an external tool proposing invariant or code changes, each requiring Verus proof checking. The paper’s equivalence proof is conditional on the modeled inputs and matching fragments, and program equivalence is undecidable, so some cases remain manual.

## technique: symbolic execution and formula encoding
The paper converts loop-free statements to guarded equalities: an `if(p) x=e` becomes a fresh-version equality guarded by `p`; if-else guards are made mutually disjoint; conjunction of guarded equalities encodes the block (Section 2.2, p. 4). Inter-procedural backward symbolic execution computes substitution stores and recovers data dependence through helper procedures (Section 3.1.2, p. 5). Repeating patterns such as array maximum are lifted to predefined functions such as `_max` before comparison (Section 2.2, p. 4). Variable maps match inputs by reading order and type, and DP arrays by type; control correspondence uses semantics-preserving loop splitting and selected loop merging, excluding DP-update merging (Section 3.2.1, pp. 5–6).

The substitution store first replaces temporary variables and procedure calls with guarded expressions over DP arrays, input variables, and loop indices. The tool then builds iteration-space and body queries, replacing each unique symbolic array expression with a scalar variable and preserving correspondence between programs. It uses commutative-operand ordering, input constraints, and array-bounds checks when constructing queries (Section 3.2.2, p. 6). Inference: Verus proof code can use ghost values and lemmas to represent these substitutions, but the paper’s symbolic store is an analysis representation, not executable Rust.

## evidence, trust, and limits
The implementation targets C and evaluates 2,226 submissions from 1,860 students at more than 250 institutes on four CodeChef problems. It verified 1,122 as correct and suggested corrections for 789, totaling 1,911 handled submissions (85%); 315 (15%) required manual evaluation. There were 114 clusters, including seven requiring manually added references. The reported average was 1.6 seconds per submission including clustering but excluding manual reference identification (Sections 5.1–5.4, pp. 8–9). The abstract states: “In an evaluation on 2226 submissions to 4 problems, we could generate verified feedback for 1911 (85%) submissions in 1.6s each on an average.”

Inference: the trusted base includes the C parser, feature extractor, SMT solver, normalization rules, and instructor-validated reference. The authors report faults in 265 distinct submissions accepted by CodeChef (Section 5.3, p. 9). The implementation does not support pointer arithmetic. The technique fails on scalar loop-carried dependencies other than loop indices, auxiliary arrays, and patterns it cannot label; nonlinear constraints and undefined expressions also limit SMT reasoning. It cannot suggest feedback for custom I/O errors, formatting, or typecasting, and supports only a subset of C constructs and library functions (Sections 4 and 5.5, pp. 7, 9–10). The paper warns: “Our approach may provide spurious feedback enforcing stylistic conformance with the instructor-validated submission.” (Section 5.5, p. 9.) Each equivalence query has a three-second solver timeout (Section 5.2, p. 8). Inference: for VL, the main product risk is trusting a bad reference or incomplete semantic model; every proposed Rust change still needs an independent Verus proof.

## techniques for the catalog
- semi-supervised clustering — group submissions by statically extracted strategy features and validate one reference per group
- reference-relative equivalence — compare matching fragments under a pre/post relational formula
- counter-example guided refinement — use SMT counterexamples to add missing guards or assignments and retry
- guarded formula encoding — translate imperative branches into mutually exclusive guarded equalities
- inter-procedural substitution — recover data dependence through helper procedures with symbolic stores
- pattern lifting — replace recurring expressions with predefined summaries such as array maximum
- verified feedback triage — return verified corrections and leave cases the tool cannot handle for manual evaluation
