# Semi-Supervised Verified Feedback Generation
(authored by agents unless marked 🧑)
Tag: `kaleeswaran2016semisupervised`, [paper](https://arxiv.org/abs/1603.04584v1)

## method and use case
The paper addresses large sets of student programs where manual feedback does not scale. Its method combines unsupervised clustering with formal equivalence checking. The abstract states: “We cluster submissions by solution strategy and ask the instructor to identify or add a correct submission in each cluster.” It then says: “We then verify every submission in a cluster against the instructor-validated submission in the same cluster.” (Abstract, p. 1.) Use this when submissions share an algorithmic strategy but differ in syntax and may contain distinct faults.

The workflow is: collect unlabeled submissions; extract strategy features; cluster by equal feature vectors; ask the instructor to validate one correct submission per cluster or add one; compare each candidate with that reference; generate corrections only when the equivalence proof succeeds; send undecidable cases to manual review. If a cluster has no correct example, add one and recluster. Inference: VL could use this as a triage layer for generated Rust proofs, grouping similar proof obligations before expensive verification, but clustering is not evidence of correctness.

## technique: strategy-feature clustering
For iterative dynamic-programming submissions, the paper extracts the DP-array type and dimensions, whether input is reused as the DP array, the number of top-level loops containing updates, loop nesting depth, loop-index directions, and the updated DP element (Section 2.1, p. 3). It uses static analysis, pattern matching, and inter-procedural dependence tracking to identify arrays whose values depend on themselves. The paper says: “The features extracted by our technique and their values for the submission in Figure 2 are as follows” (Section 2.1, p. 3), followed by the feature list. Page references here count PDF pages in the unnumbered arXiv manuscript.

Apply it by labeling input, initialization, update, and output statements; identifying top-level loops; computing the discrete feature tuple; and grouping submissions with equal tuples. The method intentionally does not encode exact initialization or update expressions, leaving correctness to verification (Section 2.1). Inference: in Verus, analogous features could include function shape, loop structure, and invariant vocabulary, but Rust’s types and proof blocks require a new extractor. This technique assumes the chosen features capture solution strategy; different strategies with equal features can be clustered together.

## technique: counter-example guided equivalence and feedback
The reference and candidate are aligned by labeled matching fragments. First compare iteration spaces, including guards. Then encode a loop-body query `ψ = pre ∧ ϕ1 ∧ ϕ2 ⇒ post`, where `pre` states equality of arrays, indices, and inputs at iteration start, `ϕ1` and `ϕ2` encode the reference and candidate bodies, and `post` states equality at iteration end (Sections 2.2 and 3.2.2, pp. 4, 6).

When SMT finds a counterexample, identify which guards differ, synthesize a guarded assignment or missing case, refine the candidate formula, and repeat. The paper reports: “If an equivalence check fails, our algorithm uses the counter-example generated by the SMT solver to refine the equivalence query.” (Introduction, p. 2). In the matrix-path example, counterexample `j=0` produces the correction `D[i][j] = D[i-1][j] + A[i][j]`; a second counterexample for `j=i ∧ j≠0` produces the diagonal case; a final valid query establishes the fixes (Figure 5, p. 4). Algorithm 1 bounds refinements by δ (10 in the experiments) and suggests replacing the candidate body by the renamed reference body when the bound is reached (Section 3.2.3, p. 7).

Inference: in Verus, the closest form is a proof lemma with `requires` describing equal initial states and `ensures` describing equal loop outputs, followed by counterexample-driven strengthening of `invariant` clauses. Inference: feedback generation would be an external tool proposing invariant or code changes, each requiring Verus proof checking. The paper’s equivalence proof is conditional on the modeled inputs and matching fragments, and program equivalence is undecidable, so some cases remain manual.

## technique: symbolic execution and formula encoding
The paper converts loop-free statements to guarded equalities: an `if(p) x=e` becomes a fresh-version equality guarded by `p`; if-else guards are made mutually disjoint; conjunction of guarded equalities encodes the block (Section 2.2, p. 4). Inter-procedural backward symbolic execution computes substitution stores and recovers data dependence through helper procedures (Section 3.1.2, p. 5). Repeating patterns such as array maximum are lifted to predefined functions such as `_max` before comparison (Section 2.2, p. 4). Variable maps match inputs by reading order and type, and DP arrays by type; control correspondence uses semantics-preserving loop splitting and selected loop merging, excluding DP-update merging (Section 3.2.1, pp. 5–6).

Steps are: normalize statements; introduce fresh variables; propagate path guards; conjoin constraints; substitute procedure summaries; compare normalized expressions; and issue a correction when the SMT model supplies a counterexample. Inference: Verus proof code can use ghost values and lemmas to represent these substitutions, but the paper’s symbolic store is an analysis representation, not executable Rust.

## evidence, trust, and limits
The implementation targets C and evaluates 2,226 submissions from 1,860 students at more than 250 institutes on four CodeChef problems. It verified 1,122 as correct and suggested corrections for 789, totaling 1,911 handled submissions (85%); 315 (15%) required manual evaluation. There were 114 clusters, including seven requiring manually added references. The reported average was 1.6 seconds per submission including clustering but excluding manual reference identification (Sections 5.1–5.4, pp. 8–9). The abstract states: “In an evaluation on 2226 submissions to 4 problems, we could generate verified feedback for 1911 (85%) submissions in 1.6s each on an average.”

The trusted base includes the C parser, feature extractor, SMT solver, normalization rules, and instructor-provided reference. The method identifies faults in 265 distinct submissions accepted by the online judge (Section 5.3, p. 9). It does not handle pointer arithmetic, some scalar loop-carried dependencies, auxiliary arrays, unsupported patterns, custom I/O errors, formatting, or typecasting. It can suggest spurious stylistic corrections; each equivalence query has a three-second solver timeout (Sections 4, 5.2, and 5.5, pp. 6, 8–10). Inference: for VL, the main product risk is trusting a bad reference or incomplete semantic model; every proposed Rust change still needs an independent Verus proof.

## techniques for the catalog
- semi-supervised clustering — group submissions by statically extracted strategy features and validate one reference per group
- reference-relative equivalence — compare matching fragments under a pre/post relational formula
- counter-example guided refinement — use SMT counterexamples to add missing guards or assignments and retry
- guarded formula encoding — translate imperative branches into mutually exclusive guarded equalities
- inter-procedural substitution — recover data dependence through helper procedures with symbolic stores
- pattern lifting — replace recurring expressions with predefined summaries such as array maximum
- verified feedback triage — generate feedback only after proof and route undecidable cases to a human
