## scope and central claim
Kovács and Voronkov give a tutorial and implementation account of first-order proving in VAMPIRE 2.6. The paper's abstract says, “In this paper we give a short introduction in first-order theorem proving and the use of the theorem prover VAMPIRE.” It teaches a reusable pipeline: encode formulas in TPTP, negate a conjecture, preprocess to clauses, search by resolution and superposition until saturation, remove redundant clauses, and inspect a refutation or a resource-bounded result.

## technique: TPTP problem encoding and refutation
Use this when a property is naturally a first-order consequence of axioms and assumptions. The paper's group example has identity, inverse, and associativity axioms, the assumption that every element squares to the identity, and the conjecture that multiplication commutes. Write each formula as `fof(name, role, formula)`; variables begin with capitals, universal quantification is `![X]:`, and function symbols use prefix syntax such as `mult(e,X)`. Save the file and run `vampire group.tptp`. The paper states, “All one needs is to write the formula as a problem in the TPTP syntax [31,33] and run VAMPIRE on this problem.” (Section 2, p. 4)

VAMPIRE proves a conjecture by adding its negation to the axioms and assumptions, then checking unsatisfiability. The paper states, “VAMPIRE tries to prove the conjecture of Figure 1 by adding the negation of the conjecture to the axioms and the assumptions and checking if the the resulting set of formulas is unsatisfiable.” (Section 2.2, p. 5) Apply this step by step: (1) state the executable or mathematical assumptions; (2) state the desired conjecture; (3) let the prover negate the conjecture; (4) inspect whether `$false` is derived. A refutation means the conjecture follows from those assumptions. In the example, the output contains 203 generated formulas but a 26-formula refutation; the reported run used 255 KB and 0.007 s. Those denominators and settings are the Figure 4 example, VAMPIRE 2.6, not a benchmark average.

Verus form: encode the same mathematical relation as `spec fn` values and `requires`/`ensures` on a Rust function, then prove the postcondition with `assert`, `lemma`, and solver automation. Inference: Verus does not consume TPTP directly; a translation layer would be needed. Inference: the refutation's negated-conjecture discipline corresponds to asking Verus to prove an `ensures` formula from `requires`, while Verus's executable function and Rust types add obligations absent from untyped first-order input.

## technique: saturation, superposition, and redundancy elimination
Use this when equality reasoning generates many possible clauses. VAMPIRE first preprocesses formulas, converts them to conjunctive normal form, then runs a saturation algorithm. The paper lists the pipeline as: “read the problem; determine proof-search options to be used for this problem; preprocess the problem; convert it into conjunctive normal form (cnf); run a saturation algorithm on it; report the result, maybe including a refutation.” Saturation means repeatedly applying sound inference rules until every non-redundant consequence has been generated or resources end. Superposition combines resolution-like inference with equality rewriting; clauses are selected fairly, new clauses are generated, and forward/backward simplification deletes tautologies, subsumed clauses, or clauses reducible by equalities.

The paper's simple saturation algorithm has these operational steps: maintain active and passive clauses; select an inference from passive material; forward-simplify the selected clause; generate superposition and other inferences; backward-simplify affected active clauses; move the surviving clause to active; stop on `$false` or saturation. The paper emphasizes, “A saturation algorithm with a fair inference selection strategy is called a fair saturation algorithm.” (Section 3, p. 10) Fairness is the completeness condition: an unsatisfiable input eventually gets a refutation if time and memory are unbounded. Inference: a Verus analogue is repeatedly applying local lemmas and quantified facts until the SMT solver closes the goal, but Verus does not expose VAMPIRE's active/passive clause engine as a user API.

## technique: resource-aware runs and proof artifacts
Always set a time limit (`vampire -t 5 group.tptp`) and optionally a memory limit (`-m`). VAMPIRE may discard clauses when memory is tight. The paper cautions that search behavior changes with a limit: it reports examples where a proof appears with less than 5% of the unlimited run time. (Section 2.3, p. 8) Treat a timeout as “not established,” not as a counterexample. The proof DAG records parent formulas and inference rules; the example uses superposition, inequality splitting, skolemisation, and 79 implemented inference rules. Statistics include generated clauses, active/passive clauses, memory, and elapsed time. Inference: for VL, preserve solver logs and proof-producing artifacts alongside Verus verification runs so a successful result can be audited rather than treated as an opaque Boolean.

## what is proved, trusted, and limited
The theorem-prover result establishes unsatisfiability of the encoded formula, conditional on sound inference, preprocessing, and the supplied axioms. The paper explicitly notes that rules introducing symbols may not preserve logical consequence but preserve satisfiability, and that a complete calculus may still fail to find a refutation within practical resources. Trusted inputs include the formalization, TPTP parser, VAMPIRE implementation, and hardware/runtime. Inference: Verus additionally trusts its verifier, SMT solver, proof erasure, compiler, and any external specifications; the first-order paper does not measure those Verus-specific boundaries.

## evidence and product threat
The paper's evidence is a worked group-theory proof and implementation statistics, not a product-scale study. Inference: the transferable lesson for agent-written verified Rust is a disciplined separation between encoding, normalization, search, and auditable proof output. The threat is specification drift: a passing proof only covers the TPTP/Verus contract actually written. VAMPIRE's undecidability and resource sensitivity also predict failures on large quantified Rust specifications; use bounded, modular lemmas and explicit invariants rather than expecting one global automatic proof.
