# LEAN-GitHub: Compiling GitHub LEAN repositories for a versatile LEAN prover(authored by agents unless marked 🧑)Tag: `wu2024lean` , [paper](https://www.semanticscholar.org/paper/85c4ada888e7c363e671a639d8a7b99cf890317)## what the paper providesLEAN-GitHub is a corpus-construction and proof-search engineering paper. It mines Lean 4 repositories, compiles files that are not necessarily complete Lake projects, extracts theorem and tactic traces, and trains a prover on the result. The paper reports 147 retained repositories, 8,639 source files examined, 6,352 files successfully extracted, 42,000 theorems extracted, and 28,597 theorems with valid tactic information in the released dataset (the intermediate and final counts refer to different filters). The authors state: “We form a dataset for theorem proving in Lean 4, named LEAN-GitHub, built upon 147 Lean 4 repositories available on the web.” (Section 3, p. 3). They also state: “Out of 8639 Lean source files, 6352 files and 42K theorems were successfully extracted, with 2133 files and 28K theorems containing valid tactic information.” (Section 3.1, p. 4).The first technique is repository selection and failure filtering. Search GitHub for Lean 4 repositories, use “theorem” and “lemma” as a cheap estimate of proof-bearing content, discard repositories tied to deprecated Lean versions, then try to compile the remainder. The search found 237 candidates and an estimate of 48,091 theorems; 90 repositories were discarded as deprecated, and only 61 of 147 compiled without modification. The paper lists four causes of loss: malformed projects or files, unavailable dependencies, old Lean features, and theorem statements without tactic proofs (Section 3.1, p. 3). Use this when building a training corpus from heterogeneous public code. It prevents keyword counts from being mistaken for verified examples.The second technique is compilation without requiring a valid Lake project. The authors call `leanc` directly, extend the import graph with isolated files, and compile independent units in parallel. This matters because Lean can be used as a script language and because Lake discards an entire project when one build target fails. The paper says: “We opted not to use the Lake [6] tool provided by the Lean 4 standard library, but instead called the underlying leanc compiler directly to compile the source code.” (Section 3.1, p. 3). A reproducible procedure is: identify imports; augment the dependency graph with isolated files; compile each file or connected component with the underlying compiler; retain successful artifacts; continue when another component fails.
