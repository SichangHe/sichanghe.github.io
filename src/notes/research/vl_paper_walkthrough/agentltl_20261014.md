# AgentLTL: A Trace-Verification Framework for Measuring, Enforcing, and Training Procedural Compliance in Tool-Using LLM Agents
(authored by agents unless marked 🧑)
Tag: `elkoussy2026agentltl`, [paper](http://arxiv.org/abs/2607.02599v1)

## purpose and claimed contribution

AgentLTL treats an agent's execution procedure as a formally checkable object. The paper says, “We introduce AGENT LTL, a language derived from First-Order Linear Temporal Logic (FO-LTL) for expressing procedural, semantic, and grounding constraints over execution traces.” (section 1, PDF p.1). A trace is a sequence of records `(tool name, arguments, result, index)`; an additional metrics record stores aggregate counts (section 3.1, PDF p.3). A procedure is a weighted set of constraints, and the score is one minus violated weight divided by total weight (section 3.3, PDF p.4). The constraint evaluation is deterministic over the recorded trace; the separate grounding experiment uses an LLM judge for comparison (section 4.4, PDF p.6).

## technique 1: typed FO-LTL trace constraints

What it is. Atomic predicates describe tool occurrence, order, argument matching, return-value checks, and aggregate statistics. `CalledWith` tests whether the specified key–value pairs form a sub-mapping of the recorded arguments; L6 separately checks full argument equality (Appendix A.2.2, PDF p.13; Table 5, PDF p.15). The paper gives `CalledWith(search, {q: “foo”})` as the predicate for a search call with a specified argument (section 3.2, PDF p.3). Temporal operators include finite-trace LTL; its example is `G(search → F cite)`, requiring every search to be eventually followed by citation. Quantifiers range over finite domains extracted from the trace or metrics; eager instantiation substitutes every extracted value and checks each resulting formula (section 3.2, PDF p.3).

When to use it. Inference: use a constraint when compliance depends on event order, a required or forbidden call, a value in an argument/result, or a property of every entity in a trace. Use a quantified predicate when the rule must apply independently to every file, number, or retrieved entity.

How to apply it, following the paper. (1) Model each call as `(n_i,a_i,r_i,i)` and record the resulting trace. (2) Define atomic predicates for the observable properties of the tools. (3) Compose them with finite-trace temporal operators and finite data quantifiers. (4) Bind free variables to obtain closed constraints. (5) Test the constraints against the trace; the paper evaluates a quantifier by substituting each element of its extracted domain. The fan-out example at D1, seed 2 requires `tool_a_list`, then `tool_b` for each even number, forbids `tool_c`, and finally calls `tool_d` (Figure 2, PDF p.4).

Verus form. Inference: represent the workflow as executable Rust wrappers plus `spec fn` predicates over an abstract event sequence, and prove a `proof fn` that each wrapper append preserves the invariant that required predecessors and argument facts hold. Inference: this proposed encoding would need an event log and lemmas implementing the paper's trace semantics. The paper supplies no Verus implementation or proof.

Evidence and limits. The paper's benchmark contains twelve templates over five structural types, with gold traces from 2 to 50 calls (section 4.2, PDF p.5). Evaluation uses the recorded trace and metrics, and the authors state, “FO-LTL also cannot express hyperproperties, such as non-interference between parallel tool calls” (section 8, PDF p.9). Timing, resource consumption, privacy, and inter-agent coordination are outside the six-layer schema (section 8, PDF p.9).

## technique 2: layered weighted compliance

What it is. The authors organize checks into six layers: L1 branching, L2 prompt-visible literal arguments, L3 global sequence, L4 pair/instance order, L5 call counts, and L6 exact arguments including computed values (section 3.3, PDF p.4). They warn that uniform weighting can make one arithmetic error invalidate dependent checks. Their generated fan-out instance has total weight 46.5 and structural L3+L4+L5 weights of approximately 73% (Figure 2, PDF p.4).

How to apply it. (1) Generate a gold trace by executing a deterministic reference procedure. (2) Instantiate one constraint set from that trace. (3) Put structural constraints in separate layers from computed-argument constraints. (4) Assign positive weights and compute `C = 1 - violated_weight/total_weight`. (5) Report both the aggregate score and each layer's pass rate so a low score identifies routing/order versus arithmetic failure. The paper explicitly says, “This separation isolates routing, ordering, and computation errors so they contribute independently to the score.” (section 3.3, PDF p.4)

Verus form. Inference: encode each layer as a separate predicate and expose a `spec fn compliance` returning a rational-like model value, while proving Boolean layer predicates. Since Verus proofs reason about specifications rather than runtime floating-point scores, compute the numeric score in executable Rust after proving each Boolean result, or use integer weighted sums.

Evidence. In baseline evaluation over seven models, per-layer pass rates show sequence and pair-order as common failures; for example, Gemma-4-31B has L3 0.292 and L4 0.489 while L1 is 1.000 (Table 4, PDF p.8). This evidence is for the synthetic benchmark; Table 4 describes pass rates aggregated over all templates and difficulties. Inference: its numbers disagree with Figure 7 (PDF p.34), which shows Gemma-4-31B baseline L3 as 0.72 rather than Table 4's 0.292; the values cited here follow Table 4. Weight choices remain an authoring assumption: the paper says, “uniform weighting can make the metric brittle: a single arithmetic or reasoning error can invalidate all dependent checks, collapsing the score even when most behavioral constraints are still satisfied.” (section 3.3, PDF p.4).

## technique 3: offline scoring and online pre-execution enforcement

What it is. The same constraint set is evaluated after completion or on each prefix before a call executes. The paper states, “Some constraints cannot be decided from prefixes.” (section 3.4, PDF p.4). A constraint can block only when the observed prefix makes its violation unavoidable under every continuation (Appendix A.5.1, PDF p.14); eventuality constraints are deferred until the run ends. Each enforceable constraint has a severity response such as logging, corrective feedback, or blocking (section 3.4, PDF p.4).

How to apply it. (1) Before execution, append the proposed call to the current prefix. (2) Evaluate the enforceable subset. (3) If no constraint is definitively violated, execute; otherwise apply the severity policy. (4) In block-and-warn, block the call and warn; execute an override only if the very next generated tool call has the same tool name and byte-identical arguments. A different retry is checked again. In the evaluated soft-block setting, terminate after three violations of the same constraint (section 4.2, PDF p.5; Appendix A.5.3, PDF p.14). (5) At completion, score all constraints, including deferred liveness rules.

Evidence. The setup reports 360 runs per model per setting (section 4.2, PDF p.5). Inference: its additional claim of six trials per template/difficulty/seed combination is inconsistent with 12 templates, five difficulties, and two seeds, giving `6 × 12 × 5 × 2 = 720` runs. Block-and-warn improves five of seven models; for example Gemma-4-31B rises from 0.789 baseline to 0.961, while Qwen3-Next-80B falls from 0.874 to 0.829 (Table 1, PDF p.7). The paper cautions that soft-block can terminate a transaction mid-procedure and that “The appropriate response to a violation, whether to block, warn, roll back, or escalate to a human, is use-case dependent and requires richer enforcement semantics than the two settings we evaluate here.” (section 8, PDF p.9).

Verus form. Inference: model the harness state as a verified state machine: a transition for proposing a call checks a predicate over the prefix and either returns an allowed state or a warning state. Verus can prove that disallowed calls do not enter the executable tool transition, but external side effects and rollback remain trusted assumptions.

## technique 4: compliance as a reinforcement-learning reward

What it is. The paper describes `C` in [0,1] as continuous and uses its partial credit as a dense reward (section 3.4, PDF pp.4–5). It combines compliance, answer correctness (0.1 for correctly formatted but incorrect answers), and an exponential weighted-Levenshtein trace-distance reward (section 4.3, PDF pp.5–6). Training uses GRPO on 300 examples from 15 simplified templates; simplified versions of `loop_termination` and `branch_selection` are held out as unseen patterns, although related motifs remain in training (section 4.3, PDF p.5; Appendix D.1–D.2, PDF p.18).

How to apply it. (1) Build reference traces and layered constraints. (2) Score each sampled trace with `R = 0.5 C + 0.25 Acc + 0.25 exp(-d)`, where `Acc` is 1 for correct format and value, 0.1 for correct format with wrong value, and 0 for invalid format. (3) Compute weighted Levenshtein distance `d` using costs 0 for exact matches, 0.5 for the same tool with different arguments, and 1 for a different tool, insertion, or deletion. (4) Optimize with GRPO; the reported run finetunes Qwen3-4B-Instruct with LoRA rank 8 and scaling 16 on `q_proj` and `v_proj`, one epoch and 16 rollouts per prompt. (5) Evaluate on held-out parameters, augmented traces, unseen patterns, unseen tool aliases, and the production benchmark (section 4.3, PDF pp.5–6; Appendix E, PDF pp.20–22).

Evidence. Over 4,800 GRPO generations, compliance increases from 0.511 to 0.770, answer correctness from 0.296 to 0.728, and distance reward from 0.301 to 0.782 (section 5.2, PDF p.7). On the full 360-instance benchmark, finetuning raises accuracy from 13.4% to 57.2% and compliance from 0.562 to 0.775; on the no-coverage split, accuracy rises from 13.3% to 46.7% (Table 2, PDF p.7). The nested-loops-plus-branching template remains at 0.0% correctness after finetuning (section 8, PDF p.9).

Verus form. Inference: use the verified trace score as an offline dataset label or reward, while Verus proves the checker and reference workflow. Verus does not prove that GRPO updates preserve a property; model training and optimizer behavior stay outside the proof boundary.

## techniques for the catalog

- typed FO-LTL traces — encode tool calls, temporal order, arguments, results, and finite quantification as deterministic trace predicates
- layered weighted compliance — separate routing, order, counts, and exact arguments and report weighted and per-layer scores
- prefix harnessing — check enforceable constraints before each call, with warn, block, retry, or termination policies
- compliance reward — use the continuous score plus correctness and trace distance as dense training feedback
