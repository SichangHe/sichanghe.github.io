# AgentLTL: A Trace-Verification Framework for Measuring, Enforcing, and Training Procedural Compliance in Tool-Using LLM Agents
(authored by agents unless marked 🧑)
Tag: `elkoussy2026agentltl`, [paper](http://arxiv.org/abs/2607.02599v1)

## purpose and claimed contribution

AgentLTL treats an agent's execution procedure as a formally checkable object. The paper says, “We introduce AGENT LTL, a language derived from First-Order Linear Temporal Logic (FO-LTL) for expressing procedural, semantic, and grounding constraints over execution traces.” (abstract, PDF p.1). A trace is a sequence of records `(tool name, arguments, result, index)`; an additional metrics record stores aggregate counts (section 3.1, PDF p.3). A procedure is a weighted set of constraints, and the score is one minus violated weight divided by total weight (section 3.3, PDF p.4). Thus the output is deterministic and does not use an LLM judge.

Inference: VL could use this separation to score whether an agent followed a required verification workflow (for example, compile, run Verus, inspect diagnostics, and commit only verified code) independently of whether the final answer sounds plausible.

## technique 1: typed FO-LTL trace constraints

What it is. Atomic predicates describe tool occurrence, order, argument equality, return-value checks, and aggregate statistics. The paper gives `CalledWith(search, {q: “foo”})` as the predicate for a search call with a specified argument (section 3.2, PDF p.3). Temporal operators include finite-trace LTL; its example is `G(search → F cite)`, requiring every search to be eventually followed by citation. Quantifiers range over finite domains extracted from the trace or metrics; eager instantiation substitutes every extracted value and checks each resulting formula (section 3.2, PDF p.3).

When to use it. Use a constraint when compliance depends on event order, a required or forbidden call, a value in an argument/result, or a property of every entity in a trace. Use a quantified predicate when the rule must apply independently to every file, number, or retrieved entity.

How to apply it, following the paper. (1) Model each call as `(n_i,a_i,r_i,i)` and record the resulting trace. (2) Define atomic predicates for the observable properties of the tools. (3) Compose them with finite-trace temporal operators and finite data quantifiers. (4) Remove free variables to obtain closed constraints. (5) Test the constraints against the trace; the paper evaluates a quantifier by substituting each element of its extracted domain. The fan-out example requires `tool_a_list`, then `tool_b` for each even number, forbids `tool_c`, and finally calls `tool_d` (Figure 2, PDF p.4).

Verus form. Inference: represent the workflow as executable Rust wrappers plus `spec fn` predicates over an abstract event sequence, and prove a `proof fn` that each wrapper append preserves the invariant that required predecessors and argument facts hold. Inference: Verus has no direct finite-trace LTL evaluator in the cited material, so an implementation would need a Rust event log and lemmas for temporal predicates; retain the paper's trace semantics rather than pretending an LTL formula is a Verus contract.

Evidence and limits. The paper's benchmark contains twelve templates over five structural types, with gold traces from 2 to 50 calls (section 4.2, PDF p.5). The language only observes recorded calls/results, and the authors state, “FO-LTL also cannot express hyperproperties, such as non-interference between parallel tool calls” (section 8, PDF p.9). Timing, resource consumption, privacy, and inter-agent coordination are outside the six-layer schema (section 8, PDF p.9).

## technique 2: layered weighted compliance

What it is. The authors organize checks into six layers: L1 branching, L2 prompt-visible literal arguments, L3 global sequence, L4 pair/instance order, L5 call counts, and L6 exact arguments including computed values (section 3.3, PDF p.4). They warn that uniform weighting can make one arithmetic error invalidate dependent checks. Their generated fan-out instance has total weight 46.5 and structural L3+L4+L5 weights of approximately 73% (Figure 2, PDF p.4).

How to apply it. (1) Generate a gold trace by executing a deterministic reference procedure. (2) Instantiate one constraint set from that trace. (3) Put structural constraints in separate layers from computed-argument constraints. (4) Assign positive weights and compute `C = 1 - violated_weight/total_weight`. (5) Report both the aggregate score and each layer's pass rate so a low score identifies routing/order versus arithmetic failure. The paper explicitly says, “This separation isolates routing, ordering, and computation errors so they contribute independently to the score.” (section 3.3, PDF p.4)

Verus form. Inference: encode each layer as a separate predicate and expose a `spec fn compliance` returning a rational-like model value, while proving Boolean layer predicates. Since Verus proofs reason about specifications rather than runtime floating-point scores, compute the numeric score in executable Rust after proving each Boolean result, or use integer weighted sums.

Evidence. In baseline evaluation over seven models, per-layer pass rates show sequence and pair-order as common failures; for example, Gemma-4-31B has L3 0.292 and L4 0.489 while L1 is 1.000 (Table 4, PDF p.8). This evidence is for the synthetic benchmark and its denominators are all constraint checks aggregated across templates and difficulties (Table 4 caption). Weight choices remain an authoring assumption: the paper says, “The weights wi are not chosen by the formalism and strongly affects the expressiveness of the score.” (section 3.3, PDF p.4).

## technique 3: offline scoring and online pre-execution enforcement

What it is. The same constraint set is evaluated after completion or on each prefix before a call executes. The paper states, “Online mode evaluates a prefix trace … before each tool execution” (section 3.4, PDF p.4). Only constraints decidable from a prefix can block; eventuality constraints are deferred until the run ends. Each enforceable constraint has a severity response such as logging, corrective feedback, or blocking (section 3.4, PDF p.4).

How to apply it. (1) Before execution, append the proposed call to the current prefix. (2) Evaluate the enforceable subset. (3) If no constraint is definitively violated, execute; otherwise apply the severity policy. (4) In block-and-warn, reject and warn, then allow a retry with identical arguments; in soft-block, terminate after three violations of one constraint (section 4.2, PDF p.5). (5) At completion, score all constraints, including deferred liveness rules.

Evidence. Table 1 reports mean compliance for 360 runs per model per setting (six trials for each template/difficulty/seed combination). Block-and-warn improves five of seven models; for example Gemma-4-31B rises from 0.789 baseline to 0.961, while Qwen3-Next-80B falls from 0.874 to 0.829 (Table 1, PDF p.6). The paper cautions that soft-block can terminate a transaction mid-procedure and that “the appropriate response to a violation, whether to block, warn, roll back, or escalate to a human, is use-case dependent” (section 8, PDF p.9).

Verus form. Inference: model the harness state as a verified state machine: a transition for proposing a call checks a predicate over the prefix and either returns an allowed state or a warning state. Verus can prove that disallowed calls do not enter the executable tool transition, but external side effects and rollback remain trusted assumptions.

## technique 4: compliance as a reinforcement-learning reward

What it is. Because `C` is continuous on [0,1], the paper uses it directly as a dense reward. It combines compliance, answer correctness (0.1 for correctly formatted but incorrect answers), and an exponential weighted-Levenshtein trace-distance reward (section 4.3, PDF p.5). Training uses GRPO on 300 examples from 15 simplified templates; two templates are held out as unseen patterns (section 4.3, PDF p.5).

Evidence. Over 4,800 GRPO generations, compliance increases from 0.511 to 0.770, answer correctness from 0.296 to 0.728, and distance reward from 0.301 to 0.782 (section 5.2, PDF p.7). On the full 360-instance benchmark, finetuning raises accuracy from 13.4% to 57.2% and compliance from 0.562 to 0.775; on the no-coverage split, accuracy rises from 13.3% to 46.7% (Table 2, PDF p.7). The nested-loops-plus-branching template remains at 0.0% correctness after finetuning (section 5.2, PDF p.7).

Verus form. Inference: use the verified trace score as an offline dataset label or reward, while Verus proves the checker and reference workflow. Verus does not prove that GRPO updates preserve a property; model training and optimizer behavior stay outside the proof boundary.

## what is proved, trusted, and relevant to VL

The framework proves only that a recorded trace satisfies authored constraints; it does not validate that the procedure itself is appropriate (section 9, PDF p.9). The synthetic arithmetic tools make ground truth deterministic, and the authors explicitly leave transfer to stochastic real tools open (section 8, PDF p.9). Constraint authoring and mis-specification are trusted. Inference: threat to agent-written verified Rust is substantial for workflow errors—skipped verification, wrong tool order, or unsupported claims can be mechanically surfaced—but the checker cannot establish semantic correctness of a Verus specification or compensate for an unsound external-body assumption. VL should reuse the paper's layered diagnostics and prefix gate, while measuring side effects and rollback before enforcing calls in production.

## techniques for the catalog

- typed FO-LTL traces — encode tool calls, temporal order, arguments, results, and finite quantification as deterministic trace predicates
- layered weighted compliance — separate routing, order, counts, and exact arguments and report weighted and per-layer scores
- prefix harnessing — check enforceable constraints before each call, with warn, block, retry, or termination policies
- compliance reward — use the continuous score plus correctness and trace distance as dense training feedback
