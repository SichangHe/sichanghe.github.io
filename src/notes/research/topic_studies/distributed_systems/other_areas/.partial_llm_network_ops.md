## Sources opened (6)

**1. NetConfEval: Can LLMs Facilitate Network Configuration?**
- Venue: Proc. ACM Netw. 2 (CoNEXT 2), Art. 7, June 2024. It won the IRTF/IETF Applied Networking Research Prize, per the search snippet.
- Authors: Changjie Wang, Mariano Scazzariello, Alireza Farshin, Simone Ferlin, Dejan Kostić, Marco Chiesa.
- URL: https://research.redhat.com/blog/publication/can-llms-facilitate-network-configuration/
- Quotes:
  - "We design a set of benchmarks (NetConfEval) to examine the effectiveness of different models in facilitating and automating network configuration."
  - "Finally, we present two GPT-4-based prototypes to (i) automatically configure P4-enabled devices from a set of high-level requirements and (ii) integrate LLMs into existing network synthesizers."
- Result from the search snippet, not the abstract: translating requirements into formal specs works with small models, while generating code that controls network systems needed larger models such as GPT-4.
- In plain English: a benchmark of four tasks, from natural-language intent to specs, API calls, routing code and protocol configs.

**2. What do LLMs need to Synthesize Correct Router Configurations?**
- Venue: HotNets 2023.
- Authors: Rajdeep Mondal, Alan Tang, Ryan Beckett, Todd Millstein, George Varghese.
- URL: https://arxiv.org/abs/2307.04945
- Quotes (my fetch returned a paraphrased abstract, so these two are from it but not word-for-word from the paper):
  - "the number of automated prompts exceeded human prompts by those factors" with 10X for Juniper translation and 6X for no-transit.
  - GPT-4 alone "performs poorly, creating drafts containing significant errors in topology, syntax, and semantics."
- Authors claim a verifier plus localized feedback ("Verified Prompt Programming") is what makes GPT-4 usable.
- In plain English: GPT-4 drafts router configs, a verifier finds the errors, and automated re-prompting fixes them.

**3. AIOpsLab: A Holistic Framework to Evaluate AI Agents for Enabling Autonomous Clouds**
- Venue: arXiv, 2025; I did not confirm where it was published.
- Authors: Yinfang Chen, Manish Shetty, Gagan Somashekar, Minghua Ma, Yogesh Simmhan, Jonathan Mace, Chetan Bansal, Rujia Wang, Saravan Rajmohan.

- Quote: "AI for IT Operations (AIOps) aims to automate complex operational tasks, such as fault localization and root cause analysis, to reduce human workload and minimize customer impact."

**4. KEN: Kernel Extensions using Natural Language**
- Venue: arXiv 2312.05531. The search snippet linked it to an eBPF workshop paper, so the venue and year are unconfirmed.
- Authors: Yusheng Zheng, Yiwei Yang, Maolin Chen, Andrew Quinn.
- URL: https://arxiv.org/abs/2312.05531
- Quote: "KEN produces correct eBPF programs on 80% which is an improvement of a factor of 2.67 compared to an LLM-empowered program synthesis baseline."
- Per the search snippet, the system is called Kgent in some write-ups.
- Per the abstract, it checks outputs with program comprehension and symbolic execution.
- In plain English: English prompt in, eBPF kernel extension out, with checks that the program matches the request.

**5. Large Language Model guided Protocol Fuzzing (ChatAFL)**
- Venue: NDSS 2024.
- Authors: Ruijie Meng, Martin Mirchev, Marcel Böhme, Abhik Roychoudhury.
- URL: https://ndss-symposium.org/ndss-paper/large-language-model-guided-protocol-fuzzing
- Quotes:
  - ChatAFL "constructs grammars for each message type in a protocol, and then mutates messages or predicts the next messages."
  - From the search snippet (an abstract excerpt I did not open as a full page): "ChatAFL covers 47.6% and 42.7% more state transitions, 29.6% and 25.8% more states, and 5.8% and 6.7% more code" than AFLNet and NSFuzz.

- In plain English: an LLM reads RFC knowledge to produce message grammars and next-message predictions for a protocol fuzzer.

## Gaps and open problems

I have no verbatim statements from the papers themselves, because none of the papers I opened were read past the abstract. From the abstracts alone:
- NetConfEval's authors "propose a set of principles to design LLM-based systems to configure networks".
- Source 2 says verification "requires formal specifications and targeted error messages". Without the specification and the localized feedback, the approach does not work.
- Source 4 shows an 80% pass rate. The remaining 20% are failures that its checks did not turn into correct programs.

## Research ideas, my own and not from the papers

1. **Verified-in-the-loop for Rust.** Replace Batfish or Campion verifiers with Rust or Verus proofs for protocol parsers and state machines generated from RFCs. The prompts-per-human-prompt leverage ratio from source 2 gives a ready metric.
2. **RFC-to-spec evaluation.** Measure how often LLM-extracted state machines in ChatAFL-style pipelines disagree with a formally verified reference implementation.
3. **Agent-on-network benchmark with faults.** Extend AIOpsLab-style fault injection to network faults such as BGP misconfigurations and link flaps, and report agent failure modes by category.
4. **Spec-light verification.** Test how far agents get when the specification is incomplete, since sources 2 and 4 rely on good specs.
5. **eBPF verifier-feedback loop.** Treat the kernel verifier's rejections as localized feedback, as in source 2, and measure the gap against KEN's 80%.
6. **Distributed-protocol model checking agents.** Have agents write TLA+ or P models of protocols from RFC text and check them against Rust implementations.
7. **Cheap-to-strong agent escalation for config tasks.** NetConfEval's claim is that small models suffice for formal-spec generation while code generation needs larger ones. Test an escalation policy on that split.
