## Natural Language based Specification and Verification

[study](../vl_paper_walkthrough/natural_language_based_specification_and_20261013.md)

- typed natural-language contract records: write each caller obligation or caller-visible effect as a small record with an enumerated kind, a target, an optional size or condition expression, and a prose description
- property-split summary passes: infer allocation, free, initialization, precondition, leak and integer-range summaries in separate passes rather than one
- callee-first SCC driver with summary cache: process strongly connected components of the call graph leaves first, rerun a recursive component, within a bound the paper does not give, while its summaries change, and store every summary for reuse
- discharge-or-propagate precondition inference: for each callee obligation decide whether the current function establishes it or must pass it to its own callers
- call-site PRE and POST annotation: paste callee contracts as comments at each call with actual arguments substituted, so the check is local to the call
- contract simplification after checking: drop every precondition the body discharges and expose only the remainder to callers
- block summaries for oversized functions: cut at syntactic boundaries, summarize each block as a named pseudo-function, and replace earlier blocks by their summaries
- name-only library summaries: obtain contracts for source-less library functions from the model's knowledge of their documentation, and treat them as trusted
- allocation-versus-free matching for leaks: decide leaks by comparing a function's allocation summary with its free summary and its callees' postconditions

## Modular Responsiveness Verification of Rust Async Runtimes

[study](../vl_paper_walkthrough/modular_responsiveness_verification_of_r_20261013.md)

- task-centric obligation — reduce a liveness property over many tasks to the fate of one arbitrary (waker, predicate) pair that must be handed over or discharged, never dropped
- pollable conditions P1–P3 — `Ready` only if the condition held, `Ready` if it held at entry, and on `Pending` the waker is registered or already woken
- reactor conditions R1–R2 — each iteration wakes every stored obligation whose predicate already holds and keeps every other one
- monotonic predicate abstraction — model each awaited condition as a fact that never turns false, so a stale positive observation remains valid
- monotone refinement pruning — treat a path that observes true and then false for one predicate as unreachable
- two-start-state pollable check — analyze `poll` once with the condition unknown and once with it true, and inspect the state before each return
- two-symbolic-obligation reactor check — seed one obligation assumed ready and one unknown, run one iteration, and require the first to be woken and the second not to be left held locally
- locally-held obligation set — track an obligation as a resource that only insert or wake may remove, so an empty set at return proves it was not forgotten
- precedes relation for strict obligation transfer — record which predicates were true when another was observed false, and require registration to precede completion for one-shot notifiers
- terminating reactor — model a one-time waker such as a channel send as a reactor body without the loop, checked per invocation
- retry-loop fixpoint — admit a try-wait-retry loop in a pollable by computing the least fixpoint at the loop head and checking the same return-site conditions
- no-op annotation macros over MIR — mark model operations in unchanged Rust with macros that expand to markers and extract the model from the compiler's intermediate representation
- seeded violation per verification condition — test a checker by breaking a real component once for each condition it claims to enforce

## Prophecy-Based Automated Verification of Message-Passing Programs

[study](../vl_paper_walkthrough/prophecy_based_automated_verification_of_20261013.md)

- program-point functions: rewrite the program so each function performs one statement and then calls a continuation, with the live variables as arguments, and make one predicate per function
- channel as prophesied message list: give both channel ends the same guessed list of future messages; the sender proves each send matches the head, the receiver assumes it
- empty-sender-list at thread end: a thread may terminate or fail only if every sender it holds has an empty remaining list
- clone as interleaving: split a sender's remaining list into two whose interleaving is the original, with a three-clause Merge predicate
- failure flag joined by disjunction at spawn: carry a flag for reaching failure and set the parent's flag to the or of the two threads' flags
- thread-discard clause: allow any thread to be abandoned with flag false provided its sender lists are empty, so that one thread's failure does not require running the others out
- timestamped prophecies: stamp each guessed message with its send time, keep each thread's last event time, and require send time strictly before receive time and non-decreasing times within a thread
- sorted-on-creation: require a new channel's guessed list to have strictly increasing stamps, which encodes first-in-first-out order across all senders
- exact-then-approximate portfolio: on timeout of the complete encoding, run the sound incomplete one and accept only its safe answer
- ordering variants by predicate swap: drop Sorted for per-sender order, use multisets and Union for no order, add receive times for a bounded buffer
- three-valued status for deadlock: extend the flag to failed, terminated or blocked, add a blocked clause for receive on an empty list, and make a blocked whole program the goal
- fold hint for list invariants: supply a counting fold over the message list when the invariant says all elements have a given value
- instrumented semantics as proof mediator: prove an encoding correct by a semantics that carries the guesses and steps only when they hold, matched step by step with resolution
- timestamp-ordered linearization: turn a tree-shaped refutation into a thread schedule by expanding nodes in increasing timestamp order

- converse as sanity check — prove the reverse direction of a classification so that a short readable predicate vouches for elaborate constructions

## Lemma Functions for Frama-C: C Programs as Proofs

[study](../vl_paper_walkthrough/lemma_functions_for_frama_c_20261013.md)

- lemma function: state a lemma as the contract of a pure terminating function and prove it by a body whose recursive calls are the induction hypotheses
- recursion-mirroring proof: give the proof function the same case split and recursive call as the specification function it is about, with the same measure
- explicit or implicit lemma use: call the lemma function with concrete arguments for control, or let the solver instantiate its generated axiom
- sound axiom generation: turn a proved contract into an axiom that is hidden from its own proof and from earlier code, and force purity and termination clauses onto the function
- loop generalisation: prove a per-value lemma, then obtain the bounded quantified statement from a loop that calls it under an invariant
- proxy with a body: wrap a logic expression in a function with an equality postcondition, and always give it a checked definition
- component ordering of lemmas: group mutually recursive lemma functions and order the groups topologically so no lemma is used before it is proved
- parametrised lemma module: prove one lemma over abstract condition and default functions and instantiate it, in place of near-identical proofs (proposed only)
- minimal lemma replacement: when converting a proof base with unproved lemmas, prove the smallest set the code proofs need, not each old lemma

## The Verifier is the Curriculum: Precision Sets the Return on Search in Code Self-Distillation

[study](../vl_paper_walkthrough/the_verifier_is_the_curriculum_20261013.md)

- all-or-nothing execution gate: accept a candidate only on exit code 0 plus no error pattern in the tool's output, and expose no score
- gameability probe: apply a cheap change that leaves behaviour fixed and see whether the signal's score moves
- gated self-distillation with gold anchor: per round, sample 8 per task, keep at most two deduplicated passing candidates, add to gold, retrain a fresh adapter from the base
- matched controls for self-training: gold duplication, filter swap, generator swap and volume cut, each at the same fuel count
- precision ladder: at fixed admitted count, replace a known share of correct fuel with incorrect fuel and fit gain against precision; here gain is about precision times the clean gain
- error-direction ladder: mask true positives or inject false positives separately at a fixed count; for filtered fine-tuning only false positives cost
- optimizer-swap check: repeat the error-direction test with the gate as an RL reward, where false negatives push away from correct outputs; the clean reward falls to 0.608, against 0.629 with false positives and 0.696 clean (Appendix Table 3)
- search-by-gate crossing: vary candidates per task and gate strictness together; more samples pay only behind the strict gate
- unoptimized readouts with negative controls: an instrumented state-change score and a blind brief judge, each calibrated on gold and on known-bad or do-nothing artifacts
- task-clustered statistics: permute within task, bootstrap over tasks and seeds, use the unbiased coverage estimator, and resample hard tasks to separate efficiency from reach

## Spec-Harness: Measuring and Improving Behavioral Adequacy of LLM-Synthesized Formal Specifications

## FORALL-LEAN-AGENT for Auditable Reasoning in Formal Mathematics and Software Verification

- shadowing guard — reject any new declaration that changes what a name in the frozen statement resolves to, since the statement text can stay identical while its meaning weakens

- statement-only retrieval — lookup, search, usages and outline tools that return declaration kinds, statements and locations without proof bodies
- verifier-controlled continuation — the harness, not the agent, decides completion from a verifier pass and resumes the same session with diagnostics until then
- outcome taxonomy — record infrastructure interruptions and zero-spend turns apart from proof failures so they can be resumed, not counted
- independent re-check with its own denominator — rebuild the statement in a trusted environment, compare exported declarations, replay in a second kernel, and report over judged candidates only
- strict versus benchmark-rule counts — report success under the benchmark's rule and under a stricter allowed-axiom rule side by side, since dependencies can carry admitted lemmas
- sorry-skeleton proving — write the proof sketch as intermediate claims each left open, then close them one at a time with a compile after each
- proof-body-only upgrade repair — after a toolchain change, let an agent edit proof bodies only and recheck statement, axioms and compilation for every repair
- reference-similarity screen — flag accepted candidates nearly identical to the withheld reference for manual inspection of how they were produced
- validate the validator — test the acceptance check on a fixed set of bypass attempts and harmless look-alikes, then replay stored candidates to look for false rejections

## 3DGen: AI-Assisted Generation of Provably Correct Binary Format Parsers

## Trigger Selection Strategies to Stabilize Program Verifiers

[study](../vl_paper_walkthrough/trigger_selection_strategies_to_stabiliz_20261013.md)

- three hazard checks on a trigger term — reject a term whose instance recreates its own shape, reject a term containing arithmetic, and ask whether the surviving term will occur in the proofs that need the quantifier
- source-level trigger selection — pick triggers on the user's expression before encoding, so helper functions added by translation never serve as triggers
- adequate and parsimonious candidates — enumerate sets of function-application terms that cover every bound variable and from which no term can be removed
- per-quantifier matching-loop check — a candidate is unsafe if the body holds another term it unifies with, apart from four listed harmless cases; remove unsafe candidates before choosing the least specific
- quantifier splitting — rewrite a quantifier over a conjunction, through at most one implication, into one quantifier per conjunct so each gets its own trigger
- trigger sharing — compute candidates on the unsplit quantifier and offer them to every piece, so a piece may fire on a term from its sibling
- extra-variable rewrite — replace a[i] against a[i+1] by a two-variable quantifier with trigger on a[i] and a[j], or by the transitive i < j form
